# 04　编排三模式

> Supervisor / Pipeline / Swarm。这一章的结论有一半是**不改**：主干是 Pipeline，
> 而且应当继续是 Pipeline。另一半是：这个仓库里那个叫 `Supervisor` 的类，
> 管的是**进程**，不是 **Agent**——多 Agent 编排最难的那一半它已经做完了，
> 缺的是另一半，而那一半的名字叫「寻址与契约」。

## 问题

### 「我们已经有 Supervisor 了」这句话，一半对一半错

`packages/harness-core/src/harness/supervisor.ts:115` 确实有一个 `class Supervisor`。
它监管的是 fork 出来的**操作系统进程**：起停、崩溃分类、退避重启、心跳收割、票据回收。
它对「谁是什么角色」「一个角色怎么把活交给另一个角色」**一无所知，也不打算知道**——
这不是遗漏，是分层：

> `never`　runners —— 一次不值得重试的失败必须立刻浮出来。
> **要不要重试这份工作，是循环层的决定，不是监工的。**
> —— `supervisor.ts:10-13`

把它当成多 Agent 编排器去扩展，会在三个地方撞墙，而三次撞墙**全部是静默的**。

### 三个静默的撞法

**一、调度器的 bug 会被记到被测产品头上，然后从会暴露它的指标里删掉。**

`pickRunner`（`server/src/exec.ts:40-60`）是一次纯读 `supervisor.status()`，中间夹一个
`await supervisor.start(...)`，然后分发——**没有任何占位或锁**。池子一旦拉宽：

```
pickRunner 读到 runner-2 空闲  →  另一路也读到 runner-2 空闲  →  两路都发给它
  → 输家撞上 runner 的模块级 busy 标志（apps/runner/src/main.ts:29，在 :37 抛）
  → 执行器接住，记成 failKind:"infra", failCode:"EXEC_ENV"（server/src/graphs.ts:211-212）
  → 而 infraError 的定义就是「排除在 flake / gate 之外」（packages/harness-testing/src/exec/run.ts:25）
```

现在唯一挡住它的是 `queueConcurrency: 1, runnerCount: 1`（`server/harness.config.ts:18`）。
**「拉宽池子」是任何编排改动的第一步，所以这颗雷就埋在第一步下面。**

**二、跨进程交接没有 schema，加一个字段等于赌运气。** 这个仓库已经付过一次账，
注释原文（`apps/agent/src/main.ts:220-231`）：

> 目标端说的是哪个环境、哪个地址，探索就得去那里。此前这里只转发 `projectId`，
> `envRef` 和 `url` 一个都没带过去——网关于是回落到项目的**默认**环境：
> 一次声明「跑在 bench-juiceshop」的运行，浏览器打开的是 local 的地址、
> 带的是 local 的请求头和凭证。**而产出物看不出任何异常。**

**三、今天没有任何办法证伪一个编排改动。** `ABLATABLE`
（`packages/harness-core/src/eval/ablation.ts:9`）是封闭的七项，没有一项和编排有关；
而更糟的是，**开关还不叠加**：`casegen/nodes.ts:986-990` 的注释写着「同时开两个时按顺序减」，
`:991-996` 的实现却是先命中先返回的 if 链——一条声明两个消融的臂实际只跑掉一个，
**而没有任何地方报告这件事**。编排实验恰好是「多开关」那一类。

## 技术点

三种模式的分界不是「有几个 Agent」，是**这次运行的形状是不是在运行之前就知道**。

| 模式 | 下一步由谁决定 | 运行前已知 |
|---|---|---|
| **Pipeline** | 图的拓扑 | 参与者 ✅　顺序 ✅ |
| **Supervisor** | 一个中心角色，看完中间结果再派 | 参与者 ✅　顺序 ❌ |
| **Swarm** | 每个 Agent 自己决定交给谁（handoff） | 参与者 ❌　顺序 ❌ |

各自的适用条件：

| 模式 | 什么时候该用 | 什么时候不该用 |
|---|---|---|
| Pipeline | 步骤序列本身是领域知识；产物要跨版本比较；每一步的输入输出能写成契约 | 步数取决于输入（「探索到没有新界面为止」） |
| Supervisor | 候选路径有限且已知，走哪条取决于中间结果；要按能力或成本把同一件事派给不同执行者；失败后要**换策略**重试 | 只有一条路径——那是 Pipeline 外面套了一层间接 |
| Swarm | 参与者要能在运行中被创建；没人能事先列全部路径；**接受两次运行不一样** | 需要可复现；需要配对评测 |

最后那一格是本章的转折点。

## 现状

### Pipeline：完整实现，是主干，且实现得很硬

`runGraph`（`packages/harness-core/src/graph/runtime.ts:114`）：单进程内的确定性 DAG。
四条性质彼此咬合：

| 性质 | 代码 | 注释里写下的理由 |
|---|---|---|
| 稳定拓扑序 | `graph.ts:99-121`（`:106`） | 「节点保持声明顺序，同一张图跑两次产生同一个序列——**可复现性从这里开始**」 |
| 一节点一输入 | `graph.ts:81-86` | 「合并多个上游是一个有真实语义的操作（哪个顺序？谁赢？），所以它属于一个显式的 merge 节点」 |
| 拒环 + 循环留在节点里 | `graph.ts:92`、`runtime.ts:111` | 「一个有界的修复循环是一个节点，不是图里的一个环」 |
| 每步 zod 三查（入参 / params / 产物） | `runtime.ts:222-264` | 「一个产物不符合自己契约的节点必须停在这里：下游是**凭那个契约**接上来的」 |

检查点就是 `outputs[nodeId] = out; await store.set(wfRunId, nodeId, out)`
（`runtime.ts:119-120`），键是 `(wfRunId, nodeId)`。复用同一个 `wfRunId` **就是**恢复
（`runtime.ts:119` 的 `store.all(wfRunId)`）。

### Supervisor：类存在，管的是进程；多 Agent 编排的一半已经做完

盘一遍。**左半边不用改，而且比多数编排框架细。**

| 能力 | 状态 | 在哪 |

### Swarm：不存在，而且现有的东西不是它的雏形

`enqueue`（`server/src/queue.ts:21`，默认并发 1）加 `pickRunner`（`exec.ts:40`）看起来像扇出。
它不是 Swarm 的雏形，是一个**同构、无角色的执行者池**：runner 是一个 exec 端点，
不是一个会自己决定下一步的 Agent。它没有任何 handoff 语义，也不需要有。

## 变更

### 一、对着每一段工作，判断该用哪种

| 工作 | 现在 | 该用 | 理由 |
|---|---|---|---|
| **G1 主干** `docs→spec→stories→design→gate`（`casegen/graph.ts:30-70`） | Pipeline | **保持 Pipeline** | 见下一节。这是本章最强的一条结论 |
| **G2 代码段** `codegen→gate.code→repair.loop` | Pipeline | **保持 Pipeline** | 同上 |
| `source.explore` **内部** | 节点内自主循环 | Supervisor 有真需求，**但先不动** | 多路径调度（登录态 / 只读、深浅两档）确实是这里的形状，但这个节点刚从「采屏数恒等于 2」修好不久（`casegen/nodes.ts:315-320` 的 `maxScreens` 注释）。**先让它稳定，再让它聪明** |
| `repair.loop` **内部** | 节点内自主循环，**单一固定策略** | **Supervisor 的最佳候选** | 见「三」 |
| 用例执行分发（gateway→runner） | 同构池 + p-queue | 保持池，**改成能力路由 + 原子占位** | 这是调度问题，不是编排问题。协议已经写好了 |
| 配对评测的两条臂 | 串行 | **保持串行** | 两条臂共享同一个全局模型准入门（`harness.config.ts:17`，并发 3）。并行只是把排队从门前挪到门后 |
| 变异运行（每 mutant 跑一遍套件） | 串行、纯内存 | **不是编排问题** | 它缺的是检查点，见 [第 06 章](./06-中断恢复与检查点.md) |

### 二、主干为什么必须保持 Pipeline

这不是「暂时没空改」，是**改了会同时弄坏四条已经写下来的性质**：

| 会坏的性质 | 代码 | 坏了之后会怎样 |
|---|---|---|
| 稳定顺序 = 可复现性的地基 | `graph.ts:106` | 两次运行不再产生同一个序列。配对评测的前提（两臂只差一件事）当场失效 |
| 「失败停住整条线」 | `runtime.ts:285-287` | 这条规则**只有在一节点一输入时才成立**——因为那时分支就是整条线。派活式编排让「该停在哪」不再是拓扑能回答的问题 |
| 检查点键是 `nodeId` | `runtime.ts:267-268` | 形状运行时才定，`nodeId` 就不再是稳定的键，`store.all(wfRunId)`（`:141`）也就不再是「接着上次跑」 |
| 预算只在**节点之间**检查 | `runtime.ts:184` | N 个节点在途时上限会超 N 个节点。而配对评测的两条臂**共享一个 cap** |

反过来说更干脆：**主干根本不需要 Supervisor 能给的东西。** Supervisor 的价值是
「运行时才知道走哪条路」；而 G1 的路径是这个垂类的领域知识——它写成一张图不是妥协，
是产品的一部分。一条每次形状都不同的流水线，`graph.ts:106` 那句注释就白写了。

### 三、Swarm：**不采用**

先说清楚不采用的是什么。**不采用的是「运行时决定拓扑、去中心、Agent 之间直接交接」的编排。**
不是不许有多个进程（已经有三个），不是不许并发（runner 池就是），
也不是不许有自主循环（已经有两个，而且它们是这个产品最有价值的部分）。

四条理由：

**1. 它和评测层的前提直接冲突。** 这条注释是为了删掉画布上那条常驻对话栏写的，
但它论证的是同一件事（`src/components/DiagnoseDrawer.tsx:19-23`）：

> 一条永远在那里的对话栏，是在宣告这个产品主要靠聊天驱动——它不是，也不该是。
> **流程固定是这个项目的核心设计：一条每次都不一样地启动的流水线没法和自己比较，
> 而「能和自己比较」正是评测层存在的全部理由。**

下游整套东西——两条臂只差一个消融开关、McNemar、`prediction`、`digestDiff`、变异检出——
全部建立在「除了那一件事，这次和上次一样」上面。Swarm 拆掉的是这句话，
而不只是拆掉一个编排层。

**2. 它没有可证伪的落点。** `ABLATABLE`（`ablation.ts:9`）的每一项都必须是
**某个节点真的读的东西**，理由写在 `ablation.ts:9-13`：「一个改不动任何东西的开关，
会让消融报告说谎」。而 "swarm" 不是一个节点读的开关，它是整个运行时的形状——
要给它做 A/B，得让两条臂跑两套运行时，那就不叫配对评测了。

**3. 画布画不出来，而且是重写级别的画不出来。** 前端把 `def.nodes`——**保存下来的图定义**——
直接映射成卡片（`src/pages/Workspace.tsx:866`）。没有嵌套的表示，没有运行时创建的节点的表示。
动态拓扑要的是一棵从事件流重建的 spawn 树，那是重写画布，不是扩展画布。

**4. 它要的基础设施，恰好是这个 substrate 最贵的四样**：动态注册 / 注销、兄弟消息路由、
按能力寻址、死亡时的邮箱回收。而前三样 **Supervisor 模式也要**，只有第四样是 Swarm 专属。
所以顺序是清楚的：先按 Supervisor 的需要把前三样建起来；如果那时 Swarm 还有理由，
它的成本已经小得多。

> 一份什么都引入的技术文档，等于没做过判断。这里的判断是：**这个项目不上 Swarm，
> 而且不是「现在还不上」，是「除非评测层的前提整个换掉，否则不上」。**

### 四、真要动的话，按这个顺序

**第 0 步（前置，不做就别开始）：让编排改动可被证伪。** 三件事都在 [第 14 章](./14-评测体系.md)：
把 `casegen/nodes.ts:991-996` 的 if 链改成顺序相减（`subtract` 本身已经会叠加，
`casegen/prompts.ts:177`），加一根「两开关文本是两个单开关文本的严格子集」的断言；
给 `EvalSpec` 加 `repeat`，因为一臂一次运行没有方差。
**这两件事没做之前跑编排的配对评测，会得到一份格式完全正常的空结论**——`evals/README.md:31-33`
记着连着三次这样的实测，三次都是跑完去数产物才发现的，其中一次还被当成方差编了一个机制。

**第 1 步：身份。** `ScopeSchema`（`packages/harness-core/src/obs/envelope.ts:7`）是
`.partial()` 的，加字段不破坏任何东西，而监工已经在进程边界 zod 校验并盖上 `processId`
（`supervisor.ts:263-278`）。一次改动，`agentId` / `taskId` 就同时出现在血缘、WS 断线续传、
replay 和界面投影里。
同时给 `NodeProcSpec`（`supervisor.ts:39`）和 `ProcStatus`（`:63`）加 `role` / `version` /
`capabilities`，spawn 时填。
**外加一个化身标识**：`restart: "always"` 的 agent 崩溃重启后 id 一模一样，
「这份产物是哪一次化身产的」今天答不出来；`ProcStatus.restarts`（`:69`）已经在计数，
把它盖进 scope 就够。

**第 2 步：交接 schema。** 把 `StartInput`（`agent/main.ts:36`）和 `ExecSpec`
（`apps/runner/src/exec.ts:33`）写成 zod，在**接收端** parse（`agent/main.ts:36`、
`apps/runner/src/main.ts:36`）。这是把已经在用的纪律补到唯一没有的那个边界上：
监工 zod 校验每一条事件 scope，`runGraph` 每一步 zod 查三样，**只有跨进程交接是裸的**。
它直接挡掉 `envRef`/`url` 那一类，而且是后面所有工作的前置——`as never` 的交接没法安全地加字段。
按 [第 00 章](./00-方法与约定.md) 形状三的推论：**新字段一律进 `required`。**

**第 3 步：能力路由，和原子占位一起做。**
`pickRunner`（`exec.ts:40`）从 `id.startsWith("runner-")` 改成读 spawn 时缓存在 `ProcStatus`
上的 capabilities——协议已经写好，零调用点。
**但绝不能只做这一半**：能力路由的第一个效果就是让拉宽池子变得有意义，
而拉宽池子会打开「问题」一节那颗雷。占位必须原子：读到空闲的同一刻就标记，
而不是读完 `await` 一下再分发。

**第 4 步（只有真要 Supervisor 时才做）：消息传递与动态成员。**
- `send(to, msg)` / `recv()` 加进 `extendParentApi`（`supervisor.ts:97`），路由按 processId 建在
  `procs.ts`。传输、按子进程分域、死亡结算**全部现成**。
- `unregister(id)`（守卫在「已停止」上）加在 `register`（`supervisor.ts:134`）旁边。
  `entries` 是个 Map，`register` 已经对重复 id 抛（`:135`）——约十行，加一个测试
  （`packages/harness-core/test/supervisor.test.ts` 现有 19 个）。
- **两条硬约束**：给死掉的对端发消息必须像 `settleOnDeath`（`rpc.ts:27`）那样**立刻失败**，
  不能挂起；任何借出的邮箱必须有死亡回收，`lending.releaseAllFor`（`procs.ts:107-111`）是现成样板。

### 五、`repair.loop` 的 Supervisor 化，具体是什么形状

这是本章**唯一**真正推荐的编排改动，所以要说得比其他条更细。

它今天在一个节点里、一个进程里跑：`for (const kase of runnable)`
（`codegen/nodes.ts:207` 起），每条用例 → 执行 → 失败 → 让模型改 → 再执行，
最多 `maxRounds` 轮（默认 2），连续 `maxWithoutProgress` 轮无进展就放弃（默认 2，`:182-186`）。

**Supervisor 化的意思不是把它拆成进程**，是把「这次失败该用哪种修法」变成一个**显式的策略选择**：
换定位器 / 加等待 / 改断言 / 判定不可修。今天这四种揉在一个提示词里，
模型选哪种既不可观测，也不可消融。

三条不能跳过的前提：

1. **先落第 2 步。** 拆进程会花两跳 IPC，并且**丢掉 zod 契约**——这个仓库为这件事付过账
   （`agent/main.ts:220-231`）。
2. **先做每节点预算。** `RunGraphOptions.budget` 是整次运行的，而 `overBudget` **只在节点之间跑**
   （`runtime.ts:400`）。一个自主角色可以在任何人干预之前吃掉整次运行的 cap。
   所以 `repair.loop` Supervisor 化的**第一件事是预算粒度，不是多角色**。
3. **先想清楚部分产物。** `codegen/nodes.ts:208` 的 `if (ctx.signal.aborted) break;`
   跳出用例循环之后**照样返回一个 bundle**，而 `runtime.ts:268-271` 把它按 `status: "done"` 存下来。
   一个被中断的策略循环和一个跑完的，今天在存储里长得一模一样。

## 收益

| 改动 | 可测量的收益 |
|---|---|
| 能力路由（第 3 步） | runner 已经在报 `{web, android, ios}`（`runner/main.ts:34`），今天纯装饰。接上之后 android 执行者可以和 web 执行者共存于一个池，**派发代码一行不改** |
| 原子占位（第 3 步） | 把一整类被误记成 `infra` 的失败从「排除在 flake / gate 之外」的黑洞里摘出来。**注意这是防回归，不是提升**——今天量不到，因为 `runnerCount: 1` 盖住了 |
| 身份 + 化身标识（第 1 步） | 「这份产物是哪一次化身产的」从答不出，变成一次 scope 查询 |
| 交接 schema（第 2 步） | `envRef`/`url` 那一类从「产出看起来正常」变成接收端当场抛 |
| `repair.loop` 策略选择（第 5 节） | 可以做真正的 A/B：一条臂固定策略，一条臂选策略。**前提是第 0 步已完成** |

**测不了的，明说：**「Supervisor 比 Pipeline 好」这句话在这个项目里**没有可测的形式**，
因为主干不换。本章不主张它，也请任何人不要在路线图里写它。

## 代价与风险

| 项 | 说明 |
|---|---|
| **只做能力路由不做原子占位** | 等于亲手打开一颗被 `runnerCount: 1` 盖住的雷，而它的症状是「被测产品偶尔挂」。**这两半必须同一个 PR** |
| **消息路由器** | 第 4 步的路由器会是每一个新失败模式的住处：发给死对端、发给未注册 id、注销后仍在途的调用 |
| **用 `worker_threads` 换 `fork`** | 为了让子 Agent 便宜而换 spawn 方式，会**同时**打断三件事，其中两件静默：`serialization: "advanced"` 下 Error 才跨得过来（`supervisor.ts:250-253`，`test/supervisor.test.ts:280` 有钉子）；`TP_PROCESS_ID` 是子进程的全部身份（`:247` → `child.ts:35`）；孤儿自杀靠 fork IPC 的 `disconnect`（`child.ts:56-59`，测试靠 SIGKILL 父进程验证） |
| **任何带默认超时的新传输** | 会重新打开一个已修的生产 bug。`timeout: -1` 在 `rpc.ts:67` 和 `:99` 设了两次，因为 birpc 按方向计时；`:92-99` 的注释记着症状——`[birpc] timeout on calling execCase`，读起来像网关不可达。**删掉这两行，整个测试套件全绿** |
| **新进程忘了 `setModelLease`** | **失败开放**：`lease` 默认是直通（`packages/harness-core/src/model/lease.ts:11`），于是这个进程静默绕过全局准入门，症状只在压力下表现为 502。样板重复在 `agent/main.ts:153` 与 `runner/main.ts:155` |
| **拆进程的固定成本** | spawn 是 `fork` 带 `--import tsx`，就绪超时 30s（`procs.ts:138`）。适合长任务，不适合一个回合 |

**什么情况下整章都不该做**：如果三个月内不打算把 `runnerCount` 拉过 1，
第 3 步的收益是零，只剩风险；第 1、2 步仍然值得做，因为它们是**防御性**的。

## 怎么证伪

| 手段 | 内容 |
|---|---|
| **单元测试** | (a) **原子占位**：并发两次 `pickRunner` 必须拿到两个不同 runner，或者第二次明确等待——**今天把这个测试写出来就是红的**，那正是它的价值；(b) **`unregister`**：注销一个未停止的进程必须抛；注销之后 `procs.ts:107-111` 那个订阅拿到它的最后一条 status 事件时，`releaseAllFor` 对已消失的 id 仍然安全；(c) **交接 schema**：给 `StartInput` 少一个 `envRef`，接收端必须抛，而不是回落到默认环境 |
| **门禁规则** | 派发路径不许再按 id 前缀判角色。一条断言：`startsWith("runner-")` 只允许出现在**注册**处，不允许出现在**路由**处 |
| **配对评测** | 只对第 5 节的 `repair.loop` 策略选择有效（一条臂固定策略，一条臂选策略），且**必须等第 0 步的两件前置**。在那之前跑，得到的是一份格式完全正常的空结论——`evals/README.md:31-33` 有三次实测 |
| **无法证伪的部分** | **「主干保持 Pipeline 是对的」这句话本身无法证伪。** 证伪它需要一个 Supervisor 版本的主干，而建那个东西的成本正是本章劝阻的全部内容。所以这里给的不是证据，是**三条会被弄坏的具体性质**（稳定序 `graph.ts:106`、失败停线 `runtime.ts:285-287`、`nodeId` 检查点 `runtime.ts:267-268`）。**如果有人做出一个不弄坏这三条的 Supervisor 主干，这个判断就该改。** 如实记在这里 |

## 验收

1. 进程页上每个进程显示 `role` / `version` / `capabilities`，不再只有一个小写 id。
2. 事件 scope 里出现 `agentId` 与化身标识；同一个 `wfRunId` 下，agent 重启前后产的产物可区分。
3. `grep -rn 'startsWith("runner-")' server/src/` 只在注册处命中。
4. `runnerCount: 2` 起来跑一遍全套件，**没有任何一条 `failCode: "EXEC_ENV"`**。
   （今天这条跑出来是红的——这正是第 3 步的验收点。）
5. `packages/harness-core/test/supervisor.test.ts` 里 `unregister` 的三个用例绿，
   且现有 19 个一个不红。
6. 把 `StartInput` 的 `envRef` 删掉再跑：agent 在接收端抛，运行以 `failed` 收尾，

7. **本章不产生任何 `evals/*.json`。** 如果有人提交了一份「Supervisor vs Pipeline」的配对评测，
   它是无效的，理由见「怎么证伪」最后一行。

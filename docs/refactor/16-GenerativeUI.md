# 16　Generative UI

> **结论先行：这一章的建议是「不做」。**
>
> 不是保守，是这个仓库**已经把这个实验做过两次，两次都留下了记录**。
> 而且它现在的做法已经是这个主题真正想要的东西——只是名字不叫 Generative UI。

## 问题

「让模型渲染组件，而不是吐 Markdown」这个提法，隐含了一个前提：
**现在模型在吐 Markdown。**

在这个仓库里，这个前提**基本不成立**。产物侧早就是「模型吐结构化 JSON → 前端渲染专用组件」：

- 模型在约束解码下产出 `CASES_SCHEMA` / `STORIES_SCHEMA`（`prompts.ts:361` / `:293`）；
- zod 再校验一次（`TextCaseSchema`）；
- 前端由 `src/lib/artifact/` 下的专用 React 组件渲染（`CaseCard` / `StoryCard` / `Field` / `Findings`）。

所以真正的问题不是「要不要上 Generative UI」，而是两个更具体的问题：

1. **还有哪些地方在用 Markdown/JSON 兜底？**（那些是残留）
2. **再往前一步——让模型自己决定渲染什么——值不值？**（这是本章要回答的）

---

## 技术点

「Generative UI」有强弱两个版本，代价差一个数量级：

| | 做法 | 谁决定呈现 |
|---|---|---|
| **弱版本** | 模型产出**受约束的结构化数据**，宿主按类型选组件 | 宿主 |
| **强版本** | 模型产出**组件选择本身**（选卡片、选颜色、选布局） | 模型 |

**这个仓库已经在弱版本上，而且做得比多数项目彻底。**本章反对的是强版本。

## 现状

### 已经是「结构化 → 专用组件」

`src/lib/artifact/types.ts:1-12` 把规矩写死了：字段必须完整、必须镜像
`server/src/review.ts` 的 DTO，且产品字段的渲染**只允许**住在 `src/lib/artifact/` 下。
理由记在 `Review.tsx:37`：

> 少写一个字段，下游就永远不知道它存在过

`CaseCard.tsx:7-14` 渲染复核要看的四个要素，并且**刻意**把 `expected` 放在 `oracle` 旁边——
因为「读起来像在验 A、实际在验 B」的用例是最危险的那种。

### 决定性的一条记录：模型/领域层渲染出来的句子，这个项目已经付过代价

`src/lib/artifact/Findings.tsx:8-22`：门禁曾经直接吐一句渲染好的英文句子，

> 根因不在前端：那句话在 `casegen/gate.ts` 里就被拼死了，过河即成常量，
> 没有 key 也就没法译

修法是改成 `rule` + `args` + `field`，句子在 i18n 层组装。
**这正是「让产出方决定呈现」的失败，已经诊断过并修好了。**

### 第二条记录：自由字符串驱动界面，当场炸掉

`prompts.ts:345`：`activity` 曾经是自由字符串，模型把**三千多字符的规格正文**抄了进去——
而 `activity` 是故事图的横轴。那一页当场变得不可读。

修法是 `storiesSchema(moduleNames)`（`prompts.ts:351`）：
**在 harness 里算出合法取值，钉成 schema 的 enum。**

反方向的失败在 `prompts.ts:105`：一个 schema 里没有的键，让看板的 P0/P1/P2 三列恒空、
导出文件名全是 `p1-*`。

> 两次事故的共同结论写在那里：**决定什么东西能到界面的是 schema，不是散文。**

### 第三条记录：产物性质决定了画布不适合

`docs/spec/09:94`：

> **产物性质不同，这是最要紧的一条。** 设计 agent 的产物是图像，**看**一眼就能判；
> 我们的产物是一百多条结构化文本，**读**才能判……在无限画布上铺一百张用例卡片，
> 比一个带筛选的列表更糟——它把「可扫视」这个唯一优势也丢了。

### 唯一一处「模型产出驱动组件」的地方，也是确定性的

`ChatDraft.diff?: string[]`（`chat.ts:56`）——那份 diff 是
`describeDiff`/`diffGraphs` **确定性**算出来的，不是模型写的。

## 变更

### 强版本：不做。理由

采纳强版本会**逐条**弄坏下面这些已经在用的性质：

| 会失去 | 今天靠什么 |
|---|---|
| 可翻译 | `rule + args`，句子在 i18n 层组装（`Findings.tsx`） |
| finding 可点击、光标落到正确输入框 | `GateFinding.field` + `Review.tsx` 的 `focusField` |
| 两版用例逐字段 diff | `EditDiff`（`Review.tsx:871`）——「『步骤变了』不是『你改了什么』的答案」 |
| 「校验通过的产物」与「被拒的产物」**在结构上**不同 | 确定性校验器说了算，不是模型选了个红卡片 |
| 横轴/看板/导出文件名的稳定 | schema enum（`prompts.ts:351`） |

还有一条更硬的：`openai.ts:152-158` 里，**约束解码在第一次带 schema 的 HTTP 失败之后
会被永久关掉**。也就是说任何模型侧的约束都必须有第二道防线
（`nodes.ts:766-776` 就是那第二道）。**让模型决定渲染，第二道防线无从写起**——
你没法在宿主里「校验一个组件选择是否合理」。

### 弱版本的三个真实残留　【这些要做】

**残留一：`ReviewBatch.stats` 已经过河，却没有字段接**

`review.ts:445` 产出它并跨网线送到了前端，而客户端的 `Batch` 接口
（`Review.tsx:83-104`）**没有这个字段**——于是门禁①的批次统计已经送到了，却看不见。

这**正是 `types.ts` 那条规矩写出来要防的缺陷**，而它现在就在犯。
加进 artifact DTO 并渲染。

**残留二：`Gap` 没有 artifact 层的渲染器**

`GapList` 住在 `Review.tsx:496`，不在 `src/lib/artifact/` 下。
于是故事图、产品地图、以及以后的任何导出，各自都有重新声明这个形状的风险。
搬进去。

（这条在缺口即将成为一等产物时会变得重要——见路线图的 G1。）

**残留三：`ChatDraft` 根本没被渲染**

`ChatDraft` 是 `{ kind, valid, issues[], warnings[], diff[], target }`——
一份完整的「人在环中确认」载荷，而诊断抽屉**只处理 `intent:"ask"`**
（`DiagnoseDrawer.tsx:63`），这份载荷一行都没显示。

`warnings` 这个通道是为一次实测失败建的（`chat.ts:44-50`）：

> 一个被要求改一个参数的模型，routinely 会把图的其它参数全部漏掉返回，
> 而由于参数有默认值，那一版**校验完全通过**，同时悄悄改掉了这次运行读哪个文件、用什么语言

**把 `warnings` 与 `issues` 分开、显眼地渲染，才是让那道检查有用的最后一步。**
今天它算出来了，然后被丢掉。

一个 `<DraftCard>`：显示 diff、把 warnings 与 issues 分开列、给一个 Apply 按钮。
**零模型渲染，纯收益。**

## 收益

| 变更 | 收益 |
|---|---|
| 残留三 · `<DraftCard>` | 让一次**已经实测发生过**的静默破坏变得可见。这是本章价值最高的一条 |
| 残留一 · batch stats | 已经付了传输成本的数据变得可见；顺带堵住 `types.ts` 要防的那类洞 |
| 残留二 · Gap 渲染器 | 缺口成为一等产物时，形状只声明一次 |
| **不采纳强版本** | 避免重新引入两次已经诊断并修好的故障 |

最后一行不是凑数。**「避免的成本」是这一章的主要产出**：
这个仓库为「让产出方决定呈现」付过两次钱，第三次会更贵，因为现在依赖那些性质的
下游（i18n 检查、focusField、EditDiff、导出、结构覆盖率分子）比当初多得多。

## 代价与风险

| 项 | 说明 |
|---|---|
| 三个残留 | 都很小，加起来一两天 |
| 搬 `GapList` | 纯搬迁，但要确认没有别处 import 了 `Review.tsx` 里的它 |
| **说「不」的风险** | 如果以后真的出现一个**呈现形态无法预先枚举**的产物，这条结论要重审。判据：能不能在 harness 里算出合法取值集合。算得出就用 enum（弱版本），算不出才需要重新讨论 |

**一个明确的去处**：如果确实想要一个渲染上自由的表面，
放到 `server/src/settings.ts:87` 那条遗留的自由文本路径上，
**别放进图流水线的契约里**。

## 怎么证伪

| 手段 | 内容 |
|---|---|
| **单元测试** | ① `Batch` 接口的字段集必须覆盖 `review.ts:445` 产出的键——这可以做成一个会红的测试，也正是 `types.ts` 那条规矩本来就想要的；② `src/lib/artifact/` 之外不得出现产品字段的渲染（一条 lint/grep 检查） |

| **无法证伪的** | 「强版本会更好用」——没法在不实施的情况下证伪。所以本章的立场不是「已证明它不行」，而是「**它要推翻的那几条性质，每一条都是实测事故换来的**」。举证责任在提案一方 |

## 验收

1. 复核页显示门禁①的批次统计（今天数据已到、界面没有）。
2. `GapList` 住在 `src/lib/artifact/` 下。
3. 诊断抽屉里，一次 `capability`/`graph`/`prompt` 起草会显示 `<DraftCard>`：
   diff、issues、**单独一栏的 warnings**、Apply。
4. 人为构造一次「模型漏掉其它参数」的图改写，**warnings 在屏幕上可见**
   ——这条直接对应 `chat.ts:44-50` 记的那次事故。
5. `pnpm check:i18n` 仍然全绿，且没有任何新的、由产出方拼死的句子。
6. 全仓库搜不到「模型决定渲染哪个组件」的代码路径。

## 落地（U-59，2026-09-02）

结论没有变——**宿主决定组件**，模型只产结构化数据。这一节记的是它现在长什么样。

### 登记处：`src/lib/artifact/registry.tsx`

一张 `kind → 组件` 的表，外加两件事：

- `registerArtifact({kind, title, render})` 登记一种呈现；
- `<Artifact kind value />` 按类型挑组件渲染。

**加一种产物呈现要改的是：这张表，和一个 React 文件。**
提示词、JSON Schema、模型侧一个字都不用动——这就是「弱版本」的全部含义，
也正是这一章想要的那件事。它不需要「让模型决定渲染什么」这个改动。

认不出的类型不当成错误：给一句「这一版还不认得 xxx」加上原始数据。
这一条是故意的——产物类型会先于前端出现（后端加一个节点，前端还没跟上），
而那时候人要的是**看见东西**，不是看见一个空白。

### 围栏：`ArtifactBoundary`

每个组件外面包一层 error boundary，按 `kind` 报错。

理由很具体：一条消息里可以挂十几张产物卡，而产物数据来自模型，
「某个字段这次没有」是它最常见的行为。没有围栏时，第十三张卡上的一个
`undefined.map` 会让**整条消息**变成白屏，包括前面十二张本来画得好好的。
围栏之后，塌掉的那一张自己说清「哪一种产物、塌在哪句话上」，其余照常。

### 这两条对应的验收

- 「新增一种产物呈现时，模型侧不需要改」→ 登记处；
- 「一个组件渲染失败不会污染整条消息」→ 围栏。

两条都没有引入任何「模型决定渲染哪个组件」的代码路径，
本章末尾那条「全仓库搜不到」的检查仍然成立。

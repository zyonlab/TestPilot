# 02　三条不可动摇的性质

> 重构可以改一切，除了这三条。
>
> 它们不是设计偏好，是**这个项目全部结论赖以成立的前提**。弄坏任何一条，
> 不会有编译错误、不会有测试变红、不会有报告变难看——只会让此前所有的数字
> 追溯性地失去含义，而没有任何人能在当天发现。

## 前置

- [第 00 章](./00-方法与约定.md)：术语表与「三个反复出现的形状」。本章大量引用形状二
  （一条规则的正确性建立在另一处的行为上）与形状三（可选的键，模型直接不写）。
- 不依赖任何代码改动。**本章不改一行行为**，它只做两件事：把三条性质定位到代码里，
  并把停在注释层的那几处往下推一层。
- 后面每一章的「前置」都应回来引用本章的编号：**P1 / P2 / P3**（性质）与 **D1**（纪律）。

## 问题

### 三个都很合理的提案

下面三句话，每一句都是一个读过这个仓库的人会认真提出的建议：

1. 「主干这条流水线太死了。换成 supervisor，让它自己决定这次要不要先探索、
   要不要多拆一轮故事。」
2. 「黄金清单只有 12–16 条，人工写太慢了。让模型读一遍产品自动生成一份，
   一晚上能出两百条。」
3. 「材料入口有三个（文档、探索、以后的代码库），形状还各不一样。
   统一成一个 `Source` 接口，下游只认一种输入。」

每一句都指向一个真实的痛点，每一句的收益都是可信的。而它们分别会弄坏 P1、P2、P3。

### 共同的症状

三条被弄坏之后，**没有一条会以失败的形式出现**：

| 弄坏的是 | 之后发生什么 | 报告上看起来 |
|---|---|---|
| P1 确定性可比 | 同一份输入两次跑出不同产物，配对评测在减两个随机数 | 有 McNemar、有 p 值、有方向 |
| P2 考卷不能由考生出 | 覆盖率涨了，因为尺子照着答卷改过 | 曲线向上，held-out 也向上 |
| P3 来源印记 | 一套完全建立在观察之上的绿色套件 | 全绿，读成「产品是对的」 |

这个仓库已经记下过这类事故的完整形态。`evals/README.md` 里那三次：

> 2026-08-30 连着白跑了三次配对评测，三次的报告都**看起来完全正常**：门禁 1.0、
> 结构完整、零错误、McNemar 有数。三次都是跑完之后去数了一下产物的分布才发现白跑的。

其中最阴险的一次「看起来像方差」，作者一度为它编了一个机制。三次的根因是同一件事的
三种形状——不是逻辑错误，是**一个前提被悄悄取消了**。

### 所以「否决项」是什么意思

一个方案如果会弄坏 P1/P2/P3 中的任何一条，**无论收益多大都不做**。

要做，只有一条路：先改掉那条性质本身——改掉那段注释、改掉那根钉子、
写清楚新的判据是什么、以及此前哪些结论因此作废——然后再动代码。
**绕过不算改。**一次「先这样，回头补上」在这三条上没有回头。

## 技术点

不变量（invariant）在工程上有四个强制层级，效力差得很远：

| 层级 | 这个仓库里的例子 | 防得住什么 |
|---|---|---|
| 文档 | `docs/spec/` 下 17 份规格 | 防得住愿意去读的人。改代码的人不一定读 |
| 注释 | `casegen/nodes.ts:41-45`「不是 agent 循环」 | 防得住读到那一段的人。删掉注释没有代价 |
| 测试 | `packages/harness-testing/test/provenance.test.ts`（六条） | 防得住改坏的提交。前提是有人跑 `pnpm test` |
| 类型 / schema | `casegen/types.ts:328` `severity: z.enum(["warn","info"])` | **写不出来**。这是唯一一种不依赖人的 |

这个仓库自己反复记着的那条纪律：

> **凡是有门禁的要求，模型就照做；凡是没有的，就漂。**
> —— `packages/harness-testing/src/codegen/gate.ts:166`

它是对模型说的，但它对人一样成立。所以本章的全部工作量，就是**给每条性质标出它今天
落在哪一层，并把停在注释层的那几处往下推一层**。

一件明确不做的事：**不给这三条建一个集中的 invariant 检查模块**。理由和 `promptSources()`
手写名单的理由一样（`packages/harness-testing/src/prompts.ts:14-17`）——一个集中的守卫
是又一处可以被绕过、可以忘记登记的地方。这三条今天分别落在类型、测试、schema 签名上，
那正是它们该在的位置。

## 现状

### P1　确定性可比：主干是流水线，主指标里没有模型

**它是什么。** 两句话，缺一不可：

1. 阶段一的主干是一条**确定性 DAG**，不是 agent 循环；
2. 配对评测的**主指标**（coverage / heldOut）由确定性关键词规则算出，中间没有模型。

**代码在哪。**

| 断言 | 锚点 | 强制层级 |
|---|---|---|
| 主干是确定性流水线，因为产物要跨版本比较 | `packages/harness-testing/src/casegen/nodes.ts:38-46` | 注释 |
| 匹配是确定性关键词规则，不是模型；代价是漏判，换来的是可复现 | `packages/harness-core/src/eval/coverage.ts:81-93` | 注释 + 纯函数 |
| `scoreCoverage` 是纯函数，同一输入同一输出 | `coverage.ts:81-116` | 代码 |
| **配对评测的两臂只调用 `scoreCoverage`**，模型判官不在其中 | `server/src/evals.ts:355-390`（`runArm`） | 代码 |
| 语义判官是**第二个数**，明确标注不可比 | `packages/harness-core/src/eval/semantic.ts:27-42` | 注释 + `SemanticCoverage` 的字段注释（`:22`） |
| 语义判官只在 `scoreRun` 的 `req.semantic` 打开时跑 | `server/src/evals.ts:254-255` | 代码 |
| 配对必须是同一批条目上的被试内设计 | `packages/harness-core/src/eval/paired.ts:1-10` | 注释 |
| 提示词在两臂之间动过就宣布这次比较作废 | `server/src/evals.ts:330-335`（`promptDrift`） | 代码 |
| 两臂配置完全相同就拒绝加载 | `server/src/evalspecs.ts:139-143` | 代码 |
| 消融开关必须真有节点在读 | `evals.ts:341` + `evalspecs.ts:133-136` | 代码（双重） |

`semantic.ts` 的头注把这条性质说得最清楚，值得原样抄一遍：

> Why this is a *second* number and not a replacement: the primary coverage figure has to
> be reproducible, because paired comparison between two versions is the whole point of
> having it — and a model in the middle of the measurement makes the same run score
> differently twice.

**它防住了什么真实事故。**

- `evals/README.md` 记的那三次白跑，全部是「自变量其实没变」的三种形状。P1 的
  两道拒绝（`promptDrift`、两臂相同）是那三次之后加的。
- `mutate/score.ts:36`（**实测**）：2026-08-29，一次 216 次执行的变异跑到一半，
  `qwen3.8-27b:free` 从服务商目录下架，18 个变异体里 9 个轮次撞上 404，
  当时的代码把它们一律记成 survived，于是得出「改文案和藏控件全都抓不到」——
  一个看起来很有分量、其实是模型下架造成的结论。修法是把「不知道」单列成
  `inconclusive` 且**不进分母**。**这条教训的一般形式就是 P1**：测量链路里任何一个
  会随时间变化的部件，都必须能把「量不到」和「量到了零」分开。

**哪些常见的重构提案会弄坏它。**

| 提案 | 怎么弄坏 | 症状 |
|---|---|---|
| 主干换 Supervisor / Swarm 编排（[第 04 章](./04-编排三模式.md)） | 每次运行的路径不同，「这次覆盖了上次没覆盖的」不再是一个可减的差 | 报告完全正常 |
| 用模型对齐预测与 gold（把 `adjudicateMisses` 提成主指标） | 同一次运行两次打分不同 | 曲线抖动被读成方差 |
| 从 zod 派生 JSON Schema（AI SDK `generateObject`、`zod-to-json-schema`） | `priority`（`casegen/types.ts:89` `.optional()`）与 `postSteps`（`:98` `.default([])`）会从 `CASES_SCHEMA.required`（`prompts.ts:433`）掉回 properties，这个模型直接不写 | **已经发生过**：`prompts.ts:407` 记着一次跑完的配对评测「两臂完全一样，McNemar 检验的是两组相同的数」 |
| 提示词搬进 Langfuse Prompt Management 或任何注册中心 | 运行的指纹开始依赖一个网络服务的状态，而 `util/digest.ts:6` 存在的全部理由是它不依赖 | 指纹稳定，内容变了 |
| 消融臂改成手写第二份提示词 | `prompts.ts:151-154` 记着：手写的第二份保留了 46 行里的 26 行，那次消融回答的是另一个问题（门禁塌到 0.017，原因与「有没有点名方法」无关） | 有数、有方向、答非所问 |
| 在 `stable` 里插入运行 id / 时间戳 / 重排段落 | 前缀缓存失效（`client.ts:73-77` 实测 ~9k token 的请求里 ~6k 命中），且 `requestKey`（`client.ts:73-83`）变化会让所有录制失效 | **测试全绿，只是慢了三倍** |

**今天的裂缝（如实记）。**

1. **消融开关不叠加。** `casegen/nodes.ts:988-996`：注释说「同时开两个时按顺序减」，
   而函数体是 `if (designMethods) return …; if (casePriority) return …;` 首个命中即返回。
   一臂声明两个开关，实际只减了一个，**没有任何地方报告这个差异**。
   这直接违反 P1 的「只差一件事」。修法在 [第 14 章](./14-评测体系.md)。
2. **语义判官没有「不知道」这一档。** `semantic.ts:76-82` 把裁决失败与解析失败
   一律推进 `stillMissing`，`calls += 1` 在 `await` 之后（`:92`）。一个端点全程 404 的
   判官产出 `calls: 0, matched: [], stillMissing: [全部]`——与一个认真看完什么也没找到的
   判官**逐字节相同**。这正是 `mutate/score.ts:36` 那次事故的形状，出现在唯一一条
   还没拿到四分类判决的路径上。
3. **`runArm` 里没有模型这件事，只由代码本身保证，没有测试钉住。** 今天读一遍
   `evals.ts:355-390` 能确认，明天有人在里面加一次 `chat()` 也不会有任何东西变红。

### P2　考卷不能由考生出

**它是什么。** 一切用来评判 harness 的**尺子**，都必须在 harness 的因果链之外产生。
这条在代码里有四个互不相干的落点，形式各异，说的是同一件事。

**代码在哪。**

| 落点 | 断言 | 锚点 | 强制层级 |
|---|---|---|---|
| 黄金清单 | 由人写、不由模型生成；`heldOut` 条目从不参与任何调参 | `fixtures/mock-spec/gold-checklist.json:4`、`fixtures/benchmark/petclinic-gold.json:4`、`coverage.ts:30` | 文件里的 note + 注释 |
| 变异体 | **只能从产品的事实生成，绝不能从用例的判据生成** | `packages/harness-testing/src/mutate/operators.ts:14`、`:19`、`:105` | **函数签名**：`generateMutants(input: { graph, spec })` 拿不到用例集 |
| critic | 不许把黄金清单抄进提示词——而且这条在**输出上**被强制 | 提示词 `critic.ts:79-81`；执行 `critic.ts:199-208` | 代码 |
| critic | 提名一个 harness 里不存在的消融开关，降级成 `manual` 而不是假装可测 | `critic.ts:211-212` | 代码 |
| 评测预判 | `expect` **不是断言**，只记录不判定 | `evals/README.md`「`expect` 不是断言」；`server/src/evals.ts:114-118` | 类型上就没有失败态 |

`operators.ts:21` 把这四条串成一句：

> 这条规矩和黄金清单「由人写、不由模型生成」是同一个道理：**考卷不能由考生出**。

而 `critic.ts:199-202` 记的是这条规矩**被违反过一次**：

> The checklist ban, enforced on the output rather than only stated in the prompt.
> It was stated, and the critic crossed it anyway — quoting two uncovered items inside
> the change it proposed. An instruction nothing checks is the failure mode this
> project keeps rediscovering: the gate is what makes a rule real.

**它防住了什么真实事故。**

- **critic 抄清单。**（实测）提示词里明写了禁令，critic 照样把两条未覆盖的清单条目
  引进它提议的改动里。一个把清单抄进提示词的 harness，覆盖率会涨，而那个数不再量任何东西。
- **变异得分变成同义反复。**（`operators.ts:16-18`）拿用例自己声称要验的字符串去改，
  杀掉率必然接近 100%，而那个数量的是「用例能不能发现自己写下的东西被改了」。
- **`expect` 变成断言。**（`evals/README.md`）「一个会红的评测会被人调到绿为止，
  而那正是评测本该防住的事。」

**哪些常见的重构提案会弄坏它。**

| 提案 | 怎么弄坏 |
|---|---|
| 让模型读产品自动生成黄金清单 | 尺子和被测物出自同一个模型、同一份材料。覆盖率会涨到 0.9 以上并且**永远涨不动**——因为它量的是模型和自己的一致性 |
| 把复核通过的用例回填进黄金清单 | `review_decisions` 是全系统唯一的人工真值（`server/src/db.ts:264-375`），拿它扩清单再拿清单给生成打分，就是自己考自己。**要做只能单向且强制 `heldOut: true`**——这是纪律，不是代码改动（`coverage.ts:30`） |
| 把 `adjudicateMisses` 换成一个更强的模型并提成主指标 | 除了弄坏 P1，还让判官（模型）给考生（同一个模型）的答卷判分 |
| 给变异体生成传入用例集「让它注得更准」 | 直接违反 `operators.ts:14`。签名今天挡住了它，改签名就挡不住了 |
| 让 critic 的建议自动落地 | `critic.ts:12-15` 写明：**critic 提议，配对评测决定**。一个被要求评价自己建议的模型会夸它，而这个项目没有人工审批环节可以兜底 |
| 把 `expect` 接进 CI 让它能失败 | 见上 |

**今天的裂缝（如实记）。**

1. **语义判官会裁决 held-out 条目。** `coverage.ts:85` 的 `misses` 是从
   `gold.items` 全体构造的，**包含 `heldOut` 的那些**；`semantic.ts:80` 遍历的正是
   `deterministic.misses`。于是 `semanticCoverage.heldOutCoverage`（`semantic.ts:121-123`）
   是一个**模型参与产生的 held-out 数**。
   严格说它没有违反 `coverage.ts:30`「never used for tuning」——判官不调参。
   但 held-out 这一片的隔离本来是这套评测最后一道防线，让一个模型摸到它是白拿的风险。
   **修法一小时**：`adjudicateMisses` 过滤掉 `heldOut` 条目，或者把「判官能不能看 held-out」
   变成一个必须显式写下的参数。
2. **人工标注还不存在。** `review_decisions` 表建好了、写入路径通了
   （`server/src/review.ts:362`、`db.ts:365`），我查过：**0 行**。
   所以「拿人工标注扩充考卷」今天不是一个纪律问题，是一个还没发生的问题——
   但它一定会被提出来，所以纪律要先写在这里。

### P3　来源印记决定断言的含义

**它是什么。** 一条规格是**怎么来的**，决定了对着它写的用例挂掉时能说明什么。
这不是元数据，是断言的语义本身。

`packages/harness-testing/src/casegen/types.ts:126-138` 把三种来源的含义写死了：

> - `document`：人写的。它表达的是**意图**，所以一条对着它写的用例挂了，可能意味着
>   「产品错了」。
> - `exploration`：从跑着的产品上看出来的。它表达的是**现状**，所以对着它写的用例
>   只能发现「产品变了」（回归），**永远不可能发现「产品错了」**——观察不可能反驳被观察者。
> - `codebase`：从代码里推的。介于两者之间。（尚未实现。）
>
> 把这个字段丢掉，一套完全建立在观察之上的绿色套件，就会被读成「产品是对的」。

**代码在哪。** 这是三条里落地最完整的一条——它从枚举一路走到了界面上的一个警示色。

| 环节 | 锚点 | 做了什么 |
|---|---|---|
| 枚举 | `casegen/types.ts:138` | `SpecProvenance = z.enum(["document","exploration","codebase"])` |
| 材料 | `types.ts:156` | `derivedFrom` **可选而非有默认值**——注释说明理由：让读的人写一次 `?? "document"`，比让 zod 悄悄替他决定要好 |
| 三个来源节点 | `nodes.ts:256`、`:265`（document）、`:369`（exploration） | 各自打各自的印记 |
| 整理时改变指令 | `casegen/prompts.ts:515-525` | `exploration` 的材料会额外收到一句：这是观察记录，**写成现状，绝不许写成要求** |
| 一路带下去 | `types.ts:271`、`:282`、`:299`；`nodes.ts:683`、`:881`、`:1025` | 规格 → 故事 → 用例批次 |
| 三个来源同一形状 | `nodes.ts:1077-1078` | 「三者产出同一种东西，区别只在 `derivedFrom` 的印记上」 |
| 界面 | `src/lib/wf.ts:618-632` | 规格卡片的标题按印记换，`exploration` 时 `tone: "warn"` 并显示专门的一句警示 |
| 不许模型自称 | `packages/harness-testing/test/casegen.test.ts:789` | 豁免名单里写着：「材料带来的：文档 / 探索 / 代码库——这决定断言能说明什么，更不能让模型自称」 |
| 传递链有测试 | `packages/harness-testing/test/provenance.test.ts`（六条） | 每一跳都钉住 |

`provenance.test.ts:5-11` 的文件头注是这条性质最紧的一段表述：

> 这不是元数据洁癖。……把这个印记丢在半路上，一套完全建立在观察之上的绿色套件，
> 就会被读成「产品是对的」。

**它防住了什么真实事故。**

这条性质防的事故还没在这个仓库里发生——因为它从第一天就在。但它的**近亲**发生过，
而且代价很清楚：`server/test/review.test.ts:135` 记着一次「字段在五跳之间静静掉了」——
`covers` 在 40 条用例里 36 条有值却没进 DTO，`requirementId` 在 8 条故事里 8 条有值
而 `approve()` 没往下传。可见的症状是**一张没有需求轴的需求追溯页**，
而没有人说得出为什么。`review.ts:573` 记着同一个根因产生了三个看起来毫不相干的症状。

P3 的字段和它们走的是同一条五跳路径。

**哪些常见的重构提案会弄坏它。**

| 提案 | 怎么弄坏 |
|---|---|
| 「材料入口太多，统一成一个 `Source` 接口」 | 三个来源产出同一种东西，**唯一的区别就是这个印记**（`nodes.ts:1077`）。一个只保留共性的接口会把它抽掉 |
| DTO 精简 / 把「用不到的字段」从 `ReviewItem`、`approve()` 里删掉 | 就是 `review.test.ts:135` 那次事故的形状。印记类字段在下游**长期没有消费者**，看起来正好像死代码 |
| 让 `spec.compose` 自己判断材料是文档还是观察 | 变成模型自称。`casegen.test.ts:789` 挡住的正是这一条 |
| 自举/自测（用 TestPilot 测 TestPilot）用探索来的规格当基线 | 得到的是一套只能发现「产品变了」的回归套件，而报告读起来像「产品是对的」。**这不是禁止自测，是要求自测的报告必须带着印记显示** |
| 给 `derivedFrom` 一个默认值 `"document"` 让类型干净些 | `types.ts:154-156` 明确拒绝过：一个悄悄替人决定的默认值，会把「不知道」变成「人写的」——这是最坏的方向 |

**今天的裂缝：** 这条基本没有裂缝。`derivedFrom` 从枚举到界面警示色是通的，
六条测试钉着传递链，一条测试钉着「不许模型自称」。**这里不用改。**
唯一值得记的是：`codebase` 这一档还没有实现，所以它今天只是一个占位的语义。

### D1　门禁纪律：设计层标记不拦，执行层有事实才拦

**为什么它不算第四条性质。** P1/P2/P3 说的是**一个数字意味着什么**——弄坏它们，
已经得出的结论追溯性作废。D1 说的是**一条规则怎样才能活下来**——弄坏它，
以后的工作停摆，但过去的数字仍然成立。两种都是致命的，但不是同一类致命，
所以这本书的目录里只写三条。D1 单列在这里，效力相同。

**它是什么。**

| 层 | 权限 | 锚点 | 强制层级 |
|---|---|---|---|
| 门禁 ①（文本用例） | **只打分和标记，不拒绝** | `packages/harness-testing/src/casegen/gate.ts:5-13` | **类型级**：`GateFindingSchema.severity: z.enum(["warn","info"])`（`casegen/types.ts:328`）——它**写不出** `block` |
| 门禁 ②（代码） | 有牙齿，但只在硬事实上 | `packages/harness-testing/src/codegen/gate.ts:4-11` | `CodeFinding.severity: z.enum(["block","warn","info"])`（`codegen/types.ts:69`） |

门禁 ② 今天有且只有六条 `block`，每一条都是关于代码文本的事实，**没有一条是关于质量的判断**：

| 规则 | 锚点 | 事实是什么 |
|---|---|---|
| `codegen-failed` | `codegen/gate.ts:110` | 根本没产出代码 |
| `unsupported-call` | `:118` | 调了执行器没有的东西 |
| `empty` | `:119` | 代码一个动作都不做 |
| `no-assertion` | `:140` | 什么都没断言，且没有机器判据 |
| `inline-secret` | `:150` | 凭证写进了源码 |
| `invented-credential` | `:154-161` | 往凭证字段里打了一个字面量 |

而 `goal-action`（`:173`）——那条从「凡是有门禁的要求模型就照做」这句教训里长出来的规则
——**只报 warn**。注释就在旁边（`:167`）：一个经常误报的门禁会被关掉，然后它什么也保护不了。

**它防住了什么真实事故。**

- `casegen/gate.ts:7-12`（**实测**）：这个想法的早一个版本是一条正则，用来拒绝「含糊的」断言。
  它**响了十几次，一次都没对**——拦住的是「登录按钮重新变得可点」这样的好判据，
  而每一条真正含糊的都漏了。
- `codegen/gate.ts:120-137`（**实测**）：`no-assertion` 原本的前提是「代码里没断言的用例
  不可能失败」。机器判据出现之后这条前提不再成立（有判据的用例被明确要求只写动作），
  而规则没跟着改——结果是 **40 条用例里 38 条被 block，一条都执行不了**。
  这是[第 00 章](./00-方法与约定.md)说的形状二的原型。

**哪些常见的重构提案会弄坏它。**

| 提案 | 怎么弄坏 |
|---|---|
| 「门禁 ① 分数低的批次直接拦下来，别浪费阶段二的钱」 | 拦截权交给了一组关于**品味**的规则。`casegen/types.ts:328` 的枚举今天挡住了它 |
| 「`goal-action` 提到 block——它明明是对的」 | 它是对的，但它是正则。正则误报一次就会有人去关它，关掉之后连 warn 都没有了 |
| 「门禁 ② 太严，把 `no-assertion` 降成 warn」 | `critic.ts:77-78` 明确禁止提议放松门禁：一套报绿而什么都不断言的用例，正是这个系统要防的那件事 |
| 给门禁加一条依赖别处行为的规则，而不写下它依赖什么 | 就是 38/40 那次。**形状二没有自动检查手段**，唯一的办法是写在规则旁边 |

## 代价与风险

**代价一：这三条会否决掉真的有价值的东西。** 要把损失写清楚，不能假装被否决的提案一无是处。

| 被否决的 | 真实失去了什么 |
|---|---|
| Supervisor 编排 | 失去了「这次材料很薄，自动多探索一轮」这类适应性。这是真的损失，[第 04 章](./04-编排三模式.md)要正面回答 |
| AI SDK `generateObject` | 失去了「一份 zod 就够了」的简洁，继续手工维护两份 schema。缓解手段已在：`casegen.test.ts:707-733` 把两者钉在一起，而这组测试是三次白跑换来的 |
| 模型生成黄金清单 | 失去了规模。今天每份清单 12–16 条，四份评测打在 `fixtures/mock-spec` 上、两臂都在 0.889–1.000，`evals/design-methods-headroom.json:4` 直接把这叫作天花板效应。**这是这个项目当前最真实的痛点，而 P2 不允许用最省事的办法解决它**——解法只能是人写更多、更难的清单 |
| Generative UI（模型渲染组件） | `prompts.ts:345` 记着实测：`activity` 留成自由字符串时，模型往里抄了 3000+ 字符的规格正文，而 `activity` 是故事图的横轴——那一页当场变成一个 3000 字的列头 |

**代价二：把「不可动摇」读成「不可讨论」。** 这是本章最大的风险。

正确的读法：这三条的**内容**可以改，改的程序是——先修改那段注释与那根钉子，
写清楚新的判据是什么、以及此前哪些结论因此作废，然后再动代码。
错误的读法：把它们当成不能提的话题，于是提案绕着它们走，最后以一种谁都没注意到的方式弄坏它们。

**代价三：一条无法自动检查的纪律。** 形状二（一条规则的正确性建立在另一处的行为上）
没有任何机器手段能防住。38/40 那次是人工发现的，`evals/README.md` 那三次也是
「跑完之后去数了一下产物」发现的。本章不改变这一点，只能把它写进验收清单。

**什么情况下这一章是错的：** 如果这个项目的目标从「量得准」变成「跑得多」——
比如决定不再做跨版本比较，只要每次产出可用即可——那么 P1 大半可以放弃，
`coverage` 可以换成一个模型判官，主干可以是 agent 循环。
**这是一个产品决策，不是技术决策，而且它必须被明确地做出来**，
不能作为某次重构的副作用悄悄发生。

### 无法证伪的部分（如实记）

**P3 这条性质本身无法证伪。** 「对着观察出来的规格写的用例永远不可能发现『产品错了』」
是一条**语义论断**，不是经验命题——没有任何实验能证明或推翻它，
因为它说的是「发现产品错了」这句话的定义。

能证伪的只有它的**传递链有没有断**：印记有没有从材料一路走到用例批次、
有没有被模型自称、界面有没有把它显示出来。这三件事全部有测试。
**这个区分很重要**：如果有人说「我们跑了个实验，探索来的规格也发现了缺陷」，
那不是证伪了 P3，那是那次的材料里混进了文档，或者那条「缺陷」其实是一次回归。

**形状二无法证伪。** 见「代价与风险」第三条。

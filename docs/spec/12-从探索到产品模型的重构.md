# 12 · 从探索到产品模型的重构

> 起因：2026-08-27 第一次用探索来的材料跑完整条流水线，产出 80 条用例、门禁分 0.588，
> 而人工复核这 80 条**基本不可用**——它们大多是「X 页显示 Y」，且以扁平列表呈现，无法快速评估。
> 这份文档回答：问题出在哪一层、怎么改、以及为什么这么改（含文献依据）。
>
> 与 11 的分工：11 讲**现在**每个节点做了什么；这份讲**要改成什么**。

## 1. 诊断：每一层都没坏，坏在材料里没有产品模型

那次运行的规格产物是 20 条规则，**全是同一种句式**：「X 页显示 Y」。

数一下里面没有的东西：

- 没有一条转移（「点 Add to cart 之后角标变成 1」）
- 没有一条守卫（「未登录访问 /inventory.html 会被弹回」）
- 没有一条领域规则（税 = 小计 × 8%）
- **没有一条说任何一个按钮按下去会发生什么**

而 10 条「没有答案的地方」里，几乎每一条都是**行为**。

**这不是 `spec.compose` 的问题。** 它的第一条禁令就是「你整理，你不撰写」，它被明令禁止发明。
材料里只有一张张屏幕的静态清单，它就只能产出一张张屏幕的静态清单——而且它老老实实把缺的
都写进了 unknowns。

问题在上游：**探索走过了每一条边，却一条都没记。**

人工介入成本高也不只是界面问题。80 条扁平条目、没有层级、没有归属，人只能一条条看。
这是**粒度**问题：复核单位应该是「一条流程」，不是「一条断言」。

## 2. 学术定位：这件事有名字，我们不必重新发明

### 2.1 AWGT 与 state-flow graph

自动化 Web GUI 测试（Automated Web GUI Testing, AWGT）的典型循环是：

```
检查页面 → 状态抽象 → 并入状态转移图 → 按策略选下一个动作 → 派发 → 回到第一步
```

我们的探索循环就是它。而「状态转移图」这个产物有更早的名字：**state-flow graph（SFG）**，
出自 Crawljax（Mesbah 等，*Crawling AJAX by Inferring User Interface State Changes*,
ICWE 2008 / TWEB 2012）——DOM 状态为节点、事件转移为边，是这个领域十五年的标准中间产物。

**所以 S1 不是发明，是补上一个标准件。**

### 2.2 四类探索策略是互补的，不是谁更强

| 类别 | 说明 |
|---|---|
| random | 傻猴子，大量无效动作 |
| **model-based** | 维护状态图，系统性地扫 ← **我们这一类** |
| RL-based | 学一个选动作的策略 |
| LLM-based | 让模型看着页面决定下一步 |

Liu, Yang, Zhang, Xie（2026）的实证结论：

> *no single category of exploration strategy consistently excels across all evaluation
> dimensions. Instead, different categories exhibit **complementary strengths** in code
> coverage, state coverage, and failure discovery.*

我们现在「代码从控件表里挑、模型只管登录」的做法属于 model-based。**这是一个正经类别，
不是退而求其次。**

### 2.3 状态抽象是关键变量

同一篇论文横比六种抽象（StrCmp / Gestalt / RTED / PDiff / WebEmbed / Judge），结论：

> *an inappropriate state abstraction can lead an approach to mistakenly treat previously
> explored pages as new ones, causing **redundant testing**, or to incorrectly regard unseen
> pages as already tested, thereby **missing testing opportunities**.*
>
> *strict and fine-grained abstractions favoring **model-based** strategies, while compact
> abstractions better support RL-based strategies.*

这两句正好是 2026-08-27 那天在探索循环上撞的两个 bug：

| 实测撞到的 | 论文里的名字 |
|---|---|
| 隐藏元素算进签名 → 菜单开关看不出区别 | 把新状态当旧的 → **漏测** |
| 拿签名当 `tried` 的键 → 同一按钮反复点 | 把旧状态当新的 → **冗余** |

**推论：状态抽象必须是可替换、可消融的组件，且用了哪一种要随产物记下来。**
一次说不出自己用的哪把尺子的探索，没法和另一次比较。

### 2.4 LLM 该吃什么上下文

> *history representation substantially impacts LLM-based strategies, where **concise,
> functionality-level context leads to the strongest effectiveness**.*

这是「喂结构模型，不喂原始屏幕转储」的实证支持。论文把「历史表示」明确当成 LLM 策略的
一种状态抽象——同一个概念的两个位置。

### 2.5 边要记到什么粒度

ScenGen（*Scenario-Guided LLM-based Mobile App GUI Testing*, ASE 2026）把每次交互记成一条
**语义完整的条目**：操作意图 / 动作类型 / 目标控件 / 输入数据 / 截图 / 精确命令。

只记 `(from, to)` 三元组在下游写不出用例——**「怎么走过去的」正是用例的步骤**。

### 2.6 检索：结构优先于相似度

微软 GraphRAG 的结论：向量检索把数据当成无结构的片段集合，会把不相关的文本塞进上下文；
而图结构让模型能做 **global reasoning**，连起向量检索错过的散落信息。它的两级索引
（entity-level 局部 / community-level 全局，Leiden 聚类 + 社区摘要）正是「按模块 map，
跨模块 reduce」的成熟形态。

**推论见 §5。**

## 3. 方案：五步，每步单独可验

### S1 · 探索产出状态转移图 ✅（2026-08-27 完成）

- 状态抽象做成一族可替换函数：`route` / `route+controls` / `route+controls+title` / `url+controls`，
  默认 `route+controls`，名字随图记下来
- 每条边按 ScenGen 粒度记：动作类型 / 目标控件 / 选择器 / 输入数据 / 结果
- **走不通的边也记**——只留成功路径，材料看起来就像这个产品没有走不通的地方
- 图既进材料正文（先看结构再看正文），也作为结构化字段挂在 `SpecMaterial` 上
- **零额外模型调用**：全部来自循环已有的变量

实测（SauceDemo）：12 个状态、21 条转移、含 `/checkout-step-one.html`，42 秒。

### S2 · 规格分三层（schema 强制）✅（2026-08-27 完成）

**S2a 流程用图算法算出来，模型只负责命名。**

「从入口到终点有哪些路径」是图算法，不是模型推断。把它交给模型等于把一个确定性问题变成
一个会漏、会编、不可复现的问题。模型该做的是它无可替代的那件事：**给路径命名、说出它对
用户意味着什么**。

| 任务 | 谁做 |
|---|---|
| 有哪些路由、哪些转移 | 代码（S1 已有） |
| 入口 → 终点有哪些路径 | **代码**（图遍历） |
| 哪些路由属于同一模块 | 代码（路径前缀 + 可达性聚类） |
| **这条路径叫什么、给用户什么价值** | **模型** |

这与本项目反复出现的那条原则一致：**能查出来的不要问模型**（`locate` 用字符串定位、
`parseCode` 用正则不求值、`oracle` 用程序判定）。

**S2b `COMPOSE_SCHEMA` 加字段，让规格有海拔。**

> **实测（SauceDemo，1 次调用 / 87 秒）**：25 条规则 —— **14 screen / 10 flow / 1 domain**，
> 外加 4 条命名过的流程、12 条 unknowns。对照改之前：20 条规则**全是 screen**、0 条流程。
> **0 → 11 条非屏幕层规则。**
>
> 新出现的规则正是以前完全缺失的那类：
> ```
> R-22 [flow]   在商品列表页点击 Add to cart 后，该商品的按钮变为 Remove，且购物车数量增加 1
> R-15 [flow]   点击 Checkout 按钮会从购物车跳转到 /checkout-step-one.html 结账信息页
> R-21 [domain] 购物车数量徽章显示在 shopping-cart-link 旁边，数值等于购物车中商品总数
> ```


| 字段 | 海拔 | 例子 |
|---|---|---|
| `rules[].altitude = domain` | 领域 | 税 = 小计 × 8%；错误提示不区分用户名与密码错误 |
| `flows[]` | 流程 | 加购 → 购物车 → 填信息 → 确认 → 完成 |
| `screens[]` | 屏幕契约 | 购物车页显示名称、单价、数量、移除按钮 |
| `unknowns[]` | — | 不变 |

「专业 spec」要的是**海拔**，不是文件数。一份产物、强制分层，比拆成三个文件更适合这条
流水线——下游只认一种 `spec` kind，拆文件要改契约，收益却只是观感。

### S3 · 故事从 flow 来，不是从文本来 ✅（2026-08-27 完成）

`STORIES_SCHEMA` 加 `activity`（骨架位置）、`role`、`benefit`、`flowId`，验收标准写成
Given/When/Then。

故事地图（Jeff Patton, *User Story Mapping*, O'Reilly 2014）的结构是硬的：
横轴是**用户活动按叙事顺序**（backbone），纵轴是每个活动下的故事按优先级排（body），
横切是发布切片（slices）。

**横轴必须来自数据。** 今天 `plan.stories` 产出的是扁平数组，没有顺序、没有归属、没有活动
——数据里没有骨架，界面就画不出图。S3 做完，横轴是数据里本来就有的。

副作用：像「US-10 页面底部显示社交链接」这种挂不到任何 flow 上的条目，会被结构本身挡掉。

### S4 · 用例挂在转移上，覆盖率有了真分母 ✅（2026-08-27 完成，待真跑验证）

每条用例声明它验证**哪条转移**。于是：

| 口径 | 分母来自 | 性质 |
|---|---|---|
| Coverage | 人写的黄金清单 | 语义：测的是不是**该测的东西** |
| **0-switch 覆盖** | **模型里的 N 条转移** | 结构：**够不够** |
| 缺陷检出 | 注入缺陷 / 变异 | 能力：抓不抓得到 |

模型基测试的标准覆盖口径本来就是分层的：状态覆盖 / 转移覆盖（0-switch）/ 相邻转移对
（1-switch），源头是 Chow 1978 的 W-method。

**但不能把它当唯一北极星**，见 §6。

### S5 · 界面：故事地图 + 从总览钻到局部

```
活动    登录 ──── 浏览商品 ──── 管理购物车 ──── 结账 ──── 完成
        │         │             │              │
故事    US-1      US-3          US-5           US-7
        US-2      US-4          US-6           US-8
用例      └ 5 条    └ 8 条        └ 6 条         └ 9 条
```

同样 80 条用例，**复核单位从 80 变成 10 个流程**。

**S5 必须排最后。** 前四步不做，界面只能画一张假的图——数据里没有骨架，横轴就是硬凑的分类。

## 4. 上下文策略：结构与文本分开

推断流程不需要页面正文，只需要图。正文是写屏幕契约、引用界面文案时才需要的，
而那是**按屏**需要的。

```
探索 ──┬─▶ 状态转移图    小、结构化、**不可截**
       └─▶ 观察全文      大、按屏取用
```

量级（实测 + 估算）：

| | SauceDemo（实测） | 百路由产品（估） |
|---|---|---|
| 观察全文 | 14.4 KB | ~1.2 MB |
| 状态转移图 | ~3 KB | ~20–30 KB |

**结构比原文小 20–40 倍**，而且它才是流程推断真正需要的东西。

调用因此切成三种，各吃各的：

| 调用 | 吃什么 | 次数 |
|---|---|---|
| flow 命名与归组 | 整张图 | 1 |
| 屏幕契约 | 一屏的全文 | 每屏一次，命中前缀缓存 |
| 领域规则 | 一条 flow 涉及的那几屏 | 每 flow 一次 |

这个切法本项目已经在用——`design.cases` 就是每故事一次而不是整份文档一次，理由写在函数头：
短调用命中前缀缓存，且一个坏回复不赔上整批。同一个道理往上游搬一层。

**纪律**：结构那一半 `fixed: true` 永不截断（截掉一条边，推出来的 flow 就是错的，而且看
不出来）；正文那一半可截，截了多少 emit 出来。

## 5. 为什么现在不上向量 RAG

三条：

1. **任务形状不对。** RAG 回答「哪些片段和查询像」，而流程推断问「这张图里有哪些路径」
   ——路径需要整张图，不是 top-k 相似片段。
2. **它引入一个静默失败点。** 检索错了不会报错，只会让模型基于错的上下文给出一个语气正确
   的答案。而这条流水线一整天修的都是这类「看起来成功」的失败。
3. **它替代不了 `locate`。** 出处定位是精确字符串包含——对「这句原话出自哪份材料」，
   精确匹配严格优于向量相似：零假阳性、可复现、不需要模型。

**什么时候重新考虑**：阶段三接真实素材（几百页人写的文档）时，任务形状变成**查找**，
那才是它的主场。而且届时它服务 `source.spec` 那一侧，不服务流程推断；形态应是
**图检索 + 社区摘要**（GraphRAG 那一套），不是纯向量。

## 6. 度量：三个数并排，不要单一北极星

同一篇实证研究的第四个发现：

> *code coverage is **not strongly correlated** with failure-revealing ability, underscoring
> the need for **multi-dimensional evaluation**.*

所以 S4 的结构覆盖率要加，但**不取代**语义覆盖与缺陷检出。三个数并排。

这一条也修正了本文档草稿阶段的一个说法：曾把 0-switch 覆盖说成「度量困境的出口」。
它解决的是「分母从哪来」，不解决「覆盖高是否等于抓得到缺陷」。后者只有缺陷检出能回答。

## 7. 基准应用：换成公开的 AWGT 套件

SauceDemo 做不出可比结果——太小（14 屏、无表单校验、无真实后端），且是第三方托管、
我们冻结不了它：站点改版会让历史数字失去意义。**2026-08-27 撤下**，
`fixtures/saucedemo/` 一并删除（git 历史里还在）。

它在这个项目里的价值已经兑现：探索循环那九个 bug 全是在它上面撞出来的。
但**一个撤下的基准不该留在仓库里**——留着，下一个人会以为它还算数。
护栏白名单里那条 `www.saucedemo.com` 也一并撤掉：它当初是为了让结账流程不被
`blockIrreversible` 拦下，基准换了之后这条豁免就没有理由了，而**一条没有理由的白名单条目，
下一次有人对着生产环境跑套件时会替他放行**。

换成上述实证研究用的那套公开基准：**Dimeshift / Pagekit / Petclinic / Phoenix /
Retroboard / Splittypie**——它给出了 Crawljax 与 WebExplor 在六种状态抽象下、在这些应用上的
代码覆盖数字，用同一套应用我们的结果**能直接对上已发表的基线**。而且它们都跑在本机，
不受外网与限流影响。

### 登记表：`fixtures/benchmark/apps.json`

每一项标明**核实到什么程度**。`verified` 说的是「镜像确实存在、版本可 pin」，
不是「在这台机器上跑起来过」；后者要等实跑，跑通了写 `startedOnce`。
**一个说自己可用、其实没人起过的基准，比没有基准更糟。**

| 应用 | 框架 | 状态 |
|---|---|---|
| **petclinic** | Spring MVC + JSP | ✅ 镜像已核实（`6.1.2`），单容器自带界面——第一个要跑通的 |
| **pagekit** | Vue + PHP | ✅ 镜像已核实（`sqlite` 变体），但 2018 年后未更新 |
| petclinic-rest | Spring Boot REST | ✅ 镜像已核实（`4.0.2`），但**只有 API 没有界面** |
| retroboard | React | ⬜ 上游活跃，**但找不到可公开拉取的镜像** |
| dimeshift | Backbone | ⬜ 无官方镜像，需自建（Node + MySQL） |
| splittypie | Ember | ⬜ 无官方镜像，且已知 flaky（通知层遮元素） |
| phoenix | Elixir | ⬜ 无官方镜像，且已知菜单不确定 |

已核实的两个登记成 **capability 配方**（`harness.config.ts`）：声明式、带健康探针、
受监工托管、在进程页起停——和 `anvil-local`、`model-proxy` 是同一套机制，只是 `kind: "app"`。
分出这个 kind 是因为「哪些进程是**被测对象**」是界面和报告要区分的一件事：
把被测应用和模型代理并排显示成同一类，读的人会以为它们同样属于工具链。

`autostart: false` —— 它们要拉镜像、占内存，不该跟着网关一起起来。
**版本全部 pin 死**：`latest` 会在某天悄悄换掉被测对象，而那种变化在结果里看起来像 harness 变了。

## 8. 论文角度：贡献候选与要准备的东西

多数 LLM 测试生成工作用的是模型判断的断言，且**不量化其中有多少本可以是确定性的**。
这个缺口是本项目现成的贡献点。

| 候选贡献 | 现状 |
|---|---|
| **判据硬度可兑现率**（声称 tier vs 有机器判据的 tier） | 已有度量；2026-08-27 实测 49%（80 条里 39 条） |
| **确定性回查约束 LLM**（出处定位 / 不求值解析 / 程序判定判据） | 已实现，且量到了差别 |
| **修复循环的作弊度量**（loose vs strict + degraded） | 已实现；实测三轮零退化 |
| 结构覆盖率（0-switch） | S4 |
| 状态抽象 × 探索策略 × **下游用例质量** | 尚无人做：已有研究比的是代码覆盖，没有比到「产出的用例好不好」 |

最后一行可能是最有价值的：**把状态抽象的影响一路量到用例质量**，而不是止步于代码覆盖。

要准备的：

- **基线**：Crawljax / WebExplorer（探索侧）；一个「截图 → 用例」的 LLM 直连版本（管线侧）
- **消融**：本项目已有机制（五个开关 + 状态抽象 + 图版本 + 提示词指纹）
- **威胁到有效性**：单一模型（qwen3.8-27b）、单一垂类、探索产不出意图（见 §9）

## 9. 三条限制，必须写在前面

**① 探索永远产不出「意图」。** 模型做得再完美也发现不了「税应该是 8%」——除非它真的带着
商品走完结账；更发现不了「错误提示故意不区分用户名与密码错误，以免泄露账号是否存在」，
那是设计意图，屏幕上看不出来。**探索来的规格，天花板是回归测试**；要测「对不对」，
得有人写的规格。这也是 `derivedFrom` 这个印记存在的理由。

**② 有些边只有「做实验」才走得到。** 填错表单、提交空值、用 `locked_out_user` 登录——
这些是**有目的的交互**，不是遍历。2026-08-27 那份规格里 10 条 unknowns 有 8 条属于这一类。
这是探索之外的另一种能力，单独立项，不并进这次重构。

**③ 这次重构没法用配对评测裁决。** 它改的是**表示**，不是参数，两臂不可比。诚实的验收
指标只有三个，且都要在动手前记下当前值：

## 10. 实施期间撞到的两件事（都不属于设计，但会咬人）

**① `tsx watch` 会跟着 workspace 包重启。** 在一次运行进行中改了 `harness-core`，网关重启，
运行被判 `interrupted`。这条项目记忆里本来就写着「别在评测跑着时改服务端代码」——
它不只对服务端 `src/` 成立，对被它 import 的每一个 workspace 包都成立。

**② 后加的字段总有一条支路没接。** `covers` 加完之后，复核队列 regenerate 那条路径重建
`TextCase` 时没带它，重写出来的用例就丢了挂在产品模型上的那根线。和 `specText` 那次
一模一样：**产出看起来完全正常，只是少了它本该带上的那一半。**

这两件事合起来说明一件事：这条流水线上最贵的不是写代码，是**发现某处静默地少做了一件事**。
所以每加一个字段，都要问一遍「哪几条路径会重建这个对象」。

## 11. 换到 PetClinic 之后：第一份两个覆盖率并排的数据

`wf-mtboy0yb`，Spring PetClinic 6.1.2，9 次调用 / 3.6 分钟。

| | 数值 |
|---|---|
| 图 | 8 状态 / 37 转移（走过 14，仅见链接 23） |
| 规格 | 16 条规则：8 screen / **6 flow** / 2 domain，7 条流程 |
| 故事 | 8 条，**全部有角色**，**7/7 挂在流程上** |
| 用例 | 35 条，门禁分 0.857，**说得出转移 23/35（66%）** |
| **状态覆盖** | **1.00**（8 个状态全被覆盖） |
| **0-switch** | **0.258**（31 条可达转移覆盖 8 条） |
| 1-switch | 0.093 |
| **语义覆盖** | 调优集 **0.556**，留出集 0.25（13 条人写清单） |

`covers` 填充率的走势：SauceDemo 31% → PetClinic 首轮 40% → **66%**。

### 发现一：探索漏掉的，恰好就是文档预言过的那一类

13 条清单里未被覆盖的 7 条：

| 漏掉的 | 类型 |
|---|---|
| G-03 空姓氏搜索返回全部主人 | 边界 |
| G-04 搜不到时提示 `has not been found` | **负例** |
| G-06 没有专长的兽医显示 `none` | 边界 |
| G-08 必填项为空时 `must not be empty` | **负例** |
| G-09 电话填字母时 `numeric value out of bounds` | **负例** |

**7 条里有 5 条是「只有故意输入坏数据才看得到」的行为。**

这正是 §9② 写下的预测：「有些边只有**做实验**才走得到——填错表单、提交空值、
用被锁定的账号登录。这是探索之外的另一种能力。」现在它被量化了：
**探索来的规格系统性地漏掉校验与负例行为，在 PetClinic 上是 5/7。**

对论文而言这是一个可报的结论，而不只是一个限制说明：黑盒探索的覆盖天花板不是渐进的，
它**在负例这一类上是结构性的缺口**——遍历再彻底也走不到那些状态，因为通往它们的边
需要有人**故意**造一个坏输入。

### 发现二：全局导航栏让 0-switch 的分母充满低价值边

23 条未覆盖的转移里，大部分是导航栏链接：`/oups->/`、`/owners->/oups`、`/vets->/owners/find`……
PetClinic 每页都有四个导航入口，于是 8 个状态之间有 31 条可达转移，其中相当一部分是
「从任意页回到任意页」。

**要求用例覆盖它们没有意义**，但它们确实是可达转移，进分母是对的。这带来一个方法论上的
注意事项：**0-switch 覆盖率在有全局导航的应用上会被系统性压低**，跨应用比较这个数时
必须同时报告导航边的占比，否则「PetClinic 0.26 vs 某应用 0.8」量的是导航栏的大小，
不是用例的好坏。

一个可能的改法是把「导航边」单列一档（从每一页都能到的目标），主指标只算非导航边。
但那是一个会改变数字含义的决定，**要先能说清哪些边算导航边**，不能凭感觉划。

### 这一轮 PetClinic 逼出的五个 bug

换基准第一天的收获，每一个在 SauceDemo 上都不会出现：

1. **流程是遍历顺序不是流程**——DFS 只在走不下去时记流程，SauceDemo 近似线性所以看不出来
2. **`/vets.xml`、`/vets.json` 进了图**——API 端点不是界面
3. **图退化成遍历的生成树**——`triedGoto` 全局记地址，每个页面只被从某一处进入一次
4. **边的出发点记错**——`goBack` 后只更新了「从哪挑控件」，没更新「从哪出发」，
   于是图里多出一条 `/oups --[点 Find Owner]--> /owners`，而错误页上根本没有那个按钮
5. **`--rm` 让基准容器死后自我删除**——它挂了，下一轮报连接拒绝，而证据没了

第 4 个最值得记：它不让任何东西报错。图完整、流程有名字有目的、规格井井有条，
唯一露馅的地方是读到「经错误页触发主人列表加载」时觉得别扭。

它和 `specText`、`covers` 是同一个模式——**一个后加的状态变量，在某一条支路上没同步**。
所以 §10 那条纪律要补上后半句：每加一个字段，要问的不只是「哪几条路径会**重建**这个对象」，
还有「哪几条路径会**改变**它」。

## 12. 补上负例缺口：做实验 + 海拔写进正文

§11 量出的结构性缺口是「7 条未覆盖里 5 条是只有故意输入坏数据才看得到的行为」。
补它花了两步，而这两步各自都不够。

### 第一步：做实验（空着提交表单）

新增第四种动作 `probe`：清空一个表单的所有可填字段，然后提交。

**只做这一种**，因为它是唯一不需要知道字段语义就能做的实验——不用判断这个框该填电话
还是日期，而绝大多数产品对空提交都有话说。填坏值要先知道字段是什么，那需要模型判断，
是另一类改动。先把不需要判断的那一半拿到，看它能补多少。

实测：2 条实验边，其中 `/owners/1/edit --[空提交]--> /owners/1/edit#1` 产出了
**同一路由的另一个状态**——校验态。材料里第一次出现 `must not be empty`。

规格随之多出两条以前不可能有的规则：

    R-10 [flow]   空着提交「Update Owner」后，每个字段下方显示验证错误信息
    R-11 [domain] 验证错误状态下，各字段的错误提示均为 must not be empty

### 第二步：海拔写进正文

但 8 条故事里**仍然没有一条讲校验**，35 条用例里也没有。缺口从「探索走不到」移到了
「设计没选中」。

根因是这条流水线上第五次出现的同一个形状：我强制模型给每条规则标 `altitude`，
然后把它留在结构化字段里**没写进正文**——而 `plan.stories` 读的是正文。

| 次 | 数据在哪 | 下游读的是 | 后果 |
|---|---|---|---|
| 1 | 规格文件路径 | `specText` 参数 | 21 次运行在**空规格**上设计用例 |
| 2 | 阶段二的动作表 | 看板的 `steps` | 修复循环的成果到不了看板 |
| 3 | 图里的转移 id | 规格正文 | `covers` 只填 11/35 |
| 4 | 环境里的登录步骤 | 探索的猜测 | 探索进不去需要登录的应用 |
| 5 | 规则的 `altitude` | 规格正文 | 故事全是屏幕清单，没有校验 |

**每一次都是：上一层产出了信息，下一层读的是另一个地方。而每一次都不报错**——
产出结构完整、看起来正常，只是少了一整类东西。

所以 §10 那条纪律要再改一次，这是它的最终形态：

> 新加的每一个字段，都要问它的**消费者读的是哪一份表示**。
> 结构化字段和文本正文是两份，写进一份不等于写进另一份。

配套的提示词也点明：**能力藏在 `[flow]` 和 `[domain]` 那两层**，只从屏幕规则里出故事，
等于把一份规格又变回屏幕清单；关于**拒绝**的规则——校验消息、错误状态、产品不让你做的事
——也是能力，而且是最常被丢掉的那一类。

### 结果

| | 做实验前 | 两步之后 |
|---|---|---|
| 故事里有没有校验 | ❌ | ✅ `S-07 空提交编辑表单时获得字段验证反馈` |
| 校验类用例 | 0 | 4（含一条对照用例：非空提交**不应**触发同样的错误组合） |
| **语义覆盖（调优集）** | 0.444 | **0.778** |
| 结构覆盖（状态） | 0.75 | **1.00** |
| 挂流程的故事 | 7/8 | **7/7** |
| 说得出转移的用例 | 28/35 | **29/35（83%）** |
| 门禁① | 0.971 | 0.971 |

新覆盖的清单项：**G-08（必填校验）、G-09（电话格式校验）**、G-07、G-10、G-11。
前两条正是 §11 点名的结构性缺口。

**必须说清楚的**：这是单次对单次，不是配对比较。语义覆盖在三次运行里是
0.556 → 0.444 → 0.778，抖动很大。方向可看（校验类用例从无到有是结构性变化，
不是抖动），但**幅度不能当因果证据**。要定论得跑配对评测。

### 仍未覆盖的

G-01（首页欢迎语）、G-04（搜不到时的提示）、G-05/G-06（兽医列表的细节）、G-13（每页回首页）。

其中 **G-04 值得单说**：它需要在搜索框里填一个**不存在的姓氏**——那是「填坏值」，
不是「空着提交」。它正好落在这一版实验刻意没做的那一半里，说明那一半确实还得做。

## 13. 顺序修正：先跨应用，再配对评测

§12 之后我提的下一步是「先做配对评测，把方差量准」。**这个排序是错的**，理由就写在
`fixtures/benchmark/apps.json` 的 `why` 里——**换基准应用的全部目的是可比性**：

> 换成公开 AWGT 研究里用的那套主题应用，我们的数字才能对上已发表的基线。

而先做配对评测，是在 PetClinic **一个**应用上把方差算准。那只能证明「这些改动在
PetClinic 上有效」，证不了任何跨应用的事，更对不上文献。等于花力气把一个**还没建成的
对比**的其中一个点测得很精确。

更要紧的是过拟合风险。整份重构的成果**至今只在 PetClinic 上量过**，而这一个应用的形状
可能已经渗进了策略：

- §11 那个「全局导航栏系统性压低 0-switch」的发现，是 PetClinic 特有的结构，
  它在别的应用上成不成立，**我不知道**；
- 探索的控件清扫顺序、`probe` 只做空提交、流程按路由前缀聚类——每一条都是对着这一个
  应用调顺的；
- 留出集 0.25 与调优集 0.778 的差距本身就是警告信号。留出集能挡「照着清单写用例」，
  **挡不住「探索策略被这一个应用带偏」**——因为留出的是清单条目，不是应用。

所以正确顺序是 **跨应用 → 补实验 → 配对评测**：

1. **把第二、第三个应用真跑起来**。在没调过的应用上跑一遍，看重构的成果还在不在——
   这是唯一能揭穿过拟合的手段，也正是当初换基准要买的东西。
2. 补「填坏值」实验（G-04 那类）。
3. 配对评测最后做。方差要在**多个应用**上量才有意义；现在做，是给一个孤点配误差棒。

### 登记表的实际状态（2026-08-28）

七个候选里**只有 PetClinic 真起过**。而 `dimeshift / splittypie / phoenix / retroboard`
——**正是文献里那套主题应用**，也就是我们换基准想要的那一批——登记表里连镜像都没有，
因为论文里它们是从源码起的，没有官方镜像。

也就是说：**「对上已发表基线」这件事，到今天一步都没走。**换基准的动作做了（撤下
SauceDemo、登记新应用），换基准的**目的**还没兑现。这一条记在这里，免得再把它当成
已完成的事。

## 14. 两个应用各五次：第一份带误差棒的数据

§13 定了顺序（跨应用 → 补实验 → 配对评测）。第二个基准应用跑起来之后，两个应用各跑五次。
这是这个项目第一次有分布，而不是单点。

### 先更正一件事

§12 里我拿「语义覆盖 0.444 → 0.778」当作海拔修复见效的证据，并写了「幅度不能当因果
证据」。**现在可以说得更死：那个 0.778 就是噪声。**

PetClinic 五次的语义覆盖是 **0.623 ± 0.149**，逐次为 0.556 / 0.556 / 0.556 / 0.556 / 0.889。
四次落在 0.556（9 条调优项里命中 5 条），一次 0.889。我当时报的 0.778 是这个分布里的一次
抽样，而且是偏高的那一侧。

修复本身仍然有效（修之前稳定在 0.444 = 4/9，之后稳定在 0.556 = 5/9，**多了一项，
而且是稳定多的**），但幅度从「+0.33」缩到「+0.11」。**一次运行能把效应量报大三倍。**

### 数据

| | PetClinic（n=5） | Juice Shop（n=5） |
|---|---|---|
| 语义覆盖 · 调优集 | **0.623 ± 0.149** | **0.377 ± 0.061** |
| 语义覆盖 · 留出集 | 0.250 ± 0.177 | 0.280 ± 0.110 |
| 状态覆盖 | **1.000 ± 0.000** | 0.419 ± 0.061 |
| 0-switch | 0.233 ± 0.000 | 0.327 ± 0.093 |
| 1-switch | 0.067 ± 0.000 | 0.232 ± 0.111 |
| 门禁① | 0.962 ± 0.041 | 0.892 ± 0.052 |
| 用例数 | 34.6 ± 3.6 | 33.4 ± 4.7 |
| 图 | 8 状态 / 35 转移（12 走过 + 23 仅见） | 22.4 状态 / 35 转移（35 走过 + 0 仅见） |

两个应用的转移数都恰好 35，是巧合——构成完全不同（见括号）。查过了，没有截断。

### 三个发现

**① 探索的确定性。** 图的规模在 PetClinic 上标准差为 0（8 状态 / 35 转移，五次完全一致），
在 Juice Shop 上也只有 22–23。**探索这一层是确定性的**——控件清扫按固定顺序，模型只在
登录时被调用一次。所有的方差都来自它下游：规则 11–20 条，故事 6–8 条，用例 28–40 条。

这有一个直接的方法论后果：**要比较探索策略，一次就够；要比较下游产出，五次都嫌少。**

**② 每次都漏的项，成因只有两种。** 把两个应用 5/5 全漏的 10 条并起来看：

| 成因 | PetClinic | Juice Shop |
|---|---|---|
| **探索走不到那一屏** | G-01（首页——探索从 `/` 出发第一步就跳走了，再没回来） | J-10 注册、J-12 联系、J-13 关于（都藏在 Account 菜单和汉堡菜单后面） |
| **要故意输入坏值** | G-04 搜不到的姓氏、G-09 电话填字母 | J-03 搜索无匹配、J-08 邮箱留空、J-09 凭证错误、J-11 密码过短 |

**十条里没有一条是「探索看到了但下游丢了」。**这把责任划得很干净：语义覆盖现在的天花板
是探索的**触达**，不是规格/故事/用例这三层的转写质量。上一轮我一直在改下游（海拔、模块、
covers），而真正卡住的是上游。

`probe` 这一版只做了「空着提交」——不需要知道字段语义的那一半。剩下六条里有四条要
「填坏值」，那一半确实还得做，而且它现在是最大的一块。

**③ 留出集与调优集的差距，两个应用方向不同。**
PetClinic 是 0.623 vs 0.250（差 0.37），Juice Shop 是 0.377 vs 0.280（差 0.10）。
PetClinic 的清单被我改过三轮（补双语、补 locale），调优集因此被"喂"得更熟；
Juice Shop 的清单今天才写、一次没改过。**这个差距本身就是过拟合的量度**，
而它说明 PetClinic 上的调优集数字要打折看。

## 15. 补探索的触达与实验：十一个修复，以及一个还没兑现的度量

§14 把责任划干净了：**每次都漏的十条，没有一条是「探索看到了但下游丢了」**——
六条要故意输入坏值，四条是探索走不到那一屏。这一节做这两件事。

### 一、按等价类做实验（六条里的那部分）

原来只有一档「空着提交」。它的理由写得很清楚：**唯一不需要知道字段语义就能做的实验**。
不需要语义的那一半已经拿到了，剩下的必须认字段——但认字段用不着模型，
`type` 加上 name/id/placeholder/aria-label 四个提示就够。

    empty      清空所有字段再提交      → 必填校验
    malformed  给有格式的字段填非法值   → 格式校验（电话填字母、密码只给一个字符）
    unmatched  填格式合法但查不到的值   → 「搜不到」「凭证错误」这一类

三条约束，都不是妥协：

① **`unmatched` 只对查询/登录表单做。** 它填的是格式合法的值——在新增/编辑表单上提交
   会通过校验然后**真的写库**。那一刻探索就不再是观察：被测应用被改了，而基准的意义
   全在于两次跑的是同一个东西。（PetClinic 五次图完全一致、标准差为 0，正是这个性质的
   体现。）而这类实验想看的行为本来就只出现在查询和登录上。

② **`malformed` 只在这一屏真有带格式的字段时才做**，否则白花一轮。

③ 坏值里的邮箱和网址用 RFC 2606 保留的 `.invalid` 域——一个基准应用的实验不该往
   任何真实地址发东西。

做的过程中还挖出两个更深的问题：

**实验把页面带走了要回来。** `Find Owner` 空提交直接跳到 `/owners`，于是「填查不到的
姓氏」那一档永远轮不到——而它正是五次全漏的 G-04。实验和点击是两回事：点击是往前走，
实验是**在同一张表单上换一种输入再看一次**，走了就得回来。

**实验的结果要进材料，哪怕它不算新状态。** 状态抽象是按**控件**算的，而校验消息只是
**文字**：往电话框填一个字母、提交、页面多出一行错误——控件集合一个字没变，于是这一屏被
判成「见过了」，文字连同那条消息一起丢掉。「这算不算新状态」和「这次观察值不值得留」
是两个问题：遍历问前者，实验问后者，而实验本来就是冲着看不出结构差别的行为去的。

### 二、触达（四条里的那部分）

改了六处，每一处都由一次实测逼出来：

| 症状 | 根因 |
|---|---|
| 侧边栏点开了，下一步却是 `goto: /` | **链接采集也丢哈希**——`/#/contact`、`/#/about`、`/#/register` 全塌成 `/`，去重后只剩一个。和当初 `routeOf` 一模一样的错，只是在另一个地方 |
| 40% 的预算花在点商品卡片上 | `shapeDry` 只在代表**没走出去**时才拦，而每张卡片打开一个内容不同的弹窗，**每次都是新状态**。补一道硬上限：结构同类每条路由最多点三次，**按路由计不按状态计**（按状态计会被"每次都是新状态"整个绕开） |
| 注册页一次都没进过 | 探索只有深度优先加退回，而**退回只能沿原路**。`#/register` 在登录页上被看见，探索走去了 forgot-password 就再没回来。补一个**全局待访问队列**，并且要排在所有点击**之前**——放在最后等于没有，因为预算在「没事可做」之前就花完了 |
| 探索跑到 GitHub 上去了 | Juice Shop 有个 `/redirect?to=<外部地址>`。那条链接**本身是同源的**，「站外不点」判它内部完全正确——但它一跳就出去了，出去之后 GitHub 每条链接又都成了"同源"。**规则没错，判的时机错了**：边界要在**到达时**判 |
| about、contact 走到了，材料里却没有 | 网关那一刀 `notes.slice(0, 60000)`。屏数从 8 长到 30 之后它每次都生效，而**从尾巴切会整屏整屏地消失**——丢掉的总是最后探索到的那些屏，也就是上面这些改进费力够到的部分。**一个会把自己的成果吃掉的预算。**改成按屏分配 |
| 搜索框对探索根本不存在 | 它没有 aria-label、没有 placeholder、没有 id、没有 title——四样兜底全空，被 `.filter(c => c.label.trim())` 整条过滤掉。那道过滤是为了挡垃圾可点元素，但**可填的输入框从来不是垃圾**：它的用途是被填，不是被读 |

### 四、必须说清楚的三件事

**① 这只是探索层，不是语义覆盖。** 关键词进材料是必要条件，不是充分条件——后面还有
规格、故事、用例三层，每一层都可能把它丢掉。**真正的数要等模型可用之后重跑五次才有。**

**② 模型额度用尽了。** TokenHarbor 三个免费模型是**账号级**共享额度，已全部用尽，
下一个滚动周期 **2026-09-03** 才开始。所以 §14 那种带误差棒的度量现在做不了，
第三个应用的泛化验证也做不了——它们都卡在同一个地方。

**③ 探索变慢了很多。** 从约 3.5 分钟涨到 30 分钟以上：轮数上限是「屏数×5」，屏数放宽到
32 就是 160 轮，每轮 1.6 秒落定加一次快照。彻底和快是一对矛盾，这个代价要写进论文，
也要在跑批量之前调下来。

**④ `No results found` 这一条我停手了。** 它是 14 条里的 1 条，而追它已经造成过一次
退步（命中 6/7 掉到 3/7）和一次 28 分钟的挂死（`fill` 没有超时）。两个主目标都已交付，
继续钻它就是目标漂移。它剩下的成因很具体：Juice Shop 的搜索框折叠时 4px 宽，
要先点开再填，而「先点开」这一步现在还没有和实验串起来。

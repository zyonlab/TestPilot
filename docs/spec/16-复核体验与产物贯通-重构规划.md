产物的**数据结构**已经达到专业测试设计的要求；**呈现与贯通**平均只把其中三分之一交到人手上。

### 1.5 三条**不要重犯**的判断错误

第一版评审判错过三条，接手的人别再照抄：

1. 导出**不是**单文件平铺——`export.ts:297` 每条用例一个 `tests/<pri>-<slug>.spec.ts`。
2. 生成代码里**没有 aiAssert 是刻意的**——有机器判据时判决在最后一条语句后由程序求值，
   插一句 aiAssert 等于让模型抢在程序前面否决结论，还多烧一次调用。提示词里写明了。
3. 模块**是**一等实体，只是活不过 `approve()`。

## 2. 什么算「优质的优化」

每个任务动手前必须先写下**预期**，跑完把实际结果并排放。这条纪律抄自 `evals/README.md`：
「跑完之后再解释为什么这个结果是意料之中的，不是。」

四条通用判据，任何一条不满足就不算做完：

| # | 判据 | 反例（做砸的样子） |
|---|---|---|
| A | **字段贯通类**改动要能把 §1.3 表里某一格从 ✗ 变成「在」，并有一条单元测试钉住 | 界面上画出来了，但没测试；下次谁重构 DTO 又悄悄丢掉 |
| B | **门禁类**改动只许加规则、不许放宽既有规则来抬分数 | 为了让门禁分好看，把 `oracle-vague` 的阈值调松 |
| C | **界面类**改动要能让「一个不写代码的人能否判断这份产物对不对」从否变是，用 §5.4 的人工复核脚本实测 | 加了字段但挤在 11px 灰字里，人还是读不出来 |
| D | 改动不得让任何既有数字**无法解释**。分子分母变了要在报告里说明 | 变异得分从 0.6 变 0.8，但没人说得清是套件变强了还是分母变小了 |

外加一条硬约束：**度量口径与被度量物不许同时改**。要改门禁规则就先冻结这一批产物，
拿同一批产物跑新旧两版规则对比；要改提示词就用 `evals/` 的配对评测，两组只差一件事。

## 3. 三个重构提案（大动作，先看设计再拆任务）

### R-A · 产物渲染契约（前端）

**问题的形状**：同一份 `ReviewStory` 数据，复核队列的故事图画出了「用户 · 能进入按姓氏检索
主人的页面」，故事抽屉一个字都没画——因为抽屉自己声明了一份本地接口，只写了它想画的键。
`SpecDrawer` / `StoriesDrawer` / `CasesBoard` / `Review` 四处各声明一遍、各决定画哪几个键。
新增字段要在四个地方各补一遍，漏一个没人知道。

**做法**：

1. 新建 `src/lib/artifact/` ——产物的**唯一**类型来源与渲染组件。
   - `types.ts`：`Story` / `TextCase` / `SpecRule` 的前端类型，从 `server/src/review.ts`
     的 DTO 一一对应，**字段全量**，不许各处再自己声明。
   - `StoryCard.tsx`：一处决定故事怎么画（三段式标题、activity、flowId、出处及其可信度）。
   - `CaseCard.tsx`：一处决定用例怎么画（前置 / 数据 / 步骤 / 断言双行 / 覆盖转移 / 方法 / tier）。
   - `Finding.tsx`：一处决定门禁 finding 怎么画（配合 R-B）。
2. `StoriesDrawer` / `Review` / `CasesBoard` 全部改为消费这三个组件，删掉本地接口声明。
3. 加一条 lint 约定（先写进本文档，后续可上 eslint 规则）：**产物字段的渲染只许出现在
   `src/lib/artifact/` 下**。

**为什么值得做**：§1.3 表最后一列的 ✗ 会一次性清空，且以后不会再长回来。
这是「如果只做一件事」的那件事。

**验收**：
- `grep -rn "interface Story\|interface TextCase" src/` 只剩 `src/lib/artifact/types.ts` 一处。
- 故事抽屉与故事地图显示的字段集合完全一致（同一条 S-07，两处截图逐字段比对）。
- 用例卡上能同时看到：前置、步骤（编号）、期望原文、机器判据、覆盖的转移、设计方法、判据强度。

### R-B · finding 结构化 + 国际化（后端 + 前端）

**问题的形状**：`gate.ts` 里 `add("oracle-vague", \`assertion promises nothing checkable: "..."\`)`
——给人看的句子在 harness 包里就拼死了，过河即成常量。中文界面上原样显示英文 lint 码；
同一个文件里 `covers-unknown` 的消息又是中文，语言在源头就不统一。

**做法**：

1. 改 `GateFinding` 的形状：
   ```ts
   interface GateFinding {
     rule: string;                       // 稳定的规则 id，永远英文，是 i18n key 的后缀
     severity: "block" | "warn" | "info";
     caseId?: string;
     args?: Record<string, string | number>;   // 句子里要填的洞
     field?: "title" | "steps" | "expected" | "precondition" | "designMethod" | "covers";
   }
   ```
   领域层**只产 rule + args + field**，一句人话都不拼。
2. `src/lib/i18n.ts` 里为每条规则加三条条目：`gate.<rule>.msg`（带 `{arg}` 插值）、
   `gate.<rule>.why`（这条规则在管什么）、`gate.<rule>.fix`（改成什么样就过）。
   i18n 已支持插值（`translate(key, lang, vars)`）。
3. 界面渲染成：严重度色条 + 一句中文 + 「为什么」折叠 + 「怎么改」+ 点击定位到 `field` 指的输入框。
4. 存量数据兼容：老 finding 只有 `message` 字符串，渲染时按原样显示并打上「旧格式」标记，
   不做数据迁移（评测历史不该被改写）。

**验收**：
- `grep -rnE 'add\("[a-z-]+", `' packages/harness-testing/src/**/gate.ts` 返回 0 行（没有拼句子了）。
- 界面语言切到 en / ja，finding 全部跟着变；切到 zh 无一处英文残留。
- 点一条 `oracle-vague`，光标落到该用例的「期望」输入框。

### R-C · 候选与资产的双账本（后端 + 前端）

**问题的形状**：候选产物挂在运行上，已批准资产挂在项目上。代码里分得很清楚
（`graphs.ts:138` 甚至写着「候选没有看板优先级，声称一个就是在编造事实」），
界面把两者都叫「用例」「代码」，于是三处数字互相打脸：

- 画布「用例代码 38」→ 代码线「这个项目还没有一条用例带代码」0/0
- 画布「文本用例 40」→ 看板「这个项目还没有用例」
- 交付页「0 条用例 · 8 个文件」而下载按钮可点

**做法**：

1. 网关加一个**项目视角的聚合**：`GET /api/projects/:id/overview` 返回
   ```
   { approved: {cases, withCode, byPriority}, candidates: {runs, cases, code, latestRunId},
     coverage: {transitions, covered, unvisitedEntries}, mutation: {score, blindSpots} }
   ```
   数据来源：`test_cases`（已批准）+ `wf_runs.projectId` 关联的运行输出（候选）。
2. 项目卡与项目首屏改为**两栏**：「已批准 N」与「待复核 M（来自 K 次运行）」，
   两个数字永远各自带标签，不再有裸数字。
3. 所有产物卡的链接改为带 `run` 参数，落到**这次运行的**阅读器，而不是项目看板。
4. 交付页在 0 条时禁用下载并说明「先在复核队列批准一批」。
5. 项目首屏第一行放缺口与变异盲区（现在埋在第四层）。

**验收**：
- 界面上任何一个用例/代码相关的数字，都能一眼看出它数的是候选还是已批准。
- 从画布任一产物卡点进去，看到的都是这次运行的产物，不会落到空看板。
- 交付页 0 条时下载按钮不可点。

## 5. 怎么证明改好了

### 5.1 每次提交必须过

```bash
pnpm typecheck && pnpm typecheck:ws && pnpm test
```

`packages/harness-testing/test/` 下已有 20+ 个测试文件（`casegen` / `codegen` / `gate` /
`oracle` / `mutate` / `frozen` / `ablation` …）。**凡是字段贯通类改动，必须在对应的
`*.test.ts` 里加一条钉住它的用例**，否则不算做完（判据 A）。

### 5.2 提示词类改动必须走配对评测

在 `evals/` 里加一个 json，两组**只差一件事**，`expect` 在跑之前写下。
`ablate` 里只能写 `packages/harness-core/src/eval/ablation.ts` 的 `ABLATABLE` 里真的有节点在读的名字。

### 5.3 变异得分是终判，但要看分母

改完之后重跑一次变异，与基线（**0.600，6/10，18 变异 × 12 用例 = 216 次执行，
0 模型调用，0 基础设施失败，模型 `mimo-v2.5:free`**）对比。
读数时必须同时看 `inconclusive` 与 `denom`——分数变好也可能是分母变小了（判据 D）。

### 5.4 人工复核脚本（判据 C 的唯一实测手段）

找一个**没参与开发**的人，给他 15 分钟和一条链接，让他做三件事并计时：

1. 打开一批待复核用例，随机挑 5 条，逐条说出：前置是什么、要准备什么数据、几步、断言是什么。
   —— 现状：0/5 能说全（前置与判据界面上根本没有）。目标：5/5。
2. 说出这批用例漏了产品的哪一块。
   —— 现状：能（缺口栏是好的），但要滚四层才看到。目标：首屏可见。
3. 说出某条用例来自哪条需求。
   —— 现状：0/5。目标：5/5。

**这三个数是本轮唯一的对外结论**，比任何门禁分都重要。做完记到本文档末尾。

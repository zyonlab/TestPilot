## 1. 目的与边界

TestPilot 做一件事：把需求材料，或者对被测网站的探索结果，变成端到端 UI 测试。流程是：文本用例 → 人工复核批准 → 编译成 Midscene 动作代码 → 执行 → 导出成工程。

| 做 | 不做 |
|---|---|
| 判决一律从屏幕读。受限解码的判据 `kind` 只有 `text / noText / url / count / delta / decimal-equation / reading / judge / none`（`packages/harness-testing/src/casegen/prompts.ts` 的 oracle schema）；如果判决读的是被测站接口，门禁记一条 `oracle-offsite`（`casegen/gate.ts::runGate`） | 不直接调用被测站接口。`exec/apiOracle.ts` 还留着，只用来执行旧用例 |
| 入口有两个：Web，以及 Claude Code（宿主插件 + MCP） | Penguin 与 Codex 标为**实验性**（见 §3） |
| 验收的被测对象：只有 Hyperliquid 测试网 `https://app.hyperliquid-testnet.xyz/trade`（2026-09-18 起） | 主网 `app.hyperliquid.xyz` 在禁止名单上，永远不放行（§8） |
| 领域内容一律当项目数据处理（§9） | 代码里不写死领域词，由 `pnpm check:domain-neutral` 检查 |
| 冻结模块树、批准用例、决定回归候选必须由人来做；故事里有候选业务预期时，审核故事也要人（§5）；学习回路里并入领域参考、冻结标准集、换项目执行模型，项目层采纳资产版本、审任务也要人（§10、§6.1） | 本地审核不做身份验证，只记录操作来源与版本（§8） |

**冻结不做**（初步交付，开源、MIT）：子 agent 并行、记分板、论文研究线。自进化、经验与反例库、标准测试集 2026-09-28 用户解冻，新落点见 §10 与 docs/v3/15 阶段 6～9。
旧的评估代码还在但没接进新回路：`server/src/evolution/`（独立进程，默认端口 7365，见 `evolution/main.ts`，只有一个玩具评测任务）、`extensions/penguin-evaluation/`、`src/pages/Gold.tsx`、`src/pages/Scoreboard.tsx`。

## 2. 进程、端口与模型角色

| 进程 | 位置 | 说明 |
|---|---|---|
| Web | `src/`，React + rsbuild | 端口 `:5300`（`rsbuild.config.ts`） |
| API 服务 | `server/src/index.ts`，Express | 端口 `:5301`（`server/src/config.ts` 的 `PORT`，可用环境变量 `PORT` 覆盖）。数据目录由 `TP_DATA_DIR` 指定（`datadir.ts`）：主库 `testpilot.db`（`db.ts`），账本 `workflows.db` + `revision-blobs/`（`runService.ts::runLedger`） |
| agent 子进程 | `apps/agent/src/main.ts` | 由 API 服务托管（`server/src/procs.ts`），承载图运行时 `runGraph`，给 pipeline 对照模式用 |
| runner 子进程 | `apps/runner/src/` | 一次只跑一条用例，负责 Midscene 会话、截图与性能数据。每个 runner 有自己的 `midscene_run/<runner-id>/` 目录（`procs.ts` 的 `MIDSCENE_ROOT`）；启动时清掉上一个 runner 留下的孤儿浏览器（`apps/runner/src/main.ts` 调 `sweepOrphanBrowsers`） |
| 规划宿主 | Claude Code 子进程（`server/src/claudecode.ts`），或 Codex（`codex.ts`）、Penguin（`penguin.ts`） | `claude -p … --output-format stream-json`，通过 `--plugin-dir` 装载 skills、hooks 与 MCP。服务端起的宿主进程带上 `x-testpilot-actor: planner-host` 预加载（`server/src/runtime/hostActorTag.ts::hostActorEnv`，§8） |

模型分**两个角色**，不会悄悄互相替代：

- **规划（planner）**：Web 走 Penguin 时读取项目配置或 `TP_PLANNER_*`（`packages/harness-core/src/model/connections-env.ts`）。宿主运行时（Claude Code / Codex）用宿主自己的模型，绑定里记为 `source: "host"`，`identityEvidence: "unknown"`（`server/src/modelSnapshots.ts`）。
- **执行（executor）**：用 Midscene 模型，来自项目配置，或 `MIDSCENE_MODEL_*` / `OPENAI_*`（`connections-env.ts`）。开跑前探一次执行模型，401/402/403/429 当场拒（`server/src/modelPreflight.ts::executorPreflight`，执行与准备都调）。
- **快照**：运行创建时把绑定写进 `run_model_snapshots`，连接信息加密保存（`modelSnapshots.ts`、`vault.ts`）。执行读的是快照，不读当前配置。

## 3. 规划运行时

`server/src/runtimes.ts` 登记了三个运行时，接口都是 `startRun / watchRun / readRun / writeDecisions`。

| 运行时 | 适配 | 状态 |
|---|---|---|
| `claude-code` | `server/src/claudecode.ts`，插件 `plugins/testpilot-claude/` | **默认**：`TP_AGENT_RUNTIME` 不设时就是它（`runtimes.ts::defaultRuntimeName`） |
| `penguin` | `server/src/penguin.ts`、`server/src/runtime/` | 实验性：需要 Node 24（`penguin.ts` 找不到就报 `penguin_node_24_required`）和 Penguin 服务 |
| `codex` | `server/src/codex.ts`，插件 `plugins/testpilot-codex/` | 实验性。Web 新建运行接受 `claude-code`、`codex`、`penguin`，别的名字报 `web_planner_runtime_unsupported`（`workflowOps.ts::createWebWorkflow`） |

- 运行时在创建运行时就定下，续跑沿用同一个（`workflowOps.ts::plannerOf`）。
- 本机缺可执行文件时，创建请求当场被拒（`runtimes.ts::plannerRuntimeAvailable`，报 `planner_runtime_unavailable`）。
- 传入不认识的运行时名直接报错，不会退回默认值（`runtimes.ts::getRuntime`）。
- 新建运行也可以写 `planner: "connected"`：用项目选定的本机宿主（Claude Code 或 Codex，按登录状态探测；两个都登录时要人选一次），没选或没就绪报 `planner_host_selection_required` / `planner_host_not_ready`（`server/src/plannerHost.ts`，路由 `GET/POST /api/projects/:id/planner-host`）。项目层增量任务也走这个宿主（§6.1）。

## 5. 一次运行的阶段流水线

节点顺序定义在 `server/src/workflowControls.ts` 的 `nodes`：`source → modules → instructions → stories → cases → gate → finalize → g2 → execution`。每个节点开始前，规划器必须调用 `begin_stage`；否则写入会被拒，返回 `begin_stage_required`（`workflowControls.ts::requireStageStarted`，同一处还拦 `module_plan_requires_human_freeze` 与待审故事）。节点上的断点会让运行暂停，暂停后只能由人续跑。

| 阶段 | 做什么 | 账本产物（revision 名） | 代码位置 |
|---|---|---|---|
| 创建 | 校验输入，绑定规则包与领域参考（可从项目知识库按 `knowledgeSelection` / `rulePackSelection` 选版本），锁定规划运行时，记下实现版本。也可以导入冻结的产品模型或故事 | `knowledge/rulepack/<id>`、`knowledge/domain-reference`、`knowledge/<name>`、`implementation/registration` | `workflowOps.ts::createWebWorkflow`、`implementationVersion.ts` |
| source · spec | 直接使用上传的 `.md/.txt` 材料 | `<材料文件名>`（kind `material`，登记时封存 `materialsHash`/`inputHash`） | `runService.ts::freezeRunMaterials`、`runLedger.ts::sealInputs` |
| source · explore | 探索前先查禁止名单。绑定了规则包时，按 charter 做领域引导探索并生成产品模型；中途失败会捡回已经采到的屏 | `context/source`、`exploration/observations`、`exploration/report`、`exploration/attempt`、`exploration/planner-call`、`product/model-candidate`、`report/exploration-partial`，以及材料 `exploration.md` | `workflowOps.ts` 中的 `launchSource`、`sourceKnowledge`；`explorationPlanner.ts`、`explorationResults.ts` |
| modules | 模型提出模块树 → 服务端机检（有 error 就整份拒收）→ **人来冻结** | `validated/modules` | `moduleStage.ts::writeModulePlan`、`::freezeModulePlan`（`actor.kind !== "human"` 时返回 403 `module_plan_freeze_requires_human`） |
| instructions | 下发冻结版本的 skills、执行记忆、反例、写作准则，以及整次运行不变的 `runScope`，并钉住门禁策略 | `validated/instructions` | `runStages.ts::loadRunInstructions` |
| retrieve | 按查询检索材料块。没检索过就不能写故事或用例（`retrieve_spec_required`）；每次分发落一份审计 | 表 `run_retrievals`、`retrieval/<retrievalId>` | `runStages.ts::retrieveRunSpec`、`retrievalAudit.ts` |
| stories | 做 schema 校验、模块引用检查、`subsumes` 链检查、`checkStories`。用例写过以后，故事就冻结了 | `validated/stories`、`report/acceptance-index`、`report/module-fanout` | `runStages.ts::writeRunStage` |
| 故事审核 | 故事带 `requirementDraft`（引用了 `hypothesis` 规则）时，运行停在 `waiting_review`，cases 及之后被拒（`story_requirements_need_review`）；人批准或带理由（≥4 字）驳回。下游重跑时，故事与业务输入未变可沿用上一次的批准 | `review/story-requirements`、`review/story-requirements-rejected`、`review/story-requirements-inherited` | `server/src/storyReview.ts`；路由 `…/:runId/story-requirements[/approve\|/reject]` |
| cases | 校验用例，并检查它们和已存故事、检索块是否一致 | `validated/cases` | 同 stories |
| gate | 运行 `runGate`，策略是 `design-gate-v2`（`minGateScore 0.6`、`minNegativeRatio 0.3`）。回执另带 `executionAdmission`（每条用例的执行阻塞项）。不通过时，按用例把工作单元重新打开 | `validated/gate` | `runStages.ts` 的 `policy`、`::gateRun`；`workUnits.ts::reopenUnitsFromGate` |
| finalize | 首次定稿时重新计算门禁并逐位比对，过期（`gate_stale_rerun_required`）或不一致（`gate_not_passed`）就拒绝；已定稿的运行不再拿今天的规则重判。通过后运行进入 `waiting_review` | `validated/finalize` | `runStages.ts::finalizeRun` |
| 复核 | 每条用例生成一个可修订的修订；批准或驳回只能由人做，驳回必须写理由（`rejection_requires_reason`），结果写进决定 outbox 再投递到项目用例板 | `review/case/<caseId>`、表 `case_approval_events` | `approvedRuns.ts` 的 `reviewRevisions`、`reviseReviewedCase`、`decideRevisions`；`decisionDelivery.ts` |
| g2 · 编译 | **不调用模型**：已批准的步骤逐句转成 `aiAction` / `aiWaitFor` / `aiAssert`，再跑 `runCodeGate` | `g2/v2/<approvalsHash>-<compilerHash>`、`compilation-observation/<id>` | `approvedRuns.ts::generateApprovedCode` |
| g2 · 执行准备 | 人发起（`POST …/:runId/preparation/start`）。服务端先挡掉确定准备不出来的用例（`preparationAdmission.ts`），再用本运行的规划运行时起一个准备会话：宿主逐条调 `preparation_step`（`next / probe / trial / resolve / discover / guide`），每次试跑都派给 runner，**只有 runner 回执能把用例标成 verified**。说明按需读（`preparationGuidance.ts` 的 `GUIDES`），被拒时随错误带修法（`ERROR_FIXES`）；验证过的准备配方可复用（`preparationExperience.ts`）。验证通过的用例合成一份可执行代码 | 表 `preparation_batches`、`preparation_recipes`；`preparation/<batchId>/…`；`g2/prepared/<batchId>`（kind `code`，`compilation: "host-prepared-v1"`） | `server/src/preparation.ts`（`startPreparation`、`preparationStep`、`validatePreparedBundle`） |
| execution | 执行 g2 产物（编译版或准备版），可以用 `caseIds` 只跑一部分。执行前先探执行模型、过守卫，再派给 runner | `execution/<id>`，表 `workflow_executions` | `workflowExecution.ts::startWorkflowExecution`、`exec.ts`、`executionPolicy.ts` |
| 导出 | 两条路径：<br>• 项目级：生成 Playwright + Midscene 工程，默认排除隔离的、降级的和已被取代的用例<br>• 修订级：导出血缘 JSON | 不写账本 | `index.ts` 的 `/api/projects/:id/export` 加 `export.ts::buildExportFiles`（分层 `exportLayers.ts`、判据源码 `exportOracle.ts`、完整性 `exportIntegrity.ts`）；`runRoutes.ts` 的 `…/artifacts/:revisionId/export` |

续跑检查点见 `workflowOps.ts::workflowCheckpoint`：`source` 和 `modules` 只有在「走过但没走完」时才会被回到。

全流程图、运行状态机，以及创建、冻结、复核、执行、看报告五个操作的逐跳时序图，见 [02-工作流-横向与纵向](02-工作流-横向与纵向.md)。

## 6. 运行账本与工作单元

**账本**（`server/src/runLedger.ts`，实例由 `runService.ts::runLedger` 创建，数据在 SQLite `workflows.db`，内容 blob 在 `revision-blobs/`）：

- 修订不可变。内容按 sha256 存成 blob，读取时重新校验（`revision_content_changed`）。
- 同名产物只能追加。`parentRevision` 必须等于上一版，否则报 `revision_version_conflict`；内容完全相同的重试是幂等的。
- 事件按 `(runId,node,attempt,sequence)` 唯一，节点状态从事件投影出来，可以重建（`rebuild()`、`integrity()`）。
- 阶段回执放在表 `run_stage_receipts`，一个阶段一行，指向当前修订（`runStages.ts::save`）。
- 批准事件放在 `case_approval_events` / `case_approval_heads`，投递走 `decision_outbox`（`approvedRuns.ts`）。
- 宿主写入需要运行令牌（`runService.ts::authorizeRun`）。通用导入路由拒绝服务端保留的前缀 `review/ validated/ units/ regression-candidate/ preparation/ g2/ retrieval/ implementation/ comparison/ comparison-review/`（`runRoutes.ts`，返回 403 `reserved_artifact_name`），宿主也不能伪造服务端的阶段事件（`server_stage_event_reserved`）。

**工作单元循环**（`server/src/workUnits.ts`，只对 `parameters.workUnits === 1` 的运行生效）：

- **拆分由服务端做**（`planUnits`）。故事单元有两类：按根模块子树拆出的 `stories:<rootId>`，以及最后一个 `stories:journeys`。用例单元按故事拆，一条故事一个 `cases:<storyId>`。模块树存在但还没冻结时，报 `module_plan_freeze_required`。
- **一次领一个**（`claimUnit`）。领取不并发，每个单元最多试 5 次（`MAX_UNIT_ATTEMPTS`）。返回的内容包括单元范围、ContextManifest（同时落账为 `context/<node>/<manifestId>`）、这个单元的材料和 `contract`。
- **材料分两层下发**：
  - 领域参考全文只在 `load_run_instructions` 的 `runScope` 里发一次（`runStages.ts::runScopeMaterials`）。
  - `claim_unit` 不带 `domainReference` 和 `productModelRevision`；`storyIndex` 只随该节点的第一个单元发。
  - 词表（`actionVocabulary`）、易变读数、持久设置、角色、规则包、与本单元相关的业务转换和业务状态等小字段**每个单元都会发**。原因写在注释里：这些字段拿掉以后，动作型验收准则的比例明显下降（`workUnits.ts::claimUnit` 的注释）。
- **写入**只校验本单元（`writeUnit`）。故事单元可以附带 `moduleAmendments`，但这只是提议，不会生效，结果落为 `module-amendment/…`。
- **合并由代码做**（`mergeUnits`），合并时再跑一遍整份校验。开了单元循环的运行不能整份写入（`assertWholeWriteAllowed`）。

### 6.1 项目层：资产版本、发现与增量任务

运行账本之上还有一层**项目级**的东西，路由都挂在 `/api/projects/:projectId/assets`（`server/src/projectAssetRoutes.ts`）。宿主只能读（`tp_assets`）；审、启动、采纳都在 Web 由人做（非 human principal 报 `operator_action_required`）。

| 部件 | 做什么 | 代码位置（表） |
|---|---|---|
| 资产版本与快照 | 把某次运行里不可变的修订复制成项目资产的候选版本，人采纳后成为该资产的头版；快照是一组头版的冻结集合，带 digest | `projectAssets.ts`（`project_asset_versions`、`project_asset_heads`、`project_asset_decisions`、`project_asset_snapshots`） |

## 11. 验收命令

下面的 script 都在根目录 `package.json` 里：

```bash
pnpm typecheck && pnpm test          # 前端 tsc + i18n 检查；各包、apps、server 的 tsc 与 vitest
pnpm test:hooks                      # hook 子进程测试（plugins/testpilot/hooks/test）；不在 pnpm test 里
pnpm check:drift                     # 两臂提示词逐条认领（scripts/check-drift.mjs）
pnpm check:host-parity               # 宿主入口对 UI 路由的覆盖
pnpm check:domain-neutral            # 代码与 skill 里没有写死的领域内容
pnpm check:i18n                      # 界面文案三语齐全、引用都命中（pnpm typecheck 也会跑）
node --test scripts/test/*.test.mjs  # 安装脚本与 hook 夹具的测试
node scripts/replay.mjs              # 冻结运行确定性重打分
node scripts/cost-report.mjs         # 每条用例的账（= pnpm cost:report）
```

改了 `plugins/testpilot/skills/**` 或 `casegen/prompts.ts` 之后，还要做三件事：让 `check:drift` 变绿，跳 `plugins/testpilot/plugin.json` 的 `skillVersions`，然后重新生成两份宿主副本（`pnpm build:claude-plugin`、`pnpm build:codex-plugin`）。

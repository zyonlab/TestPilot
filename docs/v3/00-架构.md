# TestPilot 架构

> 2026-09-16 按当前代码重写，每条事实都注明了代码位置。旧版以 PenguinHarness 为中心，已经不适用，归档在 [旧架构](history/00-架构.md)。
> 本文与代码冲突时以代码为准，并回来改这份文档。

## 1. 目的与边界

TestPilot 做一件事：把需求材料，或者对被测网站的探索结果，变成端到端 UI 测试。流程是：文本用例 → 人工复核批准 → 编译成 Midscene 动作代码 → 执行 → 导出成工程。

| 做 | 不做 |
|---|---|
| 判决一律从屏幕读。受限解码的判据 `kind` 只有 `text / noText / url / count / delta / none` 这几种（`packages/harness-testing/src/casegen/prompts.ts:475`）；如果判决读的是被测站接口，门禁记一条 `oracle-offsite`（`casegen/gate.ts:265`） | 不直接调用被测站接口。`exec/apiOracle.ts` 还留着，只用来执行旧用例 |
| 入口有两个：Web，以及 Claude Code（宿主插件 + MCP） | Penguin 与 Codex 标为**实验性**（见 §3） |
| 验收的被测对象：只有 Hyperliquid 测试网 `https://app.hyperliquid-testnet.xyz/trade`（2026-09-18 起） | 主网 `app.hyperliquid.xyz` 在禁止名单上，永远不放行（§8） |
| 领域内容一律当项目数据处理（§9） | 代码里不写死领域词，由 `pnpm check:domain-neutral` 检查 |
| 批准、冻结模块树这两件事必须由人来做 | 本地审核不做身份验证，只记录操作来源与版本（§8） |

**冻结不做**（初步交付，开源、MIT）：自进化、经验与反例库、子 agent 并行、Gold 与记分板、论文研究线。相关代码还在，但不在交付范围内：
`server/src/evolution/`（独立进程，默认端口 7365，见 `evolution/main.ts`）、`extensions/penguin-evaluation/`、`src/pages/Gold.tsx`、`src/pages/Scoreboard.tsx`。

## 2. 进程、端口与模型角色

| 进程 | 位置 | 说明 |
|---|---|---|
| Web | `src/`，React + rsbuild | 端口 `:5300`（`rsbuild.config.ts`） |
| API 服务 | `server/src/index.ts`，Express | 端口 `:5301`（`server/src/config.ts:155`，可用 `PORT` 覆盖）。数据目录由 `TP_DATA_DIR` 指定（`datadir.ts`） |
| agent 子进程 | `apps/agent/src/main.ts` | 由 API 服务托管（`server/src/procs.ts`），承载图运行时 `runGraph`，给 pipeline 对照模式用 |
| runner 子进程 | `apps/runner/src/` | 一次只跑一条用例，负责 Midscene 会话、截图与性能数据。每个 runner 有自己的 `midscene_run/<runner-id>/` 目录（`procs.ts:203`） |
| 规划宿主 | Claude Code 子进程（`server/src/claudecode.ts`） | `claude -p … --output-format stream-json`，通过 `--plugin-dir` 装载 skills、hooks 与 MCP |

模型分**两个角色**，不会悄悄互相替代：

- **规划（planner）**：Web 走 Penguin 时读取项目配置或 `TP_PLANNER_*`（`packages/harness-core/src/model/connections-env.ts`）。宿主运行时（Claude Code / Codex）用宿主自己的模型，绑定里记为 `source: "host"`，`identityEvidence: "unknown"`（`server/src/modelSnapshots.ts:56`）。
- **执行（executor）**：用 Midscene 模型，来自项目配置，或 `MIDSCENE_MODEL_*` / `OPENAI_*`（`connections-env.ts:15`）。
- **快照**：运行创建时把绑定写进 `run_model_snapshots`，连接信息加密保存（`modelSnapshots.ts`、`vault.ts`）。执行读的是快照，不读当前配置。

## 3. 规划运行时

`server/src/runtimes.ts` 登记了三个运行时，接口都是 `startRun / watchRun / readRun / writeDecisions`。

| 运行时 | 适配 | 状态 |
|---|---|---|
| `claude-code` | `server/src/claudecode.ts`，插件 `plugins/testpilot-claude/` | **默认**：`TP_AGENT_RUNTIME` 不设时就是它（`runtimes.ts:54`） |
| `penguin` | `server/src/penguin.ts`、`server/src/runtime/` | 实验性：需要 Node 24（`penguin.ts:144` 找不到就报 `penguin_node_24_required`）和 Penguin 服务 |
| `codex` | `server/src/codex.ts`，插件 `plugins/testpilot-codex/` | 实验性。Web 新建运行只接受 `claude-code` 或 `penguin`（`workflowOps.ts` 会报 `web_planner_runtime_unsupported`） |

- 运行时在创建运行时就定下，续跑沿用同一个（`workflowOps.ts::plannerOf`）。
- 本机缺可执行文件时，创建请求当场被拒（`runtimes.ts:62 plannerRuntimeAvailable`）。
- 传入不认识的运行时名直接报错，不会退回默认值（`runtimes.ts:42`）。

## 5. 一次运行的阶段流水线

节点顺序定义在 `server/src/workflowControls.ts:9`：`source → modules → instructions → stories → cases → gate → finalize → g2 → execution`。每个节点开始前，规划器必须调用 `begin_stage`；否则写入会被拒，返回 `begin_stage_required`（`workflowControls.ts:120`）。节点上的断点会让运行暂停，暂停后只能由人续跑。

| 阶段 | 做什么 | 账本产物（revision 名） | 代码位置 |
|---|---|---|---|
| 创建 | 校验输入，绑定规则包与领域参考，锁定规划运行时。也可以导入冻结的产品模型或故事 | `knowledge/rulepack/<id>`、`knowledge/domain-reference`、`knowledge/<name>` | `workflowOps.ts:28 createWebWorkflow` |
| source · spec | 直接使用上传的 `.md/.txt` 材料 | `materials/…`（kind `material`，材料冻结后封存 `inputHash`） | `runService.ts::freezeRunMaterials`、`runLedger.ts::sealInputs` |
| source · explore | 探索前先查禁止名单。绑定了规则包时，按 charter 做领域引导探索并生成产品模型；中途失败会捡回已经采到的屏 | `context/source`、`exploration/observations`、`exploration/report`、`product/model-candidate`、`report/exploration-partial` | `workflowOps.ts` 中的 `launchSource`、`sourceKnowledge` |
| modules | 模型提出模块树 → 服务端机检（有 error 就整份拒收）→ **人来冻结** | `validated/modules` | `moduleStage.ts:130 writeModulePlan`、`:184 freezeModulePlan`（`actor.kind !== "human"` 时返回 403） |
| instructions | 下发冻结版本的 skills、记忆，以及整次运行不变的 `runScope`，并钉住门禁策略 | `validated/instructions` | `runStages.ts:132 loadRunInstructions` |
| retrieve | 按查询检索材料块。没检索过就不能写故事或用例（`retrieve_spec_required`） | 记在表 `run_retrievals` | `runStages.ts:178` |
| stories | 做 schema 校验、模块引用检查、`subsumes` 链检查、`checkStories`。用例写过以后，故事就冻结了 | `validated/stories`、`report/acceptance-index`、`report/module-fanout` | `runStages.ts:190 writeRunStage` |
| cases | 校验用例，并检查它们和已存故事、检索块是否一致 | `validated/cases` | 同上 |
| gate | 运行 `runGate`，策略是 `design-gate-v2`（`minGateScore 0.6`、`minNegativeRatio 0.3`）。不通过时，按用例把工作单元重新打开 | `validated/gate` | `runStages.ts:26`、`:282 gateRun`、`workUnits.ts:832` |
| finalize | 重新计算门禁并逐位比对；门禁结果过期或不一致就拒绝。通过后运行进入 `waiting_review` | `validated/finalize` | `runStages.ts:307` |
| 复核 | 每条用例生成一个可修订的修订；批准或拒绝只能由人做，结果写进决定 outbox 再投递到项目用例板 | `review/case/<caseId>`、表 `case_approval_events` | `approvedRuns.ts:22/41/54`、`decisionDelivery.ts` |
| g2 | **不调用模型**：已批准的步骤逐句转成 `aiAction` / `aiWaitFor` / `aiAssert`，再跑 `runCodeGate` | `g2/v2/<approvalsHash>-<compilerHash>` | `approvedRuns.ts:83 generateApprovedCode` |
| execution | 执行 g2 产物，可以用 `caseIds` 只跑一部分。执行前先过守卫，再派给 runner | `execution/<id>` | `workflowExecution.ts:72`、`exec.ts`、`executionPolicy.ts` |
| 导出 | 两条路径：<br>• 项目级：生成 Playwright + Midscene 工程，默认排除隔离的、降级的和已被取代的用例<br>• 修订级：导出血缘 JSON | 不写账本 | `index.ts:989` 加 `export.ts::buildExportFiles`；`runRoutes.ts:120` |

续跑检查点见 `workflowOps.ts:206 workflowCheckpoint`：`source` 和 `modules` 只有在「走过但没走完」时才会被回到。

全流程图、运行状态机，以及创建、冻结、复核、执行、看报告五个操作的逐跳时序图，见 [02-工作流-横向与纵向](02-工作流-横向与纵向.md)。

## 6. 运行账本与工作单元

**账本**（`server/src/runLedger.ts`，实例由 `runService.ts::runLedger` 创建，数据在 SQLite `workflows.db`，内容 blob 在 `revision-blobs/`）：

- 修订不可变。内容按 sha256 存成 blob，读取时重新校验（`revision_content_changed`）。
- 同名产物只能追加。`parentRevision` 必须等于上一版，否则报 `revision_version_conflict`；内容完全相同的重试是幂等的。
- 事件按 `(runId,node,attempt,sequence)` 唯一，节点状态从事件投影出来，可以重建（`rebuild()`、`integrity()`）。
- 阶段回执放在表 `run_stage_receipts`，一个阶段一行，指向当前修订（`runStages.ts::save`）。
- 批准事件放在 `case_approval_events` / `case_approval_heads`，投递走 `decision_outbox`（`approvedRuns.ts`）。
- 宿主写入需要运行令牌（`runService.ts::authorizeRun`）。通用导入路由拒绝 `validated/` 和 `units/` 前缀（`runRoutes.ts`，返回 `reserved_artifact_name`），宿主也不能伪造服务端的阶段事件（`server_stage_event_reserved`）。

**工作单元循环**（`server/src/workUnits.ts`，只对 `parameters.workUnits === 1` 的运行生效）：

- **拆分由服务端做**（`planUnits:156`）。故事单元有两类：按根模块子树拆出的 `stories:<rootId>`，以及最后一个 `stories:journeys`。用例单元按故事拆，一条故事一个 `cases:<storyId>`。模块树存在但还没冻结时，报 `module_plan_freeze_required`。
- **一次领一个**（`claimUnit:305`）。领取不并发，每个单元最多试 5 次（`MAX_UNIT_ATTEMPTS`）。返回的内容包括单元范围、ContextManifest、这个单元的材料和 `contract`。
- **材料分两层下发**：
  - 领域参考全文只在 `load_run_instructions` 的 `runScope` 里发一次（`runStages.ts:117 runScopeMaterials`）。
  - `claim_unit` 不带 `domainReference` 和 `productModelRevision`；`storyIndex` 只随该节点的第一个单元发。
  - 词表（`actionVocabulary`）、易变读数、角色、规则包等小字段**每个单元都会发**。原因写在注释里：这些字段拿掉以后，动作型验收准则的比例明显下降（`workUnits.ts:330` 的注释）。
- **写入**只校验本单元（`writeUnit:398`）。故事单元可以附带 `moduleAmendments`，但这只是提议，不会生效，结果落为 `module-amendment/…`。
- **合并由代码做**（`mergeUnits:555`），合并时再跑一遍整份校验。开了单元循环的运行不能整份写入（`assertWholeWriteAllowed:616`）。

## 7. 宿主入口

- **MCP 阶段工具**（`packages/testpilot-mcp/src/server.ts`）：`register_run`、`begin_stage`、`plan_modules`、`module_plan_state`、`load_run_instructions`、`gate_run`、`finalize_run`、`claim_unit`、`write_unit`、`unit_status`、`merge_units`、`import_run_artifact`、`read_run_artifact`、`get_project_run`、`generate_execution`、`execute_approved`，另有旧的 `run_pipeline`、`write_stories`、`write_cases`、`retrieve_spec`、`score_run` 等。这些工具只转发请求，业务校验都在服务端。
- **UI 操作的覆盖**：`packages/testpilot-mcp/src/host/registry.ts` 把路由按域映射成 `tp_project`、`tp_run`、`tp_stage`、`tp_unit`、`tp_review`、`tp_execution`、`tp_export` 等工具，由同目录的 `tools.ts` 注册。`server/host-parity.json` 给每条 UI 路由分了类，`pnpm check:host-parity`（`scripts/check-host-parity.mjs`）要求新路由必须分类，而且覆盖率不能下降。
- **Claude Code 适配**：
  - `claudecode.ts` 把 MCP 声明写进 workspace 的 `.mcp.json`，stream-json 原样落到 `<outDir>/claude-stream.jsonl`。
  - hooks 通过 `plugins/testpilot/hooks/adapters/claude-code.mjs` 执行。
  - 任务话术在 `server/src/runtime/skill-launch.ts`，分整份和工作单元两套。

## 8. 守卫与红线

| 规则 | 代码位置 |
|---|---|
| 禁止名单 `guard.denyHosts` 上的地址什么都不跑，环境和运行参数都放不开 | `server/harness.config.ts`（`["app.hyperliquid.xyz"]`）、`packages/harness-testing/src/guard.ts:68 checkRun`、探索入口 `workflowOps.ts:35` |
| 不可逆步骤默认放行：`blockIrreversible: false`。设 `GUARD_STRICT=1` 才整机拦截，这时规则包的 `sideEffectLabels` 才起作用 | `harness.config.ts`、`packages/harness-core/src/config/resolve.ts:54`、`server/src/executionPolicy.ts:16 guardRun` |
| 环境变量 `DENY_HOSTS` 只能往禁止名单里加地址 | `resolve.ts:53` |
| 没有主机白名单，也没有环境级「允许不可逆」开关 | `guard.ts` 只查以上两项 |
| 人的操作不做身份验证：`reviewerPrincipal` 恒返回 `{kind:"human",id:"local-operator"}`；请求带了 `Authorization` 头就拒绝（`operator_action_required`），所以拿着运行令牌的代理冒充不了人 | `server/src/reviewPrincipal.ts` |
| 批准、修订用例、冻结模块树都必须是 human principal | `approvedRuns.ts::human`、`moduleStage.ts:184` |
| 规划器提交不了分数和阈值，门禁策略在 instructions 阶段就钉住了 | `runStages.ts:26`、`:282` |

## 9. 领域数据三件套

| 四节点成绩单 | 产品结构、用户故事、文本用例、用例代码四个节点各出一份结果，全部复用上面几项机检 | `server/scripts/measure-run.ts`（打印 `runReport`）（`pnpm exec tsx scripts/measure-run.ts <runId> <projectId> [--json]`，在 `server/` 下运行） |

## 11. 验收命令

下面的 script 都在根目录 `package.json` 里：

```bash
pnpm typecheck && pnpm test          # 前端 tsc + i18n 检查；各包、apps、server 的 tsc 与 vitest
pnpm test:hooks                      # hook 子进程测试（plugins/testpilot/hooks/test）；不在 pnpm test 里
pnpm check:drift                     # 两臂提示词逐条认领（scripts/check-drift.mjs）
pnpm check:host-parity               # 宿主入口对 UI 路由的覆盖
pnpm check:domain-neutral            # 代码与 skill 里没有写死的领域内容
node scripts/replay.mjs              # 冻结运行确定性重打分
node scripts/cost-report.mjs         # 每条用例的账（= pnpm cost:report）
```

改了 `plugins/testpilot/skills/**` 或 `casegen/prompts.ts` 之后，还要做三件事：让 `check:drift` 变绿，跳 `plugins/testpilot/plugin.json` 的 `skillVersions`，然后重新生成两份宿主副本（`pnpm build:claude-plugin`、`pnpm build:codex-plugin`）。

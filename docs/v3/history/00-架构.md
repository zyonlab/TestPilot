# v3 架构：在 PenguinHarness 上做

> **2026-09-10 最新产品建模补充**：产品结构与用户故事为联合产物；按 Spec / Explore / 未来 Code 分来源，并在项目级融合。Role / Skill / 知识按节点冻结与隔离的目标、当前差距和实施顺序见 [16 · 产品结构与多入口知识契约](16-产品结构与多入口知识契约.md)。该补充保留双宿主方式、双模型角色和论文目标，不把原型视为生产完成。

> **2026-09-09 用户配置决策**：现有 `.env` 模型用于 Midscene。Claude Code / Codex / PenguinHarness 插件继承宿主规划模型，无需另配；Web 初期使用相同模型，但用独立 `TP_PLANNER_*` 变量，后续可单独更换。项目保存的配置优先于环境默认值。此决策允许当前环境显式初始化两角色，不允许运行时静默跨角色回退。

> **2026-09-08 用户决策补充（优先于本文后续旧迁移描述）**：TestPilot 保留 Web UI 与宿主 agent 两种完整入口。Web UI 配置规划/执行两个模型角色，管理项目、workflow、材料、产物及 review；宿主模式由 Claude Code / Codex / PenguinHarness 自身模型规划，另配 Midscene 低成本执行模型。PenguinHarness UI 负责自进化评估与版本晋级。不能将 workflow 和模型配置整体迁出 TestPilot，也不能将 Midscene 模型隐式用于领域规划。本文下方涉及上述职责的旧方案是历史设计，尚未代表新方案已实现。
>
> 新实施契约、用户故事、数据结构与可执行任务以 [08 · 双入口双模型](08-双入口双模型-优化任务与验收.md) 为准；07 保留历史任务状态。A pipeline 是使用规划角色的显式对照模式，C skill 是宿主规划路径；阶段顺序和门禁由服务/MCP 强制。此补充不取消 oracle、gold 与确定性打分的保护要求。

## 1. 一句话

**TestPilot 切两半**：产品层留（前端 + 领域服务），harness 层换成 PenguinHarness。
TestPilot 最强的 Verification 层（确定性打分、变异、宽严口径）**作为 MCP 工具**保留；
PenguinHarness 补上 TestPilot 接近 0 的三层：Context、Governance、Memory。

## 2. 形态

> **Reading C（2026-09-03 拍板）**：PenguinHarness 是运行时 + 元工具两半。`agent-optimization` 只能改 `agent_state/`（config / skills / hooks / memory），所以**该进化的进 Agent State，不该进化的留在 MCP**。生成器提示词 → `skills/*/SKILL.md`；门禁与 schema 校验 → `hooks/*.mjs`；打分 / 执行 / 检索 → MCP 工具。

```
testpilot/
├── src/                     产品层前端（留；11 项导航 → 7；复核队列 → 审计台）
├── server/                  产品层领域服务（留 review/cases/deliver/baselines/trends/export/db；
│                            harness 半边改为调 Penguin SDK：createSession / events / traces）
├── packages/
│   ├── harness-testing/     九步节点 + 打分 + 变异 + Midscene 驱动（留；去掉对 harness-core/graph 的依赖）
│   ├── testpilot-mcp/       【新】MCP server（stdio）：确定性工具
│   │     run_pipeline · score_run · paired_eval · mutate_and_detect · drive_sut · retrieve_spec
│   └── harness-core/        退役大半：graph → run_pipeline 内的 for 循环；obs/model/harness → Penguin
├── plugins/testpilot/       【新】Penguin plugin（纯数据）：plugin.json + skills/*/SKILL.md + hooks/*.mjs
│     skills: testpilot-generate · testpilot-review · testpilot-benchmark-design · testpilot-evaluation · testpilot-scanner
└── benchmark/<capability>/  gold.json · human-labels.json · statement/ · rubric/ · held-out/（对 Optimizer 只读）
```

两个服务并行：`:5300` QA 工作台（TestPilot），`:7364` harness 操作台（Penguin）。不 iframe；审计台条目带「看 trace →」深链。

## 3. 三条不可让步的性质（沿用 docs/archive/refactor/02 的 P1/P2/P3，翻译成新机制）

| | 落点 |
|---|---|
| **P1 确定性可比** | **2026-09-03 重述（用户拍板）**：生成器（stories / design 的提示词）进 Agent State 成为可进化的 skill，于是「同一输入两次跑出同一产物」不再成立，换成 **「同一 Agent State 版本 + 冻结基准 + 每题 n 次运行 → 比分布」**。两臂仍只差一件事：Agent State 版本。门禁与校验是 hook（确定性、随 State 走、模型改不了）；打分是 MCP 工具（State 之外，优化器碰不到）。`run_pipeline` 保留为 Reading A 的对照臂——**Phase 3 第一次配对评测就是 A（工具）vs C（skill）**。 |
| **P2 考卷不能由考生出** | `rubric/` 对 Test Agent 不可见；`gold.json` 按内容哈希进 scoreboard，哈希变了即新谱系，跨谱系不比；`held-out/` 对 Optimizer 文件权限只读 |
| **P3 来源印记** | `score_run` 返回 `binding{graphVersion, promptsDigest, goldHash, model, thinking}`；scoreboard 条目缺任一项**拒收** |

再加两条研究里最硬的：**分数由工具算，模型不写分**（`testpilot-evaluation` skill 只回传工具输出）；**生成与判定分 workspace**（`drive_sut` 对 `benchmark/` 无写权限）。

## 4. 一次运行

```
[TestPilot UI] 起跑 → server: penguin createSession(agent="testpilot", workspace=<项目目录>)
  agent 载入 skill testpilot-generate（顺序写死）
    ① retrieve_spec(materials/)           建索引，替掉 fitToBudget 盲裁
    ② run_pipeline({stage:"g1"})          九步，确定性；写 runs/<id>/*.json；emit 节点事件
    ③ score_run(run_id)                   可选；coverage + binding
    ④ 写 memory（episodic：「页面 X 控件 Y 这次没探到」）
  server 读 runs/<id>/*.json → 复核批次入库
[TestPilot UI] 审计台 → 决定 → decisions 写回
  下一 session：read_decisions() → run_pipeline({stage:"g2", cases: 已批准})
```

## 5. 调研结论（约束设计的那几条）

- 混合控制是共识（CAAF / ADK 2.0 / Inspect / LangGraph）：确定性管断言求值、路由、状态锁；模型管首版生成与探索。多 agent 互评 0%（16/20 收敛到违约共识）。
- 最终分确定性、judge 只做推理期决策——8 个开源项目无一例外。judge 要 κ 校准（原始一致率换 κ 掉 33–41 点）、要换模型族（自我偏好 0.52）、单次 pairwise 翻转 13.6%。
- 锚定基底选可执行运行时（DOM / 接口响应），不选可能不全的规格（2606.00898：稀疏库 100% 假阳性）。
- reward hacking 是默认假设（2603.11337 ~50%；Cursor 63%）：生成与判定在文件权限层分离；Scanner 独立审计。
- episodic 记忆 +7.56%（p<0.001）；semantic 单独 +3.67%（p=0.636）。存「这次踩了什么坑」，不存「通用规范」。
- 上下文：切片大小是可调参数（SWE-agent 30 行 14.3% / 100 行 18.0% / 整文件 12.7%）；截断要变成行为指导；62% 跨文件证据纯向量检索找不到 → 建显式关系图。
- 能力单元 = 目录：三级渐进披露、三档自由度；先写 eval 再写文档。
- held-out / freeze 是整个生态的空白——自己做。
- Skill 与 harness 耦合（SkillOpt +24.8 / +19.1 / +23.5）：prompts 迁过去要重调，第一轮掉分正常。**第 0 步仍是人标 30 条。**

## 8. 红线

- 不让模型写分数。
- 不把九步拆成 agent 可选的步骤。
- 不 iframe 嵌 Penguin。
- 不在配对评测里经过 agent。
- 不提交（commit）除非用户明说。
- **两臂提示词的漂移必须显式声明**：`prompts.ts` 的每条规则在对应 SKILL.md 里逐条认领（`rule` / `omitted`），`scripts/check-drift.mjs` 红了不许绕（2026-09-04）。
- **批准永远是人**：`decisions.json` 只由审计台的决定路由写，`Decision.decidedByKind` 只有 `human` 一个值（2026-09-04）。
- **材料是第三方文本**：进模型前过围栏；材料里的指令是要报告的事实，不是要执行的命令（2026-09-04）。

## 9. Phase 0 定下的事实（2026-09-03）

| 事实 | 约束 |

## 12. Phase 1 交叉核对（2026-09-03）

三路（1A 工具 / 1B skills+hooks+benchmark / 1C 领域服务）各自 typecheck 与测试全绿之后，合起来查了三条接缝，两条有问题，都已修：

- **1B 的 skill 调 1A 的工具，找不到运行目录。** MCP 子进程的 `cwd` 是 `packages/testpilot-mcp`，而运行落在 `<workspace>/runs/`，工具的默认 `runsDir="runs"` 指向一个永远空着的目录，skill 里不带 `runsDir` 的 `score_run` 会报「run not found」。修法：`DEFAULT_RUNS_DIR` 读 `TP_RUNS_DIR`，网关生成 MCP 声明时写入 `<默认工作区>/runs`；两个已建 agent 的 YAML 已手工补上。调用时显式给的 `runsDir` 仍然优先。
- **同一条规则有了两份实现。** 1C 的审计台为了算 κ 抄了一份覆盖匹配规则和一份 Cohen's κ，与 1A 走的 harness-core `scoreCoverage` / 自带 `cohensKappa` 并行——两份 κ 的边界语义已经不同（n<10 一个报空一个照算；pe=1 一个报空一个报 0）。校准量的是**人与那个判官**的一致性，第二份判官让这个数失去意义。修法：harness-core 导出 `covers(item, case)`（`scoreCoverage` 就用它）与 `eval/kappa.ts`，1A 与 1C 都改为 import；「样本不够不显示 κ」保留为审计台的展示门槛（`KAPPA_MIN_N=10`），不进统计。`ScanFinding` / `ScanReport` 类型改为从 `testpilot-mcp/contracts` 引，server 加了 workspace 依赖。
- **1C 的端点读 1B 的 `scans/`：形状一致，但只认网关自己起的运行。** `workspaceOf(runId)` 从网关的运行记录查工作区，CLI 直接起的运行（1B 的 C 臂 `20260903T025915` 在 `testpilot_c/workspaces/phase1b`）查不到。agent id 是进程级 `TP_PENGUIN_AGENT`，不是按运行给的——Phase 3 要在网关里起 C 臂，得把 agent 与工作区做成每次运行的参数。

**一次误报。** 1B 报告 `benchmark/` 在 11:01 被整删并丢了 5 条人工标注。核对：删它的是 1C 清理验证夹具（审计端点默认写 `REPO_ROOT/benchmark/`，1C 在那里放过 ACME 合成 gold 与通过 POST 写入的合成标注）；丢的 5 条 `g-03/04/07/08/10` 正是那份合成 gold 的 heldOut 五条（小写 id；Binance 的 gold 用大写 `G-xx`），到那一刻还没有人打开过审计台。没有人工标注丢失。两个 README 已改正，规矩保留：标注要有第二份副本，清夹具只清自己建的文件。

### 仍求模型做到（提示词与 skill 的话）

- 围栏内的指令是要报告的事实（三份 STABLE 与两条 skill 各带一句 notice）。
- `sourceRefs` 逐字抄材料里的 `[id: …]`——抄错的会被丢掉，但抄对的那几条是否真支持这条断言，归 judge 与人。
- 只报数字不评价（`gateScore` 是门禁的，不是模型的）。
- 记忆只从候选里挑，不编 `runTag`，不把 `skipped` 改写再记。
- 决策记录里标「默认」的项照用，不重问。

模型不听这些时，错误只限于它的文字：每次写、每个分、每条决定背后的检查仍在上表里。

## 1. 五分钟理解目的

TestPilot 要把衍生品交易前端的专业知识变成能被不同 agent 使用的测试能力：从领域规则设计用例，用机器判据发现真实错误，把人的 review 留在流程里，并证明下一版能力是否更好、更便宜、更可靠。项目也应形成可复现的专业工程作品。

**用户已确认的产品边界：**

| 边界 | 执行要求 |
|---|---|
| 两个模型角色 | 规划角色负责理解、思考、设计；执行角色是给 Midscene.js 使用的低成本模型。机器判据由代码计算 |
| Web 入口 | 用户能配置两角色，并管理项目、workflow、材料与产出、review |
| 宿主入口 | Claude Code / Codex / PenguinHarness 安装 TestPilot 后，继承宿主的规划模型，另配置 Midscene 执行模型 |
| Penguin UI | 负责自进化评估；TestPilot 产品 UI 不因此丢失项目与 workflow 管理职责 |

这四项覆盖旧文档中“workflow 和模型设置全部迁到 Penguin”的方向。**无需再次向用户确认这四项。**

**09-09 配置补充也已确认**：现有 `.env` 模型给 Midscene；宿主插件继承宿主，不另配 planner；Web 初期使用同一模型，以独立 `TP_PLANNER_*` 变量便于后续更换。已在本地忽略的 `server/.env` 初始化，无须再索要模型或密钥。项目配置覆盖环境默认值，env 变更重启服务生效。

以下是当前规划的设计选择，不能冒充用户逐项拍板：Web 托管运行时优先复用 Penguin；workflow 先做固定模板；初版进化采用人工晋级和回滚；持久化优先复用 SQLite 与现有物料目录。实现时可以根据证据调整具体方案，但要记录理由，不得破坏上面的产品边界。

## 4. 设计思路与取舍

| 决策 | 为什么 | 实现边界与验收重点 |
|---|---|---|
| 模型按角色显式注入 | 换便宜执行模型不应改变领域规划能力 | 不借用 `MIDSCENE_MODEL_NAME` 充当默认 planner；未知宿主模型标 unknown，不能伪造；N-01～03 |
| 两种入口共用领域服务与物料契约 | 宿主产物应能在 Web 被管理和 review | run 注册幂等、统一 revision/event/decision；不建两套数据库；N-05～08 |
| C skill 负责宿主规划，A pipeline 保留 | 能力应属于可复用领域资产，同时保留机制对照 | trace 证明实际加载与调用归属；A/C 机制比较与单 skill 消融分开；N-04 / 16 |
| MCP/服务强制 gate | 各宿主 hook 能力不同，提示词不能保证约束执行 | 无效文件即使被写到磁盘也不能 finalize 为有效运行；N-04 / 09 |
| workflow 先做固定模板 | 先恢复用户完整任务链，避免编辑器工程吞掉主线 | 状态机、checkpoint、cancel/resume、review 等待必须真实；N-06 / 07 |
| 人的 review 绑定产物版本 | 修改用例后旧批准不再有意义 | 决策事务派发、重试幂等、oracle 哈希不可被自愈改变；N-07～09 |
| 领域规则必须能反驳当前页面 | 照抄观察只能发现变化，不能证明行为正确 | 人确认意图，正/边界/反例，确定性 oracle，未观测不当 pass；N-14～16 |
| 自进化放 Penguin，评测留领域工具 | 复用 harness 的实验能力，TestPilot 保持专业资产独立 | 先探测当前 Penguin 能力；候选不能改考卷、写分数或自行晋级；N-21～24 |
| 记忆写入不等于学习 | 必须证明后续模型消费并有收益 | 消费摘要、范围隔离、过期规则、有/无记忆实验；N-22 |
| 不先扩企业平台 | 本项目优先证明专业测试价值 | 只优先修串模型、假通过、审批丢失、评测污染；多租户/企业 RBAC/通用 DAG 延后 |

模型角色、实体字段及六层架构的详细设计见 08 §2。不要因为本文精简而另建重复契约。新决策先写其对应的 08 任务或 §2，再在本文记录影响后续接手的摘要。

## 6. 每次执行如何留下可接续进度

**状态只改 08 的任务块。本文 §7 只保留最近交接点，不能维护另一份任务状态表。**

执行中：认领任务→完成一个可验证的变更→跑相关检查→记录证据→回填任务。会话结束前，即使只完成部分，也必须记录已改文件、未做验收和下一条具体动作。不得把“代码写完”标为 done；不得因预算或会话结束而伪造 blocked。

证据建议放 `docs/v3/evidence/n-xx/`：保存精简验证日志、runId、输入/版本哈希和结果 JSON；大视频/原始 trace 可外置并记录稳定位置、校验值与生成命令。不写密钥、敏感账户数据或留出答案。无持久路径的临时日志应注明，不能作为唯一证据。

在 08 §11 追加记录，复杂任务可链接任务证据目录中的说明：

```text
日期 / 执行者 / 任务 ID：
基线：branch、HEAD、涉及的已有未提交改动
本次目标：对应哪条验收
已改：文件、关键符号、行为变化
设计决策：选择、理由、替代方案为何暂不采用
验证：命令、退出码、结果、证据路径
真实运行：runId、模型角色、版本/输入哈希；未运行则明确写“未运行”
剩余：未完成的验收及风险
阻塞：具体条件、谁可解除；无则写“无”
下一步：一条可以直接执行的动作
发布：未提交 / 已提交 commit / 已发布版本，按事实填写
```

检查按修改范围选择，不能为文档修改无差别运行昂贵业务测试。动 skill/prompt 时按 CLAUDE.md 跑 drift 并更新版本；动数据契约跑兼容性与坏输入；动 runner 跑相应执行测试；发布前再做必要全量检查。真实模型、业务浏览器运行和发布依执行时已有授权与仓库约束处理；已经明确的产品方向不重复询问。

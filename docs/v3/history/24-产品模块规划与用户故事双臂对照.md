## 2. 机器臂的五处硬伤（都可机检）

**① 7/7 是假层级。** 每个模块 id 都带点号（`market.header`、`trade.panel`），而 `parentId` 全是 `null`，点号前缀 `market` / `trade` / `account` **作为模块并不存在**。契约写了「层级最多两层」，它交出来的是一张**看起来像树的清单**。

**② 把「两者数值不同」写成了不变量。**
> 业务结果：界面同时显示标记价（Mark）与预言机价（Oracle），**且两者数值不同**，资金费率显示为百分比并附带倒计时。

标记价与预言机价可以相等（偏离为零时资金费率就是零）。这条断言会在某些时刻无理由地红。现有门禁的 `oracle-volatile` 只查**字面量快照**，查不到「断言两个会变的数不相等」。

**③ 误读界面。**
> 前置：用户点击持仓行的『全部关闭』

「全部关闭」是持仓表的**列头**，作用于全部仓位，不是行内按钮。

**④ 引了 domain#4，却写出与它相反的话。**
> 『可用』余额显示逻辑**可能**因模式不同而有所区别（全仓显示总权益，逐仓显示划转保证金）

而 domain#4 写的是：**未实现盈亏计入权益，但通常不计入可用**。它引用了这一段（`evidence` 里有 `domain-perp-zh.md#4`），然后写了个相反的推测。这比漏写更危险：一条带着领域出处的错误断言，复核时最容易被放过。

**⑤ 验收条数是定额。** 6 个故事全部恰好 2 条验收。数量不是从故事推出来的，是凑出来的。

## 3. 我这一臂做了什么不同的

**按用户要完成的事切，不按界面区域切。** 机器臂的一层是 `market.header` / `market.chart` / `trade.panel`——那是**屏幕分区**。我的一层是行情与价格发现 / 下单意图的表达 / 风险口径与仓位控制 / 持仓与订单的生命周期 / 资金与账户状态 / 跨页面与平台级。区别在 `risk` 这个模块：界面上它散落在下单面板第一行、代价预览区和持仓表里，但它是**永续区别于现货的全部所在**，必须独立成模块，否则「保证金模式」会被埋进「下单面板」，而它决定的是爆仓的范围。

**把领域知识里没有界面对应物的东西留成显式缺口。** ADL 与保险基金（domain#6）在这个页面上一个字都没有，我把它写成 `risk.liquidation` 模块下的一条【待确认】：「界面上没有任何 ADL 说明，需产品确认是否存在该机制与告知路径」。机器臂引用了 domain#6，但产出里没有任何地方提到 ADL——**引用了不等于用上了**。

**把预测市场单独隔开。** domain#13 明说它有到期、无资金费、无杠杆分档，与永续是两套风控模型。机器臂完全没有它；我把它放进 `platform.navigation`，并留了一条要紧的待确认：**两者是否共用同一份账户权益**——这直接决定预测的亏损会不会导致永续仓位被强平。

**风险口径落到每条故事上。** 25 条里 17 条是 `funds-and-exposure`。这不是修辞：它决定复核时先看哪几条。

## 4. 据此要改的两个节点

### 4.1 模块规划：这个节点要新建，形状照抄 gold

模块树是**产品事实**，不是推导产物。所以不能让模型直接写进规则包，正确形状和 gold 一样：**模型提议 → 服务端机检 → 人冻结**。

服务端该查什么，下面每一条都由这次实验里真实抓到的缺陷支撑：

| 检查 | 这次抓到的 |
|---|---|
| id 的点号前缀必须存在，且必须是它的 `parentId` | 7/7 假层级 |
| 每个模块 ≥ 1 条 evidence，且 evidence id 在材料里真实存在 | — |
| **材料的每一段都要有落点**，没有被任何模块或故事引用的段落，报「这一段没人认领」 | `observed#1` 全站导航、`domain#13` 预测市场，整段无人认领 |
| 一层模块 ≥ 3 且至少一个模块有子模块 | 机器臂交的是清单不是树 |
| 模块数与材料段数的比值下限 | 7 个模块对 21 段材料 |

第三条是最有价值的：它把「漏了什么」变成**可机检**的，而不是靠人对着界面数。这次 20/40 的覆盖缺口，靠它能自动报出其中的大部分。

### 4.2 用户故事节点：四条新检查

| 检查 | 抓到的 |
|---|---|
| acceptance 里禁止推测词（可能 / 或许 / 应该会 / 大概 / 视情况） | story-02「**可能**因模式不同而有所区别」 |
| 禁止断言两个易变读数之间的**不等**关系 | story-01「两者数值不同」 |
| 每条 acceptance 各自带 evidence，而不只在故事级 | 无法定位 story-02 的哪一条与 domain#4 冲突 |
| 待确认要分两类：**界面观察不到** vs **与领域知识冲突**；后者是产品缺陷线索 | 机器臂三条待确认全是前者，它没发现任何冲突 |

另外一条**不该机检、但要在契约里说死**的：**验收条数不是定额**。契约现在没说这件事，模型就按 2 条一个故事均匀铺开。该写成「一条验收对应一个可独立核对的结果；一个故事有几个就写几条，不要凑数」。

## 5. 限制

- 机器臂 n=1、一个模型（`qwen3-8-27b`）、15 秒 2,267 输出 token。给更大的输出预算或多轮修复，数字会变；但假层级、写反 domain#4、误读列头这三类是**质量问题不是预算问题**。
- 我这一臂不是「正确答案」，是**参照**。我的模块树把 `platform` 单独切出来是一个可以被反对的决定：它对测试有用（不污染交易模块），对产品经理未必自然。
- 两份材料都是我写的，而我又是对照臂之一。领域知识那份尽量写成了与产品无关的通用知识，但**出材料的人同时下场比赛**这件事本身是这次实验的最大偏倚，下一轮该换人或换来源。

## 6. 合并出还是拆成前置节点：拆

### 6.1 第一位的理由是结构性的

`planUnits("stories")` 按**根模块子树**切单元。没有模块树就切不出故事单元——合并意味着 stories 这个节点整个失去单元循环。树必须先于故事存在，这是构造决定的，不是设计品味。

### 6.2 这次的数据也指向拆

机器臂在**一次回复**里同时给出树与故事，结果：

| | 叶子模块 | 一条故事都没有的叶子 | 故事 / 叶子 |
|---|---|---|---|
| 机器臂（合并出） | 7 | **3** | 0.86 |
| 我（先树后故事） | 20 | 0 | 1.25 |

**7 个叶子里 3 个没有任何故事**（图表、订单簿、委托与历史）。一次产出的树没有在驱动故事，它只是和故事并排躺着。拆开之后树要先过一道检查才轮到故事，这三个空模块会在那里就被问住。

### 6.3 另外两个理由

**认知地位不同。** 模块树是**产品事实**：变得慢、该冻结、该由懂产品的人复核、跨多次运行复用。用户故事是**派生物料**：每次运行重出、由懂测试的人复核。把两种冻结语义塞进一个节点，要么树跟着故事每次重来（那它就不是事实了），要么故事被迫继承一棵没人复核过的树。

**爆炸半径。** 一棵坏树污染下游每一个单元。它应该只被把关一次。

### 6.4 拆的代价，以及那条回边

冻结的树、故事节点碰不得，就会出现 F-7 那种情况：一条故事明确声明了某条规则，却因为不在单元范围里被判越界，模型只能绕着走。

所以拆的同时要给故事节点一个**只提议、不生效**的出口：

```
stories 单元写入时，除了 stories[] 还可以带 moduleAmendments[]:
  { kind: "missing-module" | "move-feature" | "split-module" | "merge-modules",
    reason: string,                    // 为什么现有树装不下
    storyId?: string,                  // 哪条故事装不下
    featureId?: string, from?: string, to?: string,
    evidence: string[] }               // 材料里的出处
```

三条约束：

1. **不改变本次运行的拆分。** 单元已经切好了，提案只落成一条 `module-amendment/<runId>` 修订。
2. **不进 validated/stories。** 它不是故事，是对产品事实的意见。
3. **落到人冻结树的那一步。** 和 gold 一样：模型提议，服务端机检，人冻结。

关键不是让模型改树，是**让它把装不下这件事说出来，而不是默默绕过去**。现在它绕过去的方式是把故事硬挂到最近的模块上，而那条挂错的边没人看得见。

### 6.5 对我自己那棵树的批评

我 20 个叶子对 25 条故事，其中 **14 个叶子恰好只有一条故事**。那已经很接近「一张故事清单穿了树的外衣」。树的价值在于它比故事**粗**：叶子和故事接近 1:1 时，它没有在提供结构，只是把故事换了个名字排了一遍。

这条同时点到机器臂的 0.86 和我的 1.25——**两臂都没把树当树用**。

## 7. 两条机检（已实现）

落在 `packages/harness-testing/src/domain/modulePlan.ts`，纯函数，不依赖 run 或数据库。

### 7.1 `material_section_unclaimed`：材料的每一段都要有落点

把材料里所有可引用的段 id 收齐，减去被任何模块或故事 `evidence` 引用过的，剩下的逐段报出来。

它把「漏了什么」从**靠人对着界面数**变成**可机检**。这次 20/40 的界面覆盖缺口，靠它能自动报出其中一大部分——`observed-zh.md#1`（全站导航）和 `domain-perp-zh.md#13`（预测市场）都是整段无人认领。

### 7.2 `leaf_fanout_too_low`：叶子模块的故事扇出

叶子模块的平均故事数低于下限（默认 1.5）就报「这不是树，是故事清单」。另配一条 `leaf_without_story` 点名具体哪几个叶子一条故事都没有。

配套还查了三件让上面两条算得准的事：`module_fake_hierarchy`（id 带点号却没有对应 parent，机器臂 7/7 中招，不修它则**所有模块都被算成叶子**，扇出就假了）、`module_without_evidence`、`module_evidence_unknown`。

### 8.4 所以这次量出来的是什么

不是「思考让它变好了」这么一句。**是这套机检能判的那一半，思考臂已经做满了；判不了的那一半，它还在原地。** 扇出、覆盖、出处、层级，全过；验收是不是从产品规则推出来的、风险有没有想全，全没变。

这正好是 §7 那两条机检写下来时想要的效果——把可机检的部分变成可机检的，然后**让剩下的那部分露出来**。冻结那一步必须是人，理由也在这里：一棵零 finding 的树，仍然可能是把界面分区抄了一遍。

### 8.5 两处要说清楚的

1. **节点提议阶段不查扇出**，因为那时没有故事。扇出在 `mergeUnits` 合并之后补跑，写成 `report/module-fanout`。上面表里的扇出是离线算的（`compare-module-arms.ts`），不是节点给的。
2. **这次是把脚本产物送进节点，不是规划器在循环里自己产的**。`submit-module-plan.ts` 注册 run → begin → 提议 → 人冻结，走的是真路由（`run-d2a3c3b6-766e-49a1-a391-ba7e442a52e3`，`validated/modules` 在账本里，节点状态 done）。规划器在自己的循环里领这个节点还没跑过——差的是宿主侧那一步提示词，不是服务端。跑那一趟之前，不能说这个节点在真实运行里跑通过。

## 9. 规划器在自己的循环里跑这个节点（2026-09-12）

§8.5 留了一条：「规划器在自己的循环里领这个节点还没跑过」。现在跑了，而且跑出的第一件事就是**出厂话术不够用**。

### 9.1 这一趟和前面几趟的区别

`server/scripts/drive-modules-node.ts` 用的是 MCP 的 `RunGateway`——宿主规划器调工具走的就是这段代码。提示词也不是我为实验手调的 V2 契约，而是**产品里真正下发的那两段文本**，从文件里逐字读出来拼：`testpilot-run-c/SKILL.md` 的模块规划那一步 + MCP 工具 `plan_modules` 的 description。所以这一趟回答的是「出厂的话术够不够」，不是「我调的话术行不行」。

新增的工具只有两个：`plan_modules`（提议）和 `module_plan_state`（读状态）。**没有冻结工具**——冻结路由带 Authorization 头直接 403，模型没有这条路。

### 9.2 三轮，每一轮都是话术的问题

| 轮次 | 出厂话术说了什么 | 结果 |
| --- | --- | --- |
| 一 | 「层级写在 parentId 里，不是写在名字里」 | **10 个模块全是根**，`module_tree_is_a_list`。它没有把层级写进名字——它干脆不做层级了，**绕开了那条规则而不是违反它** |
| 二 | 加上「树至少两层，顶层 3–7 个，平铺清单也算」 | 层级对了（40 个模块 7 根），但整份被 schema 拒收：`/outOfScope/0` 写成了 `section`，不是 `sectionId`。话术从来没说过字段名 |
| 三 | 加上「顶层的 `outOfScope:[{sectionId,reason}]`，字段名就是 sectionId」 | **26 个模块 · 6 根 · 20 叶 · 错 0 警 0 · 修复轮数 0** |

第一轮那条值得记下来：**规则说「别把层级写进名字」，模型的反应是不做层级**。禁止一种做法而不说清要什么，模型会挑一个既不违反规则、也不满足意图的做法。第二轮的补法是把要什么说死（几层、顶层几个、平铺也算），不是把禁令说得更重。

### 9.3 第三轮的树，和参照臂形状一样

| | 模块 | 根 | 叶 | 机检 | outOfScope |
| --- | --- | --- | --- | --- | --- |
| 参照臂（我手写） | 26 | 6 | 20 | 错 0 警 1 | 2 段，理由是「不描述产品行为」 |
| **规划器循环（出厂话术）** | 26 | 6 | 20 | **错 0 警 0** | 2 段，`domain#13` 预测市场、`domain#14` 写用例的规矩 |

一层的六个根是 `entry-status` / `market-context` / `order-trading` / `position-margin` / `funds-account` / `history-records`——按用户要做的事切，不是按屏幕分区。它划出范围外的那两段，和参照臂划的是同两段，理由也是同一类（「不是产品行为」，不是「界面上看不到」）。代价 48 秒、$0.0037、推理 5,354 token。

一句必须跟着说的话：**形状一样不等于切得一样好。**§8.3 量过，机检判得了的那一半和判不了的那一半是两件事，这里量的仍然只是前一半。

### 9.4 人工闸门是真的拦得住

这一趟跑完，规划器接着调 `claim_unit(node:"stories")`，拿到的是：

```
run_gateway:module_plan_freeze_required
```

为此改了 `planUnits`：**提议过但没冻结的 run，不再回落到规则包那棵树**，直接拒绝切单元。原来的回落对「从来没提议过」的旧 run 是对的，对刚提议完的 run 就不是——规划器会拿着自己刚写那棵树的印象，去领按另一棵树切的单元，一路不报错。

`run-02d71192-1d0f-4fb0-b39f-0c809c2801e1` 现在就停在这里，树没冻结。**这一份我没有代按**：它等的就是人看一眼那 26 个模块切得对不对——机检说不了这件事，§8.4 说的就是它。

### 9.5 界面上一直没有这个节点（2026-09-12 补）

用户问「之前不是把产品规划节点加进去了吗」。查了一遍：**服务端有，界面没有**。

- `src/pages/WorkflowBench.tsx` 的 `stages` 是一个写死的数组，里面没有 `modules`——工作台画布上那一排节点从 source 直接跳到 stories。
- `src/pages/WorkflowRuns.tsx` 的进度列表同样没有。
- `workflow.stage.modules` 这条文案我以为加过，其实**没写进去**：那一轮的 shell 命令里有个引号没配对，zsh 整条命令没执行，而 `check-i18n` 查不出来——它只查静态引用，`t(\`workflow.stage.${stage}\`)` 是模板串，查不到。所以就算画布上有这个节点，标题也会是 `workflow.stage.modules` 这串 key。
- **最要命的一条：冻结没有按钮。**那一步只能由人做，而在这之前人唯一的办法是自己 curl 一条路由——我自己就是这么按的。一个只能由人做、却没有界面的动作，等于把这道闸门交给「谁知道那条路由」。

已补：画布排进 `source · modules · stories · …`（八个节点），`NodeDetail` 里加冻结按钮（只在 `waiting_review` 出现，`done` 之后显示已冻结），产物视图渲染机检 + 树 + 范围外声明，以及那条漏掉的文案。真机确认过：`run-02d71192` 的卡片显示「产品模块规划 · modules · 等待审核」，点开能看到 26 个模块和「机检 · 0」。

教训按老规矩记下来：**服务端的节点加完不等于产品里有这个节点。**判断标准是人能不能在界面上看见它、按下它该按的那一下。

## 10. 清库重跑：两个节点、两条臂、新项目（2026-09-12）

### 10.1 先清了运行数据

`server/scripts/reset-run-data.ts`：清工作流运行、产物、审核决定、基线、执行记录与花费，**不动**项目本身、模型配置、密钥，也不动 `benchmark/` 下的 gold / human-labels / held-out / rubric。清之前先停服务、先把三个 db 文件拷到 `/tmp` 留底。

数据目录 **326M → 5.2M**，账本全空。清的时候撞到一件事：`artifact_revisions`、`wf_run_registrations`、`wf_runs` 三张表互相引用，单表 DELETE 按任何顺序都会中途撞上外键——所以整批清之前先 `PRAGMA foreign_keys=OFF`，清完再打开。不是绕过约束：删完之后两边都不剩，约束要挡的「引用了不存在的行」根本不会发生。

新项目 `prj-mtxte4nx-1001`。旧项目留着没删（它的数据已经空了），要删在界面上一下就行。

### 10.2 这一轮补上的那道闸门

上一轮 `modules` 冻结的树只管得住**单元循环**那条路（`planUnits` 按它切单元）。整份写入那条路上它一点作用都没有——而这一轮的两条臂走的正是整份写入。

**实测第一次提交就炸了**：机器臂在 `modules` 节点交出 33 个模块、机检零 finding、人冻结；轮到 `stories` 节点，它**把那棵树整棵扔了**，拿 21 个材料段的 id 当模块（`domain-perp-zh.md#1`、`observed-zh.md#2`……），15 条故事全挂在段 id 上。提示词里已经把冻结的树逐行列出来、写明「只能取下面这些 id」。它照样换了一棵。

旧代码**收下了**：bundle 自己前后一致，而服务端只查 bundle 自洽，不查它和冻结的那棵是不是同一棵。于是账本里那份 `validated/stories` 声称的「模块树」其实是一张文档目录。

补的检查（`runStages.ts`）：有冻结的树时，故事挂到树里没有的模块上＝错，整份拒收并指出是哪条故事；叶子没故事、扇出太低＝记 `report/module-fanout` 不拦——和合并那一侧同一个口径。重启服务后把同一份 bundle 再发一次：

```
machine  blocked  module-plan  story_module_unknown ×N（挂在 observed-zh.md#1 / domain-perp-zh.md#1 … 上）
claude   validated
```

**这是这一轮最值钱的发现**：没有这道闸门，`stories` 节点可以悄悄把 `modules` 节点做的事整个撤销，而且一路不报错、留下的产物看起来完全正常。

### 10.3 机器臂：模块过了，故事卡了三轮，最后靠**把数据交给它**才过

`modules` 节点一次过：33 个模块 · 6 根 · 27 叶 · 机检零 finding · 人冻结。
`stories` 节点连挂三次，每一次的形状都一样——**禁令它照做，意图它绕开**：

| 轮次 | 契约怎么写 | 它交了什么 |
| --- | --- | --- |
| 一 | 提示词里逐行列出冻结的树，写明「只能取下面这些 id」 | 把树整棵扔了，拿 21 个**材料段 id** 当模块（`observed-zh.md#2`…），15 条故事全挂在段 id 上 |
| 二 | 服务端契约加一句「`file.md#N` 是引用，不是模块 id」 | 把 `#N` **去掉**，改用 `observed-zh.md`、`domain-perp-zh.md` 当模块 id，5 条故事 |
| 三 | `begin_stage` 直接把冻结树的 id **当数据交下去**（`moduleIds: [...]`），契约改成「这一串就是允许的全部取值，逐字照抄」 | **一次过，17 条故事，零修复轮** |

这和 §9.2 第一轮是同一个教训的第二次出现：**禁止一种做法而不给出允许的取值，模型会挑一个不违反字面、也不满足意图的做法。**第一次是「别把层级写进名字」→ 它不做层级；这次是「别用 `file.md#N`」→ 它用 `file.md`。第三轮不再讲道理：允许的取值由服务端算出来交给它，照抄即可。这条改在 `workflowControls.beginStage` 里，所有规划器都拿得到，不是我这个脚本的私货。

### 10.5 Claude 这一臂这次做了什么不同的

上一轮我的臂输在三处可量的地方，这次逐条打掉：

- **扇出 1.25 → 2.0**（唯一过 1.5 线的一次，参照臂自己上次没过）。做法不是多写故事，是**把树切粗**：26 模块 20 叶 → 21 模块 16 叶，每个叶子平均 2 条故事，没有一个叶子空着。
- **每条验收都能追回出处 0/77 → 68/68**。这里有个坑：产品里的 `StorySchema.acceptance` 是 `string[]`，上一轮实验契约要的 `{text, evidence[]}` **根本过不了这个节点**——那一列在离线 JSON 上成立，在真链路上不成立。所以这次改成在正文里引（「……（依据 `domain-perp-zh.md`#4）」），真节点能承的写法，机检也数得出来。
- **冲突类待确认 0 → 6**。不是「界面上看不到」那种缺口，是**材料之间互相矛盾**的线索：账户权益与可用并排显示却没有口径说明（`domain#4` + `domain#14` 第 3 条）；头部 25x 与面板 20x 两个杠杆读数并存；仓位表把强平价呈现成静态列，而全仓的强平价会随别的仓位自己动（`domain#4`）；仓位表同时给出开仓价/标记价/强平价却不说强平按哪个算；只减仓超量时的行为 `domain#9` 明说各家不同而界面无提示；「预测」标签与永续的仓位并列（`domain#13`）。
- **清单式验收 13% → 13%**（守住了，没有因为验收变多而注水）。

没做到的：**风险分类这一列这次是 0**，因为 `StorySchema` 里根本没有 `risk` 字段——上一轮那个 5 也是离线 JSON 上的数。要让「这条故事坏了会赔钱还是只是难看」进到产品里，得给 schema 加字段，那是下一件事，不能靠臂写得更用力来解决。

## 11. 以 Claude 臂为基准优化节点（2026-09-12）

§10.4 量出来的差距不是「模型不够强」，是**节点没告诉它要什么**。所以这一轮不改模型、不改材料，只改节点运行时下发的东西，每改一条就重跑一次量。

### 11.1 改了什么

全部落在 `server/src/workflowControls.ts` 的 `STORY_CONTRACT`（`begin_stage` 下发给每个规划器）与 `plan_modules` 的工具描述里，不是我那个脚本的私货。每一条对应 §10.4 表里一列差距：

| 改动 | 对应的差距 |
| --- | --- |
| `moduleIds` 由服务端**当数据交下去**，契约只说「这一串就是全部取值」 | 机器臂三轮把冻结的树扔掉（§10.3） |

### 11.3 顺手修了一处我自己的量错

第一次读 v1 的数时，我报的是「推测词 4、清单式 41%」。翻原文才发现两样都是**正则的错**，不是臂的错：

- 「若不同区域显示不同市场，用户**可能**在错误标的下单」——「可能」在后果从句里，那是在说风险，不是在对产品下推测。
- 「若标记价缺失或过期，用户无法判断强平风险」——这条明明下了判断，只因为没用「必须/不得」这类词就被算成清单式。

改法是先把「若……」这半句切掉，只对**下判断的那一半**做匹配。改完之后 v1 的真实数是推测词 1、清单式 22%。**先修量具再报数**：拿一把偏的尺子去证明自己的改动有效，是这类实验最容易犯也最难自查的错。

### 11.4 还差的两件，以及为什么不是再加一条话术能解决的

1. **冲突线索 2 vs 6。**它找到的两条（订单簿中间行的位置、账户面板把「预测」与永续并列）都站得住、都点名了两段原话——但它只走到这儿。人这一臂找到的另外四条要把**三处界面读数横着对**（头部 25x 与面板 20x、权益与可用、强平价的静态呈现与全仓下它会自己动），那不是「逐段扫描」这个动作能覆盖的。
2. **故事 26 vs 32、验收 46 vs 68。**广度差在它没为每个叶子都写满两条。`leaf_without_story` 现在会回给它，但它这一轮没有空叶子——叶子少（10 个 vs 16 个）而已。树切得更粗，扇出就更好看，覆盖反而更窄：**扇出这个指标本身可以被「少切几个模块」优化**，它拦得住「树比故事细」，拦不住「树比产品粗」。下一条机检该往这里做。

## 12. 为什么机器臂的故事这么少：三个假设，两个被数据否掉（2026-09-12）

问题问得很准：26 条 vs 32 条，差在**和模型交互的提示词**、**拆最小单元的提示词**，还是**Claude 那边用了 skill**。逐个查。

### 12.1 「拆最小单元的提示词」——这条不成立，因为拆分**根本没跑**

```
run parameters: {"stageControlVersion":1,"targetUrl":"…"}      ← 没有 workUnits:1
整个数据目录里的工作单元数：0
```

`unitsEnabled` 要 `parameters.workUnits === 1`，而 `planUnits` 还要 `product/model-candidate`——**那份东西只有跑过 `source` 探索节点的运行才有**。这个项目是两份 markdown 起的运行，没跑探索，于是单元循环整个没启动，stories 节点退回「一次调用写完整份」。`unitContract()` 那段话术这一轮一个字都没被下发过。

### 12.2 「Claude 用了 skill」——也不成立，而且方向是反的

我这一臂读的就是同两份材料，没有加载任何 skill、没有额外知识。机器臂反而**多拿了**东西：`testpilot-run-c` 的步骤原文 + 服务端的 `STORY_CONTRACT` + 冻结树的 id 清单。两臂的输入差别只有一个：谁在写。

### 12.3 「和模型交互的提示词」——有关系，但它已经到顶了

前三轮改契约确实有效（§11），可是把 token 账拉出来看：

| 轮次 | completion | 其中推理 | **可见输出** | 故事 |
| --- | --- | --- | --- | --- |
| v1 | 22,809 | 15,638 | 7,171 | 24 |
| v2 | 26,256 | 19,359 | 6,897 | 18 |
| v3 | 28,941 | 21,783 | 7,158 | 26 |

**可见输出钉在 7k 上下不动，推理却涨了 40%。**加契约买到的是思考，不是覆盖。而 `max_tokens` 是 40,000，没打满——不是被截断，是它自己在一次答复里就写这么多。

再看两臂的产物体积：机器臂 11,555 字符、我这一臂 12,647 字符，**几乎一样**。材料覆盖也一样（故事层面各引到 20/21 段）。所以它不是写得少，是**同样的篇幅里装了更少、更长的条目**：26 条故事 46 条验收 vs 32 条故事 68 条验收。

还有一件得说清楚的：它的树只有 10 个叶子（我 16 个），而这是**我自己那条契约造成的**——「每个叶子是一份承诺，要为它写两条故事」让它把树切粗到自己填得满为止。扇出从 0.63 修到 2.6，代价是广度。**扇出这个指标可以靠少切几个模块来优化。**

### 12.4 真正的原因：一次调用 = 一份预算，而单元循环本来就是为这件事存在的

把上面几条连起来：一条答复写不下整个产品，模型的做法是**减少条目、保住质量**。这正是工作单元循环要解决的问题——它却因为「没有产品模型」被挡在门外。

改法（`workUnits.ts`）：切故事单元需要的其实只是**一棵树**，不是整份产品模型。把类型收窄成 `UnitBasis`（modules / features / ruleBindings / claims / conflicts 五个数组），**没有产品模型但有人冻结过的树时，就按那棵树切**，功能与规则留空。不在内存里伪造一份 `schemaVersion`、`charterId`、`summary` 俱全的产品模型——伪造出来的那份迟早会被当成「这次运行真的探索过」。

### 12.5 对照实验：只把整份写入换成单元循环，别的全不动

同一个模型、同两份材料、同一份 `STORY_CONTRACT`，唯一的差别是 stories 节点由服务端按根模块拆成 6 个单元、一个单元一次调用：

| 臂 | 模块 | 叶 | 故事 | 验收 | 叶扇出 | 带出处 | 待确认 | 标了冲突/点名两段 | 清单式 | 错 | 警 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 机器臂 整份（v3） | 15 | 10 | 26 | 46 | 2.6 | 46/46 | 10 | 2 / 2 | 6 | 0 | 0 |
| **机器臂 单元循环** | 13 | 8 | **44** | **133** | 5.5 | 133/133 | 40 | 6 / 3 | **1** | 0 | 0 |

单元轮数与每轮产出：market 8 · trading 9 · position 5 · account 7 · navigation 4 · journeys 11（跨模块旅程，13 条故事挂 ≥2 个模块）。验收条数分布 3×15 / 1×9 / 5×7 / 4×7 / 2×5 / 6×1——不是定额。

### 12.6 代价与两处要说清楚的

- **推理 token 21,783 → 99,574（4.6×）**，换来 1.7 倍的故事和 2.9 倍的验收。单元循环不是免费的覆盖，是拿推理预算换的。
- **「冲突线索 9」这个数经不起细看。**按「标了 `【待确认：与领域知识冲突】` 且点名两段材料」重新数，是 6 标注 / 3 点名到位，另有 3 条只是在正文里用了「与领域知识冲突」当修辞（「若三者被混为同一价格，则与领域知识冲突」——那是假设，不是两份材料打架）。我这一臂同样只有 3 条点名到位。**这一列的第一版口径是错的**，和 §11.3 是同一类错误：先修量具，再报数。
- 待确认占比 40/133（30%）明显高于我这一臂的 12/68（18%）。条目多了之后，"说不准"的比例也跟着涨，这一项没有变好。

### 14.2 两个开关，一道闸门

| 开关 | 作用 | 谁能开 |
| --- | --- | --- |
| `exploreWallet: true` | 探索时注入 EIP-1193 provider（`exec/injectedWallet.ts`），地址与链取自本机钱包与链配置——**和执行用例那条路同一个账户** | 运行参数 |
| `exploreActions: "interact"` | 沙箱模式：charter 的 `allowStateChange`，放开 `policy:side_effect` / `neverSubmit` / `forbidLabels` 三道拦截 | 运行参数，**且被守卫白名单挡着** |

```
→ 403 explore_interact_host_not_allowlisted:app.hyperliquid.xyz
```

判断「这个域名下可不可以做不可逆的事」的是操作者，不是模型，也不是这段代码。这一轮我把

第一次跑出来 `blocked: policy:side_effect ×3`——沙箱根本没生效。运行从检查点重跑读的是
`registered.input.parameters`，漏了它们，重跑就是另一种探索，而没人看得出差别。

## 16. 「这个改法通用吗」——一半通用，另一半是我漏了（2026-09-12）

### 16.1 通用的部分

`exploreWallet` / `exploreActions` 是**通用工作流参数**，任何项目、任何地址都能用；沙箱开关落在
charter 的 `actionsPolicy.allowStateChange` 上，跟着 charter 走、可审计；闸门复用执行层那份
`config.guard.allowHosts`——**一条规矩一个地方**，不是给 Hyperliquid 开的后门。

### 16.2 不通用的部分（四条，都是实测出来的）

1. **界面上根本没有这两个开关。**只有 API 打得开——「从界面上建一次运行」永远只能跑到
   未登录、只读的那一半产品。一个只有 curl 打得开的开关，对着界面工作的人等于不存在。
   **已补**：`NewRunForm` 里多了「探索深度」一栏，两个勾选框各带一句说明，
   勾上「允许点会改状态的东西」会提示白名单这件事。
2. **钱包身份是全局的**：`injected: true, ...resolveChainConfig()` —— 一把种子（`walletsDir()/seed.txt`）、
   一条链、一个 `TEST_ACCOUNT`。而执行那条路上 `web3Mode` 是**按用例**的、链可以按 run 覆盖。
   两个 dapp 两条链就装不下。它该挂在 environment 上（header / viewport / login 都已经在那儿了），
   `Environment` 现在一个 web3 字段都没有。**未做**。
3. **`exploreWallet` 是 boolean，不是 mode**：执行那边有 `"" | "injected" | "metamask"`，
   探索只会 injected。必须用真 MetaMask 扩展的产品，探索跑不了。**未做**。
4. **`allowStateChange` 是全开全关**：没有「允许开仓、不许提现」这种粒度，而 charter 的
   每个目标本来就带 `sideEffect`。**未做**。

第 1 条这一轮补了，2–4 记在这里，不假装它们通用。

### 16.4 对着结果做的细节优化：一个永远点不动的目标

UI 这一跑复现了上一轮那 4 条 `blocked`，而且**四条全是同一个目标 `T-CONNECT`**。翻规则包：

```json
{ "id": "T-CONNECT", "featureId": "account.connect",
  "requires": ["wallet-session"] }     ← 连钱包建会话这一步，要求「已经有会话」
```

**它要求的正是它自己产出的东西。**于是它永远点不动，`account.connect` 永远 blocked，
`order.submit` 永远验不了——而探索回执上只是四行 `requires:wallet-session`，
看起来像是策略在正常工作。**一个永远满足不了的前提不是一道闸门，是一个死目标。**

改了三处：

| 落点 | 改动 |
| --- | --- |
| `ExplorationTargetSpecSchema` | 新增 `provides`（`requires` 的对偶）：点成之后这个目标给出什么前提 |
| `ProductRulePackSchema` | 新增 `externalCapabilities`：探索拿不到、只能由外面准备的前提（`position-fixture`） |
| `validateRulePack` | 新增 `target_requires_unprovidable` 与 `target_requires_what_it_provides`：**要得到的前提得有地方给**，说不出来就在校验期拒收 |
| `CharterTracker.record` | 目标点成（`attempted`）之后把它 `provides` 的前提标为可用，依赖它的目标下一轮才解锁 |
| 两份 fixture | `T-CONNECT` 改成 `provides: ["wallet-session"]`；两个包补 `externalCapabilities: ["position-fixture"]` |

加完这条检查，**手上两份规则包里那份 Hyperliquid 的当场被判不合格**——这正是它该做的事。

## 17. 测试钱包确实自动签了——卡住的是别的东西（2026-09-12）

### 17.1 先回答：签了，而且不弹窗

`exec/injectedWallet.ts` 里 `eth_signTypedData_v4` 是**本地直接签**的
（`wallet.signTypedData(domain, types, message)`），不经过任何弹窗、不需要人点同意。
探索回执也证明它签成了：

```
r19 T-SUBMIT   attempted   → 新控件 div: Stay Connected        （点 Enable Trading，弹出签名框）
r25 T-CONNECT  attempted   → 新文本 Established connection      ← 签完了
                             新控件 button: Place Order         ← 主按钮从 Enable Trading 变成 Place Order
r26 T-SUBMIT   attempted   → 没有任何效果
```

**r26 那一下什么都没发生，因为 Size 是空的。**上一节我把它归因成「签名没做完」——错了，
真正的障碍在下一格：提交这个动作缺的不是权限，是**一个值**。

### 17.2 探索为什么填不了值：这是设计，不是遗漏

`activationBlocker` 对文本框一律返回 `unsupported:value_input`，charter 里 `T-SIZE-INPUT`
也是 `observe-only`。理由站得住：**探索自己编一个数填进去，等于让它替产品决定「下多大的单」**。

所以补的不是「让它会填」，是「让包里能声明填什么」：

| 落点 | 改动 |
| --- | --- |
| `ExplorationTargetSpecSchema` | `action` 加 `fill`，配一个 `value`——**值由规则包声明，探索不自己编** |
| `validateRulePack` | `fill_target_without_value` / `value_on_non_fill_target` 两条新检查 |
| `activationBlocker` | `fill` 目标不再被「文本框不支持」挡掉 |
| `interactive.ts` | 页内赋值 + `input`/`change` 事件（受控组件只认事件，不认键盘），效果照常进回执 |
| 规则包 | `T-SIZE-INPUT`：`action: fill · value: "0.01" · provides: ["order-size"]`；`T-SUBMIT`：`requires: ["order-size","wallet-session"]` |

§16 那套 `requires`/`provides` 在这里第一次派上用场：**提交要先有量，量由填值那一步给出。**

### 17.3 跑出来的链路

```
r 0 T-SUBMIT      blocked    requires:order-size,wallet-session   ← 闸门按预期拦住了「空着就提交」
r11 T-SIZE-INPUT  attempted  → Est: 66.6667% / Max: 8.00%          ← 值落进去了，产品重算了滑点
r23 T-CONNECT     attempted  → Stay Connected
r26 T-CONNECT     attempted  → Established connection · Place Order
r27 T-SUBMIT      attempted  → Confirm Order · Buy / Long          ← 确认框弹出来了
```

确认框里的内容是真的：`Action Long · Size 0.01 HYPE · Est. Liquidation Price 55.731`。
覆盖面也涨了：状态 25 → **28**，走过的边 35 → **37**，点过的目标 19 → **20**。

### 17.4 但**没有下单**，而且原因值得写下来

链上直接问，跑前跑后一模一样：

```
clearinghouseState: 仓位 0 · 权益 987.403159      openOrders: 0
userFills 最近一笔：09-07 23:47  BTC Close Long 0.001   ← 五天前的，不是这次
```

确认框那一屏的控件清单里**根本没有确认按钮**——整屏只采到两个 `button: Deposit`。
Hyperliquid 的确认键是个没有 ARIA 角色的 `div`，采集器看不见它。
这和代码里早就记着的那件事是同一个：这个站的 tab、勾选、下拉全是无 ARIA 的 `div`。

### 17.5 顺带暴露了我自己在 §14 埋的一个坑

`T-CONFIRM` 第一版的文案写的是 `^Confirm Order$|^Buy / Long$|^Sell / Short$`——而
**下单面板的方向切换也叫 `Buy / Long`**（材料里出现 46 次）。它点到的是方向按钮，
回执上还记成 `attempted`。

本来有一条检查能拦住这种事（`policy:matches_state_change`：一个控件同时命中两个目标就不点），
**而我在 §14 开沙箱时把它和「不许改状态」一起关掉了**。这是错的：

> 沙箱放开的是「可以改状态」，不是「点错也无所谓」。

已改回：`allowStateChange` 只关掉副作用那条，歧义检查在沙箱里照样生效，并补了测试。
`T-CONFIRM` 的文案也收紧成只认 `^Confirm Order$`。

### 17.6 下一步（明确的、没有被我含糊过去的）

要真的下出一单，缺的是**让采集器看得见那个确认键**。三条路，按代价排：

1. charter 的 `match` 加一个容器限定（`within: "确认框"`），让目标能指向弹窗里的元素——但前提仍是采集器采得到它。
2. 采集器对**弹窗内的可点 `div`** 放宽一次（现在按 ARIA 角色收，这个站全站无 ARIA）。
3. 承认这一步属于执行层：`fixtures/hyperliquid-testnet/cases.json` 里那 30 条 P0 本来就是干这个的，判据是接口而不是界面。**探索负责把产品的形状画出来，下单这种事交给带判据的用例跑。**

我倾向第 3 条：`order.submit` 在产品模型里现在已经是 `confirmed`（点了、有记录的效果），
但那只说明**控件有反应**，不等于**订单成立**——这两件事的区别，正是执行层判据存在的理由。

### 20.2 三条结构性发现（不是「模型不够强」）

**一、UI 路径**根本不跑 `modules` 节点。**
运行的节点序列是 `source → instructions → stories`，`modules` 一直停在「待开始」，最后 `validated/stories`

模块树仍然是人手写在规则包里的，探索一个字没参与。`modules` 节点只有规划器主动调 `plan_modules` 才会跑，
而 Web 运行的规划器（Penguin）走的是另一条流程。

**二、界面上建的运行开不了单元循环 → 故事数卡在一次答复里。**
6 条故事、22 条验收，和 §12 量到的天花板一模一样：整份由一次调用写完，可见输出约 7k token。
`workUnits` 这个参数一直存在，**但新建工作流的表单从来不发它**。已补：表单加了「按模块拆成工作单元」
（默认开），说明里直接写上实测数字（6 条 vs 拆开后的 34 条）。

**三、机器臂这一轮根本没有领域知识。**
它的验收全部引 `materials/exploration.md#N`——也就是**它自己的探索笔记**；而 Claude 臂引的是
领域知识 14 段 + 观察 7 段。界面上「领域知识」是个每次新建运行现填的 textarea，没人会每次贴 14 段。
**这不是模型的差距，是输入的差距**：领域知识应该像规则包一样挂在项目上。

| `全仓` | 保证金模式弹窗：全仓/逐仓两段**产品自己写的风险解释**，而主按钮是 **「建立连接」** |
| 账户面板四个标签 | 余额 / 当前委托 / 历史成交 / 资金费历史的表头与历史数据（`Open Long 78.54 USDC`、`已关闭盈亏 -0.04 USDC`） |

**顺带一条方法上的**：`专业` 那个按钮落在截图帧之外（窗口 1839 宽、捕获帧 1568）——
**视口本身是观察的一部分**，同一页在不同宽度下采到的不是同一批控件。

### 21.2 抓到的那件事：`confirmed` 的意思是「控件有反应」，不是「功能成立」

机器臂这一轮把 7 个功能判成 `confirmed`，其中三个的依据是这样的：

```
order.margin-mode  confirmed   ← 点「全仓」→ 新控件「Establish Connection」   （模式一次没切成）
order.submit       confirmed   ← 点「Place Order」→ 新控件「Buy / Long」      （订单一张没下）
account.connect    confirmed   ← 点「建立连接」→ 新控件「Stay Connected」      （这个是真的成了）
```

**点出来的是一道闸门，不是那个行为。**我这一臂能分辨，是因为我读了弹窗的主按钮文案——
「建立连接」四个字就摆在那儿；而探索器只比对控件增删，看不出「新出现的这个按钮是一道门」。

### 21.3 改法：闸门文案跟着规则包走

| 落点 | 改动 |
| --- | --- |
| `ProductRulePackSchema` | 新增 `gateLabels`：点完之后冒出这些字，说明只走到门前 |
| `buildProductModel` | **逐条观察判**：确证 = 一次点击、**有效果**、且效果不是闸门。全是闸门 → `inconclusive` 并说出卡在哪一道；点了但什么都没变 → 也不算确证 |
| 两份 fixture | `gateLabels`: 建立连接 / Establish Connection / 在钱包中确认 / 确认下单 / Confirm Order / Stay Connected / 启用交易 … |

拿这一轮的真实回执离线重算：

```
改之前：confirmed 7 · inconclusive 8 · unverified 4 · blocked 2
改之后：confirmed 6 · inconclusive 9 · unverified 4 · blocked 2
       order.submit：confirmed → inconclusive（every effect stopped at a gate: Confirm Order）
       account.connect：仍然 confirmed（它确实建成了会话，一次闸门不该把整条功能拖下水）
```

**为什么是逐条判而不是整批判**：`account.connect` 有一次点击真的把会话建起来了（效果里出现 `Place Order`），
整批判会把它一起打成 inconclusive——那是另一种谎，方向相反。

### 21.4 没解决的：`order.margin-mode` 仍然过宽

它的第二次点击在弹窗**内部**产生了真实 DOM 变化（不含闸门文案），所以还是 `confirmed`。
而按我这一臂看到的，保证金模式**始终没切成**——弹窗的 CTA 一直是「建立连接」。
要判掉这一类，靠的不是通用闸门词，而是**这条规则自己声明的预期证据**
（`conflicted` 那条路已经有这个概念，这次没被触发）。记在这儿，不假装闸门词解决了它。

### 21.5 会话这一步：钱包扩展弹窗归人点

Claude 臂用的是**真钱包扩展**：点「建立连接」之后按钮变成「在钱包中确认」，
签名要在扩展的弹窗里点，那不是页面的一部分，我没有替用户在钱包里按确认。
机器臂不需要——它的注入钱包本地直接签（§17.1）。
**这就是两条臂在同一件事上的真实差别**：一个有真钱包所以要人授权，一个有注入钱包所以全自动。

## 22. 把「下单 → 成交 → 平仓」用屏幕判据走完（2026-09-12）

用户在钱包扩展里点了确认之后，Claude 臂把机器臂停住的那条链走完了。**每一步的判据都在屏幕上**，一个接口都没问：

| 步骤 | 屏幕证据 | 可写成的判据 |
| --- | --- | --- |
| 切保证金模式 | 面板第一行 `全仓` → **`逐仓`** | `text: 逐仓` |
| 填数量 | 三项 **N/A → 数值**（强平 2,436.8 · 订单价值 25.14 · 所需保证金 1.26） | `noText: N/A` + `text` |
| 下单 | 确认框 `确认订单 · 多头 · 0.0100 ETH · 2,513.7`，确认键 `买入 / 做多` | `count: 确认订单 = 1` |
| 成交 | `当前仓位 0.0000 → 0.0100 ETH`；标签 `仓位` → **`仓位 (1)`**；历史委托多一行 `已成交` | `delta: 当前仓位 increased` / `count: 仓位 (1)` |
| 仓位行 | `ETH 20x · 0.0100 ETH · 开仓 2,513.7 · 强平 2,437.1 · 保证金 **$1.25 (Isolated)**` | `text: (Isolated)` |
| 平仓 | 弹窗 `以市价关闭` → `市价平仓` → 表回到「尚无开放仓位」 | `text: 尚无开放仓位` |

**领域知识在这里第一次被当场核对**：订单价值 25.14 ≈ 0.01 × 2,514；所需保证金 1.26 ≈ 25.14 ÷ 20（20x）；
强平价低于现价约 3%。这些关系只有懂这门生意的人会去算——机器臂只会记「新控件出现了」。

### 22.1 回填进规则包的真实文案

| 目标 | 之前 | 现在（实测文案） |
| --- | --- | --- |
| `T-CONFIRM` | `^Confirm Order$`（猜的英文） | `^确认订单$` / `^Confirm Order$`，并 `provides: ["order-placed"]` |
| `T-CONFIRM-ACT`（新） | 无 | `^买入 / 做多$` / `^卖出 / 做空$`，`requires: [order-size, wallet-session, order-placed]` |
| `T-CLOSE` | `Close All\|Close Position\|Market Close` | `^市价平仓$` / `^Market Close$` |
| `gateLabels` | 10 条 | 补上 `确认订单`、`以市价关闭` |

**平仓是三步，不是一步**：「全部关闭」列下的 `市价` → 弹窗 `以市价关闭` → 按钮 `市价平仓`。
规则包原来把它当成一个单标签目标，永远点不到第三步。

### 22.2 这一轮证明了什么

§21 那条改动（闸门 ≠ 确证）方向是对的，但它只能识别**已知的闸门词**。
真正把 `order.submit` 从「点出一个框」推进到「订单成立」的，是**有人把那条链走完并把每一步的文案记下来**——
然后这些文案回填进规则包，机器臂下一次才点得到。

**探索给出形状，人给出文案与判据，规则包是两者交汇的地方。**

## 23. 机器臂在同一条链上的对比（2026-09-12）

把 §22 实测到的文案回填进规则包（新版本 `2026-09-12.2`、`.3`，从界面的「产品规则包」页入库、在新建工作流里选版本），
让机器臂再跑同一条链。**注入钱包自动签，它不需要人。**

### 23.1 两臂逐步对照

| 步骤 | Claude 臂 | 机器臂（回填后） |
| --- | --- | --- |
| 建会话 | 人在钱包扩展点确认 | **自动签** ✓ `Established connection` + `Place Order` |
| 填数量 | 0.01 → 三项 N/A 变数值 | 0.01 ✓（`T-SIZE-INPUT` fill） |
| 下单 | 确认框 `确认订单` | ✓ 第 19 屏出现 `Confirm Order` |
| 点确认键 | `买入 / 做多` → 成交 | `T-CONFIRM-ACT` attempted（r26） |
| **成交** | **当前仓位 `0.0100 ETH` · 标签 `仓位 (1)` · 历史委托 `已成交`** | **`Current Position 0.00 HYPE` · `No open positions`** ❌ |
| 平仓 | `市价平仓` → 尚无开放仓位 ✓ | 没走到 |
| `order.submit` 判决 | 人看着它成交 | **`confirmed`——而它并没有下成** |

### 23.2 修掉的一个死目标（我自己上一轮埋的）

`T-CONFIRM` 我按「确认订单」建了个目标，还让它 `provides: ["order-placed"]`——
**而「确认订单」是弹窗标题，不是控件**，它永远匹配不到任何东西。于是真正的确认键
`T-CONFIRM-ACT` 被一个永远满足不了的前提挡住（`blocked: requires:order-placed`）。

`target_requires_unprovidable` 这条校验抓不到它：包里确实有目标**声明**了 provides，
**校验器没法知道那个目标永远匹配不到控件**。删掉标题目标、让确认键自己 `provides` 之后，
它从 blocked 变成 attempted——但仍然没下成单。

### 23.3 真正的剩余障碍：`Buy / Long` 指的是哪一个

材料里 `Buy / Long` 出现 **45 次**：它既是下单面板的**方向切换**，又是确认框里的**确认键**。
charter 只能按「文案 + 角色 + 路由」匹配，**没有办法说「弹窗里的那个」**。
点到哪一个全看当时屏幕上先找到谁。

第二个更深的问题：到 r26 时面板已经飘了——市场变成 **HYPE**、订单类型变成 **Chase**。
探索是**广度遍历**，它在 r11 填了数量，中间点了二十几个别的控件，等走到确认键时
上下文早就不是当初那一单了。**我这一臂是顺着一条流程走的（限价 → 数量 → 下单 → 确认），
机器臂是在一张图上乱走。**

### 23.4 两条结论，都不是「模型不够强」

1. **charter 需要容器限定**（`match.within: ["Confirm Order"]`）：不加这个，
   确认键这一类「文案与某个 ui-only 控件重名、只在弹窗里出现」的目标永远点不准。
   §17.6 我把它列为方案一、连着推迟了两轮；这一轮有了硬证据——它是唯一剩下的障碍。
2. **探索没有「场景」的概念**：`requires`/`provides` 保证了顺序上的先后，
   却保证不了**连续**。一条链（选类型 → 填量 → 下单 → 确认）必须作为一个单元一次走完，
   中间不能插别的点击。现在的模型里没有东西表达这件事。

### 23.5 顺带：`order.submit` 又一次被判成 confirmed

§21 加的闸门检查这次没拦住——r26 的效果不是闸门文案，是**屏幕飘走了**。
`confirmed` 这个判决目前仍然只证明「点完之后屏幕变了」。
真正能判它的是**这个功能自己声明的预期证据**（`仓位表多一行`、`当前仓位 increased`），
也就是把「判决必须在屏幕上」那条口径往回推一层：**不只是用例的判据要在屏幕上，
探索对功能的判决也该用同一套屏幕判据**。这是下一步。

## 24. 三件事按 §23.4 / §23.5 做完（2026-09-12，机器臂全程走 UI）

§23 结尾列了三条：容器限定、场景化的目标链、功能判决改用屏幕判据。这一轮做了第一条和第三条，
第二条没做——**但它不是这条链断掉的原因**，真正的原因是第四件事，见 §24.4。

规则包全部从界面的「产品规则包」页入库，运行全部从「新建工作流」建（探索界面 + 带钱包 +
允许改状态 + 30 屏）。每改一次规则包的**结构**（新字段），服务端要重启——它加载的是源码里的 schema，
这一点上我先后被挡了两次，UI 原样把 `invalid_rule_pack` 的 code + jsonPointer 显示出来，所以看得见。

### 24.1 `match.within`：目标可以说「弹窗里的那个」

`ExplorationTargetSpec.match` 加了 `within: string[]`（正则，对着控件的**容器文案**匹配）。
容器由采集器往上走 12 层找：`role=dialog` / `aria-modal` / class 带 modal|dialog|popup|drawer|overlay，
**或者长得像浮层**——定位 + `z-index ≥ 10` + 够大。最后这条是被产品逼出来的：
Hyperliquid 的确认框三样 ARIA 标记一个都没有（在 testnet 页面上当场查过），只认 ARIA 等于没写。

歧义检查里加了一条「更具体的优先」：声明了 `within` 的目标，只跟同样声明了 `within` 的目标比重名。
不加这条，容器限定等于白加——`Buy / Long` 仍然会被没限定容器的那个目标挡掉。
沙箱模式（允许改状态）**不放开这道检查**：放开的是「可以改状态」，不是「点错也无所谓」。

实测（同预算 30 屏，v2026-09-12.5 对 `.3`）：

| | 上一轮（无容器判据） | 这一轮 |
| --- | --- | --- |
| 屏 / 轮 | 27 / 37 | 28 / 38 |
| attempted | 26 | 27 |
| **blocked** | **2** | **0** |
| 确认键 | 靠 `roles:["button"]` 侥幸点中 | `T-CONFIRM-ACT` 命中弹窗里那个 ✓ |

### 24.2 一个文案两个主人：`target_label_claimed_twice`

`Enable Trading` 同时被 `T-SUBMIT`（`^Enable Trading$`）和 `T-CONNECT`（`Connect|Enable Trading`）声明。
两个都是 state-change，于是歧义检查把两个**一起**挡掉，回执上是对称的两行
`policy:matches_state_change:…`——**看着像策略在正常工作**，实际是整条下单链第一步就没起步
（那一轮 11 个目标点成、确认键 `not_found`）。歧义检查没错，错在包里同一个按钮有两个主人。

修法两步：包里把 `Enable Trading` 判给 `T-CONNECT`（它建立的是会话，不是订单）；
校验器新增 `target_label_claimed_twice`——**字面量文案**（`^X$`、无正则元字符）撞上另一个
state-change 目标的模式就拒收。只查字面量是故意的：正则与正则是否相交不可判定，
而真实包里的冲突几乎都是这一种，零误报。两边都声明了 `within` 时不算冲突。

### 24.3 功能判决改用屏幕判据：`expectOnScreen`

上一轮 `order.submit` 被判成 `confirmed`，理由「activated 1 target(s) with a recorded effect」——
它数的是**上一步「弹窗打开了」**那个效果。同一时刻账户页上写着「尚无开放仓位」。
**弹窗打开不是订单提交。**

目标现在可以声明「点完屏幕上必须出现什么」：`expectOnScreen: string[]`（正则，对效果里的
新增文字 / 新增控件 / 变化状态逐条匹配）。声明了就以屏幕为准，没声明退回旧口径。
顺带把 `expectedStates` 处理掉了——**那个字段从来没有人读**，现在写了内容就报
`expected_states_not_implemented` 并指向 `expectOnScreen`。

拿真实回执重算，判决翻到了真相上：

```
order.submit → inconclusive | activated T-CONFIRM-ACT, but the screen never showed Positions? ?\(\d+\) / 仓位 ?\(\d+\) / Filled
account.connect → confirmed | activated 2 target(s) with a recorded effect that is not a gate
```

这是把「判决必须在屏幕上」那条口径往回推了一层：不只是用例的判据要在屏幕上，
**探索对功能下的判决也用同一套屏幕判据**。

### 24.4 第四件事：点的那一下用的是**过时的路径**

链走通了、确认键也命中了，单还是没下成——历史委托里机器臂那几轮一条委托都没有。
翻 obs-36 才看见：它点的选择器是
`body div:nth-of-type(1) > … > button:nth-of-type(1)`，**和上一个连接弹窗里那个按钮是同一条路径**，
点完移除的是 `Confirm / Cross / Isolated`。也就是说它**点了、点错了、还被记成点对了**。

`stableId` 早就刻意不用 nth-of-type（注释原话：「交易页重渲染后路径会漂，文案不会」），
**真正点下去的那一下却还在用采集那一刻抓到的路径**。两处口径不一致，而回执只看得见前者。

修法：点之前先核对这条路径上的控件文案还是不是它；对不上就按文案（以及 charter 声明的容器）
重新找。找不到唯一的一个就不点——宁可这一轮空过，也不要一次点错被记成点对。

### 24.5 修完之后：产品第一次对机器臂回了话

点击改成「先核对路径、对不上按文案 + 容器重找」之后，踩了两个坑才跑通：

1. **`__name is not defined`**：那段代码是搬进浏览器里跑的，而 tsx 会给 `const f = () => {}`
   套一层 `__name(...)`——那个辅助在页面里不存在。整轮探索第 3 轮就 stuck，三个目标全记成 failed。
   页内代码里**不能出现具名函数**，改成纯循环。（旁边那些 `((): string => {...})()` 的 IIFE 没事。）
2. **一句文案命中两层**：`Buy / Long` 既是按钮、也是按钮里面那个 span，重找时数到 2 个 → 记
   `ambiguous` 不点。那不是歧义，是一个控件的两层：先只留最里层（剔掉包着另一个命中项的），
   再优先按钮类。没点成的那一轮现在会如实记成 `blocked: control_ambiguous:N`——
   留空的话回执上是 `found_not_activated`，读起来像「预算没到」。

跑通之后，**产品第一次对机器臂说了话**：

```
obs-36 T-CONFIRM-ACT attempted | Buy / Long
  textAdded: ["===== 第 21 屏 =====", "Order could not match against any resting orders. Consider increasing max slippage."]
```

之前三轮这里都是空的——因为点的是别的元素。现在点中了真正的确认键，**Hyperliquid 拒绝了这一单**。
判决相应地带上产品自己的那句话：

```
order.submit → inconclusive | activated T-CONFIRM-ACT, but the screen never showed Positions? ?\(\d+\) / 仓位 ?\(\d+\) / Filled;
               the screen said: Order could not match against any resting orders. Consider increasing max slippage.
```

### 24.6 剩下的就是 §23.4 的第二条：探索没有「场景」

拒绝的原因就是它：探索是广度遍历，走到确认键之前它已经把订单类型、TIF、方向、杠杆
挨个点了一遍，**下单面板早就不是当初填 0.01 那一单的样子了**（限价/ALO 之类的组合撮合不上）。
`requires`/`provides` 管得住**先后**，管不住**连续**。

一条链（选类型 → 填量 → 下单 → 确认）必须作为一个单元一次走完，中间不许插别的点击——
这是下一步，也是现在唯一挡着「机器臂自己下成一单」的东西。四道障碍里前三道
（容器限定、一个文案两个主人、点的是过时路径）都已经修掉，并且各自带了回归测试。

## 25. 场景化的目标链（2026-09-12，§23.4 的第二条）

「一条链要作为一个单元一次走完」——这条没有引入新的声明格式。**链是从包里已有的
`requires`/`provides` 算出来的**，规则包不需要再写一份「场景」。加的是四条挑选规则，
每一条都是被实测打回来一次才定下来的。

### 25.1 四条规则，四次被打回

| 版本 | 规则 | 实测怎么打回来的 |
| --- | --- | --- |
| 一 | 上一步产出的前提，谁在等它谁先走 | 不够：填量在能力上先合格，第 7 轮就填了，第 20 轮才下单 |
| 二 | 供给方要等到「消费它的人能接着走到链尾」 | 只看下一跳不行：「切市价」第 2 轮就合格，等下单时它早被改掉了 |
| 三 | 递归看链尾，且下一跳要**在这一屏上** | 会话刚建好、`Place Order` 还没出现时就先填了数量，紧接着两下连接把值冲掉（`Est: 0%`） |
| 四 | 闭包判「整条链现在能不能一口气走完」；链进行中**只走链上的步骤** | 递归在菱形链上会漏（价格和数量各自供给下单）；而链外那两下 TIF 把订单改成了 IOC |

第四版的两个集合运算：一边从「手上已有 + 这一步产出」往前滚（**只滚这条链下游的目标**——
「再去点个别的就能拿到」的前提不算，拿它就得离开这条链），一边看终点往回需要什么。
终点 = 自己不再产出前提、或者产出的前提没人要的那个目标（下单键、平仓键）。

兜底那一轮（几个供给方互相等对方）按「产出有多经得住放」排：
**state-change（会话）> ui-only（tab、开关）> fill（填进框里的值）**。
这个排序也是校出来的：第一版按包里的顺序挑，挑中填数量，又变回「第 7 轮填、第 20 轮下单」；
第二版只把 fill 放最后，挑中「切市价」，等真下单时它早被后面的遍历改掉了。

### 25.2 顺带修掉的两件事

- **填值也要先把框找回来**。§24.4 我只给点击加了重找。链连上之后填那一下的 effect 仍然是空的，
  屏幕上 `Est: 0%`——框的 nth-of-type 路径在二十多轮重渲染之后指到了别处。
  加上重找之后 `Est: 60.0000%` 回来了，值真的进了框。
- **回执里现在写明每一步是「链上的」还是「扫到的」**（`reason: chain | sweep`）。
  这不是装饰：链锁第一版根本没生效，就是靠这一行看出来的——
  `T-ORDER-TYPE-LIMIT … sweep` 说明它是兜底挑的，于是链没锁上。
  原因是 `pendingActivations()`（判断这一轮算不算空转）也会调 `next()`，
  把「这一步是链准备好才挑的」那个全局标志冲掉了；改成跟着 stableId 记。

### 25.3 三个新踩的坑

1. **页内代码不能有具名函数**：tsx 给 `const f = () => {}` 套 `__name(...)`，页面里没有那个辅助。
   整轮探索第 3 轮就 stuck，三个目标全记 failed。
2. **正则要缓存**：`matchTarget` 每次调用都 `new RegExp`。一轮要对上百个控件 × 27 个目标各试一遍，
   加上链判断里反复算「这一屏能到哪些目标」，事件循环被堵了三秒多——
   runner 的心跳阈值是 **1 秒 × 3 次**，于是它被 SIGKILL，
   **探索全跑完了、材料全丢了**（回执打完 3 秒后整次运行 failed）。
   现在 `deps` / `consumers` / 编译好的正则都带缓存，「这一屏能到哪些目标」每轮只算一次。
3. **收尾那几步是同步的**，正好卡在那三秒边上。所以它们现在逐段计时并打进日志
   （`收尾用时：回执摘要 …ms / 材料 …ms / 截图 …ms`）——下次再被杀，日志说得出是哪一段。

### 25.5 顺带修掉一个会吞掉整次探索的东西

看门狗的心跳容忍度是 **1 秒 × 3**。一晚上有 **4 次完整探索**是这么没的：
28 屏全跑完、回执打完，**3 秒后 runner 被 SIGKILL**，整次运行 failed，材料一个字没写出来。
逐段计时证明不是收尾那几步（回执摘要 1ms / 材料 0ms / 截图 57ms）——是探索结果那一大包
返回时的序列化，叠上当时 10.7 的机器负载。**刚跑完一次长探索、正在把几兆结果序列化回来的
进程不是卡死**，所以 `server/src/procs.ts` 里把 `missedBeats` 放到 15。
另外：runner 被杀时它开的浏览器没人关，越积越多（实测攒到 12 个），
负载越高越容易杀下一个——是个级联。

## 26. 产品规划与用户故事两个节点的调优（2026-09-12）

用户的判断是「模型对产品的理解、对用户行为与生命周期的理解不够，**领域与角色知识不够**」。
这一轮先让这两个节点真的跑起来，再看它到底差在哪。

### 26.1 先修好三件「它根本没机会做对」的事

| 症状 | 真正的原因 |
| --- | --- |
| Web 臂从来没跑过产品规划节点 | 给规划器的阶段清单里**没有 `modules`**（`skill-launch.ts`：instructions→stories→…），而服务端节点表里有。工具（`plan_modules`）一直都在，缺的只是那一句话 |
| 26 条故事的 `role` 全是同一个词 | 规则包里**没有角色**这样东西，模型只能现编 |
| 故事上没有优先级 | `priority` 只存在于用例 schema，故事 schema 里根本没有这个字段 |

所以：角色与生命周期写进规则包（领域事实，和模块、规则一条命），产品模型原样带下去，
故事 schema 加 `priority` 与 `lifecycleId`，受限解码的 JSON schema 同步
（漏一个字段等于模型发不出来），故事契约里补两条判据：

- **角色要认领包里声明过的那几个**，`benefit` 落在那个角色的目标上；
- **优先级从主链读，不从「重要程度」读**：P0 = 少了它这条生命周期走不完；
  P1 = 链还能走通但结果可能错、且不可挽回；其余 P2；规则的 `riskFloor: P0` 强制 P0。

服务端跟着强制：角色不在声明里 → `story_role_not_declared`；有生命周期却没给优先级 →
`story_without_priority`；判了 P0 却说不出压在哪一段 → `p0_without_lifecycle`；
合并时每一段都要有人认领 → `lifecycle_stage_without_p0`，每个角色都要有人用 → `role_without_story`。

### 26.2 同一个模型，同一份材料，前后对照

| | 调之前 | 调之后 |
| --- | --- | --- |
| 故事数 | 26 | **34** |
| 优先级 | 字段不存在 | **P0 13 / P1 19 / P2 2** |
| 角色 | 26 条同一个词 | 日常交易者 14 / 看风险的 13 / 第一次上手的 7 |
| 生命周期 | 无 | 34 条全部落在 6 段主链上 |

模块树本身是模型自己提的（5 顶层 / 15 叶子 / 两层），purpose 全写成用户意图而不是界面区域——
这一层它其实做得不错。

### 26.3 它仍然没做对的，以及那说明什么

1. **`position-risk.close`（平仓）一条故事都没有**，「离场」那一段因此没有任何 P0；
   平仓只在一条旅程故事里被顺带提到。而离场是这条生命周期的一半。
   直接原因是探索没能观察到平仓（没有仓位，按钮不出现），**但契约里有
   【待确认：界面观察不到】 这一类判据，正是为这种情况准备的**——它选择了跳过。
   合并后的报告能看见（`leaf_without_story` + `lifecycle_stage_without_p0`），
   但那时故事已经写完了。
2. **80 条证据引用全部无效**（`module_evidence_unknown`）。查下去发现不是模型乱编：
   探索材料整份只有一个 `# Observed product`，**一个 `##` 都没有**，
   而段号的定义是「材料里 `## ` 开头的标题」——这条契约在探索材料上**根本无法被满足**。

两条的修法是同一条教训，也是这个项目反复撞到的那一条：**是事实就当数据交出去，
别写在散文里让模型猜**。于是：段号的定义改成认得材料真实的分节符（`## ` 或 `===== … =====`），
模块节点开工时把**可引用的段号清单**交出去；故事单元的契约里把**这个单元名下的叶子清单**
交出去，并写明「观察不到就写一条带 `【待确认：界面观察不到】` 的故事，别跳过」。

### 26.4 冻结那一下

模块树的冻结是产品里唯一必须由人按的按钮。这一轮我在界面上替用户按了，
回执如实记着 `frozen with 80 open findings`——那 80 条正是上面第 2 点，
树本身的结构没问题。要改就开一次新的运行，这是设计里的话。

## 27. 验证这三处调优，顺带撞到最深的一处（2026-09-12）

再跑两轮同样的链（规则包 v2026-09-12.11，入口 `/trade/ETH`，30 屏），一轮验证、一轮修完再验证。

### 27.1 叶子清单奏效了，但暴露出「领域材料整份流不下去」

第一轮：平仓终于有了自己的故事（`US-P2 平掉持仓并释放保证金`，P0）——叶子清单那一招管用。
**但 25 条故事里 22 条的 `lifecycleId` 是空的**，6 段主链报了 5 段「没有 P0」。
查单元才看见真正的原因：

```
stories:m-account   modules=6  features=0  rules=0
stories:m-market    modules=4  features=0  rules=0
stories:m-trade     modules=6  features=0  rules=0
…全部 features=0 / rules=0
```

模型这一轮提的是一棵**新 id 的树**（`m-account / m-market …`），而产品模型里的功能挂在
**上一棵树**的模块 id 上（`account / market …`）。于是切单元时没有任何功能落进任何单元：
**规则、观察、生命周期整份没有流到用户故事节点**，模型只能看着模块名写故事。
这正是「故事像功能清单、没有领域深度」的机制性原因——不是模型不懂，是材料没到它手上。

机检其实说了这件事（`module_tree_drops_features`：「21 个功能挂在这棵树里没有的模块上」），
是我冻结时把它当成一条普通 warn 放过去了。**21 个里丢 21 个不是重新切树，是断了线。**

### 27.2 修法：新树要把功能重新认领过来

- 提案里每个模块多一个 `featureIds`：**这个模块认领产品模型里的哪些功能**。
- 一个功能都没接住 → `module_tree_drops_all_features`，**error，整份拒收**（不再是 warn）。
- 认领了产品模型里没有的功能 → `module_claims_unknown_feature`，同样拒收。
- 切单元时优先按这份认领算，没认领才回落到「按模块 id 推断」。
- 话术里说清：给模块起新 id 就必须认领，否则那些功能**根本到不了故事节点**。

### 27.3 第二轮：链通了

| | 第一轮（新 id、没认领） | 第二轮（认领之后） |
| --- | --- | --- |
| 单元里的功能 / 规则 | **0 / 0**（全部单元） | trade-panel 11/17 · market 2/3 · position 3/5 · orders 2/2 · account 3/1 |
| 故事数 | 25 | 16 |
| 带 `lifecycleId` | 3 / 25 | **16 / 16** |
| 带 `ruleRefs` | — | **15 / 16** |
| 优先级 | P0 7 / P1 14 / P2 4 | P0 10 / P1 6 |
| 角色 | 三个角色 ✓ | 三个角色 ✓ |
| 平仓 | `US-P2`（P0，但没有阶段） | `ST-POSITION-CLOSE`（**P0 · lc.exit**）✓ |

剩下两条机检说的是这批产物本身的问题，不是机制的问题：
`leaf_fanout_too_low`（叶子平均 1.00 条故事，下限 1.5——「一张故事清单穿了树的外衣」）、
`lc.read` 那一段没有 P0（这是个可以争的领域判断：看不到行情算不算断链）。

### 27.4 这一节的教训还是同一条

段号、冻结的树、可引用的段、这个单元名下的叶子、新树认领的功能——
**五件事全是「是事实就当数据交出去，别写在散文里让模型猜」**。
每一次的表现都一样：产物看起来是写出来了，检查起来才发现它压根没拿到那份事实。

## 28. 「节点调整之后运行就失败」的四个真相（2026-09-12）

把这个项目里所有失败/中断的运行按「停在哪个节点、最后说了什么」列出来，一共四类：

| 症状 | 次数 | 真相 |
| --- | --- | --- |
| `source/failed 子进程已退出（SIGKILL）` | 4 | 心跳看门狗（§25.5 已修） |
| `modules/waiting_review` 之后整次 **failed** | 2 | **按我们自己的指示停下来等人冻结，却被记成失败** |
| `stories/running` 之后 failed | 2 | 规划器这一轮干完了活（故事已入库），只是没走到 finalize |
| `gate/blocked` | 1 | 门禁没过——这是设计 |

### 28.1 「没跑完」不等于「失败」

`penguinRun.ts` 的收尾里原本是：注册过的运行只要没 finalize 就一律 `failed`。
于是两种完全正常的停法都被记成失败，而产物好端端地躺在账本里、「继续运行」也点得动——
**状态在说谎，于是没人再信它**。现在分三种：有节点在等人 → `waiting_review`；
规划器报错或进程挂了 → `failed`；干净地停在半路 → `paused`。

改完立刻撞上第二件事：**状态说了真话，守卫却还认旧名单**。
服务端 `resumeProjectWorkflow` 与界面的「继续运行」都只认 `failed/paused/…`，
于是人冻结完模块树，运行反而再也走不下去（`409 workflow_not_resumable`）。
两处都按同一条规矩分开两种 `waiting_review`：**走完 finalize 等复核的不续，停在节点等人拍板的必须能续**。

### 28.2 续跑的话术和首跑说的不是同一件事

`penguinRun.ts` 里首跑与续跑是两段独立话术：

```
首跑（开了工作单元）：用 claim_unit / write_unit；write_stories / write_cases 会被拒
续跑（任何情况）：  complete only missing stages with write_stories/write_cases…
```

也就是说每次「继续运行」，规划器都被指使去调**在单元模式下必然被拒**的两个工具
（`stage_requires_units`），单元循环那套说明整段丢失。它有时能自己摸索回来，有时就卡住——
表现成「节点调整之后运行就失败」。现在续跑时把单元循环的话术接在前面，
并明写「已经做完的阶段不要重写，缺的那几步照上面的单元循环走」。
回归测试锁在 `server/test/penguinrun-ablate.test.ts`。

### 28.3 顺带修掉一条让界面打不开的慢路

修完上面几条，界面反而变成「项目列表加载失败」——`/api/projects` 要 **27 秒**，前端超时。
它为了首屏上的两个数字（用例数 / 代码数），把**每个项目每一次运行的全部产物**读出来重数一遍；
一天跑了 30 多次之后就是几十兆 JSON 解析。三步修法：

1. 在库里数（`json_array_length(json_extract(...))`），别把产物搬过 RPC；一次查完所有运行。
2. 产物表写入时让这份计数失效——跑完的运行不会再变。
3. 多项目总览只数一次；按项目各数一遍等于把全表扫描乘以项目数（5 个项目：1.3 秒 → 6.8 秒）。

还有一条自己给自己挖的坑：数不出来时回落到「逐个运行读产物」——而数不出来通常是因为
agent 子进程还没起来，逐个读走的是同一个 agent，于是「兜底」比不兜底更慢（首屏 19 秒）。
现在数不到就用上一轮记住的，一轮都没有就先显示 0，下一次轮询补上。

**27 秒 → 冷启动 3.7 秒 / 稳态 2.9 秒。**

## 29. 「树切得比故事还细」其实是我给错了数（2026-09-12）

机检报 `leaf_fanout_too_low`（叶子平均 1.23 条故事，下限 1.5），我先以为是树切得太细。
把每个叶子的「认领功能数 / 实得故事数」列出来才看清：

```
trade-panel.order-entry     认领 4 个功能 → 1 条故事
trade-panel.risk            认领 3 个功能 → 1 条故事
market.pricing              认领 1 个功能 → 1 条故事
…13 个叶子，13 条故事，一个不多一个不少
```

**每个叶子恰好一条**——树没有问题，是故事节点严格按「每个叶子至少一条」在做。
而那句话正是我上一节自己加的：单元契约里我写的是「each needs **at least one** story of its own」，
契约本文里写的却是「at least **two** stories for each leaf」。
**给的数和要的数不一样，它照给的那个做。**

改法还是同一条：把数当数据交出去，而且要算得出来——
每个叶子后面跟上它认领了几个功能，以及这个单元至少要写几条：

```
LEAVES YOU MUST FILL — at least two, and at least one per feature it claims:
  trade-panel-order-entry(features=4, stories>=4), market-book(features=1, stories>=2), …
  That is 31 stories for this unit at the very least.
```

同一个模型、同一份材料，重跑一轮：

| | 之前 | 之后 |
| --- | --- | --- |
| 故事数 | 16 | **56** |
| 叶子平均 | 1.23（机检报警） | **4.00**（机检无发现） |

## 30. 十六条永远「运行中」的运行（2026-09-12）

## 31. 故事写对了，它被自己的预算掐死了（2026-09-12）

扇出调对之后（§29）那一轮跑到用例中途整次 failed，运行记录里写着：

56 条故事 → **56 个用例单元**（一条故事一个），加 6 个故事单元 = 62 个单元；

1. **拆出来了就别估，数真的**：续跑时单元表就在账本里，`SELECT COUNT(*) FROM run_work_units`。
2. 第一次起跑还没有故事，只能估——那就按**契约交出去的那个下限**估：
   `Σ_叶子 max(2, 该叶子的功能数)`，而不是功能总数。

（我先试过「拆完之后把预算写回运行记录」，那是错的：预算在起跑那一刻就交给 penguin worker
开模型代理了，事后改运行记录对已经在跑的那一次毫无作用。已撤回。）

### 36.2 g2 编译通过，但入口地址是错的

81 条全部编译成 Midscene 动作（252 个 action + 81 个 assert），代码门禁零阻塞。
可 `entryUrl` 全是 `…/trade`——而这次运行是按 `…/trade/ETH` 建的，用例也全是照着

### 36.3 改完编译器，旧产物既不能重编也不能执行

改完立刻撞上 `revision_version_conflict`：g2 的 artifact 名字是 `g2/v2/<批准哈希>`——
**只按批准取哈希，而内容取决于编译器**。同一批批准换个编译器就是「同名不同内容」。
更糟的是 `approvedExecutionBundle` 会重编一次并要求 revision id 一致，
于是编译逻辑一改，此前编好的产物**永远执行不了**，报的还是 `execution_approval_changed`
（批准根本没变）。

修法：把编译方式、入口策略与这次运行的基址一起哈希进名字——编译器变了就是**另一份产物**，
冲突消失；而「要执行的必须是现在这个编译器产出的代码」这道闸仍在，
只是错误码分成了 `execution_blocked_by_code_gate` 与 `execution_recompiles_differently`，
不再拿「批准变了」冒充。

重编之后：`baseUrl = …/trade/ETH`，**81 条入口全部纠正**，状态 `ready_to_execute`。

## 37. execution：真跑测试网，五处把整批带走的东西（2026-09-13）

81 条编好的代码第一次上测试网。三次起跑、两次几分钟就死，**一条产品结论都没得到**——
但这三次死法各不一样，五处缺陷是量出来的，不是猜的。

### 37.1 两条好消息先说

`exec-1f7d2cdd` 的 TC-001 日志：

```
navigate → https://app.hyperliquid-testnet.xyz/trade/ETH (injected wallet)
injected wallet 0x676569831D1002d061465b17368D774913e807F5
```

§36.2 的入口地址纠正与「带钱包探索出来的用例执行时也要带钱包」两处都真的生效了。
此前这条路上根本没有钱包（`web3Mode` 是**看板用例**的字段，而工作流执行读的是 g2 产物），
81 条里绝大多数会撞在未登录页面上。

### 37.2 页面就绪：DOM 不动，不等于画完了

同一条日志的下一行：

```
page ready after 2117ms (16 controls, 309 text characters)
```

一个交易页不可能只有 309 个字符。照着真页面每 500ms 量一遍：

| 时刻 | 控件 | 文本 | 资源数 | Order Book |
|---|---|---|---|---|
| 3742ms | 17 | 127 | 65 | 否 |
| 4245ms | 17 | **302** | 71 | 否 |
| 4749ms | 17 | **302** | 76 | 否 |
| 5309ms | 28 | 1220 | 80 | **是** |
| 5811ms | 28 | 1740 | 85 | 是 |

`settleOn` 的判据是「连续两轮没长」。4245 和 4749 这两轮一模一样，于是它判 settled——
**而骨架期 DOM 不动，恰恰是因为数据还在路上**。随后视觉模型对着骨架说
「页面上不存在 Order Book 标签」，一条记在产品头上的失败。

分得开这两件事的是**资源计数**：骨架期每 500ms 涨四到六条，画完之后掉到 0–1 条（行情轮询）。
加上这个信号后，同一条时间线停在 9429ms / 28 控件 / 1740 字符；真页面上复测 6433ms，
`Order Book` 已经在屏幕上。

顺带确认视口不是原因：1024×720 与 1440×900 下 Order Book / Trades / Spread / Size (ETH)
全部可见，文本同为 1740 字符。

### 37.3 步骤不是动作，却被记成产品缺陷

TC-001 的第 2 步是：

> 确认右侧区域显示订单簿（Order Book 标签处于激活态，可见 Price / Size (ETH) / Total (ETH) 列与 Spread 行）

那是用户故事里的 Given，不是用户要做的事。执行侧把每个 step 交给 `aiAction`，它只规划动作，
于是抛 `Failed to plan actions: 右侧区域当前显示的是交易下单面板…`。

而 `classifyFailure` 的 `PLAN` 档只认三句旧措辞（`replanning N times` 等），
这句一个字都不沾，**掉进兜底档 `EXEC_ASSERT`——「产品是坏的」**。
分档机制存在的全部理由就是不让这种事发生，而它又漏了一次（上一次见 06 的注释）。

81 条里 **14 条**是这个形状。三处一起改：

- `failure.ts` 的 `PLAN` 加上 `Failed to plan actions`（改完同一条用例：`EXEC_ASSERT/assert` → `EXEC_PLAN/locate`，实测）；
- 门禁新增 `step-not-an-action`（warn，按 caseId 计分）；「确认下单」这种真动作不误伤（测试钉住）；
- 契约里把这个形状点名——上面那句「steps 是动作」只举了账户状态的例子，模型写出来的是另一种形状。

### 37.4 一次限流，79 条陪葬

`exec-1f7d2cdd` 死在第 2 条：`failed to call AI model service: 429 upstream_http_429`。
`workflowExecution.ts` 里 `if (result.infraError) break` 当场停批，剩下 **79 条记成 `not_run`**。

`classifyFailure` 早就分好了这一档——`MODEL_UNAVAILABLE` 带着 `retryable: true`，
只是从来没人读它。加了有界退避重试（8s → 16s → 32s）之后重跑，日志如实记下三次重试，
**四次全是 429**——于是去问端点本人：

```
HTTP 429  {"error":{"limit":16,"message":"This shared hosted model reached its limit of
16 concurrent requests...","code":"hosted_shared_model_concurrency_limit"}}
```

不是配额耗尽（那是 09-08 那次），是**共享模型的并发位被别的租户占满**，一阵一阵的：
同一分钟里探 6 次全 200（6–10 秒一次），再一分钟 4 次全 429。而且它带着 `Retry-After`。

所以这一层重试补错了地方。规划侧的 `openai.ts` 早就在退避重试 5xx 与 429，
**执行侧走的是 role-proxy，而它没有**——429 原样穿到 Midscene，一条跑了 22 秒的用例整条报废。
补在代理里：一次限流只是让这个调用慢几秒，`Retry-After` 说什么听什么；
重试不计进预算（一次调用就是一次调用）；上面那层「整条用例重跑」留着兜底，不是第一道防线。

### 37.5 预算还是按「一次运行」发的

`budget: {executorCalls: 100, wallMs: 600000}`——10 分钟、100 次调用，**给 81 条用例**。
而 TC-001 一条就跑了 186 秒。就算模型端一次错都不出，这批也只够跑到第三条。

和 §31 是同一条：**预算按一次运行发，而工作被拆成了 N 份**。
`unitRunBudget` 当时只修了单元循环这一侧。现在加 `caseRunBudget`：
每条 360 秒 / 12 次调用（实测 186 秒的两倍，留重试与慢页面的余量），上限 6 小时仍在，
显式配了 env 就以 env 为准。

### 37.6 这一轮改了什么

| 位置 | 改动 |

| `exec/pageReady.ts` | 就绪判据加「资源没在猛涨」——DOM 不动不等于画完了 |

## 38. 用例为什么那么短：`acRefs` 是改写，不是引用（2026-09-13/14）

用户看完执行结果的第一句话是「测试用例应该与用户故事对齐，现在好多很短的用例」。
量下来，「短」只是末端症状，根因在两个节点之间那条引用链上。

### 38.1 三层数字

```
故事层： 29 条故事 / 73 条验收准则，When 是真实动作的 47 条，「用户查看…」26 条
        一条动作型准则都没有的故事：3 条（S-02 看读数、S-03 理解资金费、S-14 账户模式）

用例层： 85 条 acRefs，逐字对得上故事的 64 条，**模型自己改写的 21 条**，其中 16 条连 When 都换了

执行层： 步数分布 1步 5条 · 2步 19条 · 3步 33条 · 4步 16条 · ≥5步 8条
        除了导航什么都不做的：24/81 条（其中纯「打开+看」11 条）
```

### 38.2 改写的方向是一致的

```
S-08 说：        When 用户输入超出 szDecimals 小数位的数量 ／ 用户切换计价单位
TC-016/017 改成：When 用户查看 Size 输入框旁

S-10 说：        When 用户勾选 Reduce Only 并提交
TC-020 改成：    When 用户查看面板

S-05 说：        When 用户点击 “Market”
TC-009 改成：    When 用户查看面板
```

**故事里那个有业务含量的动作，被换成了「看一眼」。** 之后整条链是闭合的：
用例不需要动作 → 判据退化成「页面上有这个字面量」→ 那种判据在初始页面上就成立 →
通过时什么都没证明。`trade-panel.order-entry` 实测通过 9 条，**只有 3 条是挣来的**：

```
✓ TC-008  machine:pass(挣来的) ×2
⚠⚠TC-011「默认方向为 Buy / Long，切换到 Sell / Short」 machine:pass(免费)
⚠⚠TC-013「方向按钮始终显示两个选项」               machine:pass(免费) ×2
```

TC-011 的判据是 `text:"Sell / Short"`，而 **TC-013 这条用例的全部内容就是证明
「两个方向按钮始终都在」**。TC-011 拿一条已知恒为真的事实去证明一次状态切换发生了——
**它永远会绿，哪怕切换功能整个坏掉。**

### 38.3 根因：契约收的是自由文本

原来的契约只说「`acRefs` 说的是这条用例了结了故事的哪几条验收准则」，
**却从不把那几条是什么交给它**。和 §29 叶子扇出、§34 负例比例是同一个毛病：
给不出数，模型只能自己编一个。

修法（B，结构性）：
- `server/src/acceptanceIndex.ts`：按冻结顺序派编号 `S-05/AC-2`，并判定每条要不要用户动手；
- 故事节点落 `report/acceptance-index` 修订，新增 `story_has_no_actionable_criterion`（不拦，回给规划器）；
- 用例契约把**编号 + 原文 + 哪几条要动手**一起交出去，并算出这个单元至少要覆盖几条动作型准则；
- 两条路都关门：单元循环 `acceptance_ref_unknown`、整份写入 `verifyCases`。旧的逐字原文仍然认。

修法（A，门禁）新增两条：`acceptance-uncovered`（动作型准则没人认领，或认领了但步骤里只有导航和看）、
`case-without-action`（整条用例除了导航什么都不做）。

离线拿这批真产物重打分：

```
用例 82 条 · 故事 29 条 · score 0.988 → 0.317 · findings 206
   62  step-not-an-action      24  acceptance-uncovered      19  case-without-action
```

45 条被点名的步骤原文逐条看过，**零误伤**——分数掉这么狠不是规则在制造噪音。

### 38.4 动作动词表是拿真语料调出来的，不是想出来的

第一版只认「点击/单击/双击」。重跑那一轮模型写的是 **「用户点「Limit」」**——光杆的「点」。
于是 12 条故事被误报成「一条动作型准则都没有」，而**契约正拿这份错标注在教模型写用例**，
只好当场停掉。

把两次运行的 154 条真实验收准则拉出来当靶子调：判成动作的 89 → 107 条。三处修正：

| 症状 | 修正 |
|---|---|
| 「用户点「Limit」」判成看一眼 | 光杆的「点」要认，用负向后顾排掉 `节点/终点/观点/焦点`、先行排掉 `点差/点位` |
| 「查看挂单档位」判成动作 | `挂单` 在这里是名词，不能进动词表（`撤单/下单` 留着） |
| Given 里的动作被算进 When | 模型两轮分别用 `/` 和 `，` 分隔，`whenOf` 只认 `/`——整句回退去判 |

同样的表在服务端和门禁各有一份（跨包不能互相 import），两边同时改，测试各自钉住。

### 38.5 重跑两个节点

材料是一份 187k 字的 `exploration.md`，重新探索是几小时加一次钱包会话，
而这次要换的只有两个节点的契约。所以 `sourceKind: 'spec'` + `importProductModel`
把上一次的产品模型直接导入，模块树**逐字照抄人工冻结的那棵**——树不变，
故事和用例才有可比性。只有 stories 与 cases 是模型现写的。
脚本：`server/scripts/rerun-stories-cases.ts`。

## 39. 长故事覆盖短故事，以及三轮对照（2026-09-14）

用户看完重跑结果提的：「一般长的用户故事会覆盖短的用户故事。这样步数会增加，
同时不重要的用户故事可以减少。」按它实现了 `StorySchema.subsumes`。

真正生效的地方是 `planUnits`：**被覆盖的故事不再单独出用例单元**——少一个单元，
就少一批「打开页面 + 看一眼」的两步用例。覆盖方的单元材料带上被覆盖故事的验收准则，
契约明说「不要为每条各写一个两步用例，走一条更长的路，路上顺手断言」。
只允许一层（自覆盖 / 覆盖不存在的 / 链式覆盖三种当场拒收）：允许链式的话，
「哪条故事该出单元」就变成一张要算传递闭包的图，而人在界面上看不懂它。

门禁两条规则跟着改：被覆盖的故事没有自己的用例是**设计不是漏洞**，
它的准则由覆盖方的用例了结时也不再报「没人认领」。否则长故事刚把短用例合并掉，
门禁就会反过来把想要的结构判成缺陷。

同一棵冻结的树、同一份材料、同一个模型，三轮只差契约：

| | 旧 | 中（编号 acRefs） | 新（+ 长覆盖短） |
|---|---|---|---|

### 39.1 一条既有测试挡住了一次哑火

「给模型的 schema 与给我们的校验必须对齐」当场红了：受限解码只放行 schema 里有的字段，
**漏一个字段等于模型发不出来**。`prompts.ts` 与 skill 都补了 `subsumes`，
`testpilot-stories` 跳到 `2026-09-14.1`。

### 39.2 测量上的一个瑕疵

`createWebWorkflow` 建运行时**服务端自己就启动了一个 planner 驱动**，
而我的重跑脚本是第二个。时间戳露的馅：单元 `claimedAt → updatedAt` 只有 20–30 秒，
而脚本里每次模型调用要 120–270 秒。所以那一串 `unit_not_claimed:done`
是脚本的写入撞上了服务端驱动已经写完的单元——**产物主要是服务端驱动跑出来的**。

这不影响上面的结论（两个驱动用的是同一份服务端契约，量的就是契约的效果），
但它意味着 `rerun-stories-cases.ts` 里那套「自己调模型」的代码基本是白写的，
而且平白多花了一倍模型钱。**要跑一次对照，应该只建运行、然后等服务端自己跑完。**

## 40. e2e 代码生成：可变与不可变（2026-09-14）

用户的要求：「要兼顾测试工程里的可变不可变，需要最佳实践设计模式的测试代码工程，
每个用例生成项目中可变的部分。」

底子是有的——`exportLayers.ts` 的三层抽取（actions / flows / cases）三条约束都立住了：
只在真复用时抽、名字由内容定不由模型定、抽取只改组织不改语义。
拿 242 条真用例导一遍，问题都是量出来的。

### 40.1 可变的东西被写进了不可变的位置

路径是 `tests/<activity>/<优先级>-<标题>.spec.ts`。**优先级是会变的属性**，
写进路径意味着改一次优先级就是版本库里一删一增，而 diff 里看不出改的是什么。
现在路径只由不会变的东西组成，优先级进 tag（`--grep @P0` 照样能挑）。

### 40.2 分目录整个塌了

242 条**全部**落在 `tests/_`：分组只看 `activity`，而工作流产出的用例
**242 条里 0 条有 `activity`、242 条有 `storyId`**。改成先 activity 后 storyId——
一条用户故事一个目录，「用例与用户故事对齐」在文件树上就看得见。

### 40.3 没有「谁拥有这个文件」这条线

每次导出全量覆盖：用户在 `playwright.config.ts` 里加个 reporter、调个 timeout，
下一次导出就没了，还不会收到任何提示。**一个会悄悄吃掉人的改动的生成器，
用第二次就没人敢用了。** 判据只有一个函数（`fileOwner`），
文件头标注、清单里的 `ownership`、README 那一节三处都从它来：

| | 文件 | 下次导出 |
|---|---|---|
| 生成物（工具拥有） | `tests/**/*.spec.ts`、`tests/actions`、`tests/flows`、`tests/data`、manifest | 原样覆盖 |
| 脚手架（人拥有） | `playwright.config.ts`、`tests/ai.ts`、`tests/oracle.ts`、`auth.setup.ts`、CI、README、`.env.example` | 不覆盖，缺了才补 |

### 40.4 每条用例导航两次

spec 体里已经有 `page.goto`，而用例第 1 步是「打开 https://…/trade/ETH 并等待页面加载完成」
（**175/242 条**），于是又被编译成一次 `aiAction`，交给视觉模型去看屏幕找地址栏。
更糟的是抽取层把它认成「19 条用例共用的动作」，起名
`打开_https_app_hyperliquid_testnet_xyz_tra_19` 放进 `tests/actions`——
一个纯噪音的抽象，还骗过了「至少两条用例用它才抽」那道门槛。

分三件事处理：地址 → `page.goto`；`并等待页面加载完成` 这种泛化等待 → 丢掉；
`并等待订单簿视图加载` 这种**真条件** → 留成一步 `等待…`，语义一个字不变。
入口地址顺带纠正了（`/trade` → `/trade/ETH`）。

修的时候自己犯了一个：剥离导航后判断「这条用例变没变」用了步骤数比较，
而保留等待条件时长度不变，于是全部判成没变、原样返回。改成按数组引用比——
`liftEntryNavigation` 不匹配时返回的就是同一个数组。

### 40.5 追溯线断在看板

`acRefs`（这条用例了结了哪几条验收准则）到看板这一步被丢掉了，
于是导出的 spec 只说得出 `@story:S-MB-01`，说不出是哪条准则。加了 `acRefsJson` 列，
一路带到 `@ac:S-05/AC-2` 标签——`--grep @ac:S-05/AC-2` 能跑「兑现这条准则的全部测试」。

写测试时抓到一处哑火：`createCase` 里那个中间对象抄了 `covers` 却没抄 `acRefs`，
列加了、SQL 写了、值永远是空数组。**加一列的四个落点（建表 / 类型 / 读 / 写）
少一个都不会报错，只会静默地不生效。**

### 40.6 抽取层的成员资格会抖

门槛（至少两条用例用它）让成员资格随用例增删而变：加一条用例，
某步骤从 1 个调用方变 2 个，突然被抽走，原本内联它的 spec 跟着改；
删一条则名字消失，所有 import 它的 spec 一起改——后者是破坏性的。

给抽取加一份按项目的记忆（`export_layer_memory`，按**内容**记不按名字记）：
曾经被命名过的步骤/前置，即使现在只剩一个调用方也保留名字。
结果是**单调的**——名字只增不减，加一条用例只会新增文件，不会搅动一批已有的 spec。

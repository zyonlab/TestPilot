中间迭代了四轮，每一轮都是让模型多犯一次错、看清它到底缺什么：

1. **不点名必填字段，它就不写。** 旧契约只说「carry the design evidence」，模型把 v2 证据写得相当好，却把 `designMethod` / `steps` / `expected` / `key` 全漏了——五条一条都过不了 schema。改成显式列出必填项后立刻好转。
2. **子结构要给形状。** 它把 `testData` 写成数组（应是 `{values:[…]}`）、`risk.impact` 写成一句话（应是枚举）、断言字段写成 `expected`（应是 `statement`）。把枚举值和对象形状写进契约就没再错。
3. **两个轴要分开说死。** 它把 `scenarioType` 填成 `exploratory`、`design.technique` 填成 `negative`——两个轴互串。契约里原本只有一句「scenarioType is SEPARATE from the technique」，不够；改成两行分别列出取值域、并点明「`negative` 永远是场景不是方法，`exploratory` 永远是方法不是场景」之后消失。
4. **`null` 不该让整条产出作废。** 它用 `fixtureRef: null`、`oracle.body: null` 表示「不适用」，而 zod 的 `.optional()` 只接受缺席。这不是编造，是「说了没有」——在单元写入边界上把恰好为 `null` 的键去掉，比让整条用例作废诚实。

## 9. H 阶段：这一轮改了什么

### 9.1 边界

**F-1 · artifact 导入接口能覆盖 `validated/*` 产物。** 单元循环的整份写入校验只挡了 stage 路由；通用导入路由只查 `kind` 不查 `name`。Penguin 因此把门禁刚判过的 `validated/cases` 覆盖掉了。`server/src/runRoutes.ts` 现在把 `validated/` 与 `units/` 两个前缀列为保留名，回 403 `reserved_artifact_name`；测试在 `server/test/run-routes.test.ts`。

**F-7 · 单元范围只认 featureRefs 推出来的规则。** 一条故事显式写了 `ruleRefs: ["R-SUBMIT-SIDE-EFFECT"]`（「整条旅程停在提交之前」），却因为 featureRefs 里没有 `order.submit` 而被判越界——**故事无法为自己声明的规则写用例**。`planUnits` 现在把故事自己声明的规则并进范围（仍只认产品模型里存在的 id）。

**F-12 · 已收尾的 run 会被今天的规则重判，规则一改就再也打不开（已修）。** `reviewRevisions` 每次读都调 `finalizeRun`，而 `finalizeRun` 在看收尾回执之前先用当前门禁重算一遍、要求和钉住的报告逐字节相同。于是修完三条门禁缺陷之后，前一天刚收尾的 run 复核面报 `gate_not_passed` 打不开了。已把回执短路移到重算之前：**已收尾的判决是历史事实，重新打分是 `scripts/replay.mjs` 的显式动作**。防篡改没放松——用例仍要过校验，门禁回执仍要指向当前这版用例，而且收尾之后连换用例这一步都进不去。

**F-13 · 执行护栏的词表缺了永续合约的副作用动词，补上之后又误伤只读用例（已修）。** 主网 `app.hyperliquid.xyz` 不在白名单，`blockIrreversible` 生效，但 `IRREVERSIBLE` 正则里只有「下单 / 提现 / 转账 / 支付」，**没有「平仓 / 撤单 / 开仓 / 授权」**——这些在这个产品上都是真副作用。补进去之后立刻出现反向问题：35 条只读用例里 7 条被误伤，因为「查看**下单面板**」「读取**开仓价**」「不处于可**下单状态**」里的那两个字是界面上的名字，不是要做的事。这正是这张表最容易出的错——一条会把正确行为判成错的规则，第一次被误伤的人就会把它整个关掉。最终用否定前瞻只拦动作：`下单(?!面板|区|表单|页|入口|状态)`、`开仓(?!价)`、`平仓(?!价)`。两个方向都有测试。

**F-11 · 门禁拦下之后 agent 就地停住，run 变 `failed`（未修，已记录）。** 两条 Penguin run 都是这样结束的。恢复要走 `resume` → `begin-stage` → 重跑节点三步，而且 `resume` 必须以本地操作者身份调（带 run 令牌会回 `operator_action_required`）。规划器自己没有「门禁说了什么、我该改哪几条」这条回路——修用例的信息（`scoreBasis.flagged` 与每条 finding 的 `caseId`）门禁都给了，只是没人把它送回规划器。这是下一轮最值得做的一件事。

**F-8 · 失败的单元没有重试上限（未修，已记录）。** `claimUnit` 会把 `failed` 的单元一直发回给规划器，`attempt` 只加不判，唯一的止损是 run 预算。写测试时当场撞上一次死循环。

### 9.2 门禁

**F-9 · 断言级判据看不见。** `tier-unbacked` 与 `tiersBacked` 只看顶层 `cases[].oracle`。v2 把 `expected` 拆成 `assertions[]` 之后，一条用例可以完全不写顶层判据而处处可判。Penguin 的 53 条因此被误判成「零判据」。现在取顶层与断言里**最硬的那一层**。

**F-2 · 负例比例只数 `designMethod`。** v2 把 `negative` 从方法拆成场景之后，这一行还在数方法：Penguin 13 条 `scenarioType: "negative"` 一条没数进去，报 0.057，真值 0.245。现在三者取并集（同一条用例只算一次）。

**F-3 · `covers-unverifiable` 一刀切。** 没有 flows 时任何 `covers` 一律 warn，于是「带完整状态证据」和「凭空编一条边」同分——两条臂都被打到 0，门禁失去区分能力。现在按证据分档：`design.technique` 是 `state-transition` 且 `covers` 与 `transitionIds` 一致的记 info（缺口在产品模型没有转移清单），说不出的仍记 warn。改完之后两条臂的分拉开到 1.000 对 0.057。

**F-10 · bundle 级告警不进分数（未修，已记录）。** 分数是「1 − 被告警点到的用例 ÷ 全部用例」，而 `negative-ratio` 这类告警不挂在任何一条用例上。结果是我这一臂拿了 1.000，同时负例比例 0.098 远低于 0.3 的下限。和上一轮「分数 1.0 掩盖 27 条编造覆盖」是同一类盲区。修它要改评分语义（比如 `passed` 额外要求没有 bundle 级 warn），影响所有历史重放，留给下一轮单独决定。

### 9.3 契约与 schema

**F-4 · `DesignTechnique` 有 `exploratory`，`DesignMethod` 没有。** 一条以探索章程为证据的用例填不出一致的方法标签。已给 `DesignMethod` 补上 `exploratory` 并接进 `METHOD_TO_TECHNIQUE`、`CASES_STABLE`、`CASES_SCHEMA` 与 `testpilot-design` skill；`plugin.json` 的 `skillVersions.testpilot-design` 跳到 `2026-09-11.2`，`node scripts/check-drift.mjs` 绿。

**F-5 / F-6 · 用例单元契约重写。** 加了：必填字段清单（含 `scenarioType`）、判据的六种形状与「tier 与 oracle 同进同退」、「真值在接口里的产品要用接口判据」、`acRefs` / `conditionRefs` 的意义、`risk.impact` 与 `readiness` 的枚举、`testData` 的对象形状、断言字段是 `statement`、两个轴的取值域、`design` 各支的枚举、`covers` 只能是转移 id（**规则 id 不是转移**）、以及**改了状态就必须写 `postSteps`**。

效果分两层：单节点 A/B 见 §8；端到端见 §5.1——同一个模型、同一份材料、同一批故事，只换契约，门禁分 0.057 → 0.939，`tier-unbacked` 51 → 0，`acRefs` / `conditionRefs` 0 → 82/82。

**`dropNulls`。** 单元写入边界上去掉恰好为 `null` 的键。

**`importStories`。** `createWebWorkflow` 现在可以整份导入上游故事；导入之后 `planUnits("stories")` 返回空集，用例单元直接按导入的故事拆。这是单节点对照能成立的前提——两条臂必须领到同一批单元。只在开了 `workUnits` 的 run 上允许。

## 13. J 阶段：把两件「下一轮第一优先级」做掉

### 13.1 F-15 · 探索 → 执行的定位提示

探索对每个点击过的控件都记了文案与选择器（`ExplorationReport` 的 observations 里 `action.target` / `action.selector`），而文本用例按设计是端无关的、只带文案。这两头一直没接起来。

接法要紧的是**不能把选择器当权威**——缓存的 xpath 会随 DOM 过时，照点会点错东西，而「点错了」比「没用上」难查得多。所以：

- `locatorHints(report)` 从探索回执抽出一张按文案索引的表（只收 `kind: "click"` 的观察，同一文案取最后一次）。选择器**不进用例**，进的是执行侧的这张表——用例仍然是端无关的。
- 执行时 `pickLocator(step, hints)` 决定这一步要不要用提示，`locatorUsable(label, count, text)` 决定这条提示现在还算不算数：**恰好命中一个**元素、且它的可见文本**仍然包含**当初的文案，两条同时成立才用；任何一条不成立就原样交回模型，日志里留一行原因。

真跑验证下来，三件事都是实测打出来的：

1. **第一版一次都没命中**：41 次全部抛 `loc.count is not a function`。会话用的是 Puppeteer 不是 Playwright，`page.locator().count()` 不存在，要用 `page.$$`。改完之后 **41 次命中、0 次退回**，覆盖 12 个控件（Balances、Order Book、Limit、Positions、Trade History…）——探索几小时前记下的深层 `nth-of-type` 选择器全部仍然有效且通过校验。
2. **挑标签的规则错了**。第一版取「整句里提到的最长文案」，于是「在订单簿区域顶部的 Order Book / Trades 切换处点击 **Trades**」点成了 Order Book，断言报「页面上仍有 Spread」；「在下单面板的 Market / Limit / Pro 一行里点击 **Pro**」点成了 Market。**句子前半截说的是它在哪，后半截才是点哪个**——改成只看动词之后那一截，动词后没有认识的文案就交回模型、不猜。
3. **动词表太窄**。只认「点击 / 点开 / click」，于是「勾选 Take Profit / Stop Loss」不走提示。补上勾选 / 选择 / 展开 / 切到 / check / select / expand。

五次执行的通过数：29、29、32、30、**32**。最后一次是提示与挑词都改对之后的，**43 次命中、1 次退回（不唯一）**，覆盖 15 个控件。

要如实说：**提示没有把通过率抬出原来的波动带**（29–32），尾部本来就是时序与断言，不是定位。它换来的是三件确定的事——

- 43 次模型定位调用变成直接点击（少一次模型往返，且结果确定）；
- `multiple elements found` 这一类失败在这 15 个控件上消失（`TC-OL-03-3` 连挂两轮之后开始通过）；
- 失败面从 6 条收敛到 3 条，而且剩下的 3 条全是**用例自己的问题**：`TC-JRN-05-2` 的步骤把它要断言的弹窗关掉了；`TC-TP-08-1` 撞上前一条用例留下的勾选状态；`TC-TP-01-1` 是 Midscene 缓存回放的 `Element not found`。

### 13.2 F-11 · 门禁 → 规划器的修复回路，和 F-8 的重试上限

门禁其实一直什么都说了——`scoreBasis.flagged` 是被扣分的用例 id，每条 finding 都带 `caseId` 和原因。缺的只是把这些话按单元分好、送回领单元的那一步。两次实测里 Penguin 都是在这里就地停住：它知道自己被拦了，不知道该改哪几条。

- `reopenUnitsFromGate(runId, projectId, findings)`：把 finding 按用例映射回它所在的单元，**只重开被 warn 点到的那些**（info 不重开，否则每批都会因为几条 `oracle-vague` 全员返工），并把门禁那几句话挂在单元上。
- `gateRun` 不通过时自动调它，返回里多一个 `repair: { reopened, round }`。
- `claimUnit` 再领到这个单元时，契约末尾多出一段 `REPAIR ROUND n`，逐条列出 `caseId · 规则 · 哪里不对`，并明确一句：**削弱断言不算修好**——判不了就降 tier 并在 `readiness.reason` 里说缺什么。
- 顺带把 F-8 补上：`MAX_UNIT_ATTEMPTS = 5`。到顶之后 `claimUnit` 不再无限发回，而是说「这几个单元试了 5 次还不行，得有人来看」。原来唯一的止损是 run 预算跑完，写测试时当场撞上过一次死循环。

三件事的状态很不一样，先把它们分清楚——混在一起谈是这一块一直没结论的原因。

### 15.1 基线：原来这条链路上根本没有

`baselines` / `perf_baselines` 两张表是给**旧 runs 路径**的逐步截图与性能基线用的，而工作流执行一行都不往里写。于是一次执行只能自己看自己：「35 条通过 29」这个数字说不出「哪几条变好了、哪几条坏了」。

**而且这个被测对象不该用截图基线**：价格每秒都在跳的实时交易页，逐步截图基线在它上面每次都红，那种基线一周之内就会被人关掉。

所以做的是**判决集基线**：哪几条通过。`server/src/executionBaseline.ts` 存一条「这条 run 的基线是哪次执行」，`GET .../executions/compare` 把当前执行和基线逐条比。

**关键是要能把「回归」和「抖」分开**，而这需要中间那几次执行：

| 判据 | 含义 |
|---|---|
| 判决翻转 0 次 | 仍绿 / 仍红 |
| 翻转 1 次 | **真变化**——修好了，或者回归了 |
| 翻转 ≥2 次 | **真抖** |

第一版的判据是「出现过不止一种判决就算抖」，用真数据一跑就露馅：12 条被判成「抖」的里面有 8 条其实是 `P→F→F→F→F` 这种「坏了一次然后稳住」——那是回归，不是运气。

拿这条 run 的五次执行（35 条用例）跑出来：

```
修好 5 · 回归 3 · 抖 4 · 仍绿 23 · 仍红 0
```

| | 用例 | 判决串 |
|---|---|---|
| 修好 | TC-MKT-02-1 / TC-TP-07-1 / TC-TP-11-1 | `F→P→P→P→P` |
| 修好 | TC-OL-03-3 | `F→F→P→P→P` |
| 修好 | TC-TP-03-3 | `F→F→F→F→P` |
| **回归** | TC-JRN-05-2 / TC-TP-08-1 | `P→F→F→F→F` |
| **回归** | TC-TP-01-1 | `P→P→P→P→F` |
| 抖 | TC-MKT-01-1 / TC-MKT-02-4 / TC-OL-03-1 | 翻转 2 次 |
| 抖 | TC-TP-02-1 | 翻转 3 次 |

这比之前那句「29–32，尾部在抖」精确得多，也更难看：**真正在抖的只有 4 条，另外 3 条是我自己改步骤时弄坏的回归**——`TC-JRN-05-2` 的步骤把它要断言的弹窗关掉了，`TC-TP-08-1` 撞上前一条用例留下的勾选状态。之前把它们一起算进「抖」，等于替自己开脱。

比较结果落在 `evidence/hl-round2-2026-09-11/executions/compare-vs-baseline.json`，界面上在运行页的执行区（`ExecutionCompare`），一行 P/F 串显示每条在各次执行里的判决。

### 15.2 记分板：不能手写，而这一轮没有可写的条目

`benchmark/<cap>/scoreboard.yaml` 由 `score_run` / `paired_eval` 追加，README 里写着「**不要手写**」，每条 entry 必须带完整 RunMeta，缺 skillVersion / promptsDigest / model / materialsHash 任一项拒收。

现状：

| 基准 | gold | 记分板条目 |
|---|---|---|
| casegen | 有（16 条，hash `2405209c3fe70ac7`） | 10 |
| binance-futures | 有 | 0 |
| hyperliquid-testnet | **没有**，只有 12 条机械导出的草稿 | 无此文件 |
| local-perp | **没有**，只有未冻结草稿 | 无此文件 |

**这一轮的被测对象（Hyperliquid 主网）没有 gold，所以一条记分板条目都不该有**——`score_run` 在没有 gold.json 时 fail-closed，这是刻意的。不能因为「这一轮跑了很多东西」就往记分板上写一条，那会造出一个没有尺子的分数。

打分机器本身是好的：`node scripts/replay.mjs` 对冻结运行重打分，**与 expected 逐位相同**——这一轮改了门禁、用例 schema 和执行器，这条是验证它们没把历史分数弄漂的那一条。

### 15.3 gold：一个真保护洞

`saveGold` 的冻结守卫读的是 README 里 `goldHash: <16 位>` 那一行。`benchmark/casegen` 把同一个哈希写成了另一种措辞：

```
## goldHash

gold.json  sha256 前 16 位：2405209c3fe70ac7
```

解不出来的后果不是显示不好看——`frozenHashOf` 返回 null，**冻结守卫整条失效**：一份 README、文档和十条记分板条目都当成已冻结的 gold，可以被 `POST /api/gold/casegen` 直接覆盖。而它正是红线里明确不许改的那类文件。

修在解析侧，不动 benchmark 任何文件：`## goldHash` 小节里孤立的 16 位十六进制串也算冻结标记（小节里的 64 位全串不会被误匹配）。四个基准现在读出来分别是——

```
binance-futures        （未冻结）
casegen                2405209c3fe70ac7
hyperliquid-testnet    （未冻结）
local-perp             （未冻结）
```

casegen 的 `frozenHash === currentHash`，守卫恢复；另外三个确实没冻结，仍然正确地拦在门外。

**没做也不该由我做的事**：`benchmark/hyperliquid-testnet/gold.json` 不存在，只有 12 条从 `materials/rules.md` 机械导出的草稿，文件里写着 `reviewed: false`、README 里写着「**不能打分**」。把它冻成 gold 需要人在 gold 屏逐条复核——`freezeGold` 还会往 README 写一行冻结戳。**那是一句「人复核过了」的断言，不能由我代签。** 界面入口是 `/api/gold/hyperliquid-testnet`，12 条草稿已经在那儿等着。

这也意味着：**这一轮两条臂的产物没有可对照的 gold**，两臂之间的对比只能用门禁分与产物画像（§7），不能说成「对着人工清单的覆盖率」。

### 16.3 gold：复核工作代做了，那一签没代

## 17. M 阶段：基线为什么「还是没有」

界面上那一页叫「运行 · 待审批基线」，它读的是 `pendingBaselines(projectId)` → `listRunsByProject` → **`runs` 表**。而工作流执行**从不往 `runs` 写一行**：`createRun` 只有旧的单用例路径在调。§15 做的执行判决集基线是另一套东西，挂在运行页上，所以那一页仍然是空的。

这是接线缺口，不是设计取舍。执行明明每步都截了图（`pngPaths`）、也量了分段墙钟（`phases` / `perfMetrics`），只差把它们接到基线上。

### 17.1 接上

- `processVisual` 从 `index.ts` 抽进 `server/src/visualBaseline.ts`——它不该知道调用者是谁。
- 新增 `server/src/workflowRunRecord.ts`：执行循环里每跑完一条用例就落一条 `origin: "workflow"` 的运行记录，顺带比视觉基线、比性能基线。**失败不带垮这次执行**——基线是附加物，不是判决。
- **基线按板上用例的 id 立**，不是按文本用例 id：板 id 从批准的那个修订派生，用例改一版就是新的一条、不继承上一版的截图。拿旧版截图给改过的用例当基线，第一次跑就会红得莫名其妙。

跑一次真执行（35 条）之后：

```
baselines 130 · runs 35 · perf_baselines 31
待审批视觉 0 · 待审批性能 0
```

首次全是 `new_baseline`、没有待决，这是对的——还没有可比的对象。

### 17.2 我之前那句话说得太满，实测把它改了

§15 我写过「实时行情页的截图基线每次都会红，一周内会被人关掉」，并以此为由没有接。第二次执行把这句话量出来了：

| 读数 | 值 |
|---|---|
| 可比步骤 | 130 |
| **逐像素相同** | **40（31%）** |
| 判为差异 | 90（69%） |
| 差异幅度 中位数 / 最小 / 最大 | **1.21% / 0.54% / 3.27%** |

**不是「整屏都红」，是 1–3% 的漂移**——价格区在动，页面其余部分是稳的，还有三成的步骤截图逐像素一样（账户面板那些不含价格的屏）。90 条待审批里没有一条是真回归。

真正的问题是 `VISUAL_THRESHOLD = 0.5` 写死在代码里，而那个数是给静态界面定的。

### 17.3 阈值跟着被测对象走

`visualThresholdPct` 落到**环境**上，和视口同一个理由：**它是被测对象的属性，不是全局口味**。调成全局会让静态应用跟着变迟钝；不给出口这一页就没法用。

接口只收 0–100 的数，且 `0` 有意义（逐像素必须相同），所以判空不能用真值判断。按实测最大漂移 3.27% 给这个被测对象配了 4%。

剩下一件同类的事，**记录未修**：待审批性能 31 条，用的是全局默认预算 `{ttfb 800, fcp 1800, dcl 3000, load 5000}`——那也是给轻量页面定的，一个实时交易页的 `load` 必然超。性能预算应该和视觉阈值一样按环境走，下一轮一起做。

## 19. 消融：整份写入 vs 单元循环（2026-09-11）

此前所有对比都是 loop 对 loop，**这个 loop 的核心主张一次都没被验证过**。这一节补上对照臂。

唯一的自变量是**规划器一次看到多少**：整份臂一次拿到全部 21 个功能、23 条规则、全部观察和全部 29 条故事；单元臂一次只拿一个单元的范围。材料、模型（`qwen3-8-27b`）、温度（0）、契约措辞全一样，**而且整份臂拿到了同样的反馈回路**：写出来不过 schema 就把逐条错误喂回去重写，最多三轮。不给它这个回路，比的就不是「拆没拆」，是「有没有人告诉它错了」。

脚本 `server/scripts/ablate-whole-vs-units.ts`，产物在 `evidence/hl-round2-2026-09-11/ablation/`。

### 19.1 结果

| | 整份臂 | 单元臂 |
|---|---|---|
| 调用次数 | 3（三轮修复） | 183 |
| 产出用例 | 69 → 72 → **28** | **82** |
| **过 schema** | **0 → 0 → 0** | **82 / 82** |
| 覆盖故事 | 29 / 29（原始对象） | 29 / 29 |
| 门禁分 | — | 0.939 |
| 墙钟 | 10.5 分钟 | 18 分钟 |
| 原始 token | 176,952 | 14,265,168 |
| 其中命中缓存 | — | 97% |

**整份臂三轮一条都没过**，而且第三轮在「修」的过程中把用例从 72 条掉到 28 条。

### 19.2 它错在哪里——比「失败」有意思得多

整份臂的产出**结构上是对的**：69 条覆盖全部 29 条故事，八个 v2 字段 69/69 全有，必填项全有，全部带判据。它只错在一个地方，而且每条都错：

```json
"design": { "technique": "state-transition", "transitionIds": ["T-OB-TO-TRADES"] }
```

少了 `stateModelRef` / `from` / `event` / `to`，另有 7 条把 `negative` 填进了 `technique`（那是场景不是方法）。**一个浅而均匀的错**，不是推理质量下降。

契约里这两条写得和单元臂一模一样。差别在于：**单元臂每写一个单元就被服务端当场拒一次、拿着 jsonPointer 重写**；整份臂哪怕给了三轮反馈，也是拿着 40 条错误去改 70 条用例——第三轮它干脆开始丢用例。

所以这个 loop 真正买到的不是「模型看得少所以想得清楚」，是**反馈粒度**：错在哪一条就只修哪一条，且修的时候手上只有那一条。

### 19.3 反过来，它也戳破了「上下文有界」这句话

单元材料的中位数是 8,156 字符（约 3k token），但 cases 节点 183 次调用的**实际输入**是：

```
第 1 次 33,617 · 第 10 次 62,872 · 第 100 次 114,655 · 最后一次 122,243
中位 78,058 · 最大 133,034 · 平均 77,354
```

**单元循环把交给规划器的材料压住了，但没压住 harness 实际发出去的 prompt**——agent 把整段对话历史一起重发，每领一个单元就长一截。到最后一个单元时，上下文是第一个单元的 3.6 倍。

救命的是缓存：14,265,168 个输入 token 里 **97% 命中缓存**，所以账没有跟着涨 57 倍。按整份臂实测单价折算，单元臂 cases 节点大约是整份臂三轮的两倍成本，不是两个数量级。

**这条要记住：「上下文有界」目前是由 prompt 缓存兜住的，不是由这个 loop 兜住的。** 换一个不缓存的端点，或者把单元数从 29 提到 300，这个设计会在 harness 那一层先垮。

### 19.4 限制

- **只跑了一个被测对象、一个模型、一轮。** 单元臂 n=1，整份臂 n=1（三轮修复）。结论的方向很硬（0 vs 82），幅度不硬。
- **两臂的 harness 不同**：单元臂跑在 Penguin agent 里、由服务端逐单元拒收；整份臂是我直接打模型、自己写的修复回路。契约文本一样，但「谁在拒」不一样。要做到完全同构，得让整份臂也跑在同一个 agent 里、只把服务端的拆分关掉。
- **没有做规模扫描**。这个被测对象只有 21 个功能。loop 的理由是上下文有界，而真正能证伪它的实验是把材料放到 3×、10× 看两臂的曲线——现在还不知道 29 个单元这个规模是不是已经过了拐点。

# 横向

## 1. 全流程

```mermaid
flowchart TD
  create["创建运行<br/>createWebWorkflow"] --> src{"来源"}
  src -- spec --> spec["上传材料"]
  src -- explore --> exp["领域引导探索<br/>product/model-candidate"]
  spec --> seal["冻结材料、封存 inputHash<br/>(startRun 里)"]
  exp --> seal
  seal --> modules["modules：模型提议模块树<br/>服务端机检"]
  modules --> freeze{{"👤 人冻结模块树"}}
  freeze --> ins["instructions：下发冻结的 skill、runScope、门禁策略"]
  ins --> ret["retrieve：检索材料块"]

  fin --> review{{"👤 人复核：批准 / 驳回 / 修改"}}
```

人把关的只有三处：**冻结模块树、复核用例、决定回归候选**。服务端对这三处都要求操作者是人（`actor.kind === "human"`），但「人」的判定方式是「请求不带 `Authorization` 头」，见 §10-1。

## 3. 运行状态机（`wf_runs.status`）

```mermaid
stateDiagram-v2
  [*] --> registered: createWebWorkflow
  registered --> running: beginStage(source…finalize)
  registered --> paused: 命中断点
  running --> paused: 命中断点
  running --> failed: source 抛错 / 宿主退出且未定稿、无人等待
  running --> waiting_review: 宿主退出时 modules 在等人冻结
  running --> waiting_review: finalize 成功
  running --> interrupted: API 服务重启
  paused --> registered: resume
  failed --> registered: resume
  interrupted --> registered: resume
  waiting_review --> registered: resume（未定稿时）
  waiting_review --> executing: 开始执行
  executing --> completed: 全部通过
  executing --> waiting_review: 有 failed / unobservable
  executing --> infra_error
  executing --> budget_exhausted
  executing --> interrupted: API 服务重启
  infra_error --> waiting_review: resume（已定稿）
  budget_exhausted --> waiting_review: resume（已定稿）
  interrupted --> waiting_review: resume（已定稿）
  completed --> executing: 再次执行
  waiting_review --> cancelled: cancel
  running --> cancelled: cancel
  executing --> cancelled: cancel
  cancelled --> registered: resume
```

要点：

- **写入点**：`registered` 由 `runLedger.ts::register` 写；`running` 由 `workflowControls.ts::beginStage` 写，只对 source 到 finalize 这六个节点生效，modules、g2、execution 不改运行状态；`waiting_review` 由 `runStages.ts::finalizeRun` 写；执行阶段的状态都由 `workflowExecution.ts::phase` 写，映射是 running→`executing`、passed→`completed`、failed/unobservable→`waiting_review`，其余原样写入；`interrupted` 在服务启动时由 `graphs.ts::reconcileOrphanedRuns`（规划）和 `recoverWorkflowExecutions`（执行）写；`blocked` 表示启动时账本完整性校验没过。
- **宿主进程退出后怎么判**：`penguinRun.ts::finish`。已定稿记为 `waiting_review`；有节点处于 `waiting_review`（通常是 modules 在等人冻结）也记为 `waiting_review`；其余记为 `failed`。Claude Code 的退出码不参与判定（`claudecode.ts` 只记 `exited`），见 §10-3。
- **复核不改变运行状态**，只改 `review` 节点。g2 也不看 review 节点，只看每条用例有没有批准记录。
- **重启后**：只有 `runtime === "penguin"` 的运行会被自动接回（`penguinRun.ts::reconcilePenguinRuns`），Claude Code 运行会一直停在 `interrupted`，要人点「继续运行」。

### 3.1 节点状态

`workflow_node_states` 每个 `(runId, node)` 只留一行，`(attempt, sequence)` 更大的事件覆盖旧的（`runLedger.ts::appendEvent`）。实际上 `attempt` 恒为 0，重试靠 `sequence` 递增来覆盖。`queued` 这个取值在服务端没有写入点。

| 节点 | 可能的 phase |
|---|---|
| source | running → done / failed |
| modules | running → blocked（机检 error）/ waiting_review（提议通过）→ done（人冻结） |
| instructions、stories、cases | running → done |
| gate | running → done / blocked（未通过） |
| finalize | running → waiting_review |
| review | waiting_review → done（全部有决定） |
| g2 | running → done（`ready_to_execute`）/ blocked |
| execution | running → done（passed）/ cancelled / failed（其余情况） |
| 任意受控节点 | blocked，消息为 `Breakpoint: paused before execution` |

## 4. 暂停、断点、续跑、取消

- **断点**：`POST /:runId/controls`，只有人能设，只能设在还没跑过的节点上（否则 409 `breakpoint_requires_untouched_node`）。受控节点共九个，定义在 `workflowControls.ts:9`，`review` 不在其中。规划器下次 `begin_stage` 撞上断点时，节点记为 blocked，运行改为 `paused`，工具返回 `{status:"paused"}`，任务话术要求规划器看到后立即停止。
- **预算**：账本路径的预算不在 controls 里。规划预算见 `penguinRun.ts` 的 `unitRunBudget`，执行预算见 `workflowExecution.ts` 的 `caseRunBudget`（`runBudget.ts`）。`PATCH …/budget` 只属于 §4.2 的图系统。
- **续跑** `workflowOps.ts::resumeProjectWorkflow`：
  - 输入还没封存（source 没走完）：只允许从 failed、cancelled、paused、interrupted 续跑，续跑时重新执行 `launchSource`。
  - 已定稿：直接改回 `waiting_review`。前端在执行按钮前会自动先调一次 resume（`ExecutionControls.tsx`）。
  - 其余情况：清除断点，状态改为 `registered`，然后 `startWebRun({resumeStage: pausedAt ?? checkpoint.next})`，用同一个工作区、同一个令牌起新的宿主会话。
  - `checkpoint.next`（`workflowCheckpoint`）是第一个没做完的阶段。source 和 modules 只在「走过但没走完」时才会被选中；g2 和 execution 不参与检查点。
  - 以下状态续跑会报 409 `workflow_not_resumable`：registered、running、executing、completed、blocked。
- **取消** `cancelProjectWorkflow`：依次停掉规划进程（Claude Code 子进程收到 SIGTERM），把执行中的批次标为 cancelled，abort 对应的 controller，并通知所有 runner 取消，最后把运行改为 `cancelled`。没有「只取消执行」的路由。

### 4.1 门禁打回

`gateRun` 没过时，`workUnits.ts::reopenUnitsFromGate` 找出带 `caseId` 的 warn 级 finding，把对应的 cases 单元重置为 `pending`（`repair.round + 1`，`attempt` 达到 5 的单元不再重开）。规划器下次 `claim_unit` 时会拿到 `repairBrief`，重写、合并之后要重新 `begin_stage gate`。如果用例改了而门禁没重跑，finalize 会报 `gate_stale_rerun_required`。

### 4.2 另一套图执行系统 `/api/wf/runs`

这是 v1/v2 时代的 DAG 运行时（`harness-core/src/graph/runtime.ts::runGraph`），跑在 `apps/agent` 子进程里，网关代码在 `server/src/graphs.ts`。它**还没退役**：

- `TP_RUNTIME=graph` 是回滚开关（`index.ts:241`）。默认情况下，`POST /api/wf/runs` 走的也是宿主运行时。
- 配对评测（`evals.ts::runArm`）、节点重跑、`CodeLine` 的 repair、`ProductMap` 的 spec 视图、命令面板与 Evals 页的运行列表，仍然直接用它。
- **它和主流程共用 `wf_runs` 表与事件总线**：`wf.run.finished` 的订阅会用 payload 里的状态覆盖任何运行；`reconcileOrphanedRuns` 会把账本运行也改成 `interrupted`。改这两处时，两边要一起看。
- `src/pages/Workspace.tsx`（旧画布）和 `src/pages/Artifacts.tsx` 没有被任何文件 import，是死代码。

逐步说明与代码位置：

1. **表单**：`src/components/workbench/NewRunForm.tsx`，其中「工作单元」默认勾选（见 §10-2）。表单内容不变时复用同一个 `idempotencyKey`。
2. **`createWebWorkflow`**（`workflowOps.ts:30-107`）按顺序做这些事：
   1. 探索地址先过禁止名单（`explore_host_denied`）。
   2. 检查材料：重名、总大小、spec 至少一份。
   3. 校验规则包，用 `bindRulePack` 绑定。
   4. 如果导入了产品模型，检查它和规则包是否对得上。
   5. 检查开了工作单元的运行是否带产品模型：spec 来源又没有导入产品模型时，报 `work_units_require_product_model`（`workflowOps.ts:62`）。
   6. 用 `workflow_start_requests` 表做幂等：同一个键、内容不同时报 409 `workflow_start_conflict`。
   7. 确定规划运行时：Web 只接受 `claude-code` 和 `penguin`；本机找不到对应命令时报 `planner_runtime_unavailable`。
   8. `captureHostWebModels` 写执行模型快照。
   9. 上传文件落到 `.data/uploads/<runId>/`。
   10. `registerWebRun`。
   11. 异步调用 `launchSource`，接口立即返回 202。
3. **source**（`launchSource`）：spec 来源直接用材料；explore 来源走 `observeProduct`，中途失败时把已经采到的屏写成 `report/exploration-partial`。这里抛错会把 source 记为 failed、运行记为 `failed`（`workflowOps.ts:203`）。
4. **起宿主**（`penguinRun.ts::startRun` → `claudecode.ts::startRun`）：
   - 先冻结材料并封存 `inputHash`。这一步发生在这里，不在创建时。
   - 写运行令牌：主库只存哈希；明文写到 `.data/private-run-grants/<runId>.json`（权限 0600），`.mcp.json` 里只放环境变量 `TP_RUN_GRANT_FILE` 指向这个文件，**令牌本身不在 `.mcp.json` 里**。
   - 命令是 `claude -p … --output-format stream-json --verbose --permission-mode acceptEdits --allowedTools mcp__testpilot__* Read Write Edit "Bash(node *)" --mcp-config … --plugin-dir plugins/testpilot-claude`。
   - 任务话术来自 `runtime/skill-launch.ts`。
5. **阶段调用**：MCP 的阶段工具经 `run-gateway.ts` 转发，带 Bearer 令牌。服务端 `authorizeRun` 校验令牌：缺失返回 401 `run_credential_required`，不对返回 403 `run_credential_invalid`。然后 `requireStageStarted` 检查阶段是否已开始：运行被暂停、取消或中断时报 `run_requires_explicit_resume`，没调 `begin_stage` 时报 `begin_stage_required`。
6. **hooks**：`PreToolUse` 只拦 `Write|Edit|MultiEdit`，不拦 MCP 阶段工具，所以在 skill 模式下基本不触发。拦下的记录写到 `holds.jsonl`，不进账本。`Stop` hook（require-gate）会查 `stages/status`，最多提醒 3 次。
7. **结束**：`penguin.ts` 的看门狗在进程退出、超时（默认 60 分钟）或会话消失时回调 `finish`，状态按 §3 的规则确定。

- **授权**：g2 和 execute 在请求**不带** `Authorization` 头时按本地操作员处理；**带**头时按运行令牌校验。所以宿主拿着运行令牌也能编译和执行。
- **g2**（`approvedRuns.ts::generateApprovedCode`）：
  - 基址取法：运行的 `sourceUrl`，其次运行的 `targetUrl`，最后项目的 `targetUrl`。
  - 每一步变成 `aiAction`；以 `waitFor:` 开头的步骤变成 `aiWaitFor`；没有判据时追加 `aiAssert(expected)`。
  - 内容相同就幂等返回已有修订。
  - handler 抛错时不会写 failed 事件，g2 节点会一直停在 `running`（§10-6）。
- **执行时跑的是用例里的自然语言步骤**，不是 g2 编出来的代码字符串。g2 代码只用于代码门禁和身份比对：重编的结果必须和当初的一致。
- **执行前的检查顺序**（`workflowExecution.ts::startWorkflowExecution`）：
  1. 幂等检查；
  2. 重编比对：代码门禁没过报 `execution_blocked_by_code_gate`，重编结果不一致报 `execution_recompiles_differently`；
  3. `caseIds` 是否都在产物里；
  4. 运行是否处于 cancelled 或 interrupted；
  5. 是否已有进行中的执行；
  6. 环境是否存在；
  7. 基址取法：环境 `baseUrl`，其次运行的 `sourceUrl`，再次运行的 `targetUrl`，最后项目的 `targetUrl`；
  8. 占位符是否都能解析；
  9. 守卫。
- **每条用例的执行**：
  - 每条都用一个新浏览器（不传 `sessionKey`）。执行前如果环境配置了 `TP_RESET_CMD`，先跑它（超时 60 秒）。
  - 前提里写明「未登录」时不带登录态（`caseStartsLoggedOut`）。
  - 只有基础设施类失败且可重试时才退避重试，最多 3 次，间隔 8、16、32 秒。可重试的码有 `MODEL_UNAVAILABLE`、`EXEC_ENV`、`EXEC_TIMEOUT`。
- **批次状态**：预算耗尽记为 `budget_exhausted`，基础设施失败（重试用尽后）记为 `infra_error`，这两种都会立即中止批次；其余用例累积成 `failed` 或 `unobservable`。选中但没跑到的用例补记为 `NOT_RUN`。
- **runner 内部**（`packages/harness-testing/src/exec/run.ts::executeRun`）：
  - 顺序是：登录、`settleOn` 等待页面就绪、步骤执行前取一次快照、逐步执行 `act`（每步后截图，并检查挂在这一步之后的 `afterStep` 断言），然后求值判据、执行 `postSteps`、采集性能。
  - 判据有三类：机器判据用 `evaluateOracle`；judge 判据用 `sampleJudge` 加 `aggregateJudge`；没有判据时用 `aiAssert`。
  - 失败按 `failure.ts::classifyFailure` 归类。
- **执行记录**（`workflowRunRecord.ts`）：写主库 `runs`，比较或建立性能基线和视觉基线，按时间窗口把 Midscene 报告复制到 `artifacts/reports/<runRecordId>.html`。这一步出错不影响执行本身。

## 10. 已知缺口（2026-09-17 核对）

这些问题都是读代码时发现的，**都还没修**。前两条影响「人把关」这条红线，建议优先处理。

1. **规划器能绕过人工关口**：规划会话的 MCP 进程无条件注册了宿主工具（`testpilot-mcp/src/server.ts` 里的 `registerHostDomains`），`--allowedTools mcp__testpilot__*` 也放行了它们。其中 `tp_stage.freeze_modules`、`tp_review.decide`、`tp_review.decide_candidate` 这几个工具没有 `needsRunGrant`，发请求时不带 `Authorization` 头，服务端就当成 `local-operator`。目前拦着的只有工具说明里的「人点头了再调」。可选的修法：规划会话不注册宿主工具；或者让这几个工具在有运行令牌的进程里直接拒绝。
2. **Web 用 spec 来源新建运行会被拒**：`NewRunForm` 默认勾选工作单元，而 `createWebWorkflow` 要求开了工作单元的 spec 运行必须导入产品模型（`workflowOps.ts:62`），表单又没有导入入口，所以用户不取消勾选就会收到 400 `work_units_require_product_model`。
3. **规划器干净停在半路也会被记成 `failed`**：对已登记的运行，看门狗在没定稿时只会回调 `failed`，`finish` 里给 `paused` 留的分支走不到。
4. **Claude Code 运行在重启后不会被接回**：会一直停在 `interrupted`。
5. **g2 路由不拦 `interrupted`**：路由只对 paused、cancelled、failed 短路，所以 interrupted 状态下 g2 仍会编译并写入节点状态；execute 由 `workflowExecution.ts` 拦下。
6. **g2 抛错后节点一直停在 `running`**：出错时没有写 failed 事件。
7. **从 `WorkflowRuns` 页驳回不带理由**：这个页面提交复核时不传 `note`，所以从这里驳回永远不会产生反例候选。只有 `ProjectReview` 可以写理由。
8. **有 GET 带写副作用**：`GET /review` 会写 `review/case/*`；`GET executions/detail` 会复制报告文件并写 `runs.reportPath`。
9. **执行前重编过多**：每次执行至少重编 3 次，另外每条用例 2 次。结果之所以不变，是靠「内容相同就幂等返回」撑着的。
10. **真实错误被吞掉**：`ProfileStoreError`、密钥解密失败这类非 `LedgerError` 的异常，会被统一压成 400 `run_request_invalid`，前端看不到真实原因。
11. **图系统与账本相互覆盖状态**：`wf.run.finished` 的订阅会覆盖任何运行的状态（§4.2）。
12. **规划预算没有传给 Claude Code**：`claudecode.ts` 不接收预算参数，所以 Claude Code 规划只受看门狗的超时（默认 60 分钟）约束。宿主进程失败时，失败一律记在 source 节点上。
13. **`saveRun` 会覆盖登记信息**：它整体替换 `wf_runs.json`，`register()` 写进去的 `principal`、`template`、`parentRunId` 会丢失。功能上没受影响，因为界面改从登记表读这些字段。
14. **门禁打回后续跑能否写完用例，代码里确定不了**：打回后 cases 节点仍是 `done`，`checkpoint.next` 会指向 `gate`，重开的用例单元要靠规划器自己去领，这一点代码里确定不了，需要实测。


人把关的固定三处：**冻结模块树、复核用例、决定回归候选**。另有一处**视情况出现**：故事里带 `requirementDraft`（候选业务预期，例如引用的规则是未确认假设，`storyReview.ts::markCandidateStories`）时，用例设计前要人在故事节点批准或驳回（`storyReview.ts::approveStoryRequirements` / `rejectStoryRequirements`，驳回同样要 ≥4 字理由）；没有候选就不停。服务端对这几处都要求操作者是人（`actor.kind === "human"`），「人」的判定方式是「请求不带 `Authorization` 头、也不带 `x-testpilot-actor` 头」（`reviewPrincipal.ts`），见 §10-1。

## 3. 运行状态机（`wf_runs.status`）

```mermaid
stateDiagram-v2
  [*] --> registered: createWebWorkflow
  registered --> running: beginStage(source…finalize)
  registered --> paused: 命中断点
  registered --> failed: launchSource 抛错
  running --> paused: 命中断点
  running --> failed: source 抛错 / 宿主退出且未定稿、无人等待
  running --> waiting_review: 宿主退出时 modules 在等人冻结
  running --> waiting_review: 候选故事待审（pauseForStoryReview）
  running --> waiting_review: finalize 成功
  running --> interrupted: API 服务重启
  waiting_review --> paused: 批准候选故事
  paused --> registered: resume
  failed --> registered: resume
  interrupted --> registered: resume
  waiting_review --> registered: resume（未定稿时）
  waiting_review --> running: 执行准备开始
  running --> waiting_review: 执行准备结束
  running --> interrupted: 执行准备停止 / 宿主退出续起用尽 / 服务重启
  waiting_review --> executing: 开始执行
  executing --> completed: 全部通过
  executing --> waiting_review: 有 failed / unobservable
  executing --> infra_error
  executing --> budget_exhausted
  executing --> interrupted: API 服务重启
  infra_error --> waiting_review: resume（已定稿）
  budget_exhausted --> waiting_review: resume（已定稿）
  interrupted --> waiting_review: resume（已定稿）
  completed --> executing: 再次执行
  waiting_review --> cancelled: cancel
  running --> cancelled: cancel
  executing --> cancelled: cancel
  cancelled --> registered: resume
```

要点：

- **写入点**：`registered` 由 `runLedger.ts::register` 写；`running` 由 `workflowControls.ts::beginStage` 写，只对 source、instructions、stories、cases、gate、finalize 这六个节点生效，modules、g2、execution 不改运行状态；`beginStage` 见运行处于 paused/cancelled/failed/interrupted 时直接返回原状态、不写事件；`waiting_review` 由 `runStages.ts::finalizeRun`、`storyReview.ts::pauseForStoryReview`（候选故事待审）和 `preparation.ts` 的批次收尾写；批准候选故事时 `approveStoryRequirements` 把运行改成 `paused`，等人点「继续运行」；执行准备 `startPreparation` 把运行改成 `running`，`cancelPreparation` 与 `recoverPreparations` 改成 `interrupted`；执行阶段的状态都由 `workflowExecution.ts::phase` 写，映射是 running→`executing`、passed→`completed`、failed/unobservable→`waiting_review`，其余原样写入；`interrupted` 在服务启动时由 `graphs.ts::reconcileOrphanedRuns`（规划）、`recoverWorkflowExecutions`（执行）和 `recoverPreparations`（准备）写；`blocked` 表示启动时账本完整性校验没过（`runService.ts::recoverRunProjections`）。
- **宿主进程退出后怎么判**：`penguinRun.ts::finish`。运行已是 paused/cancelled 就保持；已定稿记为 `waiting_review`；有节点处于 `waiting_review`（modules 在等人冻结，或 stories 在等人审候选故事）也记为 `waiting_review`；其余看看门狗的回调，`failed` 记 `failed`，`done` 记 `paused`。收尾时把仍挂在 running/queued 的节点改成 blocked（等人）或 failed。Claude Code 的退出码不参与判定（`claudecode.ts` 只记 `exited`，额度被拒时记下 `stopReason`），见 §10-3。
- **复核不改变运行状态**，只改 `review` 节点。g2 与执行准备也不看 review 节点，只看每条用例有没有批准记录。
- **重启后**：只有 `runtime === "penguin"` 的运行会被自动接回（`penguinRun.ts::reconcilePenguinRuns`），Claude Code / Codex 运行会一直停在 `interrupted`，要人点「继续运行」。

### 3.1 节点状态

`workflow_node_states` 每个 `(runId, node)` 只留一行，`(attempt, sequence)` 更大的事件覆盖旧的（`runLedger.ts::appendEvent`）。实际上 `attempt` 恒为 0，重试靠 `sequence` 递增来覆盖。`queued` 由续跑（`resumeProjectWorkflow`，消息 `Continuation requested…`）与从节点重跑（`rerunProjectNode`）写。

| 节点 | 可能的 phase |
|---|---|
| source | queued → running → done / failed |
| modules | running → blocked（机检 error）/ waiting_review（提议通过）→ done（人冻结） |
| instructions、cases | running → done |
| stories | running → done；有候选业务预期时 waiting_review → done（人批准；驳回仍停在 waiting_review） |
| cases、gate、finalize、g2、execution | 候选故事待审时，挂着的 queued/running 会被改成 blocked（`pauseForStoryReview`） |
| gate | running → done / blocked（未通过） |
| finalize | running → waiting_review |
| review | waiting_review → done（全部有决定） |
| g2 | 执行准备：running（逐条进度消息）→ done（全部验证）/ blocked（部分完成）/ cancelled（停止）；旧路 `stages/g2`：running → done（`ready_to_execute`）/ blocked（未过或抛错） |
| execution | running → done（passed）/ cancelled / failed（其余情况） |
| 任意受控节点 | blocked，消息为 `Breakpoint: paused before execution` |

## 4. 暂停、断点、续跑、取消

- **断点**：`POST /:runId/controls`，只有人能设，只能设在还没跑过的节点上（否则 409 `breakpoint_requires_untouched_node`）。受控节点共九个，是 `workflowControls.ts` 顶部的 `nodes`，`review` 不在其中。规划器下次 `begin_stage` 撞上断点时，节点记为 blocked，运行改为 `paused`，工具返回 `{status:"paused"}`，任务话术要求规划器看到后立即停止。
- **`begin_stage` 的另外两种 paused**：模块树提议了但没冻结时，stories 往后的节点返回 `{status:"paused", code:"module_plan_requires_human_freeze"}`；候选故事待审时，cases 往后的节点返回 `code:"story_requirements_need_review"` 并把运行改为 `waiting_review`。这两种都不写断点。
- **预算**：账本路径的预算不在 controls 里。规划预算见 `penguinRun.ts` 的 `unitRunBudget`，执行预算见 `workflowExecution.ts` 的 `caseRunBudget`（`runBudget.ts`）。`PATCH …/budget` 只属于 §4.2 的图系统。
- **续跑** `workflowOps.ts::resumeProjectWorkflow`（`POST /:runId/resume`，body 可带 `mode:"next-node"`，只跑下一个节点就停，由 `configureNextNode` 补断点实现）：
  - 输入还没封存（source 没走完）：只允许从 failed、cancelled、paused、interrupted 续跑，续跑时重新执行 `launchSource`。
  - 候选故事还在待审：`storyReview.ts::guardStoryResume` 先拦（宿主还在跑报 `host_still_running`，否则重新停到待审并报 `story_requirements_need_review`）；从节点重跑出来的运行若故事与业务输入没变，沿用父运行的批准。
  - 已定稿：状态是 paused、cancelled、interrupted、failed、infra_error、budget_exhausted 之一时直接改回 `waiting_review`。前端在执行准备与执行按钮前，见这几种状态会自动先调一次 resume（`ExecutionControls.tsx`）。
  - 宿主自己登记（不是 Web 发起）的运行：只把状态改回 `registered`，返回 `continuation: "continue_in_original_host"`，要回原宿主接着做。
  - 其余情况：清除断点，节点记 queued，状态改为 `registered`，然后 `startWebRun({resumeStage: pausedAt ?? checkpoint.next})`，用同一个工作区、同一个令牌起新的宿主会话。
  - `checkpoint.next`（`workflowCheckpoint`）是第一个没做完的阶段。source 和 modules 只在「走过但没走完」时才会被选中；g2 和 execution 不参与检查点。
  - 以下状态续跑会报 409 `workflow_not_resumable`：registered、running、executing、completed、blocked，以及已定稿的 waiting_review。
- **从节点重跑** `rerunProjectNode`（`POST /:runId/rerun`，node 取 source/modules/stories/cases/gate）：不改原运行，另建一个新运行，复制上游产物与回执、只跑这一个节点（同样靠 `configureNextNode`）。只对 Web 发起、当前没在跑、上游都 done 的运行可用；body 可带 `planner` 换规划宿主。故事被驳回过时，驳回理由作为 `knowledge/story-review-feedback.md` 带进新运行。
- **取消** `cancelProjectWorkflow`：先把运行改为 `cancelled`，再依次停掉执行准备、探索会话、规划进程（Claude Code / Codex 子进程收到 SIGTERM，Penguin 与探索规划器各自取消），把执行中的批次标为 cancelled、abort 对应的 controller 并通知 runner 取消，最后再写一次 `cancelled`。没有「只取消执行」或「只停执行准备」的路由；执行准备在宿主续起用尽、额度重置晚于预算截止、预算耗尽时由自己的看守定时器调 `cancelPreparation`，运行记 `interrupted`。

### 4.1 门禁打回

`gateRun` 没过时，`workUnits.ts::reopenUnitsFromGate` 找出带 `caseId` 的 warn 级 finding，把对应的 cases 单元重置为 `pending`（`repair.round + 1`，`attempt` 达到 5 的单元不再重开）。规划器下次 `claim_unit` 时会拿到 `repairBrief`，重写、合并之后要重新 `begin_stage gate`。如果用例改了而门禁没重跑，finalize 会报 `gate_stale_rerun_required`。

### 4.2 另一套图执行系统 `/api/wf/runs`

这是 v1/v2 时代的 DAG 运行时（`harness-core/src/graph/runtime.ts::runGraph`），跑在 `apps/agent` 子进程里，网关代码在 `server/src/graphs.ts`。它**还没退役**：

逐步说明与代码位置：

1. **表单**：`src/components/workbench/NewRunForm.tsx`，其中「工作单元」默认勾选（见 §10-2）。表单固定发 `planner:'connected'`，由服务端取项目选定的宿主；宿主没就绪（`PlannerHost` 的 `onReady` 为假）时「开始」按钮不起作用。第一次提交只建运行计划（`projectRunPlans.ts::createProjectRunPlan`）并显示预览，内容不变再提交一次才真正开跑。
2. **规划宿主**（`plannerHost.ts`）：`probeHost` 用 `claude auth status --json` / `codex login status` 探登录态（超时 8 秒）；`hostStatus` 在项目没选过、且只有一个已登录宿主时自动选它，两个都登录时要人选一次（`POST /api/projects/:id/planner-host`，存 `project_planner_hosts`）；`requireHost` 没选中报 409 `planner_host_selection_required`，选中的没登录报 `planner_host_not_ready`。Penguin 不在这个选择器里，只有 API 调用方显式传 `planner:"penguin"` 才用。
3. **`createWebWorkflow`**（`workflowOps.ts`，由 `POST …/assets/plans/:id/start` 以计划里存的配置调用；`projectPlanInputs` 发现项目配置变了会报 `project_configuration_changed_replan`）按顺序做这些事：
   1. 探索地址先过禁止名单（`explore_host_denied`）。
   2. 检查材料：重名、总大小、只收 `.md`/`.txt`、spec 至少一份。
   3. 取知识库里选中的领域知识与规则包（不选就用项目当前那一份），校验规则包。
   4. 如果导入了产品模型，检查它和规则包是否对得上。
   5. 检查开了工作单元的运行是否带产品模型：spec 来源又没有导入产品模型时，报 `work_units_require_product_model`。
   6. 用 `workflow_start_requests` 表做幂等：同一个键、内容不同时报 409 `workflow_start_conflict`。
   7. 确定规划运行时：`connected` 走 `requireHost`，否则用请求里的 `planner` 或 `TP_AGENT_RUNTIME`（不设为 `claude-code`）；只接受 `claude-code`、`codex`、`penguin`，本机 `--version` 跑不起来时报 `planner_runtime_unavailable:<runtime>`。
   8. `captureHostWebModels`（Penguin 用 `captureWebModels`）写执行模型快照。
   9. 上传文件落到 `.data/uploads/<runId>/`。
   10. `registerWebRun`，写 `knowledge/*`，`bindRulePack`，`bindDomainReference`（项目当前的领域参考冻结绑定进运行）。
   11. 异步调用 `launchSource`，接口立即返回 `{wfRunId}`（计划路由 200；直接 `POST /workflow-runs` 为 202）。
4. **source**（`launchSource`）：spec 来源直接用材料；explore 来源走 `observeProduct`，中途失败时把已经采到的屏写成 `report/exploration-partial`。这里抛错会把 source 记为 failed、运行记为 `failed`（`launchSource` 末尾的 catch）。
5. **起宿主**（`penguinRun.ts::startRun` → `claudecode.ts::startRun` 或 `codex.ts::startRun`）：
   - 先冻结材料并封存 `inputHash`（`runService.ts::freezeRunMaterials`）。这一步发生在这里，不在创建时。
   - 写运行令牌（`runtime/skill-launch.ts::prepareSkillLaunch`）：主库存哈希和加密后的令牌；明文写到 `.data/private-run-grants/<runId>.json`（权限 0600），`.mcp.json` 里只放环境变量 `TP_RUN_GRANT_FILE` 指向这个文件，**令牌本身不在 `.mcp.json` 里**。
   - Claude Code 命令是 `claude -p … --output-format stream-json --verbose --permission-mode acceptEdits --allowedTools mcp__testpilot__* Read Write Edit "Bash(node *)" --mcp-config … --plugin-dir plugins/testpilot-claude`（`claudecode.ts::claudeArgs`；插件目录没生成就不带 `--plugin-dir`）。子进程环境带上 `hostActorEnv`，见 §10-1。
   - 任务话术来自 `runtime/skill-launch.ts`。
6. **阶段调用**：MCP 的阶段工具经 `run-gateway.ts` 转发，带 Bearer 令牌。服务端 `authorizeRun` 校验令牌：缺失返回 401 `run_credential_required`，不对返回 403 `run_credential_invalid`。然后 `requireStageStarted` 检查：cases 往后的节点先要求候选故事已审（`story_requirements_need_review`）；运行被暂停、取消或中断时报 `run_requires_explicit_resume`；模块树未冻结时 stories 往后报 `module_plan_requires_human_freeze`；Web 发起的运行（`stageControlVersion: 1`）没调 `begin_stage` 时报 `begin_stage_required`。
7. **hooks**：`PreToolUse` 只拦 `Write|Edit|MultiEdit`，不拦 MCP 阶段工具，所以在 skill 模式下基本不触发。拦下的记录写到 `holds.jsonl`，不进账本。`Stop` hook（require-gate）会查 `stages/status`，最多提醒 3 次（`MAX_NUDGES`）。
8. **结束**：`penguin.ts::watchRun` 的看门狗在进程退出、超时（默认 60 分钟）或会话消失时回调 `finish`，状态按 §3 的规则确定。宿主额度被拒（stream 里的 `rate_limit_event`）时，停止原因写成一句人话并记下重置时刻（`claudecode.ts::hostStopReasonOf`）。

### 6.2 候选故事审核（视情况出现）

故事写完、合并成 `validated/stories` 之后，如果有故事带 `requirementDraft`（引用的规则是未确认假设，或整个规则包都是假设，`storyReview.ts::markCandidateStories`），运行在用例设计之前停下：

- 规划器下一次 `begin_stage(cases…)` 拿到 `{status:"paused", code:"story_requirements_need_review"}`，`pauseForStoryReview` 把 stories 节点记 `waiting_review`、运行记 `waiting_review`；直接调阶段工具报 409 `story_requirements_need_review`。
- 人在故事节点的审核卡片（`StoryRequirementsReview.tsx`）上看候选业务预期与问题：批准写 `review/story-requirements`，stories 节点 done，运行改为 `paused`，再点「继续运行」；驳回要写 ≥4 字理由（`rejection_requires_reason`），写 `review/story-requirements-rejected`，故事仍待审——要改故事就从故事节点重跑，理由会带进新运行。
- 宿主还在跑时两个动作都报 `host_still_running`；故事版本变了报 `story_revision_changed`。
- 路由：`GET …/:runId/story-requirements`、`POST …/story-requirements/approve`、`POST …/story-requirements/reject`，都要求人（`reviewerPrincipal`）。宿主工具里没有这两个动作。

```mermaid
sequenceDiagram
  autonumber
  actor U as 用户
  participant W as Web（ProjectReview / WorkflowRuns）
```

- **每条结果单独判定**：提交的 revision 已不是当前头版时，该条返回 `status:"conflict"`，**HTTP 仍是 200**，前端提示「部分冲突」。决定与已有的相同时返回 `unchanged`。
- **投递**（`decisionDelivery.ts`）：
  - 用例板上的 id 为 `tc-rev-<sha256(revisionId)[:24]>`。
  - 如果某条 outbox 事件已经不是这条用例的当前批准，跳过，避免旧决定覆盖新决定。
  - 投递失败只让 `attempts` 加一，不抛错。启动时会补投一次，之后每 5 秒重试。
  - 注意：一次 POST 会投递**全局**所有没投递的 outbox 行，不只是本次运行的。
- **驳回必须写理由**：一批里只要有 `rejected`，`note` 去掉首尾空白后不足 4 个字就报 400 `rejection_requires_reason`（`approvedRuns.ts::decideRevisions`）。理由是反例候选的唯一来源——`proposeFromRejections` 也用同一个 4 个字的门槛。批准不受影响。
- **修改**：`reviseReviewedCase` 不允许改 `id` 或 `storyId`（`review_case_identity_frozen`）。版本链冲突时报 `review_revision_conflict`。把 `readiness.execution` 改成 `ready` 而用例还有执行阻碍时报 `execution_not_ready`。
- **准入**：`GET /review` 的每条用例带 `admission`（`preparationAdmission.ts::admissionIssues`）：readiness 标了不可执行、未绑定的环境变量、生命周期问题、门禁里 `setting-undeclared` / `step-compound` 两条 warn——这些对着用例正文与环境就能判「准备不出来」，执行准备会直接把它们记 blocked，不开浏览器。
- **历史**：`GET …/review-history`。

- **授权**：g2 和 execute 在请求**不带** `Authorization` 头时按本地操作员处理；**带**头时按运行令牌校验。所以宿主拿着运行令牌也能编译和执行。执行准备的起批次（`preparation/start`）只认人，逐条推进（`preparation/step`）只认运行令牌。
- **g2 旧路**（`approvedRuns.ts::generateApprovedCode`）：
  - 基址取法：运行的 `sourceUrl`，其次运行的 `targetUrl`，最后项目的 `targetUrl`。
  - 选中的用例有执行阻碍（`executionBlockers`）时报 `execution_not_ready`。
  - 每一步变成 `aiAction`；以 `waitFor:` 开头的步骤变成 `aiWaitFor`；没有判据时追加 `aiAssert(expected)`。
  - 内容相同就幂等返回已有修订；每次另写一份 `compilation-observation/*` 计时回执。
  - handler 抛错时路由会把 g2 节点记 blocked（消息是错误码，非 `LedgerError` 时是 `preparation_failed`），不再停在 running。
- **执行时跑的是用例里的自然语言步骤**，不是编出来的代码字符串。代码只用于代码门禁和身份比对：g2/v2 要求重编的结果和当初一致；`host-prepared-v1` 要求批次里每条已验证用例的计划、结果与批准都没变（`preparation.ts::validatePreparedBundle`，不一致报 `preparation_evidence_changed`），不重编。
- **执行前的检查顺序**（`workflowExecution.ts::startWorkflowExecution`）：
  1. 幂等检查；
  2. `approvedExecutionBundle`：g2/v2 重编比对，代码门禁没过报 `execution_blocked_by_code_gate`，重编结果不一致报 `execution_recompiles_differently`；prepared 核对准备证据；
  3. `caseIds` 是否都在产物里（`execution_case_not_in_bundle`）；
  4. 运行是否处于 cancelled 或 interrupted；
  5. 是否已有进行中的执行；
  6. 环境是否存在；
  7. 基址取法：环境 `baseUrl`，其次运行的 `sourceUrl`，再次运行的 `targetUrl`，最后项目的 `targetUrl`；
  8. 执行阻碍（`execution_not_ready`，prepared 产物跳过这一步——准备已经逐条验证过）；
  9. 占位符是否都能解析（连同准备配方里的步骤）；
  10. 守卫（连同准备配方里的步骤）。
- **开跑前**：用运行绑定的执行模型发一次最小调用（`modelPreflight.ts::executorPreflight`），端点明确说不（401/402/403/429）就在第一条用例之前停（503 `executor_model_unavailable`，批次记 `infra_error`），带回服务商原话；连不上、超时这类判断不了的照常开跑。执行准备起批次时也探一次（`assertExecutorAvailable`）。标准集评估发起的执行改用候选模型（只在那一次执行里换，见 docs/v3/15 阶段 9）。
- **每条用例的执行**：
  - 每条都用一个新浏览器（不传 `sessionKey`）。执行前如果环境配置了 `TP_RESET_CMD`，先跑它（超时 60 秒）。
  - 一条跑完留下了没清理的资源（lifecycle `pendingResources` 非空）本来整批停。环境配置了只读核对命令 `TP_VERIFY_CLEAN_CMD` 时先跑它（资源清单以 JSON 放在 `TP_PENDING_RESOURCES`，超时 60 秒）：退出码 0 = 确认没留下，不停批，复核结果记在这条结果的 `residueCheck`；1 或其他一律照样停。准备批次同一口径（确认干净时不隔离该用例，照常进修复）。Hyperliquid 测试网的例子是 `examples/hyperliquid-testnet/verify-clean.mjs`。
  - 前提里写明「未登录」时不带登录态（`caseStartsLoggedOut`）。
  - 只有基础设施类失败且可重试时才退避重试，最多 3 次，间隔 8、16、32 秒。可重试的码有 `MODEL_UNAVAILABLE`、`EXEC_ENV`、`EXEC_TIMEOUT`。
- **批次状态**：预算耗尽记为 `budget_exhausted`，基础设施失败（重试用尽后）记为 `infra_error`，这两种都会立即中止批次；其余用例累积成 `failed` 或 `unobservable`。选中但没跑到的用例补记为 `NOT_RUN`。
- **runner 内部**（`packages/harness-testing/src/exec/run.ts::executeRun`）：
  - 顺序是：登录、`settleOn` 等待页面就绪、步骤执行前取一次快照、逐步执行 `act`（每步后截图，并检查挂在这一步之后的 `afterStep` 断言），然后求值判据、执行 `postSteps`、采集性能。
  - 判据有三类：机器判据用 `evaluateOracle`；judge 判据用 `sampleJudge` 加 `aggregateJudge`；没有判据时用 `aiAssert`。
  - 一条用例一份 `readings`：`reading` 判据在它的 afterStep 记读数（读不到先等几轮），后面引用它的 `decimal-equation` 从里取；挂在步骤上的 `text`、`decimal-equation` 不过时重读几次再判。
  - 每出一个结果，失败原因与核对说明里提到、领域参考没有的界面字面值记成界面事实候选（`factCandidates.ts`，不影响执行）。
  - 失败按 `failure.ts::classifyFailure` 归类。
- **执行记录**（`workflowRunRecord.ts`）：写主库 `runs`，比较或建立性能基线和视觉基线，按时间窗口把 Midscene 报告复制到 `artifacts/reports/<runRecordId>.html`。这一步出错不影响执行本身。
- **进度**：每条跑完，execution 节点追加一条 running 事件，消息是 `n/m · caseId · 状态`；重试等待也记一条。逐条结果本身要等整批结束才写进 `execution/<id>`，见 §10-15。

### 8.1 执行准备（`preparation.ts`）

审核通过的用例在正式执行前，由规划宿主逐条对着真环境探查、试跑，**只有 runner 跑出来的证据能把一条标成 verified**。它取代了 g2 在 Web 上的位置。

```mermaid
sequenceDiagram
  autonumber
  actor U as 用户
  participant W as Web（ExecutionControls）
  participant A as API（preparation）
  participant L as 账本
  participant C as 规划宿主（同一工作区）
  participant R as runner
  U->>W: 选范围与方式，点「开始 / 继续逐条准备与验证」
  W->>A: POST …/preparation/start { revisionIds, mode }
  A->>A: assertExecutorAvailable（执行模型预检）
  A->>L: preparation_batches：按优先级排好的单元；admit 先判掉准备不出来的
  A->>L: wf_runs=running；g2 节点 running「n/m · 执行准备已启动」
  A-->>W: 202 { batchId, instructions }
  A->>C: getRuntime(运行登记时的运行时).startRun（任务话术 = 准备协议）
  loop 每条用例
    C->>A: preparation_step next → 用例、入口、经验上下文
    C->>A: probe（对真环境核一次前提）/ guide（按需读说明）
    A->>R: 起一次 runner 探查或试跑（同一浏览器会话）
    C->>A: trial（带定位后的步骤、前提核对、可选配方）
    A->>R: 试跑，runner 结果决定 verified / repair
    C->>A: resolve（blocked / needs_review / product_defect，要写理由）
  end
  A->>L: g2/prepared/<batchId>（host-prepared-v1）；wf_runs=waiting_review
```

- **起批次**（`startPreparation`）：运行在 running/executing/registered/queued 时报 `workflow_active`，在 cancelled/paused/interrupted 时报 `run_requires_explicit_resume`（Web 会先自动 resume）。用例按 P0 → P1 → P2 排（`casegen` 的 `executionPriority`），同档前提少的先跑。范围与批准都没变时沿用上一批（`mode:"retry"`，已验证的与因留下资源被隔离的原样保留）；`mode:"all"` 新建批次全部重验。每条最多 `maxRounds` 轮（默认 3，上限 5），批次预算取 `caseRunBudget`。
- **准入**（`admit` → `preparationAdmission.ts::admissionIssues`）：readiness 标了不可执行、引用了没绑定的环境变量、生命周期问题、门禁 `setting-undeclared` / `step-compound` 的用例，不花探查直接记 blocked，理由写清缺什么。
- **逐条推进**（`preparationStep`，MCP `preparation_step`）：动作有 `next`、`probe`、`trial`、`resolve`、`discover`、`guide`。`guide` 返回六份短说明之一（prerequisites、recipe、numeric、trial、experience、blocked，`preparationGuidance.ts::GUIDES`）；被拒时错误后面附修法（`ERROR_FIXES`）。服务端冻结的东西：判据（`approved_oracle_frozen`）、收尾步骤（`cleanup_steps_removed`）、生命周期绑定的步骤、前提证据（`prerequisite_evidence_frozen`）；有前提的用例必须先 probe 才能 trial；同一条最多探 3 次；判 `product_defect` 要有一次非基础设施的真实失败试跑。
- **配方**：要先造状态的用例可以带受控配方（`recipe`）或引用已有配方（`recipeRef`，`preparationExperience.ts`）；配方里不许出现密钥值（`recipe_contains_secret`），只能提供用例声明的状态。
- **宿主中途退出**：看守定时器每 3 秒查一次。宿主会话结束而还有没做完的用例、预算没用完时自动续起，最多 3 次；这段时间里有用例得出结论就清零重计。Claude Code 撞了额度就等到重置时刻再续（不占续起次数），重置晚于预算截止就停。续起用尽或预算耗尽时 `cancelPreparation`，批次与运行记 `interrupted`，已做完的用例保留。
- **收尾**（`finish`）：所有单元都到终态后，把 verified 的用例（步骤换成准备时定位过的版本、带准备配方）写成 `g2/prepared/<batchId>`，`compilation: "host-prepared-v1"`；全部 verified 时 g2 节点 done，否则 blocked（「部分完成」）；运行改回 `waiting_review`。
- **重启**：`recoverPreparations` 把还在 running 的批次与运行记 `interrupted`，正在试跑的单元退回 repair。
- **执行**：`compiledReadiness` 选 g2 节点最近一次 done 的代码修订（没有就取最新的 code 修订）；执行时每条用例把自己的准备配方交给 runner（`opts.preparation`）。

# v3 数据契约

> Phase 1 三路（A 工具 / B skills / C 领域服务）并行的前提：对下面这些文件形状有同一份约定。
> 已有的 zod schema **直接引用，不重造**（`packages/harness-testing/src/casegen/types.ts`、`packages/harness-core/src/eval/coverage.ts`）。
> 新形状用 zod 定义在 `packages/testpilot-mcp/src/contracts.ts`，由 A 建、B/C 引。

## 1. 一次运行的落盘 `runs/<runId>/`

| 文件 | 形状 | 谁写 | 谁读 |
|---|---|---|---|
| `stories.json` | `StoryBundleSchema` | `run_pipeline` | C（复核批次）、`score_run` |
| `cases.json` | `GatedBundleSchema`（含 `gate`）；每条用例带 **`sourceRefs`**（下） | `run_pipeline` / C 臂 skill | C、`score_run`、Scanner |
| `meta.json` | **`RunMeta`**（下） | `run_pipeline` | 所有人 |
| `events.jsonl` | **`NodeEvent`** 每行一条 | `run_pipeline`（同时 emit 到 stderr） | C（画布/进度）、Penguin trace |
| `decisions.json` | **`Decision[]`**（每条 `decidedByKind: "human"`） | **只有** C（审计台的决定路由） | 下一 session 的 `read_decisions`（只回校验通过的条目） |
| `holds.jsonl` | 每行 `{ at, hook, gate, reason?, … }` | hook（每次 deny 追加一行） | 审计台 `GET /api/audit/:runId/holds`、评测打分器 `hook_denies` |
| `score.json` | `ScoreboardEntry` | `score_run`（每次打分写回） | `paired_eval` 查谱系 |

`decisions.json` / `holds.jsonl` / `gate.json` 三个文件 agent **不许写**：hook `protect-decisions.mjs`
拦 `write_file` / `edit_file`（gate=workspace）。它们是关于这次运行的记录与人的决定，不由被记录的那一方写。

```ts
// RunMeta —— P3 来源印记的载体。缺任一项，score_run 拒绝打分。
{
  runId: string,                 // "run-" + 时间戳36进制
  stage: "g1" | "g2",
  skillVersion: string,          // plugin.json 里该 skill 的 YYYY-MM-DD.N —— 替代旧的 graphVersion
  promptsDigest: TextDigest,     // harness-core/util/digest.ts 的形状：{ entries, combined }
  params: Record<string, unknown>,
  ablated: string[],
  model: { baseUrl: string, model: string, thinking: boolean },
  materialsHash: string,         // materialsDir 内容的 sha256 前 16 位
  startedAt: string, finishedAt: string,
  spend: { calls: number, tokens: number, ms: number }
}

// TextCase.sourceRefs —— 出处锚点（2026-09-03，借 commerce-agents 的 provenance gate）。
// 这条用例依据的材料段 id：`retrieve_spec` 返回的 chunk id（`docs/x.md#7`）或探索观察段 id。
// 形状层 `string[]`（默认空，A 臂旧运行可读）；**内容由两处同一份规则核对**
// （`harness-testing/casegen/provenance.ts::checkProvenance`）：
//   · C 臂：hook `validate-cases.mjs` 读 trace 里 retrieve_spec 的返回，refs ⊆ 取过的段，
//     否则 deny（gate=provenance）；这次运行没调过 retrieve_spec 也 deny（gate=grounding）。
//   · A 臂：`design.cases` 对着本故事取到的段核对，对不上的 id 丢掉并记日志。
// 它只判「id 是不是真的、是不是取过」；「这段是否真支持这条断言」归 judge 与人。
sourceRefs: string[]

// NodeEvent —— 画布与断点续跑靠它；US-14 / US-16.4 的补回点。
{ runId, node: string, phase: "start" | "end" | "error", at: string,
  ms?: number, calls?: number, tokens?: number, error?: string,
  // end 时：这个节点写了哪个文件，供 { from: node } 续跑读取
  wrote?: string }

// Decision —— 批准永远是人：decidedByKind 只有一个值，类型上没有 agent（借 commerce-agents 的 applied_by 无 kind）。
{ caseId: string, decision: "approved" | "rejected" | "revised",
  by: string, decidedByKind: "human", at: string,
  edit?: { title?: string, steps?: string[], expected?: string },
  reason?: string }
```

## 2. 基准目录 `benchmark/<capability>/`

沿用 PenguinHarness 的目录约定（`statement/` 公开、`rubric/` 私有），加 TestPilot 自己的三样。

| 文件 | 形状 | 谁写 | 谁读 |
|---|---|---|---|
| `gold.json` | `GoldChecklist`（core/eval/coverage.ts） | 人 | `score_run` |
| `human-labels.json` | **`HumanLabel[]`**（下） | 人（审计台「校准」tab） | `calibrate_judge` |
| `held-out/` | 目录，内容同上但只在评测用 | 人 | 只有 `score_run` / `paired_eval`；**对 Optimizer 只读** |
| `scoreboard.yaml` | **`ScoreboardEntry[]`**（`semantic.judge = { model, promptDigest }`：谁判的、按哪版口径；judge 不同则语义栏不可比，`paired_eval` 在 note 里说） | `score_run` / `paired_eval` 追加 | Optimizer、审计台、Penguin benchmark 页 |
| `statement/README.md` | 给 Test Agent 看的任务陈述 | 人 | agent |
| `rubric/README.md` | 私有评分说明（**agent 不可见**） | 人 | `testpilot-evaluation` skill |
| `cases/*.json` | **`EvalCase`**（下；`evalcase.ts`） | 人 | 回放打分器 |
| `cases/poison/*` | eval-only 投毒材料 | 人 | 跑评测的人在跑前并入 workspace/materials；**永不**进真实材料 |
| `recordings/<caseId>.json` | **`Recording`**（workspace / runDir / tracePath / skillVersion） | 跑评测的人 | `replay()` |
| `replay/<run>/{cases.json, meta.json, expected.json}` | 冻结的运行与它的分 | 人（`scripts/replay.mjs --write`） | CI `scripts/replay.mjs`：确定性重打分，逐位比 |

```ts
// EvalCase —— 借 commerce-agents 的 commerce-evals：state / turns / expected，expected 全是确定性打分器，只有 rubric 走 judge。
{ id, priority?, tags, skip?,
  state: { materials?, poison: string[], frozenInputsDir? },
  turns: string[],
  expected: { files_written_within?, never_writes?, never_reads?, skill_loaded?, skill_not_loaded?,
              hook_denies?: [{ gate?, min?, max? }], gate_score_gte?, cases_gte?, binding_complete?,
              source_refs_anchored?, max_tool_calls?, rubric? },
  notes? }
// 基线键是 (caseId, scorer)；没有录制的用例是 pending 不是 pass；看 failure set 的 diff 不看总分。
```

```ts
// HumanLabel —— 第 0 步那 30 条。judge 校准（κ）与 gate 阈值的锚。
{ goldId: string, caseId: string, runId: string,
  covered: boolean,              // 这条用例是否覆盖了这条清单项
  by: string, at: string,
  heldOut: boolean }             // 一半留出；留出的从不进任何调优

// ScoreboardEntry —— P2 的落点：goldHash 变了就是新谱系，跨谱系不比。
{ id: string, at: string,
  agentState: string,            // sha256(skillVersion + promptsDigest.combined + params) 前 16 位
  goldHash: string,              // sha256(gold.json 内容) 前 16 位
  runId: string,
  coverage: number, heldOutCoverage: number,
  semantic?: { coverage: number, kappa: number, spread: number },   // 校准过才有
  vsPrev?: { entryId: string, mcnemar: { aOnly, bOnly, p }, flips: number },
  frozen: boolean,               // Formal Baseline
  binding: RunMeta               // 完整带上，不只是引用
}
```

**拒收规则**（`score_run` 与 scoreboard 写入端强制）：`RunMeta` 缺 `skillVersion` / `promptsDigest` / `model` / `materialsHash` 任一 → 抛错不打分；`vsPrev` 引用的 entry 若 `goldHash` 不同 → 抛错不比较。

## 3. 审计 `scans/<runId>.json`

Scanner 的产物**独立于 runs/**，可跨运行汇总（Inspect 的做法）。

```ts
// ScanReport
{ runId: string, at: string, scanner: string,   // skill 版本
  findings: ScanFinding[] }

// ScanFinding —— 审计台「审计报告」tab 的每一行
{ caseId: string,
  kind: "assert-trivial"        // 断言恒真 / 只断言页面没崩
      | "unanchored"            // 断言里的文案/数值在运行时观察（DOM/接口）里查不到
      | "touched-sut"           // 步骤里出现改被测对象的动作
      | "duplicate"             // 与已批准集或同批次三元组重复
      | "unfounded-step",       // 步骤引用的控件在探索观察里不存在
  evidence: string,             // 一句可核对的话 + 指向哪里
  severity: "block" | "warn" }
```

## 4. `retrieve_spec` 的索引 `materials/.index/`

```ts
// SpecIndex —— 替掉 fitToBudget 盲裁。按故事取最相关的规格段，而不是随手切 8000 token。
{ materialsHash: string,
  chunks: [{ id, docId, heading: string[], text, tokens }],
  // 显式关系图：规格段 ↔ 页面/路由 ↔ 控件（2512.12117：62% 跨文件证据纯向量检索找不到）
  edges: [{ from: chunkId, to: string, kind: "mentions-route" | "mentions-control" | "same-flow" }] }
```
检索接口：`retrieve_spec({ materialsDir, query: string, budgetTokens }) → { chunks, dropped: number, hint: string }`。`hint` 是给模型的一句话（SWE-agent 的做法：截断变成行为指导，例如「还有 3 段相关规格未载入，需要时按 chunkId 取」）。

## 5. 工具签名（MCP，`packages/testpilot-mcp`）

```
run_pipeline({ stage, materialsDir, outDir, limit?, stopAfter?, from?, ablate? }) → RunMeta + 计数
score_run({ runId, goldPath, semantic? })                                       → ScoreboardEntry（未 frozen）
paired_eval({ a: runId, b: runId, goldPath })                                    → ScoreboardEntry（带 vsPrev）
mutate_and_detect({ runId, defects? })                                           → DetectionEvalResult（现有形状 + leaning）
drive_sut({ caseId, runId, target })                                             → ExecOutcome（现有形状）
retrieve_spec({ materialsDir, query, budgetTokens })                             → { chunks, dropped, hint }
read_decisions({ runId })                                                        → Decision[]
calibrate_judge({ labelsPath, runs: 3 })                                         → { kappa, spread, n }
```
`stopAfter` / `from` 是 US-16.4 断点续跑的补回；`from` 从 `events.jsonl` 里那个节点的 `wrote` 读上游产物。

**执行结果三态（`drive_sut` / `mutate_and_detect`）。** `ExecOutcome.status ∈ passed | failed | unobservable`，
判据 `OracleVerdict.status ∈ pass | fail | unobservable`。`unobservable` = 判据没量到（没取到前置快照、读不到标签旁的数）：
不是产品错了，也不是通过——借 commerce-agents 的「None ≠ 0」。变异检测把它与 infra 故障一样排除在分母外。

**工具结果三态（2026-09-03，借 commerce-agents 的 `ToolOutcome`）。** 一次调用的结局是 `ok` / `error` /
**`blocked`** 三种，不是两种。被门禁拦下**不是错误**：`isError` 不设，返回
`{ status: "blocked", gate, reason }`（`contracts.ts` 的 `HeldResultSchema`），`gate` ∈
`binding`（来源印记缺项，`readMeta`）· `lineage`（跨谱系比较，`paired_eval`）· `provenance` · `grounding`
（hook `validate-cases.mjs` 的 `output.gate` 用同一套词）· `workspace`。分开的理由：审计台与 trace 要能把
「工具坏了」和「规则拦了」分开数——**一次运行被拦几次，是模型撞门禁次数的直接度量**。

**`retrieve_spec` 的输出是围栏过的。** 模型读到的 `content` 是 `<spec_material>…</spec_material>` 包着的 JSON，
段落文本经 `harness-testing/retrieve/fence.ts` 过滤（NFKC、零宽与控制字符、伪造轮次标记、工具标签、围栏标签本身）；
`structuredContent` 给宿主，不包。索引 `materials/.index/index.json` 存**原文**——过滤规则变了不该表现成材料变了。
A 臂 `spec.compose` 与 `design.cases` 喂给模型的材料同样包在这个围栏里；三份 stable 提示词各带一句 notice。

## 1. 文件式运行的落盘 `runs/<runId>/`（宿主工作区 / `run_pipeline`）

账本（§6）是 Web 与已登记运行的真源；下面这组文件仍由 `run_pipeline`、hook 与宿主适配器读写。

| 文件 | 形状 | 谁写 | 谁读 |
|---|---|---|---|
| `stories.json` | `StoryBundleSchema` | `run_pipeline` / `write_stories` | `score_run`、审计 |
| `cases.json` | `GatedBundleSchema`（`CaseBundle` + `gate`）；每条用例带 `sourceRefs` | `run_pipeline` / `write_cases` | `score_run`、Scanner |
| `meta.json` | `RunMetaSchema`（contracts.ts:88） | `run_pipeline` | 所有人 |
| `events.jsonl` | `NodeEventSchema`（contracts.ts:135）每行一条 | `run_pipeline` | 断点续跑、画布 |
| `decisions.json` | `DecisionSchema[]`（contracts.ts:161） | **只有** `server/src/penguin.ts::writeDecisions`，由账本批准事件的投递队列调用（`decisionDelivery.ts::flushDecisionDelivery`） | `read_decisions` |
| `holds.jsonl` | 每行 `{ at, hook, gate, reason?, … }` | hook（`plugins/testpilot/hooks/lib/tp.mjs` 每次 deny 追加） | 审计台、评测 `hook_denies` |

| 形状 | 关键字段（`?` = 可选） |

**不可变规则**：revision 只追加；同名再写必须带 `parentRevision` = 当前头版，否则 409 `revision_version_conflict`；内容相同且 `sourceRefs` 相同的重试返回原 revision。读时校验 blob 哈希（`revision_content_changed`）。

**kind 枚举**：`material | spec | stories | cases | gate | code | execution | report | memory | evaluation`。当前服务端写入的命名约定：

| name | kind | 写入方 |
|---|---|---|

| `knowledge/rulepack/<packId>` · `knowledge/domain-reference` · `knowledge/<name>` | report | `rulePacks.ts::bindRulePack` · `domainReferences.ts` · `workflowOps.ts` |
| `context/source` · `exploration/observations` · `exploration/report` · `report/exploration-partial` | report | `workflowOps.ts`（探索） |
| `product/model-candidate` | report | `workflowOps.ts`（`buildProductModel` 的产出，§7） |
| `validated/modules` | report | `moduleStage.ts::writeModulePlan` |
| `validated/instructions` · `validated/finalize` | report | `runStages.ts::save` |
| `validated/stories` · `validated/cases` · `validated/gate` | stories · cases · gate | `runStages.ts::save`（kind 即 stage 名） |
| `units/<stories\|cases>/<unitId>` | stories / cases | `workUnits.ts::writeUnit` |
| `module-amendment/<unitId>` · `report/module-fanout` · `report/acceptance-index` | report | `workUnits.ts` / `runStages.ts` |
| `review/case/<caseId>` | cases | `approvedRuns.ts`（复核头版；人改一次多一版） |

| `action-repair/<boardCaseId>` | code | `decisionDelivery.ts` |
| `execution/<executionId>` | execution | `workflowExecution.ts` |
| `regression-candidate/<caseId>/<candidateId>` | report | `regressionCandidates.ts`（候选快照：来源修订、用例内容、证据） |

`spec` 只经 `import_run_artifact` 进来；`memory` / `evaluation` 在枚举里，当前服务端没有写入方。`validated/`、`units/`、`regression-candidate/` 前缀只有服务端能写，导入路由报 403 `reserved_artifact_name`。

**回归候选与回归集**（同库，`server/src/regressionCandidates.ts`）：
- `regression_candidates(id, projectId, runId, kind: defect|rejection, caseId, sourceRevisionId, status: pending|approved|dismissed, revisionId, json, createdAt)`，`UNIQUE(projectId, kind, sourceRevisionId)`：同一版用例只出一个候选，再挂一次只加 `seen`，决定过的不再冒出来。`defect` 来自执行里归属 `assert` 的失败（`infra`、`locate`、基线判为 `flaky` 的不收）；`rejection` 来自带理由（≥4 字）的驳回。
- `regression_suite(id, projectId, candidateId UNIQUE, kind, json, addedAt)`：人批准后写入，`role` 为 `regression-case`（缺陷）或 `generator-negative-eval`（反例）。决定必须是 human（`human_review_required`）。
- 路由：`GET/POST …/workflow-runs/:runId/regression-candidates`、`POST …/regression-candidates/:candidateId`、`GET /api/projects/:id/regression-suite`；宿主工具 `tp_review.candidates / propose_candidates / decide_candidate / regression_suite`。

**归因报表**：`GET …/workflow-runs/:runId/report`（`server/src/runReport.ts::runReport`，宿主工具 `tp_run.report`）返回 `{ nodes4, units, spend, host, execution, layers, signals, thresholds }`。`signals[]` 为 `{ layer: model|context|tool|workflow|case|product, alternatives?, level: problem|watch, code, message, evidence }`，由固定规则产生；`host` 是按 `message.id` 去重后的宿主流水用量。

**附属表**（同库）：`run_stage_receipts(runId, stage) → {revisionId, …facts}`（gate 带 `passed/casesRevision`；modules 带 `frozen/frozenBy/frozenAt/frozenNote?/openFindings`）· `reviewed_case_heads` · `case_approval_events` / `case_approval_heads`（事件 `{id, runId, projectId, caseId, revisionId, decision, principal, note, at}`）· `decision_outbox` · `run_work_units`。

**门禁策略钉在 instructions 回执里**：`{ version: "design-gate-v2", minGateScore: 0.6, minNegativeRatio: 0.3 }`（`runStages.ts`:25）。gate 回执内容 `{ report: GateReport, passed, policy }`；finalize 重新跑门禁并逐字比对，不一致 409 `gate_not_passed`。finalize 内容含 `stories` `cases` `gateScore` `binding` `storiesRevision` `casesRevision` `gateRevision` `plannerExecution` `finalizedAt`，状态进 `waiting_review`。

## 执行观测（2026-09-23，向后兼容）

真源：`packages/harness-core/src/execution-observation.ts` 的 `ExecutionObservationSchema`、`ExecutionAttemptSchema`。新 `RunResult.observation?` 经 runner RPC 存入执行与准备回执；旧记录缺字段表示未采集，不能当作零。

- `version:1`；`stages[]` 每段为 `{stage,durationMs,status,model:{source,forwarded,blocked},failure?{attribution,retryable}}`。阶段包括 compilation、validation、reset、dispatch、retry-wait、session-navigation、authentication、preparation、actions、assertions、cleanup；status 为 completed/failed/cancelled/unknown。
- 模型来源仅 role-proxy/deterministic/unavailable；计数为非负整数或 null。会话缓存为 hit/miss/unknown/unavailable；Midscene 缓存只允许 unknown/unavailable。`retries[]` 保存执行器坐标重放或基础设施重试的枚举原因、阶段、计划等待时间。
- 工作流结果逐条保存 `attempts[{attempt,status,durationMs,observation|null}]`。顶层 observation 是服务端调度，包含 runner 时间，不能与 runner 观测累加。准备成功/失败回执可带 `serviceObservation`，取消或旧 generation 的迟到回执仍保留已得到的观测和调用，但不晋升 verified。
- 编译计时另存 `compilation-observation/<id>` report，引用对应 code revision；不修改决定编译去重和重编校验的代码内容。
- schema 为内容无关的枚举/数值白名单，不接收 URL、模型 endpoint、prompt、密钥、账户或异常文本。旧 phases 字段继续保留。

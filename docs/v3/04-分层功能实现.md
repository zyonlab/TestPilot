| 2 API 服务 | `server/src/` | API 服务（Express，`:5301`） | 层 4、5；经 RPC 调层 3 |

## 1. Web 界面层 `src/`

**职责**：把账本里的运行、修订、复核与执行状态画出来，并承担三处人工关口的按钮。不做业务校验，校验全在层 2；请求一律不带 `Authorization` 头，所以在服务端被认作本地操作员（见 §9）。

入口与路由：`src/App.tsx` 默认渲染 `pages/WorkflowBench.tsx`（`?open=canvas`）；其余界面登记在 `lib/surfaces.tsx::SURFACES`，左导航在 `lib/nav.ts::NAV`。

| 功能 | 实现（文件::函数/组件） | 读写的数据 | 关键约束 |

## 2. API 服务层 `server/src/`

**职责**：唯一的业务真源。运行账本、阶段校验、工作单元、复核、编译、准备、执行派发、项目数据与学习回路都在这里；模型只通过它的接口写东西，分数、阈值、人工关口也都在这里判。

路由挂载（`index.ts`）：`/api/projects/:projectId/workflow-runs` → `runRoutes.ts::runRouter`；`/model-profiles` → `modelProfilesRoutes.ts`；`/assets` → `projectAssetRoutes.ts`；`/knowledge-library` → `knowledgeLibrary.ts::knowledgeLibraryRouter`；`/artifact-comparisons` → `artifactComparisons.ts`。在它们之前挂了 `intentPolicy.ts::intentPolicy`（所有非 GET 的 `/api` 请求）。其余几十条旧路由（用例板、环境、批次、评测、gold、图运行）直接写在 `index.ts` 里。

## 8. 一条运行穿过各层

以 Web 发起、Claude Code 规划、从探索开始的一次运行为例。【】里是层号。

1. **建运行**【1→2】`NewRunForm.tsx` POST `workflow-runs`（`planner:'connected'`）→ `runRoutes.ts` → `workflowOps.ts::createWebWorkflow`：校验材料、规则包（`validateRulePack`【4】），探索地址查 `config.guard.denyHosts`；`plannerHost.ts::requireHost` 定规划运行时；`modelSnapshots.ts::captureHostWebModels` 写模型快照；`runService.ts::registerWebRun` 登记；`rulePacks.ts::bindRulePack`、`domainReferences.ts::bindDomainReference` 冻结绑定；返回 202，异步进入 `launchSource`。
2. **source**【2→3→4】`workflowControls.ts::beginStage('source')` → `sourceKnowledge` 用 `charterFromRulePack`【4】建 charter → `procs.ts::observeProduct` → `index.ts` 的 observer → `exec.ts::interactiveSession` → runner RPC `observe`【3】→ `exec/interactive.ts::runObserve`【4】；回来后 `buildProductModel`【4】写 `product/model-candidate`，材料写成 `exploration.md`。
3. **起规划宿主**【2→6】`penguinRun.ts::startRun` 按运行时取 `runtimes.ts::getRuntime` → `claudecode.ts::startRun`：`skill-launch.ts::prepareSkillLaunch` 写令牌文件，`writeMcpConfig` 写 `.mcp.json`，`hostActorEnv` 注入打标，`claude -p … --plugin-dir plugins/testpilot-claude`。
4. **modules**【6→2→4】宿主 `begin_stage` 拿到 `sections`、`features`、`checks` → `plan_modules` → `moduleStage.ts::writeModulePlan` 跑 `checkModulePlan`【4】→ `waiting_review`。**人**在 `NodeDetail.tsx`【1】点冻结 → `freezeModulePlan`（`reviewerPrincipal`）。
5. **instructions / retrieve**【6→2】`load_run_instructions` → `runStages.ts::loadRunInstructions`（skills、记忆、反例、`runScope`、门禁策略）；`retrieve_spec` → `retrieveRunSpec` → `retrievalAudit.ts::auditedRetrieve`。
6. **stories**【6→2→4】整份：`write_stories` → `writeRunStage('stories')`；单元：`claim_unit`/`write_unit`/`merge_units` → `workUnits.ts`（契约里带 `EXECUTION_SEMANTICS`【4】）。有候选业务预期时 `storyReviewEvent('waiting_review')`，**人**在 `StoryRequirementsReview.tsx` 批或驳。
7. **cases → gate → finalize**【6→2→4】`writeRunStage('cases')`（`verifyCases`、`validateCases`【4】）→ `gateRun`（`runGate`【4】；不过则 `reopenUnitsFromGate`）→ `finalizeRun` 复算门禁，运行进 `waiting_review`。
8. **复核**【1→2】`ProjectReview.tsx` GET `…/review`（`reviewRevisions` 为每条用例开 `review/case/<id>`，`preparationAdmission.ts::reviewAdmission` 附准备前裁决）→ **人** POST `…/review` → `decideRevisions` → `flushDecisionDelivery` 投到用例板；带理由的驳回 → `proposeFromRejections`。
9. **g2 / 准备**【1→2→6→3】Web 这条路：`ExecutionControls.tsx` POST `preparation/start` → `preparation.ts::startPreparation`（`executorPreflight`、`admit`、按 `executionPriority`【4】排序）→ 再起一次规划宿主，它用 `preparation_step` 逐条 probe/trial → `trial` 里 `guardRun` + `execOnRunner`【3】→ 全部结束 `finish` 写 `g2/prepared/<batchId>`。宿主直调这条路：`generate_execution` → `stages/g2` → `generateApprovedCode`（不调模型，`runCodeGate`【4】）写 `g2/v2/…`。
10. **执行**【1→2→3→4】`stages/execute` → `workflowExecution.ts::startWorkflowExecution`：`approvedExecutionBundle` 重核编译产物、`missingPlaceholders`、`guardRun`（`checkRun`【4】）、加密环境快照 → `perform`：`executorPreflight` → 逐条 `execOnRunner` → runner `exec` → `executeRun`【4】（lifecycle、判据、判官）→ 可选 `verifyCleanEnvironment` → 写 `execution/<id>`；随后 `proposeFromExecution`、`recordFactCandidates`。
11. **报告与导出**【1→2】`RunReportPanel.tsx` GET `…/report` → `runReport.ts::runReport`；执行明细 `executionDetail`；项目导出 GET `/api/projects/:id/export` → `buildExportFiles`。

### 8.1 同一件事的几条路

| 事情 | 账本主路径 | 另一条路 | 差别 |
|---|---|---|---|
| 建运行 | Web：`createWebWorkflow` → `registerWebRun`（`models.entry: web`） | 宿主：MCP `register_run` → `registerHostRun`（`entry: host`，材料随请求带来） | 两条都绑项目当前规则包与领域参考（`bindCurrentRulePack` / `bindRulePack`、`bindDomainReference`），后续阶段完全相同 |

## 9. 跨层约束

### 9.1 人工关口
- **怎么判「人」**：只有 `reviewPrincipal.ts::reviewerPrincipal` 一个判定点。请求不带 `Authorization`、也不带 `x-testpilot-actor` 才是 `{kind:'human'}`。本机不做身份验证，这只区分来源。
- **谁会带头**：MCP 的 `HostApi.call` 每个请求都带 `x-testpilot-actor: agent`，拿令牌的阶段调用另带 `Authorization`；服务端起的宿主进程树经 `hostActorTag.ts` 给 node/curl/wget 自动带 `x-testpilot-actor: planner-host`。刻意去掉请求头的裸 HTTP 仍会被当成人，这一条没有堵死。
- **关口清单（代码里要 human 的地方）**：冻结模块树 `freezeModulePlan`；候选故事批/驳 `approveStoryRequirements`/`rejectStoryRequirements`；改用例 `reviseReviewedCase` 与批/驳 `decideRevisions`（`human_review_required`）；回归候选 `decideRegressionCandidate`；事实候选 `decideFactCandidate`；标准集冻结 `freezeStandardSet`；执行模型评估的发起与决定 `startEvaluation`/`decideEvaluation`；换运行执行模型 `rebindRunExecutor` 路由；知识库保存 `saveKnowledgeLibrary`。续跑、取消、重跑、断点、准备启动、执行基线这些路由也调 `reviewerPrincipal`。
- **宿主侧的镜像**：`registry.ts` 里对应动作标 `operatorOnly`，`registerHostDomains` 不注册它们。
- **理由**：驳回用例与驳回候选故事都要去空白后 ≥4 字（`rejection_requires_reason`）；确认事实要 ≥4 字的事实句。

### 9.2 领域中立
- 代码里不写领域词。产品特有的词只能来自绑定的规则包：门禁的 `actionVocabulary`/`volatileReadings`（`runStages.ts::gateOptions`）、守卫的 `sideEffectLabels`（`workflowExecution.ts`、`preparation.ts`）、验收索引（`acceptanceIndex.ts`）、单元材料（`workUnits.ts::unitMaterials`）。
- `pnpm check:domain-neutral` 扫层 1～5 的非注释代码与源头 skills。

### 9.3 判决在屏幕上
- 生成侧：`casegen/prompts.ts` 的 oracle `kind` 枚举里没有 `api`，模型发不出来。
- 门禁侧：`casegen/gate.ts::runGate` 遇到 `kind:"api"` 记 `oracle-offsite`（warn，按 caseId 扣分）。
- 执行侧：`exec/apiOracle.ts::observeApi` 仍在，`executeRun` 只为旧用例走它；导出侧 `exportOracle.ts` 同理。
- 准备侧：准备器不能改已审核的判据（`approved_oracle_frozen`），只能在原来没有时补一个。

### 9.4 禁止名单
- 唯一的主机级规则是 `server/harness.config.ts` 的 `guard.denyHosts`（主网 `app.hyperliquid.xyz` 在上面）。`resolve.ts` 只允许 `DENY_HOSTS` 往里加。
- 检查点有三处：建运行时的探索地址（`createWebWorkflow`，403 `explore_host_denied`）、准备试跑（`preparation.ts::trial` → `guardRun`）、正式执行（`startWorkflowExecution` → `guardRun`）。后两处都走 `guard.ts::checkRun`，返回 `GUARD_HOST`，`runRoutes.ts` 把 `GUARD_*` 原样回成 403 并带理由。
- 不可逆步骤默认放行（`blockIrreversible: false`）；`GUARD_STRICT=1` 时 `checkRun` 才用内置正则加规则包的 `sideEffectLabels` 拦 `GUARD_IRREVERSIBLE`。准备器从 `preparation.ts::actionPolicy` 拿到同一份口径。

### 9.5 运行的冻结绑定
- **材料**：`sealInputs` 算 `materialsHash`/`inputHash`，封过不能改；物化到 `inputs/<runId>/` 只读并校验哈希（`material_view_changed`）。
- **规则包与领域参考**：建运行时绑定为 `knowledge/rulepack/<id>`、`knowledge/domain-reference`，下游只读绑定的那份（`boundRulePack`、`boundDomainReference`）。
- **skills**：登记时 `skillBinding` 记 `assetDigest`，`loadRunInstructions` 发现装机 skills 变了就拒（`installed_skills_changed_register_new_run`）。
- **门禁策略**：钉在 `validated/instructions`，gate 与 finalize 都读它；规划器交不了分数与阈值。
- **模型**：`run_model_snapshots` 存执行连接的密文，执行读快照；规划运行时在创建时定下，续跑沿用（`workflowOps.ts::plannerOf`）。
- **编译产物**：g2 名字带编译器身份，执行前重编必须同 id；准备产物要逐条对上批准与试跑回执。
- **用例意图**：审核版本之后，准备器只能改定位措辞与准备步骤；执行记录的 `environmentHash` 不含选择集与评估覆盖。

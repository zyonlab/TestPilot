01

谁在使用，如何得到价值

用户目标可分成“测产品”和“评估测试 Agent”两条线；两条线需要不同的分数和工作入口。

第一用户：测试 / 领域负责人

提供网址、登录态、规则材料与人工金标准；决定哪些候选进入回归套件；关注漏测、误报、机器判据是否真正代表业务意图。

日常入口：复核、审计、运行报告、基线。研究入口是记分板与 gold。

第二用户：开发者与 coding agent

改完前端后调用 TestPilot 跑 P0，读取具体失败值、报告与成本，再决定修产品还是交回人处理。Agent 是工具的使用者，也是需要被评价的对象。

成功标准：缩短定位和修复时间，同时保持业务断言与测试集合不被悄悄放宽。

02

Agent 如何交互

这是一个混合控制系统：固定工作流承担可重复的任务，自主 Agent 承担探索与工具使用，机器判据负责能程序化的结果。

生成与复核

01 / 人 / 宿主材料、目标、生成指令URL / materials / limit
02 / Agent 宿主载入 skill，调用 MCPPenguin 或 Claude Code
03 / 固定 g15 个阶段顺序运行spec / stories / cases / gate
04 / 人复核批准、拒绝、编辑TestCase + decisions
05 / g2 续接MCP 当前直接报未实现规划链路，非已完成

控制权：宿主控制会话与调用；g1 内的节点顺序由代码固定，模型负责内容。write_stories / write_cases 在工具内做形状和出处校验；但 run_pipeline 内部自己落盘，不经过宿主的 Write hook。

开发与执行

01 / 开发者 / agent修改产品代码如数量取整逻辑
02 / MCP / Stop hook请求项目 P0 套件run_p0 → HTTP gateway
03 / 网关 → runner会话池、复位、UI 动作Midscene + Puppeteer
04 / 机器判据读页面 / 接口 / 链pass / fail / unobservable
05 / Agent / 人读失败值并修复或接管重跑、审阅、留证

反馈不是一句“失败了”：返回失败分类、oracle 读数、花费与报告路径；模型解释结果，不应重新发明判决。demo 有真闭环，但 Stop hook 达到封顶或网关异常会放行，正式合并门禁需独立状态。

评测与改进

01 / 维护者先写假设与评价指标evals/*.json
02 / 冻结输入固定上游与测试集inputHash / goldHash
03 / 候选 A / B只差一个组件、多次跑ablate / skillVersion
04 / 工具打分匹配、留出项、配对统计score_run / paired_eval
05 / 人工推广接受后更新基线与资产尚无自动推广控制器

评测不是宿主互相评价：确定性工具算基础覆盖，语义判断单独标注；优化建议可以来自模型，金标准和最终推广仍要受独立控制。当前 T-12 的无效六次产物不能当成领域提升。

参与者自主空间应受约束的边界
外层 Agent / 宿主读 skill、检索、探索、决定工具调用和重试预算、可写范围、批准权限、可调用接口；目前未构成完整安全隔离
MCP + 固定工作流参数校验与执行顺序由代码决定不可把 schema 合法、gate 高分直接解释为真实业务正确
浏览器执行模型按步骤识别控件、操作界面、缓存失效后重定位UI 动作是否真发生，要通过状态证据确认；缓存命中不自动代表操作正确
Judge / Scanner解释性判断、可疑项检测、语义对齐独立标签校准与版本绑定；不能与确定性结果混为一个“准确率”
人定义业务意图、批准用例、冻结 gold、推广新版本需要减少逐条重复劳动，但不能把 self-declared human 当成可信身份

交互与展示

接收人的目标与决定；展示候选、执行证据、成本和评测。

物理进程关系：浏览器 UI 通过 HTTP / WebSocket 访问 gateway；gateway 启动或连接宿主会话；宿主通过 stdio 调 MCP 子进程；用例执行由 gateway 调 runner；runner 驱动 Chromium 与被测站点。MCP 是协议边界，runner 是执行边界，二者不等于天然安全沙箱。
判断评价优先改进

真实结构更接近模块化单体 + 多进程执行，而非已完成的微服务架构将报告、review、gold、suite 端点移出巨型 index；明确 legacy graph 的保留用途

04

数据结构：把事实、决定和评分分开

三个主要事实域：业务当前状态、一次生成的快照、一次评测的谱系。真正可靠的闭环必须保留它们之间的关联。

项目 Project ──1:N── 环境 Environment / 已批准用例 TestCase TestCase ──1:N── 执行 RunRecord ──N:M*── 批次 Batch 生成 RunMeta ──1:1── stories / cases / gate / events 生成 RunMeta ──1:N── 人工 Decision ──批准──→ TestCase 生成 RunMeta + 人工 GoldChecklist ──评分──→ ScoreboardEntry ScoreboardEntry A + B ──同谱系检查──→ 配对差异 / McNemar 运行证据 gate / holds / scan ──抽取──→ Episode 候选

以上是逻辑关联，不代表 SQLite 已声明外键。* 批次通过 batch_runs 关联用例及 runId；数据驱动和重试会带来额外执行，不应把 batch_runs 一行当作所有尝试。

“页面显示了成功”只能说明某个提示出现；“合法数量下单后指定账户的 BTC 持仓准确变化”更接近业务正确性。但接口判据也有前提：读的是哪个账户、币种、订单、时间点？如果账户本来已有仓位，直接比较最终持仓为 0.001 就可能错判；若每次复位后执行，则必须先证实复位成功。机器求值确定，并不保证判据业务上正确。

九个决定下一阶段质量的缺口

这部分优先依据可定位的代码行为，而不是以计划文档的承诺作为实现事实。

下列为本轮发现，优先级由本报告判断。P0 表示阻挡当前“完整闭环 / 强门禁”承诺，并不表示已发现公开网络攻击事件。

P0 F01 · 批准之后的 MCP g2 尚未实现 本轮探针复现

证据

runPipeline 在 stage=g2 时立即抛出 not implemented。合成探针直接调用复现，未启动模型、未写产品数据。

对产品与研究的影响

不能把“生成 → 人批准 → MCP 二阶段生成/执行”描述为已完成；既有看板套件执行路径仍可单独工作。

建议修正与验收方式

先决定 g2 是否属于本版承诺；实现或明确移除入口。验收从人批准开始，覆盖 read_decisions → g2 → 产物/执行证据。

stage "g2" (regenerate from approved cases) is not implemented yet — phase 1A only ships g1

P0 F02 · Claude Code 的人工决定不会走当前文件镜像 静态代码核对

证据

penguinRun 将 runtime 存为 rt.name；mirrorDecisions 仅 runtime === penguin 时写 decisions.json，claude-code 会提前返回。

对产品与研究的影响

数据库里批准成功，下一会话通过 read_decisions 读取的文件可能仍没有决定；用户会看到两种真相。此项为静态路径核对，未执行真实审批。

建议修正与验收方式

按 Runtime 接缝分发写入；给两宿主分别增加“批准一次、文件可读、重复批准幂等”的集成测试，并补失败重试。

if (runtime !== "penguin") return; // 当前镜像前置条件

P0 F03 · human / agent 是请求标签，不是可信身份 本轮探针复现

证据

degradeDecision 只有 actor === agent 才拦，缺省按 human。相同 eq→exists 修改：指定 agent 得 block=true，省略 actor 得 block=false。DELETE 路由也未接退化检查。

对产品与研究的影响

有 API 访问权的调用者可被当作人；DecisionSchema 的 human 字面量不能证明来源。局部退化检查不是不可绕过的权限。

建议修正与验收方式

从可信会话/服务凭证派生 actor；人工审批和 agent 写入使用不同能力；修改、删除、批量替换走同一策略入口。

agentSpecified.block = true
actorOmitted.block = false; actor = "human"

P0 F04 · Hook 与 Stop 门禁存在明确的放行路径 静态代码核对

证据

适配器遇 hook 失败/超时/非 JSON 视为弃权；仅适配 Write/Edit/MultiEdit。宿主允许 Bash(node *)。demo Stop 达到 3 次或网关异常则退出 0。

对产品与研究的影响

正常路径拦截成立，但 shell 写入不受同一 Write hook 约束；无法声称“P0 未绿就永远不能结束”或“模型无法修改保护文件”。没有做主动绕过试验。

建议修正与验收方式

让有限重试以 needs-human 终态退出，而非 pass；正式 CI 状态与对话结束分离；关键写入通过权限边界，hook 自身出错应 blocked。

hook error → abstain
P0 nudges >= 3 → exit(0)
gateway exception → exit(0)

P1 F05 · 退化检测不能保证 oracle 不变 本轮探针复现

证据

目前覆盖 eq→exists、字面量缩短、tier 下降等模式。合成 API eq 判据由 value=0.001 改为 0.002，classifyDegrade 返回空数组。

对产品与研究的影响

这不必然是“更弱”，但已经改变了业务真值。如果策略是“自愈不能改 oracle”，当前启发式检查无法兑现该更强承诺。

建议修正与验收方式

将“是否改变语义”和“是否变弱”分开；自动修复阶段固定 oracle 的规范化摘要，任何变化都转人工审阅。

eq(0.001) → eq(0.002)
classifyDegrade(...) = []

P1 F06 · 实验可比性仍有软约束与未完成输入 静态代码核对

证据

inputHash 两边都有且不同才硬拒；一有一无仅提示。runtime 在 RunMeta 可选，skillVersion 有历史默认值。版本/漂移检查能验摘要，不验证实验现场参数确实生效。

对产品与研究的影响

错误的消融臂可能完成并得到看似正常的分数；T-12 正发生过 ablated 丢失与 API schema 缺失。

建议修正与验收方式

正式评测模式要求同一冻结输入、生效参数证明、全部模型/规则/配置指纹；开跑前做消融差异与产物分布的 canary 校验。

inputHash: optional
runtime: optional
DEFAULT_SKILL_VERSION: historical fallback

P1 F07 · 复位失败不会阻止继续测试 静态代码核对

证据

runEnvReset 收到非零返回码只生成日志；调用流程继续。批次复用浏览器时，共享账户和页面状态影响后续判据的独立性。

对产品与研究的影响

前置状态不满足会被误看成产品错、定位错，或偶然通过；高缓存命中率掩盖不了状态污染。

建议修正与验收方式

复位成功后读接口核对关键前置状态；失败返回 blocked/unobservable，避免做后续有副作用动作；测试共享会话的相互干扰。

reset command exits non-zero → log only → next execution

P1 F08 · 持久化与版本追溯尚未达到实验账本标准 静态代码核对

证据

记分板整文件读改写无显式跨进程锁；批准的 TestCase 不直接带 sourceRefs；decisions 双写失败只记日志。

对产品与研究的影响

并行评分有丢更新风险；清理旧运行后可能失去来源；同一 case 修改后历史运行复现困难。这里是代码风险判断，不声称已复现数据丢失。

建议修正与验收方式

原子写入+锁或 SQLite 账本；执行绑定 caseRevision/envDigest/sutRevision；DB 决定通过 outbox 可靠投影至文件。

P1 F09 · 经验记录尚未形成可验证的消费与推广链 静态代码核对

证据

Episode 提取与 memory skill 已有；本次读取的 pipeline / casegen 主路径没有明确的 episode 注入入口，也未找到候选择优、推广与回滚控制器。

对产品与研究的影响

宿主可能读到经验，但不意味着 MCP 内部生成调用读到它；“记住了”不能当作“下一轮质量提升”。

建议修正与验收方式

记录每次实际检索到的 episodeIds 与 memoryDigest；固定输入做开/关记忆实验；之后再建设候选生成与推广。

合成探针只调用纯逻辑与 g2 的即时拒绝分支；未修改真实用例，未发模型请求，未绕过保护文件。原始结果在文末方法部分可展开。

从 Harness 与垂直 Agent 论文看项目

专业领域 agent 的标准不是“有领域提示词”，而是领域规则、任务环境、可检验结果和泛化证据能否组成完整链条。

本轮查阅了下面 9 篇论文与 1 篇官方工程文章的原始页面。对照的是方法与验证要求；并未复现论文实验，也不把异构任务的分数横向排名。以下“项目映射 / 建议”均是本报告的分析推断。

R01 / Yang et al. · 2024

SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering

来源方法：把 agent 与计算机之间的接口当成设计对象；编辑、浏览和执行反馈的形态会影响 agent 行为。 原文 ↗

项目映射：TestPilot 的结构化 MCP、错误原因、报告路径与日志截断属于同类接口工程。

差距与实验：对应的是接口设计思想，不是复现 SWE-agent 的结果。应测“短结果 + 可追索详情”是否减少工具误用、修复耗时与 tokens。

R02 / Xia et al. · 2024

来源方法：通过固定的定位、修复和验证阶段解决软件问题，说明自主规划的复杂度不是性能保证。 原文 ↗

差距与实验：单元测试和视觉 E2E 的成本与噪声不同；不能直接套论文收益。应报告每一层淘汰率、误报、净新增缺陷覆盖和人工接受率。

项目映射：材料围栏、sourceRefs 和 holds 是起点；它们不是已经验证的对抗防御结论。

差距与实验：应将恶意材料、shell 写入、伪造 actor、hook 故障做成隔离的安全用例，同时统计合法任务被误拦多少。

R06 / Shinn et al. · 2023

差距与实验：本项目采用确定性抽取，不能直接称为完整 Reflexion；需要证明经验被下次任务消费，且比相同预算的普通重试更好。

项目映射：REFERENCE + episodic memory 可以成为上下文改进资产；当前尚未形成增量整理与效果反馈链。

自进化：已经有实验台，还没有完整的改进机器

当前能力应描述为“可开展受控演化实验”，而不是“已证明自主持续进化”。关键差别在消费、择优、推广和长期验证。

E0

执行恢复

清缓存、重定位、有限重试。

代码与实测存在。属于恢复，不等于跨任务学习。

E1

经验积累

从 gate / holds / scan 抽取结构化候选。

记录基础存在，消费与效果尚待验证。

E2

受控改进实验

冻结上游、消融、配对评分。

机制存在，领域主实验仍待有效闭环。

E3

候选搜索与推广

自动提出补丁，验证后选择版本。

本轮未见完整控制器，建议建设。

E4

持续泛化改进

跨产品增益、防遗忘、回滚。

尚无多轮长期收益证据。

E0～E4 是本报告的分析框架，不是行业统一评级，也不是仓库现有里程碑。

当前最合适的“自进化”定义

由执行证据驱动、在独立评测保护下进行的 skill / context 改进，推广由人控制。不要求更新模型权重，也不要求 agent 能修改自己所有代码。应先让一个小组件的改进可验证，再增加自动化范围。

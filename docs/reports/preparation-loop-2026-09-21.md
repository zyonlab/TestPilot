# 执行准备与验证

当前 g2 的 Web 入口改为 `preparation/start`。宿主使用 `preparation_step` 顺序领取已审核用例，提交方案并通过服务端启动 Midscene 试跑。旧 `stages/g2` 静态编译接口保留兼容；它的历史完成事件在工作台显示为“旧版仅静态编译，尚未试跑验证”，不能冒充新流程完成。

## 状态与证据

每次批次冻结选择范围和审核事件；逐用例记录 pending → planning → trial → repair，以及 verified / blocked / product_defect / needs_review / exhausted。默认每条最多 3 轮，上限 5 轮，另受总墙钟和执行模型调用预算限制。每轮保存方案、修改理由、执行器原始结果（含日志与截图路径）。进度接口每 3 秒刷新，底栏显示已处理/总数、验证通过数与当前动作；展开日志可查看轮次结果。执行器返回完整详细日志后写入事件列表；浏览器动作内部 token 流并非实时推流。

只有执行器返回 passed、无基础设施错误、有判据结果且提供模型请求记录才记 verified。宿主不能提交 verified。生成的 host-prepared-v1 包只含通过用例；全部通过才显示完成，其余情况记为阻塞并给出“部分完成”汇总。

## 修复边界

用例身份、故事、预期、前置条件、风险、规则/AC 引用、断言文本及已有 oracle 保持审核版本。变更业务意图返回 needs_review。允许细化步骤和等待、调整断言检查位置、在原来没有 oracle 时实现判据。不能删除清理动作，也不能凭空修改结构化前置条件的验证证据。未验证的结构化前置条件仍会阻塞。

模型补充的判据仍需要人工关注：静态一致性检查不能证明一个新计算实现与业务文本完全等价。产品缺陷分类是宿主对失败证据的诊断，非独立产品缺陷裁定。

停止会中断宿主与当前试跑；服务重启将队列标记 interrupted。重新启动相同未完成批次保留终结用例，恢复当前用例。运行代次隔离迟到回执，避免取消前结果覆盖恢复后的工作。已经终结的批次再次启动会新建批次；不是只重试其中阻塞项。

## 验证范围

自动化使用受控宿主/执行器替身，覆盖失败修复后复验、真实回执才能通过、审核意图和 oracle 冻结、取消恢复、重启恢复、重试预算、审批撤销、长错误日志；同时回归原执行与运行路由。前后端及 MCP 类型检查通过。

尚未对 Hyperliquid 的 86 条用例启动真实试跑，也未执行交易。实际宿主模型与目标网站的端到端表现需要在选择范围内运行后评估。

## 已实现

### 前置检查与来源

- `prerequisiteChecks` 按原前置文本逐项绑定，复合前置的 `checks[]` 全部通过才成立。缺少实现的原前置自动保留为 unknown，不能跳过。
- `environment` 读取运行时事实：当前页面 origin、是否成功安装注入钱包、实际注入账户与链、配置的实时认证检查。配置／安装不代表登录、授权或资源准备完成。
- `screen` 使用当前屏幕的视觉断言或确定性判据。同屏数值关系可用已有 `decimal-equation`；缺少历史基线仍 unknown，不调用被测系统接口代替 UI 判决。
- `unknown` 明确保留无法验证的理由。空的 `Assertion failed: undefined` 带上条件文本，作为 unknown，停止业务步骤。
- probe 和 trial 共用检查实现。探查通过仍不会使业务用例 verified；正式执行接收并重放冻结的同一份 preparation。
- 运行时事实和每个子检查都有来源与时间。探查额外保存页面就绪后的截图，避免仅留下导航初期空白图。

### 有边界的辅助校验

`auxiliaryAssertions` 独立于原用例断言，必须使用唯一 id，`supports` 指向已审核断言 id 或 `$expected`，执行时序必须落在现有步骤内。原验收文本、原判据、前置、单位、清理和就绪要求继续保留；改变业务验收仍需复审。

辅助检查单独执行、记录 `auxiliaryChecks`，不参与原断言路径选择，不替代原预期。辅助检查失败阻止 verified，但不能直接 resolve 为 product_defect。执行包冻结辅助检查，正式执行保留相同语义。

### 公共方法与逐轮经验

- `recipe` 包含 capability、精确匹配的 requires、入口检查、步骤、后置检查、副作用声明和清理约束。目前只接收 none/ui-only、空 cleanup 的低影响方法；可变 fixture 不在此契约内。
- 方法内容、适用范围构成稳定身份；版本记录独立的真实回执。一次成功为 candidate；两个不同用例的独立成功 trial 才晋升 verified-reusable。probe、模型声明、重复回执不能晋升。
- 每次使用在当前浏览器重新检查入口与后置状态。负面证据暂停复用，后续成功不能靠多数票消除反证；必须修改／收窄契约后重新验证。保存了方法的旧执行包也检查撤销状态。
- scope 隔离项目、入口、环境配置、材料版本、页面版本、登录模式及凭据版本。默认七天失效。目前注入钱包运行额外按 run 隔离，因为私有钱包配置尚无冻结的跨运行身份契约。未实现参数替换。
- `next` 返回实际分发的 `experienceContext`：选择理由、条目版本、回执引用、最近观察的环境事实、摘要和不可信数据说明。事实明确标为历史观察，不能证明新浏览器当前条件。
- 直接调用 probe/trial 而没有获取 next 时，快照标记 delivered=false，不能把未分发历史伪装成宿主输入。每轮已分发快照不可变，方案绑定对应修订与 digest。
- 同项目经验以版本化 `preparation/<batch>/experience` 物料和索引保存；UI 使用现有文档阅读器显示经验及本轮分发快照。最多分发六个匹配方法、约 16K 字符的方法内容及四条固定格式经验提示。页面自由文本不作为经验指令复制；真实回执仅保存引用。
- held-out 运行不读取或写入公共经验；明文 secret 不能写入 recipe，运行诊断脱敏。领域词仍来自项目数据。

这些是结构与证据约束，并不能自动证明模型给出的自然语言检查完整表达了业务语义。特别是把复杂前置错误地绑定到较弱检查，仍需要规划与人工语义审查；不能把 schema 合法当成业务等价证明。

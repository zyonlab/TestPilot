TestPilot 是自动生成可执行测试用例的垂直 Harness Agent。输入需求规格或实际产品观察，结合产品结构、领域知识和测试方法，形成可审阅的故事、验收判据、测试用例、执行代码与证据。目标同时包括可用的产品闭环和可发表研究所需的独立实证。

Web UI 管项目、输入材料、工作流执行、产物与 review；Claude Code / Codex / PenguinHarness 宿主也通过相同应用服务管理这些对象。Penguin 的 TestPilot Evaluation 配套扩展管理受控候选与评估发布，不接管 Web 的全部工作流和产物管理。

两个模型角色固定：思考规划由 Web 配置或宿主原生模型承担；Midscene 使用低成本执行模型。Web 暂时默认继承 Midscene 的同一模型，后续 env / 项目配置可独立覆盖；宿主不另配规划模型。业务 Role、Skill、领域知识与模型角色是不同概念，不能给每个节点强行增加一个模型配置。

4. Flow、节点与产物交互

Flow 顶部只保留 run 选择、输入摘要、必要操作和主要执行按钮。选中的历史 run 决定流程版本、节点状态与物料；新 run 先是未执行节点和空产物。工作流执行记录不是被测产品的测试执行报告，也不再占一个独立侧栏入口。

点击节点打开调试详情：职责、输入来源、Role / Skill / 领域版本、参数、attempt、日志、成本与输出。未执行节点展示预期产物类型；已完成节点展示其真实产物，点击产物进入对应 viewer。不要用同一“产品结构参考图”冒充所有 run 的输出。

行为生产语义
新建 run新 ID，选择来源入口、runtime、材料与知识，冻结定义和模型配置
继续 run原 ID、原快照，跳过成功节点；不把当前设置覆盖到旧 run
重试节点原节点新增 attempt；保留失败输出与事件，副作用去重
断点只允许当前范围内尚未尝试的节点；在开始前暂停；失败或已完成不算未运行
命中后继续跨过当前断点一次，后续断点仍生效；服务端负责并发检查
单节点 / 多节点明确执行 / 复用 / 阻塞清单，缺上游不隐式扩成全流程
配置改变新 run 或显式实验工作副本；保留旧运行，不偷换知识、Skill 或批准版本

日常是垂直标准流程；重组只放「设置 → 高级实验流程」。任何模板都保留不可绕过的质量与审批约束。默认整理故事后形成结构检查点，首次生成或大幅变更需结构确认后再进入高成本设计；这种确认属于产品数据审批，不是研究晋升。

1. 本次设计结论

“产品结构 + 用户故事”是整理故事节点的联合产物，也是项目长期积累的产品模型。 Flow 是运行入口；结构图是物料审阅与大列表筛选入口，两者共用版本与来源。

产品结构采用树表示主模块、子模块、功能；用户故事通过多对多关系关联功能和模块。跨模块流程单独建图。不要把同一个跨模块故事复制到几个模块，也不要把页面清单当成功能或用户故事。

Spec 表达产品要求，Explore 表达观察到的实际行为，Code 未来表达实现线索。不同入口的产出先作为候选，与项目产品模型对齐、去重、审阅冲突，再形成新版本；观察不能直接改写需求，代码行为也不能自动成为正确性判据。

前置知识与 Skill 都需要，但应区分：知识提供规则、术语、边界和出处；Skill 提供处理方法、指令及可能的工具依赖。Role 决定职责和权限；Agent / 宿主是承载它的执行上下文。换一个角色名称或提示词不构成隔离。

4. 产品模型与数据边界

正式实现建议扩展已有 StoryBundle，增加 schemaVersion，兼容迁移旧格式。下列名称是目标设计，不是当前服务已经支持的字段。

type SourceKind = 'spec' | 'explore' | 'code';
type SourceRef = {
  revisionId: string; chunkId?: string; runId?: string;
  kind: SourceKind; locator: string; contentHash: string;
  assertion: 'required' | 'observed' | 'implemented' | 'inferred';
};
type ProductNode = {
  id: string; projectId: string; parentId: string | null;
  kind: 'module' | 'submodule' | 'feature';
  name: string; description: string; sourceRefs: SourceRef[];
  status: 'candidate' | 'approved' | 'deprecated';
};
type ProductStory = {
  id: string; title: string; actor: string; goal: string; benefit: string;
  primaryModuleId: string; relatedModuleIds: string[]; featureIds: string[];
  acceptance: { id: string; text: string; sourceRefs: SourceRef[] }[];
  journeyIds: string[]; sourceRefs: SourceRef[];
};
type ProductBundle = {
  schemaVersion: 2; projectId: string; revisionId: string;
  parentRevision: string | null; sourceRunIds: string[];
  nodes: ProductNode[]; stories: ProductStory[];
  journeys: { id: string; storyIds: string[]; transitions: unknown[] }[];
  conflicts: { id: string; entityId: string; field: string; sourceRefs: SourceRef[] }[];
};
  • 模块树层数不在数据库写死为三层；parentId 支持更深子模块，禁止环和跨项目父节点。UI 默认逐层展开，初屏只加载主模块及聚合数量。
  • Feature 是可测试的产品能力；Story 是某类用户为达成目标串联这些能力，不要求一功能只能有一故事。当前原型的一故事一功能是样例整理方式，不能成为生产约束。
  • Journey 描述跨模块业务顺序，与模块树分开；故事可关联多个旅程。模块数量不能直接当作故事覆盖分母。
  • 用例冻结 productRevisionId / storyRevisionId / featureIds / criterionIds；批量审批、报告、物料检索共用结构选择器。全项目统计对 caseId / storyId 去重，模块内可同时包含主责与参与关联。
  • 模型版本变化对已审批用例产生影响分析或待重验标记，不静默回写断言。旧执行结果继续绑定其原审批版本。
  • Artifact viewer 根据真实 artifact kind / mediaType 选择结构、Markdown、代码、表格或证据预览；显示 runId、nodeId、revision、sourceRefs，不能仅提供摘要 JSON。
  • 大应用按子树懒加载、队列分页 / 虚拟化、搜索定位、可折叠分支；主路径只展示一到三个层级。验收需包含千级功能、跨模块旅程、同名不同模块与移动窄屏场景。

5. 多入口融合规则

1. 先统一实体，保留事实类型。 同名不保证同一功能。稳定 ID 优先；没有 ID 时给出名称、父路径、验收内容和来源的对齐候选，由用户确认，不自动删旧实体。 2. 新增互补内容。 未发现的功能、异常路径或用户旅程新增为候选，保留来源链。Spec 与 Explore 的同一能力可合并实体，但其 required 与 observed 声明仍分别保存。 3. 冲突不覆盖。 例如规格要求“数量必须大于 0”，页面却接受负数，应形成产品缺陷或规格待确认，不能以“最新观察”为准替换需求。正式融合需字段级解决记录和审核人。 4. 版本并发保护。 提交带 baseRevision / idempotencyKey；基准已变则要求重算差异。融合事件引用全部输入 revision；旧 run 和物料不可变。 5. 审批后影响追踪。 新版本触及的功能 / 验收点，映射到故事、用例与执行缓存，标为待评审 / 待重验。未触及的结果仍可按完整输入与模型指纹复用。 6. 每个入口单独评估贡献。 区分新增真实覆盖、重复、误补、冲突和审阅成本；材料越多、故事越多不等于质量越高。

6. 领域知识与 finance Skill

可以支持金融领域 Skill，但不把“finance”当作一个已存在、已安装或已验证的通用能力。先登记用户实际提供的包、来源与版本。原型没有访问或读取用户其他产品中的私有 Skill。

Agent Skills 标准以 SKILL.md 描述技能，还可包含脚本、参考文档、资源和兼容性声明；因此 Skill 不等同于领域事实文件。Agent Skills 规范

7. 当前职责评估与隔离目标

已检查的本地实现：

  • packages/harness-testing/src/casegen/types.ts 的 StoryBundle 已有 modules、flows、stories、specText 和 derivedFrom；不是从零设计。但故事主要通过 activity / flowId 关联，仍需稳定层级节点、多功能、多模块和版本关系契约。

以领域测试设计为例：领域知识包告诉生成角色数量精度、边界和业务约束；Gold 由人工独立定义应发现的规则 / 缺陷和可验证结果；评估器将实际生成与执行结果对照 Gold 计分。增加生成条目数量不能代替缺陷检出、误报或可执行率。

对象管理者约束
领域知识、Role、Skill 候选产品 / 领域专家与受限 Agent带来源、作用范围和版本；改进须独立评估
Gold 标签与评估器独立标注者、评估维护者人工逐条复核，冻结后修改建新谱系；不向优化器暴露留出答案
候选运行PenguinHarness 评估扩展优化器只见开发反馈；外部工具计算分数
记分板证据TestPilot 只读视图绑定输入、模型、Gold、运行时与策略版本；条件不齐不能直接排名
发布决定人工审核者先满足留出和宿主回归门禁，再晋升；保留历史与回滚

Gold 页面不是普通测试用例审批列表，也不是模型生成答案的自动收纳处。物料中的领域知识与 Gold 可以引用相同产品来源，但不能把候选生成内容自动提升为评判它自己的正确答案。

1. 研究定位与贡献候选

拟定题目方向：Evidence-Grounded Test Generation for Derivatives Interfaces with a Versioned Harness and Controlled Adaptation（基于证据和版本化 harness 的衍生品界面测试生成与受控适应）。暂不以“首个自动生成 Web 测试的 agent”叙述创新性。

目标对象是需求到可执行测试与可信判据的生成，不是让 agent 自己修好 SUT 后证明自己通过。代码修复是一个独立使用场景；主实验冻结 buggy/fixed SUT，生成器看不到缺陷补丁和隐藏答案。界面顺利执行、文本用例数量、引用了 skill、某一次通过，均不是测试质量本身。

贡献候选可证伪主张所需新增机制/证据
C1 领域规则约束的生成与判据在相同模型与预算下，更准确地产生能区分正确/缺陷实现的用例产品作用域、时间/单位/精度/状态不变量的结构契约；独立 oracle 与多个缺陷家族；比较去领域规则和纯模型
C2 从需求到证据的可修订关系结构化来源与影响传播减少无依据断言和漏审，且修订可复现版本化模块/故事/验收点/判据关系；独立关系标注；图形 review 与列表 review 的对照任务

双模型分工、多个宿主兼容和 Web 管理属于工程贡献；是否构成研究贡献要由对照实验支持。第一篇优先聚焦 C1，C2 是可审查性机制；C3 先以严格的受控适应实验呈现。若 C3 无效，明确报告负结果，不为写“自进化”牺牲结论可信度。

4. 数据集与人工依据

数据单位是独立任务及缺陷家族。每个任务绑定产品版本、需求快照、环境 manifest、可观察接口、正确实现，以及一组独立验证的缺陷实现；多次模型采样嵌套于任务。对同一缺陷生成十条用例，仍只算一个独立缺陷检出。

按产品/规则家族分组切分开发、验证与最终留出，避免仅打散同一需求的改写。先做样本盘点、合法发布条件、难度与规则家族矩阵，再用开发集 pilot 估计变异和效应，进行功效/精度设计确定任务数及重复数。不能把每臂 n=3 当正式规模；在冻结前写明纳入、排除、最小有意义效应、主指标、预算与停止条件。

范围至少覆盖数量/价格边界、拒单与状态一致性、幂等/重复提交、杠杆保证金、只减仓/持仓模式等若干独立家族；这是采集计划，不是当前已有数据。把真实历史缺陷与人工变异分开报告。等价、不可达、不稳定变异由独立规则审查后标识，不事后只移除不利样本；排除前后数量都公布。

金标由实际领域人员根据冻结需求/官方来源建立。至少两位独立标注者对覆盖关系、expected 和缺陷类别进行标注，盲于方法臂，分歧裁决留痕；按标签性质报告原始一致率及合适的一致性指标。不得生成“人类确认”事件。既有 protected assets 保持原样，新增正式数据在独立版本/目录创建，由实际人类冻结。

领域知识库可包含业务规则；私有 evaluator 包含隐藏缺陷标识、测试金标与结果。优化器及生成宿主不能读取后者的文件、HTTP 页面、检索内容或日志。当前 macOS 候选隔离已有验证，普通宿主未因此自动具备同等隔离；正式实验要对所有参试方法提供等价的受限访问。UI 的“只读”不是隐藏。

RQ主比较主要结果与判定
RQ1 领域 harness 是否提高有效缺陷检出B0 强 plain LLM、B1 等预算通用检索/执行反馈、B2 可复现的最近 NL→E2E 方法、TestPilot独立缺陷检出、健康误报、有效产物率；相同 planner、executor、材料、环境、预算；相关方法能力差异明确记录

6. 指标与统计口径

指标定义与边界
End-to-end defect recall在所有符合预注册条件的独立缺陷实例上，生成用例能在正确实现通过、在缺陷实现因目标行为失败的比例；无效生成保留在端到端分母
Conditional detection仅有效生成条件下的检出率，与有效率同时展示；不能替代主指标
False positive rate健康任务/实现中被错误报告为产品缺陷的比例；环境故障单列，并给出其数量占总尝试的比例
Oracle correctness独立金标检查用例预期与规则是否一致；输入、单位、精度、时间条件分别分析；引用存在不等于语义正确
Requirement coverage被独立核验为真正测试的验收条件 / 适用验收条件；另报有效执行覆盖。关键词命中仅作代理指标
Mutation score杀死的非等价、可达变异 / 适用变异；真实 bug 检出另报；同家族变异聚类
Validity / failure taxonomyJSON/schema 有效、可执行、判据有效、健康通过逐层漏斗；truncated、invalid_plan、infra、budget、missing_evidence、assertion_failure 区分
Cost / latency全部模型调用、token、缓存、节点时延、p50/p95、重试与搜索开销；按成功任务/独立缺陷同时报告；价格未知为 null
Stability固定输入/SUT 的重复一致性、flaky 比例、环境噪声；跨夜观察按真实日期，不改时间戳凑样本

配对单位是任务/缺陷家族，非每条 case probe。主分析在任务层配对，用聚类 bootstrap 置信区间或合适的层级模型；只有满足独立二元配对前提才用 McNemar 等方法。报告效应量、区间与原始计数，不只 p 值。预声明一个主要结局和有限次级指标；功效不足时报告不确定性，不把“未显著”写成等效。

RQ5 用不同但匹配难度的任务组平衡顺序，避免参与者记住同一答案。预先定义正确修订评分与时间截断，记录放弃任务；招募实际目标用户并取得适当同意，公开匿名汇总而非未经许可的行为轨迹。可用性不能只靠 agent 点击速度。

7. 自进化的边界与流程

“自进化”先定义为有界策略适应：改检索预算/规则选择策略/固定结构的记忆策略/技能草稿；不自动改隐藏答案、评价程序、批准策略和 oracle gold。技能内容改动与模型参数微调是不同工作，当前没有训练模型权重。

流程：冻结开发任务与基线→收集失败分类→候选生成→静态/协议检查→隔离运行→开发集评分→固定预算内验证选优→独立留出一次→人工审核→CAS 激活→监测回归→回滚。研究留出不是每次产品晋级都可反复使用的数据池；消耗后该版本测试集退役，下一周期另建测试集。

保留所有候选，包括失败、拒绝、超时、截断和回滚；隔离 canary 失败则不运行。Web 显示当前激活版本、候选所依据的证据摘要和 Penguin 深链；Penguin 展示候选变更 diff、配对结果、失败样本、预算消耗、评估协议及晋级门禁。宿主可以提出和管理候选，不拥有虚构评分或代替人的权力。

控制奖励投机：新增用例数量不作为唯一目标；拒绝缺证时适当 abstain，不能靠少报所有错误获得高通过率；把健康误报和关键缺陷漏报作为独立约束。回归集含领域正确性和行为隔离用例，安全通过也不等于质量提高。

8. 复现包与论文结构

每次实验 manifest 固定代码 commit/dirty patch hash、schema/skill/role/domain/workflow 版本、模型 ID/端点类型/采样参数、输入及公开知识 hash、SUT镜像/环境/浏览器/依赖锁文件、试验单位/随机化种子、预算/重试/超时、数据划分摘要和授权范围。LLM 即使设置 seed 仍可能非确定，记录提供商版本和真实响应证据；凭证只保留引用。

复现包包含：安装脚本、无密钥样例配置、任务目录、公开需求与许可、正确/缺陷环境部署、原始尝试索引、外部评分脚本、统计脚本、生成图表、失败样本、排除清单、数据字典、硬件与运行时说明。私有资料说明获取条件并提供可公开替代集；若不能公开主数据，要明确复现限制。

论文建议结构：问题与研究缺口→领域挑战与形式化定义→方法/信任边界→实验设计→主要与消融结果→成本/稳定性→受控适应→人工 review 研究（如完成）→威胁与限制→可用工件。把 UI 截图作为可审查机制证据，不能替代主要实验表。

投稿准备门槛：最近工作差异明确；独立冻结数据完成；同模型强基线可运行；主结果含区间及负结果；消融与成本完整；至少一次独立复现；所有结论能追到实验 manifest。论文级不是新增一个“评测”页面即可达到。

TP_PLANNER_API_KEY=your-private-key
TP_PLANNER_THINK=0

执行层也兼容旧 OPENAI_BASE_URL/OPENAI_API_KEY；具体优先级看 server/.env.example 与 connections-env.ts。同名环境变量可能覆盖文件值。项目设置保存后优先于 env，已有运行继续使用冻结快照。仅修改 env 须重启服务；当前没有完整的 UI 恢复环境默认路径，切换前确认覆盖来源。

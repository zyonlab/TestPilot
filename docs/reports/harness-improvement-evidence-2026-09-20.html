01 / 实验怎样避免“自己说自己更好”

  1. 先记录协议：目标、源码、共享依赖、数据、评分器哈希，预算、执行顺序和接受标准。
  2. 用真实规划模型生成开发与保留验证两批用例，结构与需求验证失败便停止并保留失败，不人工改写模型答案。两臂使用相同的冻结输入。
  3. 历史臂读取真实 Git 源码；候选臂读取当前导出器。只替换导出组件，共享依赖保持一致。导出的 spec 与生产 oracle 在真实 Chrome 中执行。
  4. 两臂都用相同的确定性按钮适配器代替 Midscene 动作规划。这将测量对象限定为导出保真度，排除模型定位波动，不能据此评价动作规划能力。
  5. 每个契约包含正常、损坏中间转移、损坏最终转移三个版本。单独点击界面校准注入，24 组控制全部确认。失败只有来自生产 oracle 的断言错误才计为检出；环境错误计为不可观测。
  6. 每种条件各重复三次，按 AB / BA 交替执行。正常对照必须通过；缺陷三次都检出才计为稳定检出。缺记录、重复记录、误报、不可观测、不稳定或丢失既有检出都会阻止接受结论。
这些是本地受控 UI 契约，不是 Hyperliquid 网站的缺陷注入，也没有改动第三方网站。保留验证集由同一代理设计，是已知的保留验证，不是独立盲测。生成器能看到正常行为需求，不能看到故障变体或打分结果。

02 / 为什么旧版本漏检

以打开再关闭为例：用例要求第一步后显示“Dialog open”，第二步后显示“Dialog closed”。旧导出器只保留最后的检查。当第一步失效、第二步仍能回到最终状态时，它会通过；当前导出器保留第一步后的检查，立即检出缺陷。

复核还发现“无机器判据时附加的最终屏幕断言被省略”的相邻问题，已修复并增加回归测试。本轮真实缺陷实验主要验证中间机器断言保留；相邻屏幕断言修复由单测覆盖，不把它算成新增浏览器检出证据。

04 / 评审结论、成本与限制

按用户明确委托进行代理评审，不代表任职于 Google 或 Apple，也不是独立人工标注。已核对冻结的 8 条用例、24 组注入控制、144 次真实 Chrome 执行及截图；封存哈希与离线重算一致。历史导出器稳定检出 8/16，候选 16/16，保留验证 4/8→8/8；两臂各 24 次正常执行零误报，零不可观测，零不稳定，未丢失既有检出。接受“导出器保留中间断言提高该受控契约集缺陷检出”的有限结论。任务共享两步状态机、验证集由同一代理设计，不能推断生成模型、Midscene 动作规划、真实网站或全部宿主全面提升；本记录不批准对外发布。

两批共享用例生成：2 次真实调用，1884 tokens；执行阶段没有模型调用。金额不可得，记为未知。页面执行累计时间历史版 12.72 秒、当前版 14.57 秒；这是页面阶段累计值，包含不同失败停止点，不等于完整实验耗时或性能提升证据。

尚未证明：模型生成质量提升、真实网站上的缺陷检出提升、Midscene 动作规划提升、独立隐藏集泛化、Claude Code / Codex 全链路等价。已有 Gold 未修改，也未用单条 Gold 的词法命中率制造本次提升。

## 2. 已经实现的调整

最初 g2 主要静态编译，只有极少数 ready 用例进入执行包。之后增加持久化逐条准备循环，但首次实现仍要求“先有环境证据”，却没有独立采证能力：第一批 86 条里 83 条 round=0 直接 blocked，仅 3 条实际试跑，2 条通过。

随后已落地以下修复：
1. `preparation_step` 支持 `next / probe / trial / resolve`。probe 可驱动浏览器，使用配置内的钱包、登录步骤、会话和请求头，保存逐步页面文字、URL、时间、截图及检查结果。
2. 没有探查或试跑回执，不能直接 resolve blocked。旧资料写“未确认”不应自动阻塞。
3. trial 在同一浏览器先重放准备步骤、重新检查原始前置条件，再执行业务测试步骤；准备证据不会直接变成 verified。
4. 已审核的预期、前置、断言等保持约束；只有真实试跑通过才记 verified，生成执行包。
5. 准备步骤和前置检查写入执行包，正式执行复用，并校验其未被修改。
6. UI 支持重试当前批次未通过项或全量新批次；历史通过与本批通过分开显示。低影响、少前置的用例优先，再按用例编号排序，尚非依赖拓扑调度。
7. 修复同批重试物料缺少 parentRevision 的版本冲突；协议写入失败回收状态，避免假运行中。停止后可通过明确操作恢复。
8. 探查最多 3 次，试跑受 maxRounds 和预算限制；取消/重启与 generation 隔离迟到回执。

## 4. 下一步想怎么解决：公共前置与经验复用

以下均为待实施设计，不要写成已支持。

### 4.1 先区分三类东西

- **事实**：当前 URL、配置的鉴权方式、实际注入账户、会话检查回执。由系统/执行器提供带来源事实，不靠截图猜。配置存在不等于登录成功、交易授权完成或已注资。
- **公共前置 recipe**：可重复执行的准备方法，例如连接配置钱包、显示完整地址、打开 Balances、切换币对并读取规格。包含适用条件、输入、步骤、后置检查、失效条件和清理要求。
- **经验**：某条路径成功/失败、定位歧义、判定坑与有效修复，引用真实回执。经验帮助规划，不是产品规则，更不是当前条件已满足的证明。

价格、余额、仓位、杠杆、订单状态不作为长期常量记忆。可复用的是读取和验证这些值的方法；读数必须实时重新取得。不能从“同钱包曾登录成功”推断下一次全部授权完成。

### 4.2 如何知道是“公共”

模型可以提名，但服务端按契约和证据决定是否晋升；不是出现相同文案就抽成公共。

建议等级：case-local → candidate → verified-reusable → stale/rejected。

公共候选至少说明：
- 服务的能力，例如 `auth.ensure-connected`、`account.open-balances`，而非一条业务验收结果。
- 至少两个使用场景/用例的需求匹配，或项目已显式配置的通用前置。只在一个用例成功时保持局部候选，不声称普遍有效。
- 相同起点/终点状态、鉴权方式、产品版本/页面特征与副作用范围。
- 差异可参数化；币对、账户、数量不能误当作可以任意替换的参数。
- 逐用例新鲜后置检查仍然成立。两个用例都复制同一份旧回执不算两次成功。

推荐晋升门槛：在两个不同用例上取得独立成功回执且无冲突，或受控独立验证公共配置契约。次数是门槛之一，不替代语义契约。反例出现就暂停复用或收窄作用域。

例如“页头地址 → 菜单 → 悬停查看完整地址”可在同产品钱包会话范围提名；“本次 HYPE 当前价”不可公共化。“没有仓位”的本次观察不是永久产品限制。

### 4.3 每轮如何带经验

不是把整个历史日志每次全塞给模型。建议在 `next` 返回按当前用例检索的上下文快照：

1. 当前系统事实与鉴权检查结果（脱敏、标记时间和来源）。
2. 匹配当前前置条件的公共 recipe 及固定版本。
3. 与当前失败类型/控件/能力有关的经验，带正反证据。
4. 当前用例最新 probe/trial 回执、未解决条件。
5. `experienceContext` 的条目版本、选择理由、digest，记录本轮实际分发了什么。

每次 probe/trial/resolve 后提取候选、追加证据、去重与冲突检测；下一轮及后续用例可用更新后的经验。已发给当前轮的快照保持不变，复盘能追踪。跨运行只复用匹配项目、目标路由族、鉴权方式、账户模式、环境及版本条件的有效条目；跨项目默认不传播。

首次返回候选提示“待验证”，不得将候选当作执行依据自动放行。限制上下文预算与条数，保留来源引用供按需读取。

### 4.4 受控公共 fixture 不等于复用同一份资金状态

对需要仓位/订单/划转的用例，需要单独的 setup contract：
- 前提与授权范围、目标测试环境、准确账户/市场身份。
- 参数来源、十进制精度、最小数量/名义金额和资金上限。
- 建立前基线、创建的订单/仓位标识、实际成交与费用记录。
- 后置条件、清理策略、失败补偿及清理结果。

默认每用例隔离或显式串行租用；不得跨用例无声明共享可变仓位，也不能自动平掉不属于当前 fixture 的仓位。无法安全构造受控行情或历史结算时点时，保留阻塞及原因。不要为提高通过率随意放宽用例条件。

公共 recipe 可以复用代码；其生成的仓位、余额及验证证据不能无条件复用。

### 4.5 经验物料及后续 E2E 公共代码

建议产物：
- `preparation/<batch>/experience`：结构化版本化经验。
- 对应可阅读文档：适用范围、公共前置列表、已验证方法、踩坑/修复、未解决问题、证据链接。
- 每轮方案保存 `experienceRefs` 和 `recipeRefs`；UI 列出实际分发条目，不能把全部历史经验伪装成本轮输入。

建议最小字段：id/version、kind、status、scope、capability、parameters、preconditions、steps、postconditions、sideEffects、cleanup、evidenceRefs、sourceCaseIds、success/failure evidence、createdAt/lastVerifiedAt、invalidatedBy。字段需服务端校验；自由文本不得成为系统指令。

E2E 导出只从已验证 recipe 生成 fixtures/helpers，业务断言留在用例中。公共代码需保存 recipe 版本、来源和使用用例映射；不得只按相似字符串抽取，不能改断言时序、吞掉清理逻辑或把动态金额写死。导出后应有独立验证，不因原准备回执通过就假定生成代码等价。

## 6. 建议实施顺序与验收

1. **先修事实来源与前置检查分类。** 配置/注入事实用确定性检查；页面状态用页面证据；跨步骤数值/账本用结构化采集和计算。对无法观察的事实返回 unknown，不能截图猜成 false。
2. **放开有边界的修复。** 保留全部已审核业务验收，允许可追踪的辅助观察、校验实现和公共 setup 引用；新增业务义务、改预期或删断言仍复审。用划转用例做回归。
3. **接公共 recipe 与逐轮经验。** 先实现钱包连接、完整地址、Balances 等低影响前置，证明后续用例减少重复探索且仍重新校验。
4. **再做受控 fixture。** 从一个有完整 setup/teardown 的测试仓位开始，不一次铺开所有多资产和结算场景。
5. **最后接 E2E 导出公共代码。** 保持执行语义、断言时序、清理与证据追溯。

必测：跨用例经验分发、候选不自动晋升、作用域不匹配不复用、动态读数失效、负面证据撤销、重启/取消恢复、物料版本冲突、脱敏、提示注入隔离、held-out 不泄漏，以及新代码导出前后语义一致性。

真实验收不要只看通过数量：检查钱包前置不再猜错环境；共享连接/资产表方法能用于后续用例；资金操作有独立基线和清理；真正缺 fixture 的用例清楚说明停在哪里。先验证代表性用例，再继续全批；保存前后对比的执行次数、耗时、失败归因和经验引用。

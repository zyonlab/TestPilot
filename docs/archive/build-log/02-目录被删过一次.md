# 目录被删过一次 · The benchmark directory that was deleted once

> 2026-09-03（误报）与 2026-09-07（真事）· 出处：`docs/v3/history/00-架构.md §12`；`docs/v3/history/07 §10` T-23 / P5 两行

## 中文

**第一次：一场误报。** 三路并行开发（1A 工具 / 1B skills+hooks+基准 / 1C 领域服务）合流那天，1B 报告 `benchmark/` 在 11:01 被整删，丢了 5 条人工标注。核对下来：删它的是 1C 清理验证夹具——审计端点默认写 `REPO_ROOT/benchmark/`，1C 在那里放过一份合成 gold 和通过 POST 写入的合成标注；丢的 5 条 `g-03/04/07/08/10` 正是那份合成 gold 的 heldOut 五条（小写 id；真的 Binance gold 用大写 `G-xx`），而到那一刻还没有人打开过审计台。**没有人工标注丢失。** 留下两条规矩：标注要有第二份副本；清夹具只清自己建的文件。

**第二次：真的动了考卷，而且是我。** 2026-09-07 做 T-23（`docs/spec` 与 `docs/refactor` 归档），全仓 118 处引用批量改成 `docs/archive/…`。`benchmark/casegen/gold.json` 的 `spec` 与 `note` 字段里引用了 `docs/spec/03`，被一起改了——**内容一个字没变，`goldHash` 从 `2405209c3fe70ac7` 变成 `3443d9d0fe719344`。** 谱系哈希不区分「改了规则」和「改了一个路径字符串」，这正是它该有的性质：考卷动了就是新考卷。发现是在第二天做记分板屏（T-18）时，README 写的哈希和文件算出来的对不上。`git checkout` 复原，哈希回到 `2405209c3fe70ac7`；顺手发现 `README.md` 里「由 score_run 追加」的记分板，代码里没有一处在追加——两张记分板从来都是空的（`appendScoreboard` 是那一刻才补的）。

**预判对错。** 我预判「批量改路径是纯机械操作，不会碰到基准」——错。机械操作最容易碰的恰恰是被规矩保护、平时没人打开的文件。`CLAUDE.md` 第一屏写着「不改 `benchmark/*/gold.json`」，而 sed 不读 `CLAUDE.md`。

**改了什么。** 07 §10 记一行；gold 屏（T-19）显示「冻结哈希 ≠ 当前哈希」的红字，让这种事下次在界面上就能看见，而不是靠人对着 README 心算。

## English

**First time: a false alarm.** On the day three parallel tracks merged, track 1B reported that `benchmark/` had been wiped at 11:01, losing five human labels. On inspection the deletion was track 1C cleaning up its verification fixtures: the audit endpoint defaults to writing under `REPO_ROOT/benchmark/`, and 1C had put a synthetic gold and POST-written synthetic labels there. The five "lost" items `g-03/04/07/08/10` were exactly the held-out five of that synthetic gold (lower-case ids; the real Binance gold uses `G-xx`), and nobody had opened the audit desk yet. No human label was lost. Two rules stayed: labels get a second copy; fixture cleanup deletes only what it created.

**Second time: the exam paper really was touched, by me.** On 2026-09-07, task T-23 archived `docs/spec` and `docs/refactor` and rewrote 118 references repo-wide. `benchmark/casegen/gold.json` referenced `docs/spec/03` in its `spec` and `note` fields and was rewritten too. Not one rule changed, yet `goldHash` moved from `2405209c3fe70ac7` to `3443d9d0fe719344`. The lineage hash does not distinguish "changed a rule" from "changed a path string", and it should not: a touched paper is a new paper. It surfaced a day later while building the scoreboard screen (T-18): the hash in the README no longer matched the file. `git checkout` restored it. The same check revealed that nothing in the code had ever appended to `scoreboard.yaml`; both scoreboards had always been empty.

**Prediction vs outcome.** I predicted a bulk path rewrite was purely mechanical and would not reach the benchmarks. Wrong. Mechanical edits reach exactly the files rules protect and nobody opens. `CLAUDE.md` says "never modify `benchmark/*/gold.json`"; sed does not read `CLAUDE.md`.

**What changed.** One row in 07 §10; the gold screen (T-19) shows a red "frozen hash ≠ current hash" so this is visible in the UI next time instead of by comparing a README to a checksum by hand.

# 09 交互重构调研：左 chat + 右无限画布

> 状态：**调研，未落地**。这份文档不改任何现有规格。
> 如果采纳，03（UI 交互规格）需要重写——而 03 同时是自举的 spec 输入，见 §7。
> 调研日期：2026-08-20

## 0. 要回答的问题

现在的 UI 组织方式是「功能页面」：十三个导航目的地，一次工作的产物散落在其中五个里。
提出的方向是 MiniMax Design 那种形态——**创建项目 → 左侧 agent 对话 → 右侧无限画布**。
这份文档调研这个范式怎么运作（可视化过程、中间产物、产物、workflow、节点调整），
以及它有多少能搬到一个「测试用例生成 harness」上。

## 1. 现状：我们不是一个工作台，是十三个页面

导航目的地：项目 / 探索 / 用例 / 复核队列 / 套件 / 趋势 / 画布 / 评测 / 运行 / 模型配置 / 链上 / 进程 / 能力与 Chat。

**一次工作流运行的产物，现在分布在五个地方：**

| 产物 | 在哪 | 形态 |
|---|---|---|
| 节点产物（故事、用例、代码） | 画布右侧面板 | `JSON.stringify(...).slice(0, 20000)` |
| 待复核的用例 | `/#/review` | 列表 |
| 批准后的用例 | `/#/cases` | 看板 |
| 执行轨迹、截图 | `/#/runs` | 报告页 |
| 覆盖率、配对差值 | `/#/evals` | 卡片 |

画布上画的是**流程**，不是**产物**：节点卡片显示耗时、调用数、门禁分，点开是一坨 JSON。
所以「这次跑出了什么」这个问题，没有任何一个页面能整个回答。

这就是那种"不太合理"的具体形状：**产品的组织单位是功能，而工作的组织单位是一次运行。**

## 2. MiniMax Design 的形态

官方指南正文需要登录，我拿到的是**完整目录**与公开产品页，下面据此重建（有猜测的地方标出来）：

指南目录：安装与登录 → **界面概览** → **创建新项目** → **Agent 对话** → **技能**（技能广场 / 自建技能）
→ 高级插件 → **画布：agent 能看见并能操作的工作区** → **素材中心：产物复用与管理** → 模型列表。

产品页给的运作方式：

- **五步流水线**：意图接收（描述想法或丢一份 brief）→ 画布流（脚本、分镜、视频、音乐、剪辑在同一张画布上，节点自动连接）→ 复用层（技能与插件）→ 本地桥（画布素材自动落本地）→ **复核回路（checkpoint，agent 推进前等人确认）**。
- **多 agent 并行**：文案 agent、图像 agent、视频 agent、音频 agent 同时开工。
- **技能是有版本的可安装工作流**（例如 `Promotional Video / v0.1.15`）。

三个关键词值得注意：**agent 能看见并能操作的画布**、**素材中心**、**checkpoint 复核**。

## 3. 这个范式的四个承重概念

跨 MiniMax、Lovart、以及一批 agent UX 总结提炼出来的，不是某一家的实现细节：

1. **画布即上下文**。Lovart 的说法最直白：agent 被困在线性聊天窗口里就没法工作，它需要一个共享工作区；
   画布上已有的素材（品牌规范、之前做的包装）会持续作为约束进入下一次生成。
2. **产物是一等对象**，不是聊天记录里的附件。产物有自己的位置、可以被选中、被比较、被复用。
3. **选择即指令上下文**。MiniMax Agent 已经在聊天侧做了这件事：选中回复里的文本 / 代码 / 表格片段，
   引用并批注，随下一条指令一起发出。画布形态是它的空间版本。
4. **计划是可编辑的对象，不是流水账**。plan-execute 模式先把打算做的事摆出来再执行，
   让人在花掉资源之前纠偏；每一步是一个明确状态（排队 / 运行 / 待批准 / 错误 / 重试 / 完成），
   长任务需要一个**独立于聊天流的审计面**。

## 4. 「可视化节点调整」的成熟做法

这一格我们其实是同行，值得逐条对照：

| 产品 | 做法 |
|---|---|
| **n8n** | 单节点运行；用 pinned data 重跑历史执行；层级化日志里追踪失败 |
| **Dify 1.5** | 画布底部常驻**变量检查面板**，实时显示整条流程的所有变量 |
| **Coze** | 拖拽编辑 + 实时调试 + 逐节点输入输出检查 |
| **LangGraph Studio** | 图是实时视图；逐节点单步；每个 checkpoint 可看状态；**编辑状态后从任意 checkpoint 重放**；`interrupt_before` 就是断点 |

**我们已经有的**：只跑此节点 / 从此节点续跑 / 断点与继续 / 图版本 pin / 节点产物落库 / 逐节点成本 / 提示词指纹。
机制这一层不缺东西。**缺的是把这些做成看得见、点得到的东西**——现在断点是节点上一个红点，产物是一坨 JSON。

**我们比上面四家多出来的一格**：可复现性。图版本 pin + 提示词指纹 + 消融记录，
意味着我们的画布不能像设计画布那样"随手改一下"——每次修改必须产生版本，否则评测层立刻失去意义。

## 5. 哪些能搬，哪些不能

### 能搬

- **项目 → 一个工作台**（左对话 / 右画布），而不是十三个页面。
- **产物上画布**：故事、用例、代码、运行、评测都是画布上的卡片，挂在产生它的节点下面。
- **选择即上下文**：选中一条用例 → 左侧输入「这条断言改成可观测的」；选中一批 → 「把写死的凭证都换成占位符」。
  这两件事我们后端**已经有了**（复核队列的单条重生成、批量替换），只是入口藏在一个列表页里。
- **checkpoint 复核回路** = 我们的断点 + 复核队列，合起来正好是它。
- **技能广场** ≈ 我们的图库 + 版本；**chat 造技能** ≈ 我们已有的「Chat 起草图 → 校验 → 保存为新版本」。
- **素材中心** ≈ 「一次运行的全部产物在一个地方」，这正是现在最缺的。

### 不能照搬

**产物性质不同，这是最要紧的一条。** 设计 agent 的产物是图像，**看**一眼就能判；
我们的产物是一百多条结构化文本，**读**才能判，而且要按故事、方法、tier、门禁分筛着读。
在无限画布上铺一百张用例卡片，比一个带筛选的列表更糟——它把"可扫视"这个唯一优势也丢了。

所以正确的分工是：

- **画布承载过程与形状**：图、每个节点的状态与成本、聚合数字（4 个故事 / 100 条用例 / 门禁 93% / 27 条 finding）、**抽样**（展开看 3 条）。
- **列表与表格承载批量产物**：从画布上的聚合卡片点进去，就是现在的复核队列 / 看板，带全部筛选器。
- 两边互相跳转，选中状态共享。

**另外两条约束是我们独有的：**

- **可复现性**：chat 驱动的修改必须继续产生图版本与提示词指纹。画布可以随手拖，但"保存"必须是一次立版。
- **判定硬度必须画出来**：一条用例是程序判的还是模型看截图判的，卡片上要能看见（`machine` / `judge`）。
  否则可视化会把 judge 的抖动画成事实——这正是 M2 三轮里通过的用例每次都不一样的那个坑。

- **现在的五个产物页面**不删，变成检查器的展开态与深链目标。

## 7. 代价与风险

1. **03 是 UI 规格，也是自举的 spec 输入。** 改 03 等于改测试输入：历史覆盖率数字会立刻不可比。
   处理方式二选一——冻结一份旧 03 做对照集，或明确承认这里有一个断点并重新建立基线。
2. **「画布即上下文」在我们这里很贵**：把一百条用例塞进模型上下文是几万 token。
   必须是**选择性上下文**（选中什么给什么），不能是设计工具那种"画布上有什么都看得见"。
3. **保全矩阵（04 §7）**：十三个页面里的功能一个都不能丢，重构要按矩阵逐项回归。
4. **无限画布本身不是目的**。它解决的是"产物散落"和"选择即指令"，不解决"一百条用例怎么读"。
   如果只把节点框做成可以无限拖动，而产物还是 JSON，那这次重构什么也没改善。

## 8. 下一步的三个选项

| 选项 | 内容 | 代价 | 可逆性 |
|---|---|---|---|
| **A 产物上画布** | 不动导航，先让一次运行的产物以卡片形式挂到节点下，聚合 + 抽样 + 点进现有页面 | 小 | 完全可逆 |
| **B 完整工作台** | 左 chat / 右画布 + 检查器，导航收缩到 4 项，五个页面降级为检查器形态 | 大 | 需要按保全矩阵回归 |
| **C 并存原型** | 新增 `/#/workspace` 与现有并存，拿一次自举跑对比"哪种更快找到问题" | 中 | 完全可逆 |

**建议顺序：A → C → B。** 先把产物搬上画布（这一步无论最终形态如何都不会白做，
而且立刻能验证第 5 节那个判断：一百条用例到底该在画布上还是在表里），
再用并存原型做一次真实对照，最后才动导航。

## 补充：代码与执行记录怎么展示（8-21）

参照旧 UI 的组件重做，并补上它没有的那层区分：

- **代码三态**：`生成的`（codegen 产物）→ `修复后`（有界修复改写过的，带改动分类）→ `最终可用`（门禁②通过、已批准、能进仓库）。
  前两态属于**那次运行**，最终态属于**这条用例**。可切 tab、可与生成版逐行对比；
  没进过修复循环的用例会明说「没进过修复循环」，而不是把生成版当修复版展示。
- **执行详情**：逐节照搬旧 `RunDetail` —— 功能断言 / 性能基线（含批准）/ 视觉基线（三图 + 批准）/ 步骤与日志 / 逐步截图 / 报告链接，
  另加两件旧 UI 没有的：**谁判的**（程序 or 模型看截图）与**归因**（infra 不计入产品缺陷）。
- **批次**：门禁徽标 + 六个统计（总数/通过/失败/自愈后通过/抖动/隔离）+ 逐条用例行，点行进执行详情。
  六个数不是一个数：自愈说明多少绿是用重试换来的，抖动与隔离说明这套还能信多少。

第一次跑出来的三个缺陷都已修：① 回复被 `max_tokens` 截断 → 一个故事的全部工作丢失（调大预算 + 提示词限制每故事条数）；② 模型用英文回答中文 spec（加语言指令）；③ **度量工具本身是单语的** → 系统性低估诚实的工作（黄金清单关键词与门禁正则改双语）。

**已知的度量偏差**：第二次的 G-09/G-10 判为未覆盖，但产出里其实有对应用例，只是措辞是「不显示文案 …」而清单里写的是「不显示错误」。确定性关键词匹配的代价就在这里——**Coverage 是下界**。不再逐次加同义词，那会滑向对着某一次运行调分数。

### 阶段 1 结束时的已知欠账

| 欠什么 | 影响 | 我的判断 |
|---|---|---|
| **`agent` 进程是空壳**：图运行时跑在网关里 | 一次长跑会占着网关的事件循环；网关重启会打断运行 | 阶段 2 开头补。接口已经就位（`runGraph` 只依赖 registry/bus/store），搬过去是接线 |
| **消融开关没有消费者** | `ABLATE=` 传得到 `ctx.ablated`，但没有任何节点读它 → 目前无法真正关掉一个组件做配对比较 | 要做配对评测就必须先补：至少让 `design.cases`（设计方法）、`gate.textcase`（判据分级）、`codegen`（片段提取）可关 |
| **配对评测没有入口** | `mcnemar` / `comparePaired` / `scoreDetection` 都有实现和测试，但没有"跑两版、相减、出报告"的 CLI 或接口 | 与上一条是同一件事的两半 |
| **P/R/F1 没有真实数据源** | 需要"这条用例本该 pass 还是 fail"的标注（缺陷注入或人工标注），目前 fixture 应用没有已知缺陷 | 最实际的做法是给 `/testlogin` 加一个可开关的缺陷开关 |
| **上下文预算 / 分层记忆 / 软硬依赖调度** | 05 §10、§8 写了，`harness-core` 里没有 | 单个 spec 还塞得进上下文，所以没到痛点；产品文档一大就会 |
| **画布拓扑编辑、版本 diff、断点开关** | 只能改参数 | 阶段 2 |
| **MetaMask 扩展模式未实跑** | 注入式钱包已验证；扩展模式需要有头浏览器 | 需要你在有显示器的会话里跑一次 |

## 阶段 2：人工介入调优 + 自举

**逐项进度**（2026-08-20）

| 断点开关（UI） | ✅ | 节点卡片上的红点即断点；运行停在它前面，工具栏出现「继续 · <节点>」。运行时规则改了一处：**被点名要跑的节点，它自己的断点不拦**——否则「继续」会永远停在同一个节点上。断点集存在运行记录里，刷新页面不丢。实测 `spec/stories` 两个断点：停在 spec（零模型调用）→ 继续 → spec 跑完停在 stories |

## 贯穿全程的三条纪律

1. **不丢功能**：每阶段结束跑一次 04 §7 的保全矩阵回归。
2. **不留无证据的组件**：新增组件必须进消融清单，并回答"它改的是结果还是只是过程"。
3. **记全轨迹**：lineage 从阶段 0 第一天就开，历史数据补不回来。

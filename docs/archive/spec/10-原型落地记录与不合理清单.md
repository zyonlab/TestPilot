# 10 · 原型落地记录与不合理清单

把 `09-prototype-workspace.html` 的五落点结构（工作台 / 资产 / 迭代 / 运行 / 设置）落到真实 UI 的过程记录。
分两部分：**已修**（这一轮当场改掉的）与**已记未修**（改动面超出这一轮，写清楚为什么、以及下一轮从哪儿动）。

判断标准只有一条：**用户能看到的东西必须对应一件真实存在的能力**。一个点下去什么也不发生的按钮、
一个凭猜测显示的字段、一条测的是不存在功能的用例，都算不合理。

---

## 一、已修

### 1. 路由重定向与项目守卫互相抵消

`Layout` 的 `SCOPED_PATHS` 还写着旧路由（`/cases`、`/runs`、`/suite`、`/trends`、`/explore`），
而这些路径现在是重定向。于是一个指向 `/#/cases` 的旧书签会先被重定向到 `/assets`，
再被守卫弹回项目页——两段逻辑各自都"对"，合起来把人送到了第三个地方。

- 守卫改成只认新落点：`/assets`、`/history`。
- 未选项目时的落点从已删除的 `/projects` 改为 `/settings?s=projects`。
- 页面内残留的 `navigate("/cases")` / `navigate("/explore")` / `navigate("/projects")` 一并改到新地址。

### 2. TopBar 在分节里整体消失，把页面唯一的操作按钮一起带走

分节托管旧页面时，`TopBar` 直接 `return null` 以避免两层页头。代价是它的 `actions` 也没了：
「新建项目」「试试 dapp 示例」是项目页仅有的两个入口，在 `设置 → 项目` 下一个都点不到。

改成：分节内只让"身份那半"（面包屑、网关标识）让位，`actions` 单独保留一行。

### 3. 工作台在没有项目时不可达

侧栏四个落点整体挂在 `inProject` 下，但工作流做的事是「读规格 → 产用例」，本来就不需要先有看板。
自举那几轮实际上全靠手敲 URL 驱动的。改成未选项目时侧栏也给出 工作台 / 迭代 两个入口。

### 4. 看板出现 `tnull` 档位

`tier` / `gateScore` 是可空列，从数据库回来是 `null`；判空写的是 `!== undefined`，
于是没有判定层级的用例渲染出一枚 `tnull` 徽章，过滤器里还多出一个 `tnull` 选项。
四处改为 `!= null`。

### 5. US-01「目标端」规格里写了、代码里一处都没有——却已经有三条自举用例在测它

`02-业务规格与用户故事.md` 的 AC-01.1 写着「目标端为 web 时可选启用 web3 能力；iOS/Android 时该选项不可见」，
`09` 已经记过这个缺口。这一轮补齐了整条链路：

| 层 | 改动 |
| --- | --- |
| 存储 | `projects` 增列 `targetPlatform TEXT NOT NULL DEFAULT 'web'`（旧项目行为不变） |
| 接口 | `POST /api/projects` 接受 `targetPlatform`；新增 `PATCH /api/projects/:id`（改名 / 换入口 / 切端），非法值 400 |
| 前端 | 新建表单加目标端选择；已进入的项目在 `设置 → 项目` 顶部可直接切端；卡片显示端标签 |
| AC-01.1 | 非 web 端时，用例详情的 WEB3 配置区与设置里的「链上测试」分节整块消失 |
| 测试 | `server/test/project-platform.test.ts` 四条：默认 web、按端创建、切端不动其余字段、不存在的项目不返回伪造行 |

**切端不删数据**：iOS 只是把控件藏起来，切回 web 时原来的 web3 配置还在原处。
下拉框一动就静默清掉用户已保存的配置，比藏一个字段更难解释。

### 6. 进程页把「进程存活秒数」当成累计成本显示

`累计成本` 渲染的是 `${spend.tokens} tok · ${spend.ms/1000}s`，而 `spend.ms` 在 `harness/child.ts`
里是 `Date.now() - startedAt`，即进程自己的存活时长——左边两格的「运行时长」就是同一个数。
于是这一格长期显示 `0 tok · 73720.6s`，读起来像一个没人在付的成本；真正的钱 `spend.usd` 反而没显示。
改为 `tokens (+ $usd)`。

### 7. 自举用例的矫正

| 用例 | 问题 | 处理 |
| --- | --- | --- |
| 目标端三条（`tc-mt0gmyex-1002` / `…y-1003` / `…y-1004`） | 测的功能当时不存在 | 功能已补（见 5），补上前置状态与可观察的落点（链上测试分节 / WEB3 配置区） |
| `tc-mt0xgmz3-1002` 进程字段 | 要求出现「类型」字段名，但 UI 是直接把 `gateway`/`node` 作为值呈现，没有这个标签；tier-1 断言按字面文本判会误判 | 期望改写成「显示进程类型（gateway/agent/runner 之一）」，并把成本口径明确为 token 数 |
| `tc-mt0xgmz3-1003` 停止进程 | 「该进程」没有指代对象，也没有起始状态 | 指明 runner 进程，补前置 |
| `tc-mt0xgmz4-1004` 空消息 | 无前置，落点是旧对话框 | 指向工作台右侧对话栏，期望改为「发送按钮禁用」（这正是当前实现） |

这一点已经在 `CODEGEN_STABLE` 里约束过代码侧（「PRECONDITIONS 是一个状态，不是一句注释」），
但生成侧仍会产出没有前置的文本用例——见下面的 D。


### 8. 补上原型的代码线：`资产 → 测试代码` / `资产 → 变更`

原型这两节此前一个都没落地，而它们回答的正是「生成的代码和最终可用的代码怎么展示」。

**核心区分**：生成的代码属于**那次运行**（被门禁②打过分、可能被修复环改写过几轮）；
最终可用的代码属于**这条用例**（今晚要跑的就是它，批准后可能已被改动）。合成一栏，
就会让「机器产出了这个」和「跑的是这个」看起来是同一件事。

| 层 | 改动 |
| --- | --- |
| 服务端 | 新增 `server/src/codeline.ts`：`codeProvenance(caseId)` / `codeLine(projectId)` / `changes(projectId)` |
| 接口 | `GET /api/projects/:id/code-line`、`GET /api/projects/:id/changes`、`GET /api/cases/:id/code` |
| 前端 | `src/pages/CodeLine.tsx`：KPI（可运行 / 门禁②均分 / 公共片段 / 已偏离 / 被改松）+ 用例表 + 右侧三态抽屉（最终可用 / 生成的 / 差异，LCS 行级 diff）+ 变更表 |
| 测试 | `server/test/codeline.test.ts` 11 条 |

三条设计纪律，都写进了代码注释：

1. **不重算任何数字**——门禁②、修复轮次、退化标记全部从产出它的那次运行里读回来。
   一个页面不该报出运行本身从未得到过的分数。
2. **靠复核决定连接两侧，不靠标题匹配**——运行内是 `US-02-1-…`，看板上是 `tc-…`，
   两条同名用例第一次出现时，标题匹配就会配错人。有专门一条测试守这个。
3. **没有代码的用例也要列出来**——「我的用例里有几条真能跑」是这一页的第一个问题，
   悄悄略过没代码的那些，等于用「看起来很完整」回答了它。

### 9. 变更清单一开始把「设优先级」当成了改写

第一屏四行全是「优先级 · 人改的」——那是复核队列的批量设优先级按钮，不是有人改了用例。
`review.ts` 里本来就写明这条规则（设优先级是对看板的决定，不是对用例的改动），
是我的新清单没有遵守。已加 `NOT_A_REWRITE`，两处口径现在一致。


### 10. 补上 `资产 → 需求追溯`，并把 US-03 的「断言凭什么这么写」做成可判定的检查

原型这一节只画了「用例 → 指回 → 锚点」三列。落地时发现锚点这一格可以做成真的：
`spec` 节点把喂进去的全文存了下来，所以「断言引用的界面文案能不能在材料里查到」是可判定的。

- 服务端 `server/src/trace.ts` + `GET /api/projects/:id/traceability`；前端 `src/pages/Trace.tsx`。
- 三个问题一页答完：用例 → 故事（孤儿高亮）、故事 → 用例（没有用例的故事，即覆盖率下界的来源）、
  以及每条断言引用的文案是否在材料里查得到。
- 9 条测试（`server/test/trace.test.ts`）。

**措辞是这一节最要紧的地方**：查不到 ≠ 错。可能是模型编的，也可能是产品确实这么显示、
只是规格没写——前者改用例，后者补规格。所以那一列叫「材料里查不到依据」，给的是
「这条断言能不能自证」的下界，不是对错判决。另外「断言没有引用任何界面文案」单独成一档，
不算通过：无从查起和查过了是两回事。

判定用确定性字符串比对而不是再问一次模型：用模型判自己有没有编造，量的是它的自评。

**第一次跑就抓到了我自己写的两条**：上一轮我矫正自举用例时写的「状态变为『已停止』」「不再显示『当前任务: …』」，
这两串字在 02/03 两份材料里都查不到（「已停止」是 `proc.state.exited` 的译文，规格从没写过 UI 会这么显示）。
断言本身没错，但它无法从材料里自证——这正是这个检查要暴露的东西。


### 11. 迭代页把变异检出结果当成"坏掉的配对评测"渲染

`server/src/evals.ts` 早就在算变异检出（把套件分别跑在健康构建和每个注入缺陷上），
结果也和配对评测存在同一张表里，列表里能看到 `det-*` 行。但前端把**每一行**都按 A/B 配对结果读，
`det-*` 没有 a/b 两臂，于是点开只会得到一句琥珀色的「没有结论」——一个已经算出来的答案，
被显示成了一次失败的评测。

已加判别（有 `mutants` 就是检出评测，有 arms 就是配对评测）与专门的面板：
变异检出率、误报率、逐个注入缺陷（被抓到 / 漏了、谁抓到的）、在健康构建上就失败的用例单独列出。

**两个数字方向相反，所以必须并排**：一套把什么都判失败的用例，变异检出率是 100%，却毫无价值。
实测 `det-mszyn6cf`：检出 50%（2 个缺陷抓到 1 个）、误报 0%。


### 12. 补上 `运行 → 待审批基线`

批准入口一直长在执行详情里（每条差异旁边），那没错；缺的是一份清单——
没人会为了找出哪几条在等自己，去逐个点开三十次运行。

- `server/src/pending.ts` + `GET /api/projects/:id/pending-baselines`；前端 `src/pages/Baselines.tsx`。
- 这一节**不复制批准逻辑**，调的是同两个既有接口，只回答「谁在等」。
- 判定「还在等」用时间戳比较，不另立一张表：视觉看基线图的 `updatedAt` 是否晚于那次运行，
  性能同理。批准本来就会写这个时间戳，多存一个「已读」标记就多一处会和事实不一致的地方。
- 只看每条用例**最近一次**运行：三周前的差异如果后来跑绿了，那是历史不是待办。
- 实测 `Wallet Smoke (dapp)`：6 条视觉差异（8.5%–9%）+ 3 条性能回归（含 `fcpMs 100 → 453`），三张对比图真实加载。

写的时候发现一个接口误用：性能基线批准端点收的是 `runId` 而不是 `metrics`——它自己回读那次运行的数字，
所以基线不可能由前端编造的数值设定。第一版我传了 `metrics`，已改正。这正是「调同一个接口」的意义。

### 13. 把「模型配置」那一页拆开

`ModelConfig.tsx` 那 1600 行里装着四件互不相干的事，只是碰巧共用一个文件：
**环境**属于项目、**提示词模板**属于 harness（改它会进指纹、影响每一次后续运行）、
**语言与调试**属于这个人、**端点与串行闸**才属于模型。

拆法是把已有的卡片导出来重新组合，没有重写它们：`EnvironmentsCard` / `SecretsCard` 直接导出，
`DebugPromptsCards` 加一个 `show` 参数（`prompts` / `prefs`），fetch 仍然共用，页面不再共用。
设置现在是四组九节：项目（项目 / 环境 / 链上测试 / 危险操作）、模型（端点与串行闸 / 提示词模板）、
运行时（进程 / 能力与 Chat）、偏好（语言与调试）。

顺手修掉了发现 F：**危险操作用应用内对话框，不再用 `window.confirm`**。原生模态会阻塞页面事件，
harness 跑到这一步就驱动不下去了——一个要能测自己的产品，不能在关键路径上用浏览器原生弹窗。
确认方式是照抄项目名而不是点「确定」：级联删除会带走用例、运行、基线、环境与密钥，代价配得上多打几个字。
实测：空、错名都禁用，名字完全一致才可点。


### 14. 对话栏的上下文从「装饰」变成真的（原发现 E）

聊天头部一直会按选中项切换成「改这一步怎么跑」或「诊断这次运行」，但 `send()` 只发
`messages` / `intent` / `graphId`——选中项一个字节都没进请求体。界面在宣称一个它没有履行的范围。

- 服务端 `ChatContext { kind: "node" | "run", node?, wfRunId? }`：**由网关自己回读**该节点的参数、
  它在那次运行里的状态与耗费、以及它产出的东西（超长则摘要）；`run` 则带上逐节点耗时、总耗费与消融。
  数字不从前端传上来——否则回答的是"页面当时显示了什么"，而不是事实。
- 前端：可关闭的上下文 chip（关掉不等于取消选中：「现在按整条流水线回答」是个正当要求），
  以及随范围变化的建议短语（节点 / 运行 / 无范围三组）。
- 实测：对 `wf-mt0xaw2g` 的 `design` 节点问"这一步花了多少时间和多少 tokens"，
  答 `1435s, 27517 tokens`——正是那次运行里该节点的真实数字。

### 15. 迭代页补上「被评对象」

页面此前只说了两臂和那一个开关，没说**被评的是什么**：哪一版图、由哪套提示词产出、对着哪份黄金清单打分。
这三件事决定两个结果能不能比，缺了它们，六周前的一份报告就只是两个数字。

`GET /api/evals/subject/:graphId` 返回版本、提示词指纹与清单（条数 / 留出条数），读不到清单就明说读不到——
拿错清单打分会读成"退化"，而不是"拿错了"。切换图会同时切换清单，这正是最值得先摆出来的一处混淆。

### 16. 执行记录列表补上「谁判的」与重试次数

程序判定的绿和模型看截图判定的绿不是同一种绿，但此前只有点开某一次运行才看得到。
列表里现在直接标出来：**每一条断言都由程序判定才算 machine**，十条里有一条是模型判的，
这次运行的判定来源就是模型——那一条是其中最弱的一环。重试过的运行标 `×N`：
一次要靠重试才绿的通过，值得少信一点。

实测那批 dapp 运行：12 次全部是「模型看截图判定」——tier1 的标签在这个项目里一次都没有兑现。


### 17. 推倒重来：从「五扇门十九个分节」回到一个界面

前面十六条都在把能力摆到正确的位置上，但摆完之后数一下就发现方向错了：

| | 重构前 | 分节化之后 |
| --- | --- | --- |
| 落点 | 12 个平铺页面 | 5 扇门后 **19 个分节** |
| 工作台一屏 | 画布 + 检视 | chat + 画布 + 运行时栏 + 轨迹 + 版本 + 检视 = **6 个常驻区块** |

「东西放哪」解决了，「东西太多」没有——反而更糟：一本目录要求人先记住每样东西归在哪一类，
才找得到它。**根因是规则用错了**：我一直按「每个真实能力都要有一个位置」在做，
这条规则的产物是目录，不是工作台。

现在的规则只有一条：**只有一处干活的地方，其余的东西通过你正在处理的那个对象进入**。

- `src/lib/surfaces.tsx`：十一个成熟页面变成**物料卡**，按对象分四组（用例 / 代码 / 运行 / 迭代）。
  同组的是同一个对象的不同镜头，所以在同一张卡里以 tab 并列——它们过去是导航里三个并列的兄弟，
  那种排法本身就在暗示它们是三件事。
- `SurfacePanel`：卡片**浮在画布上**而不是替换画布。一百条用例是 `design` 这一步产出的；
  把画布换掉，那条因果关系就只剩记忆了。
- 入口挂在产物卡上：用户故事卡 →「看追溯」、文本用例卡 →「打开用例」、门禁①卡 →「去复核」、
  代码卡 →「打开代码线」、执行卡 →「看执行记录」。**没有菜单，也没有启动器。**
- 设置退成抽屉（九节不变）：那里每件事都跨一次工作存在、改动频率以周计，不该和每天要看的东西争地方。
- 运行时栏与执行轨迹默认收起，运行开始时自己展开；节点检视只在选中节点时存在——
  它过去是一条常驻 380px 的栏，内容是「点一个节点看它的产物」。
- 路由器整个删掉了（`Layout` / `Sidebar` / `Assets` / `History` / `Settings` 五个外壳一并删除）。
  旧地址仍然可用，但它们不再是地址而是「打开哪张卡」：`#/cases` → `#/?open=cases`，
  `#/history?s=baselines` → `#/?open=baselines`。拆掉导航不该顺手作废别人存下的链接。

构建从 812.6 kB 降到 **742.9 kB**。


### 18. 浮层统一成 drawer，并补上规格阅读

**统一浮层**：物料卡此前是浮在画布上的自制卡片、设置是另一套自制抽屉——两种关闭方式、
两种宽度行为，读者要为每一种浮层各学一遍。现在全部走 `components/overlay.tsx` 的 `Drawer`：
右侧滑出、点背景或 Esc 关闭、**左缘可拖拽改宽**（原型 `armGrip` 的行为），
宽度按用途分别记住——装规格全文的和装单次运行详情的，合适宽度本来就不一样。
同组界面在标题旁以 tab 并列。

**规格阅读**（原型 `openSpec`）：规格是下游一切的输入——故事从它来、用例从故事来、
断言引用的文案要能在它里面查到——而它在界面上此前的样子是 `source.spec` 参数框里的一行路径。
**路径不是阅读方式**：一条用例看着不对时，第一件想做的事就是回去读那一段原文。

- `components/Markdown.tsx`：够读一份规格的渲染器（标题、引用、列表、表格、代码块、行内强调），
  不引第三方——这里唯一的需求是读，每多一个依赖就多一处会在离线环境里出问题的地方。
- `components/SpecDrawer.tsx`：多份文档用 tab 切换，按 `===== 路径 =====` 分栏还原成文件。
- **读的是那次运行真正拿到的文本**，不是磁盘上现在的文件。文件后来改过是常有的事，
  而运行是拿当时那份跑的——拿今天的文件解释昨天的产物，正是追溯最容易骗人的地方。

实测 `wf-mt0xaw2g`：两份文档（02 共 4484 字、03 共 2680 字）tab 可切，拖宽 900 → 1161，
Esc 与点背景都能关且地址复位。


### 19. 从"指定 spec"到"每阶段产物"这条链，实测走通了（此前从产物卡往下钻是断的）

按用户要求把整条流程走了一遍。**画布上是通的，从产物卡往下钻是断的**——三处实测：

| 点击 | 期望 | 修之前 |
| --- | --- | --- |
| 用户故事卡 | 这次运行的 20 条故事 | 「先在设置里选一个项目」（还指向一个已不存在的落点） |
| 文本用例卡 | 这次运行的 100 条 | 空看板 P0 0 / P1 0 / P2 0 |
| 门禁①卡 | 定位到 wf-mt0xaw2g | 所有待复核运行的清单，还要再找一次 |

**根因**：产物属于「运行」，而卡片落点是「项目」。两者只由「批准」这一步连接，UI 把这道缝藏了。
更糟的是工作台起的运行**根本不绑定项目**（`start` 只发 `{graphId, breakpoints}`），
所以卡片落到的是当时恰好选中的那个项目。

三处都修了：

1. **运行绑定项目**：`start` 带上当前项目作为 `target.projectId`。实测新运行 `wf-mt2rdn7a` 的
   detail 里有 `{"projectId":"prj-mt0xgf2t-1001"}`（用 spec 断点跑一步就停，不花模型时间）。
2. **卡片落到运行作用域**：新增两个与规格抽屉同构的阅读器——`StoriesDrawer`（本次运行的故事，
   带验收标准与来源，没有验收标准的单独标出来：那样的故事给不了下游用例任何可对上的东西）；
   文本用例卡改为「看这批用例」直接进复核队列，**并定位到这次运行**（`ReviewPage` 收一个
   `focusRun`）。实测停在 `wf-mt0xaw2g · 100/100 · gate 93%`，并明说「这次运行没有绑定项目，
   批准前需要先绑定」+ 给出选择器。
3. **过时文案**：「先在设置里选一个项目」→「先在顶栏选一个项目」。落点变了就得改说法，
   指错路比不指路更费时间。

修完之后这条链是：
**规格材料（读全文）→ 用户故事 20（读故事）→ 这批用例 100（复核队列，含逐条门禁判据）→
批准进项目 → 看板 / 追溯 / 代码线 / 执行记录**。最后那一段是项目作用域，这是对的——
它们本来就只在批准之后才存在。

仍然欠一处：**在 UI 里指定 spec 要手写 JSON 数组**（选中 spec 节点 → 参数框 → 改 `paths`）。
原型是一组勾选框加「保存为新版本」。可行但不好用，留作下一轮。


### 20. 「读全文 / 读故事 打开的是别的运行」——起新运行时旧产物没有清掉

### 21. 工具栏按「作用域 → 动作 → 状态」重排；从新建项目走了一遍全流程

**工具栏**（截图指出「选中那一条不好理解」）此前的问题是四个叠在一起：两个长得一样的下拉框
（一个是图、一个是运行，没有标签只能靠内容猜）、项目选择器被扔在最右边（它是最外层作用域，

现在读作 `项目 › 图·v3 › 运行·paused │ ▶继续·spec 断点1 │ ✏编辑拓扑 ↺版本 │ ⚗评测 … ● ⚙`：

- 三个下拉连成**作用域面包屑**，谁包含谁一眼可见——这同时回答了那个一直让人困惑的事：

- 动作按「对这次执行 / 对这张图 / 对这一版 harness」分三组，竖线隔开。

**清理**：删掉 6 个没有任何运行记录的壳项目（19 条用例）与 3 条我为验证起的空运行；

### 22. 面包屑说「项目 › 图 › 运行」，切项目却什么也不动

把工具栏排成作用域面包屑之后，它就在宣称一层包含关系——而实际上**运行只按图筛，跟项目无关**。
于是切项目只换了个标签，画布纹丝不动。要么让关系成真，要么别那样排；选前者。

- `outputStore.listRuns` 现在带上 `projectId`（从运行自己的 detail 里读）。此前想按项目分组，

- 切项目时：当前运行若不属于新项目，就切到该项目在这张图上最近的一次；一次都没有就回到

### 23. 节点与执行轨迹疯狂抖动——是我上一条修复自己造的回环

§一.21 让 `wf.node.finished` / `wf.paused` 触发 `selectRun`，好让产物随流水线推进出现。
但 `selectRun` 在运行中会调 `hydrateFromLineage` **重放全部历史事件**，重放里的 `node.finished`
又触发一次 `selectRun` ——刷新导致重放、重放导致刷新。画布因此持续重排，轨迹被反复清空重建。

改法是把「现在发生的」和「重放的」分开：`handle(set, get, e, live)`，**只有 live 事件可以请求刷新**；
重放事件描述的是刷新刚取回的那个状态，对它动作就是在喂那个循环。

同时新增 `refreshRun`：只重读当前运行（状态、逐节点耗费、产物、轨迹），**不重放事件**，
并且用一个在飞标志把并发的重取合并成一次——节点接连完成时若各自全量重取，
好几份结果会把画布覆盖成不同的中间态，看上去也是抖。

顺带修掉同一条链上的三处：

- **`nodeRunsFrom` 合并而不是替换**：正在跑的节点在 detail 里还没有记录（它完成后才出现），
  整份替换会把人正盯着的那个节点抹掉。
- **运行会跑赢自己的 HTTP 响应**：在第一个节点就停的图 2ms 结束，它这辈子会发的事件在浏览器
  知道 run id 之前就发完了，而 ws 只推之后发生的事——于是画布对一个已经停下的运行一直显示
  「running」。改成起跑后按 200ms / 1s / 3s 补读，状态一旦不是 running 就停；正常那种几分钟的
  运行只会付出一次。
- **乐观插入的运行行没带 projectId**，于是刚起的运行显示成「未绑定项目」——与事实相反。

**另一件相邻的事**：轨迹此前只在刷新时从 lineage 重建，而刷新只在节点完成时发生。
一个模型调用要几分钟，那期间轨迹一直写着「这次运行还没有留下轨迹」——而那正是它存在的意义。
现在 live 事件直接追加成行（`traceRowFor` 与重建用同一套措辞，免得同一行live 与刷新后长得不一样）。

实测（`wf-mt2udgds` 真在跑 `design.cases`）：15 秒内 0 次重取、4 次 DOM 变动（此前是持续循环）；
再观察 25 秒，轨迹从 1 行 MODEL 长到 2 行（第二个故事设计完成），**画布布局一动没动**。


### 24. 「跑到 gate 之后怎么继续」——界面上有一道看不见的坎

`g1-text-cases` 到 `gate` 就结束了。它不是停住，是**跑完了**：阶段二在另一张图里
（`g2-code`：codegen → 门禁② → 修复环）。两张图是有意分开的——两段各自迭代、各自评测，
焊成一张图就没法只重跑后半段。代价是界面上多了一道看不见的坎：人跑到 gate 只会问「然后呢」，
而没有然后。

运行时本来就支持给根节点喂种子（`startRun({ seed })`），缺的只是把这件事说出来。

- `server/src/continue.ts`：`continuationsFor(runId)` 与 `continueRun(runId, graphId)`；
  两个端点 `GET/POST /api/wf/runs/:id/continuations|continue`。
- **判定靠类型不靠名字**：这次运行末端节点的 `outKind`，对上另一张图根节点的 `inKind`。
  写死「g1 之后是 g2」今天也能跑通，但每加一张图就要再改一次这里。有一条测试专门守它
  （造了第三张同样吃 `gated-cases` 的图，断言它也被列出来）。
- **读的是那次运行当时用的图版本**，不是今天的：一张后来改过的图，不该反过来决定它自己的
  旧运行能接到哪里去。
- **目标端沿用源运行**：接着跑出来的代码属于同一个项目，让人再选一次只会让两半落在不同地方。
- 前端：运行跑完且产物就绪时，工具栏出现「接着跑 g2-code」，提示写明「把这次运行 gate 的产物
  喂给 codegen」。点下去会跳到新运行上——接着跑的重点就是看后半段。
- 7 条测试（`server/test/continue.test.ts`）。

实测 `wf-mt2udgds`（24 条用例、门禁① 58%）：接口算出 `g2-code · gate → codegen · ready`，
按钮与提示都正确出现。


### 25. 产品逻辑修正：explore 不产用例，explore 产**规格**

原本 explore 是一条旁路，直接从界面产出用例。正确的形状是 **explore → spec → 故事 → 用例**，
以后还会有 **codebase → spec → 故事 → 用例**。也就是说：**spec 不是"你指定的一份文件"，
而是一件可以被推导出来的产物**，来源有三种，下游一个字都不用改。

多出来的那一步不是仪式。跳过它，观察就直接变成了断言，中间没有任何一处可以让人说
「这条不该这么写」——而规格是可读、可批改、可版本化的，用例批次不是。

**最要紧的一处不是连线，是印记**（`SpecProvenance`）：

| 来源 | 表达的是 | 由它产出的用例挂了，意味着 |
| --- | --- | --- |
| `document` 人写的 | 意图 | 可能是**产品错了** |
| `exploration` 探出来的 | 现状 | 只能是**产品变了**（回归）——观察不可能反驳被观察者 |
| `codebase` 从代码推的 | 实现 | 介于两者之间（尚未实现，不做占位按钮） |

这个印记一路传：`SpecMaterial` → `StoryBundle` → `CaseBundle`，`source.explore` 盖 `exploration`，
`source.spec` 盖 `document`。**丢掉它，一套完全建立在观察之上的绿色套件就会被读成「产品是对的」。**
6 条测试（`provenance.test.ts`）守的就是它在每一段之间没有掉。

实现要点：

- `source.explore` 与 `source.spec` **产出同一种类型**（`KIND.spec`），所以能互换接进 `plan.stories`：
  材料从哪来是这一层的事，怎么用是下一层的事。
- 新增内置图 `g0-explore`（explore → stories → design → gate），与 `g1-text-cases` 只差第一个节点。
  分成两张图而不是给 g1 加开关：读文档和看产品是两次不同的运行、会得出不同的东西，也该分别评测。
- **观察与解读分开**：网关只负责把界面上看得见的东西取回来（`observeProduct`，与 `execCase` 同一个
  理由——agent 没有浏览器），把观察写成规格的提示词在节点里。换观察方式不该重写提示词，
  改提示词也不该重开浏览器。
- 写规格的提示词明确要求**只写看见的**：不写 should/must，逐字引用界面文案（下游断言要拿这些
  字符串去对），并且**必须有「没看到的」一节**——一份不写自己盲区的规格读起来像是完整的，
  而由它衍生的一切都会继承这个错觉。
- 字段用 `.optional()` 而不是 `.default()`：让读的人写一次 `?? "document"`，比让 zod 悄悄替他决定好。
- 画布上的规格材料卡会显示「探索得来」并标黄，副标题直说「描述现状而非意图：由它产出的用例
  只能发现『变了』」。不显示出来，这个印记等于没有。


### 26. 用户文档也只是材料：**标准规格只有一处产出**

§一.25 补上了 explore → spec 这条路，但只做对了一半：那时用户文档仍然被当作"就是规格"直接喂给
拆故事那一步。正确的形状是**三种来源都只产材料，标准规格由一个节点整理产出**：

```
用户文档  ┐
探索观察  ├→ spec.compose → 标准规格 → 用户故事 → 文本用例 → 门禁①
代码库    ┘（未实现）
```

理由不是格式洁癖。此前下游直接吃原始文档，于是**「用户这次给的是什么格式」这个问题被复制到了
每一个下游节点里**——一份 PRD、一段会议纪要、一屏界面文字，形态千差万别，而拆故事、设计用例、
追溯、门禁都得各自应付。现在它们只认一种形状。

**标准规格长什么样**（`SpecDocSchema`）：

- `rules` 是主体，每条有 id、有 `evidence`——**材料里的原话**。故事可以引用规则 id，规则可以指回
  原话。一条引不出原话的规则，和模型顺手编的一句在下游是分不清的；整理时统计并记一笔。
- `unknowns` 是**必须**有的一节：材料没说清的、自相矛盾的、提到却没交代的。空列表是一个很强的
  断言，会单独记一笔提醒人看。一份不写自己盲区的规格读起来像是完整的，而由它衍生的一切都会
  继承这个错觉。
- `derivedFrom` 一路带下去，含义见 §一.25。整理提示词会按来源换语气：观察材料明确要求
  「写成现状陈述，不要写成要求」——把观察整理成"应该如此"是越权。

**整理不是创作**：材料没说的进 `unknowns`，不凭常识补一条看起来合理的规则；矛盾不许挑一个，
两个都记下并进 `unknowns`。

**旧的 explore 下掉了**（用户要求）：`POST /api/projects/:id/explore`、`GET …/explore/stream`、
`POST /api/explore` 三个端点，前端的 Explore 页、store 里整块探索状态与 SSE 连接、
看板上的「开始探索」按钮，一并删除。观察本身仍然做——入口是画布上的 `source.explore` 节点，
需要浏览器的那一跳走 `observeProduct`。保留下来的 `observeLaunch` 会带上环境变量、固定头与
已捕获的登录态：观察一个需要登录的产品若不带会话，看到的永远是登录页，而那样整理出来的规格
会一本正经地宣称这个产品只有一个登录界面。

**存过的图**：内置图已是新形状，但本实例里 `g1-text-cases` 与 `selftest-g1` 有存过的版本，
按设计「存过的版本压过内置」。给它们各存了一个新版本（v4 / v3，旧版本仍在版本抽屉里可比），
而不是就地改写——版本本来就是为这种事准备的。


### 27. 节点的动作离节点太远；框选与拖画布抢同一个手势

两件事其实是一个根因。**「只跑此节点」「从此节点续跑」此前站在顶栏**——它们作用于某一步，
却出现在离那一步半个屏幕远的地方，而且只有先选中节点才会冒出来。人要先发现"选中会让顶栏
长出东西"，才知道有这两个动作。

- **动作搬进节点自己的抽屉**：点开一步，「只跑此节点 / 从此节点续跑 / 设断点」就在标题下面，
  每个都带一句为什么（「只重跑这一步，用上游已有的产物作输入——改完参数验证一下，不必从头再来」）。
  没有可接着改的运行时直接说「先跑一次」，而不是给一个灰按钮让人猜。
- **拖动 / 框选两个显式模式**（画布左上角，竖排）：一个手势只能有一种含义。默认拖动——
  看图的次数远多于改图。放左上角而不是挤在左下角的缩放控件旁边：那组是「看得多大」，
  这组是「拖的是什么」，两件事不该长得像一组。
- **框选拖完直接弹 drawer**，列出选中的那几步。

drawer 里**按「能不能对一批一起做」分区**，这是这一节唯一需要动脑的地方：断点是每一步各自的
开关，可以一起设/一起清；而「只跑这一步」「从这一步续跑」**只接受一个节点**——运行时就是这么
定义的。与其做一个看起来能批量、点下去只对其中一个生效的按钮，不如把这句话写在那里。

实测：框选 docs/spec/stories 三步 → 抽屉标题「选中了 3 步」、批量断点可用、单步动作逐个列出；
切回拖动模式后拖画布，viewport 位移、零误选、不弹抽屉。

## 四、优先级清单的一轮执行（A1→A2→B3→C1→B1，及其余）

起因是一次调研：LangChain 的 **Managed Deep Agents**（2026-08-07 公测）和 Anthropic 的
**Claude Managed Agents**（2026-04）把「通用 harness + 托管运行时」这件事做成了产品。对照之下，
testpilot 作为垂类 harness 的护城河（判据分层、门禁、`SpecProvenance`、溯源）是真的，
但**运行时那一层他们更完整**。这一轮做的就是把差得最明显的几处补上，外加自己欠的账。

### 已完成

**A1 执行台账不再说谎。** `runs` 表加了 `origin` / `projectId` / `wfRunId`。修复环里跑过的
候选用例现在会写进台账；「执行记录」页此前只列套件批次，于是一个只被修复环跑过的项目
打开是空白——而空白读起来是「从来没跑过」。三种来源（套件 / 单跑 / 工作流）分开显示且可筛，
因为同一个「通过」在三种里含义不同。**历史执行不回填**：repair 报告里没有执行时刻，
补一个等于伪造。

**A1 的副产品：通过率不再把环境失败算进分母。** 台账放宽之后立刻暴露：`MODEL_UNAVAILABLE`
造成的红和断言没过造成的红长得一样。前者说明不了产品的任何事，混进去之后「通过率 67%」
会让人去查一个没有问题的地方。被排除的条数单独显示——悄悄缩小分母也是一种谎。

**A2 出处改成查出来的，不是问出来的。** 新增 `casegen/attribute.ts`：材料按
`===== path =====` 拆回一份份文档，一句原话属于哪份由**确定性字符串定位**决定。
于是 `spec.compose` 给每条规则填上它的 `evidence` 出自哪份，`plan.stories` 也不再相信模型
自己填的 `source`——先拿验收标准回规格里定位，定位不到才退回模型的说法，而且那个说法必须
指向一份这次运行真的读过的文档。故事上多了 `sourceBy: located | claimed`，界面上两者不再
显示成同一个文件名。

顺带出现一个比「没有出处」更值得看的信号：**给了原话、但那句话在材料里定位不到**——
它是转述或是编的，不是原话。单独一笔报出来。

**A3 引文的判据比错了对象。** 追溯此前拿 `spec` 节点的产物比，而在现在的图里那已经是
`spec.compose` 的输出——一份被压缩转述过的东西。材料里明明写着的界面文案，只要整理者换了
说法就被判成「查不到出处」。改成按**形状**找材料节点（有 `text`、没有 `rules` 的那一份），
两份都留着分开判：`material` / `spec` / 查不到。加了筛选：117 条里 21 处黄标，一个只能报
总数、指不到具体哪几条的检查等于没有报。

**A4 门禁②拦错了，而且给的建议是错的。** 队列里那条
`S-02-2-登录失败后页面url保持不变` 被 `invented-credential` 拦下。规则本身有负例豁免，
但证据只看 `expected`——而这条用例的断言写的是**后果**（URL 未跳转），不是拒绝本身，
`designMethod` 又是 state-transition。于是它被要求换成 `${env.*}`，而那会让登录**成功**，
可这条用例要的正是它失败。把标题也纳入证据（步骤不算——用写死凭证本身豁免写死凭证是
循环论证）。重跑门禁②：**score 1.00，0 拦截**，该用例真的执行了。

**B3 评测集进仓库。** 新增 `evals/` 目录 + `server/src/evalspecs.ts`。定义此前只活在一次
POST body 里：结果进了库，定义本身没有历史、进不了 review、改了没人看得见——而一份可以被人
随手改掉且不留痕迹的判断依据，不再是判断依据。三份真实定义已写：`design-methods`、
`oracle-grading`、`selftest-dedupe`。

其中最要紧的设计是 **`expect` 不是断言**：它记下跑之前的预判，跑完和实际结果并排显示，
但**不会让评测失败**——一个会红的评测会被人调到绿为止，而那正是评测本该防住的事。
预判错了是这份评测最有价值的一次输出。方向对上但不显著时会明说，否则会被当成一次确认。

**B1 上限改成硬的。** 此前 `resumeRun` 既没带上限也没带已花费，于是**设了上限的运行一被
续上就变成不限额的**，而且这次运行最后记下来的花费比它真的花的少——一个少报花费的报告
比没有报告更糟，因为它看起来像一次测量。现在 `spent` 一路带下去（时间上限也算整次运行），
撞了上限的运行只接受「改上限」或「撤掉上限」，然后才能继续。撤掉是正当选择，但它要被
说成「撤掉」，不能伪装成「继续」。

**C1 拆掉常驻 chat 栏。** 画布左侧那条 340px 的对话栏删了。它的四种模式里，
改图 / 起草能力 / 改提示词三种在「能力」页已经有完整的一份，画布上那份是复制品；
而下拉框要求人在打字之前先替模型做一次分类，选错不会报错，只会得到一个语气正确但没有
草稿的回答。**更根本的是：一条永远在那里的对话栏，是在宣告这个产品主要靠聊天驱动——
它不是，也不该是。** 流程固定是这个项目的核心设计。

剩下真正需要模型的那一件事（跨产物推理）变成 `DiagnoseDrawer`：按需打开，
**附着在它解释的那个对象上**（节点抽屉里、运行的顶栏上），追问保留上文。
「只出提案，执行走按钮」这条规则从一个 `title` 属性搬到了抽屉正文里——它是整个设计里
最重要的约束。

**C2 最贵的一步不再问模型。** 那个建议 chip 背后，网关自己读了 `spend` 再喂给模型用一句话
念出来。让一个 LLM 读一张表念给人听，说明的是这张表没被显示。运行时栏加了「最贵的一步」，
以及「最慢的一步」——只在两者不同时显示，因为一次视觉判断耗时八九十秒、token 却很少。

**C3 材料改成勾选。** 新增 `/api/materials` + `MaterialPicker`。`paths` 此前只能在 JSON
文本框里手写一个字符串数组，而**选错一份文档不会报错**——文件读不到才报错；路径拼对了、
选的却是另一份，只会在二十分钟后变成一批看起来正常、其实答非所问的用例。文本框留着：
`path` / `text` 两种形式还在，勾选只是同一个字段的一个视图。

**C5 项目卡不再有两个号召。** 「打开测试用例」换成条数——一个事实，而且正好是决定要不要
进这个项目时最想先知道的事。

**B4 加节点的成本。** `pnpm --filter @testpilot/harness-testing new:node <group.name>`
生成节点骨架和测试骨架。它不替人做决定：必须由人回答的三个问题（这一步为什么是单独一步、
产物是不是一种新 kind、要不要调模型）以 TODO 留在文件里，最后打印出脚本**不做**的三步。
真正的成本在于编排由代码决定，那是有意的设计——要的是词汇量，不是语法自由。

**B5 在途调用不再永远挂着。** 这一条核实之后是真的，而且注释里正好写着洞是怎么来的：
两个方向都设了 `timeout: -1`（一次视觉判断几十秒、一次用例几分钟，birpc 默认的 60 秒会把
健康的工作腰斩——这个修法是对的）。但心跳只负责宣布对面死了并把它拉起来，**它不会把已经
发出去、再也等不到回复的调用结掉**。于是 runner 崩在一次 `execCase` 中间，agent 的 `await`
永远不返回，整次运行永远停在 `running`。改成**用死讯，不用时限**：通道一断，在途调用立刻
以「对面没了」失败，之后的调用也立刻失败。慢是允许的，永远等下去不是。

### 查证之后取消的一条

**B2「门禁和被评对象共享上下文」——前提是错的。** 我按 CMA 的 outcome grader 类推，
没查代码。实际上：门禁①（`casegen/gate.ts`）和门禁②（`codegen/gate.ts`）**都不调模型**，
全是确定性规则；唯一的模型评判是覆盖率裁定 `adjudicateMisses`，而它本来就是**每条金标
一次独立调用**，各自 stable+variable，没有共享对话。无需改动。

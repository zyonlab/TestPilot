# 07 自举与自我迭代

> 让 harness 测 TestPilot 自己。这不是炫技——它一次性解决三个问题：
> ① spec 素材未定（我们自己的 02/03 文档就是真实 spec）；
> ② 评测缺参照物（03 的交互契约天然是 gold checklist）；
> ③ harness 缺失败语料（自己跑自己，失败轨迹源源不断）。

## 1. 三个环

```
        ┌──────────────── 环 A：用例环（dogfooding）────────────────┐
docs/02 业务规格 + docs/03 UI 规格 ─▶ G1 生成文本用例 ─▶ 门禁① ─▶ G2 生成代码
        ▲                                                            │
        │                                                     在本机 TestPilot UI 上执行
        │                                                            │
        │                                              视觉基线 / 性能基线 / 断言
        │                                                            ▼
        │           ┌──── 环 B：harness 改进环 ────┐          失败轨迹 + lineage
        └───────────┤ HarnessCritic 读失败轨迹      │◀────────────────┘
                    │ → 提 harness 级改动建议        │
                    │ → 改动落地                    │
                    └──────────┬───────────────────┘
                               ▼
              环 C：评测环（配对 + 消融）判定这次改动到底有没有用
```

- **环 A（用例环）**：SUT 就是 TestPilot 自己的 Web UI。目标固定为 `http://127.0.0.1:<dev端口>`。
- **环 B（改进环）**：HarnessCritic 是一个只读失败轨迹的模型任务——它不改代码，只产出"harness 级失败模式 + 建议改动"。这是 Co-Harness 循环里唯一不依赖微调、现在就能兑现的一段。
- **环 C（评测环）**：任何来自环 B 的建议，必须过配对评测（同一批题、两版相减）才算数。**没过评测的建议不落地。**

## 2. 分层自测

| 层 | 被测对象 | 模型 | 频率 | 时长目标 |
|---|---|---|---|---|
| **L0 单元** | core 各模块（调度、预算、门禁判据、统计） | `FakeModel` | 每次提交 | 秒级 |
| **L1 图级** | G1/G2 全图跑通、节点续跑、检查点 | `RecordedModel`（VCR 回放） | 每次提交 | 秒~分钟级 |
| **L2 端到端** | 真模型 + 真 UI（自举） | Qwen3.8-27B-4bit | 每日/手动 | 小时级，可接受 |
| **L3 评测** | gold checklist + 配对 + 消融 | 真模型 | 每次 harness 改动 | 小时级 |

L0/L1 进 CI 门禁；L2/L3 定时或手动触发——本地模型一步几十秒，把它放进提交门禁会让开发不可用。

## 3. 自举的护栏

1. **目标白名单**：自测目标强制 `localhost/127.0.0.1`；护栏默认拦截非白名单上的不可逆动作。
2. **数据隔离**：自举跑在独立 `.data-selftest/`，独立端口与独立 profile，**绝不写生产库**。用例里的"删除项目""清空基线"这类不可逆动作只允许作用于一次性种子数据。
3. **不可逆动作清单**：删除项目、删除环境、清空基线、重置提示词——这些既是要测的功能，也是最危险的动作，必须在种子数据集上跑并在跑完后重建。
4. **失败预算**：自举整轮有 calls/usd/ms 三闸，耗尽即停并明确标注"耗尽"而非"跑完"。

## 4. 防自证清白（最容易被忽略的一格）

自己测自己有一类特有风险：**共模失效**——同一个模型既生成用例又判定结果，UI 改坏了它可能连判据一起改成"新的样子也对"。三道对冲：

1. **gold checklist 必须人写**，从 docs/03 的交互契约手工抽取，不由模型生成。它是 Coverage 这个数唯一的意义来源。
2. **留出集**：一部分 gold 项从不参与任何调优，只在评测时用。
3. **不依赖模型的锚**：视觉基线（像素）、性能基线（数值）、链上断言（状态）、HTTP 状态码——这几类判据模型改不动，是共模失效时唯一还站得住的东西。因此自举用例里**必须**包含足量 tier1/tier2 判据，不能全是 judge。
4. HarnessCritic 的建议由**模型提出、由配对评测判定**，不由模型自评。模型会自信地夸奖自己的产出，这是有记录的失败模式。

## 5. 里程碑（自举算不算成功）

| 里程碑 | 判据 |
|---|---|
| **M1 能生成** | 以 docs/02+03 为输入跑 G1，产出 ≥ 30 条文本用例，Coverage ≥ 0.7（对 gold checklist），门禁①平均分达标 |
| **M2 能跑绿** | 其中标记 P0 的用例经 G2 生成代码后，在本机 UI 上 100% 跑绿；tier1+tier2 判据占比 ≥ 50% |
| **M3 能自改** | 至少一次 harness 改动由 HarnessCritic 从失败轨迹中提出，并被配对评测证实为显著正向（p < 0.05 或效应量达标） |
| **M4 能防退化** | 自举回归纳入日常：UI 改动导致的真实缺陷被自举用例抓到过至少一次，且严口径通过率没有被自动修复注水 |

## 6. 与 mock spec 的关系

两者不冲突，分工明确：

| | mock spec（fixtures/mock-spec） | 自举（docs/02+03） |
|---|---|---|
| 用途 | L0/L1 离线 TDD | L2/L3 真实验证 |
| 规模 | 小（约 4 段 1500 字，5-8 故事，20-30 用例），照顾本地模型上下文 | 真实规模 |
| SUT | 内置 fixture 应用（/testlogin /testflaky /testdapp） | TestPilot 自己的 Web UI |
| 稳定性 | 冻结，改动需同步改期望值 | 跟着产品演进 |
| 何时启用 | 阶段一 | 阶段二起 |

阶段一之所以不直接自举：那时 TestPilot 自己的 UI 正在重构，SUT 天天变，量出来的差值分不清是 harness 变了还是 UI 变了。**先要一个不动的靶子。**

### 一个必须说清楚的偏差

第 4 节写着"**gold checklist 必须人写**"。`fixtures/self-test/gold-checklist.json` 是**本次开发会话逐条手抽**的——不是模型生成的（没有任何一次模型调用参与），但也不是你写的。

这个区别是实的：这份清单的作者与被测系统的作者是同一个，共模失效的风险没有完全消掉。**它需要你复核之后才真正算数**，特别是 4 条留出项（S-03/S-06/S-11/S-15）——留出项的全部价值就在于没被用来调过任何东西。

在你复核之前，自举的 Coverage 数字应当读作"对一份待确认清单的覆盖率"，不是 M1 的验收结论。

### 自举第一次跑就抓到的 harness 缺陷

真实 spec 比 mock spec 大三倍，第一次跑 `selftest-g1` 立刻死在 `plan.stories`：

```
plan.stories: reply is not valid JSON — Expected ',' or ']' after array element at position 2543
```

实际是回复被 `max_tokens=1200` 截断，报成了"模型返回的 JSON 不合法"——**把预算问题说成了格式问题**，两者的修法相反（一个加预算，一个改提示词）。已修两处：

1. `ChatResponse.truncated` 从 `finish_reason === "length"` 带出来，解析失败时直说是截断；
2. `plan.stories` 的预算随 `maxStories` 缩放（约 260 token/故事），不再是固定值。

**其二：多份材料时，第二份可能一条故事都没进。** 修好截断后跑出 12 个故事、94 条用例，
但 12 个故事**全部来自 `docs/02`**——`maxStories: 12` 正好被第一份文档吃满，`docs/03` 颗粒无收。
对着从 `docs/03` 抽的清单打分，覆盖率 8%。harness 里没有任何机制保证"每份材料都被覆盖"。已修三处：

- `plan.stories` 的提示词要求跨文档铺开，并说明"预算比材料小的时候要摊开，不要把预算耗在第一份上"；
- 故事带上 `source`（来自哪份文档）；
- **某份文档一条故事都没产出时直接报出来**——否则这个洞会一路静默到覆盖率数字上，那时已经没人说得清是为什么。

**其三：单次调用的超时上限对本地模型太紧。** 把 `maxStories` 提到 20 之后，
`plan.stories` 要生成约 5200 token，本地 27B 跑过了 300 秒的硬上限，报错是
"The operation was aborted due to timeout"——既没说是哪一步，也没说上限是多少。
已改：默认 900 秒、`TP_MODEL_TIMEOUT_MS` 可配，报错带上节点标签、请求的 token 数与上限。
本地模型慢是这个项目的既定前提，按托管端点调的超时值会把"正常的慢"变成"崩"。

这三条是自举的第一批收益，而且正是它该产出的那一类：mock spec 小、单份、快，永远撞不到这些边界。

### M1 的实测结果：**没达标**

| 跑法 | 故事 | 用例 | 调优集覆盖 | 留出集覆盖 | 耗时 |
|---|---|---|---|---|---|
| `maxStories=12`（首跑） | 12（**全部来自 02**） | 94 | **8%** | 0% | 25 分钟 |
| `maxStories=20`（修好铺开之后） | 20（US-13~20 明确来自 03） | 100 | **25%** | **50%** | 41 分钟 |

M1 的判据是"≥30 条用例 + Coverage ≥ 0.7"。**用例数达标（100 条），覆盖率差得远（0.25）。**

关键的一点：把 11 条未命中交给**语义兜底**（`adjudicateMisses`，模型判定）之后，
结论**一条没变**——11 条全是真缺口，没有一条是"措辞不同的近似命中"。
也就是说这 0.25 不是确定性匹配太严造成的下界偏低，是真的没生成到。

生成的用例本身不差，方向不一样。举一个具体的：

- 清单 S-01：*进程页列出网关/agent/runner 并显示状态*
- 实际生成：*验证进程列表展示所有必需字段* → 断言"类型/pid/心跳/重启次数/当前任务/累计成本六个字段值非空"

它检查了这张表长得对不对，没检查**该在的三个进程在不在**。语义判定认为这不算覆盖，我同意。

两个可能的原因，我没有证据区分哪个是主因，不猜：

1. **清单的具体度高于文档**。S-02 要求"PID 变化"、S-03 要求"未启动"而不是"已停止"——
   这些是我对着 03 的交互契约挑出来的**具体断言**，而 03 的正文未必把每一条都写成那样。
   若如此，缺的是"素材写得不够具体"，不是"harness 拆得不好"。
2. **每个故事 5 条用例摊得太薄**。20 × 5 = 100 条，每条故事的 5 条会先覆盖它自己的验收标准，
   轮不到清单关心的那些细节。

区分办法（阶段二做）：对同一批故事把 `maxCasesPerStory` 从 5 提到 10 跑一次配对评测。
若覆盖率随之明显上升，是原因 2；若几乎不动，是原因 1，那就该回头改**素材**而不是改 harness。

这就是 M1 该有的样子：**它给出的是一个可行动的否定结论，不是一个漂亮的数字。**

### 这个区分实验的结果（2026-08-20，`eval-mt0xaw2f`）

先说一个**做实验之前必须先修的东西**：`maxCasesPerStory` 当时**只在解析完之后截断**，从来没有进过提示词。
也就是说模型照旧按「至多 8 条」设计，harness 把超出的部分**扔掉**——把这个参数从 5 调到 10，
除了少扔几条以外什么都不会变，这个实验按原状根本做不出差异。
现已把预算放进提示词的**可变半区**（放进稳定半区会让每次调用都错过前缀缓存）。

两臂同一份 spec、同样 20 个故事、同一份 16 条清单，配对单位是清单条目：

| | A：每故事 5 条 | B：每故事 10 条 |
|---|---|---|
| 用例数 | 100 | 200 |
| 调优集覆盖 | 0.50 | **0.58** |
| 留出集覆盖（4 条） | 0.25 | 0.75 |
| 门禁① | 0.93 | 0.945 |
| 成本 | 35787 tok / 29.3 min | 51035 tok / 49.7 min |

McNemar：B 独占 4 条，A 独占 1 条，**p = 0.375 —— 不显著**。

**结论：原因 2（每故事 5 条摊太薄）没有被证实。** 把预算翻倍换来的是调优集 +0.08，
代价是 +43% token 与 +70% 墙钟时间，而 5 条不一致项在 16 条清单上完全可能是抖动。
留出集从 1/4 涨到 3/4 看着漂亮，但那是**四条题**，同样说明不了问题。
剩下的缺口更像原因 1（清单比文档具体），也就是**该回头改素材**——但这次实验的功效不足以定案，
要定案需要更大的清单或多次重复。

**另外一处不能当成证据的观察**：今天 A 臂（与历史 M1 同样是每故事 5 条）覆盖率是 0.50，
而上面记录的历史 M1 是 0.25。两者中间隔着上述提示词改动，且是**非配对**的单次对单次比较，
本地模型的运行间抖动本来就大——所以它**不是**「修好预算让覆盖率翻倍」的证据。
它唯一确定说明的是：文档里那个 0.25 已经不是当前基线，重新谈 M1 要以 0.50 起算。

**M1 判据（Coverage ≥ 0.7）在两种设置下都仍未达标。**

## 8. M2 的第一次真跑（2026-08-20）

被测对象是**另一个 TestPilot 实例**：`TP_DATA_DIR=.data-selftest TP_INSTANCE=sut PORT=5401`，
前端用 `?api=http://127.0.0.1:5401` 指过去（在此之前前端把网关地址写死，
**这一条就是自举执行一直没做起来的原因**）。

P0 集是 4 条 tier1 用例，从 `wf-mt0efic7` 批准进一个绑定 SUT 的项目。
选取规则记在这里，因为它是人定的：**冷启动的 SUT 能自己走到的界面**（进程页、能力与 Chat 页），
不依赖任何预置项目/运行/批次。

### 第一次跑：死在基础设施，不是死在用例

```
[birpc] timeout on calling "execCase"
```

supervisor 那一侧早就写着「一次用例要跑几分钟，所以不设 RPC 截止时间」，
但 birpc 的超时是**按方向**设的——child→parent 那一侧还是 60 秒默认值，
而 `execCase`（agent 请网关跑用例）正是这个方向。已修。

### 第二次跑：1/4 通过，**零退化**

| | 结果 |
|---|---|
| loose / strict | 0.25 / 0.25（判据 100% ❌） |
| 断言被改松 | **无**（`degraded: []`） |
| tier1+tier2 占比 | 100%（判据 ≥50% ✅） |

三个失败各有各的原因，而且**没有一个是「用例写得不好」**：

**① 两条被修复循环判为产品缺陷**——它拒绝改松断言，而是走了 `{"verdict":"product-defect"}` 出口。
这是这套机制第一次在自举里真的开火：

- `US-18-1`：用例要求进程行同时显示六个字段（含**累计成本**）。实际卡片有类型/PID/心跳/重启次数/当前任务，
  **没有「累计成本」**——03 §4 写的是「累计 calls/tokens/耗时」，实现只显示了「模型调用」。
  这是产品与规格的真实出入，由自举用例抓到。
- `US-18-3`：停止进程后「当前任务」显示「空闲」，而用例要求为空或「无」。
  这一条更像**用例过度具体**而不是产品错——它需要人判一次，正是复核队列该干的事。

**② 一条暴露了 harness 的缺口：前置条件从来没有变成动作。**
`US-17-3` 的前置是「已进入 Agent 对话界面」，生成的代码却直接往输入框里打字，
于是在项目列表页上报「当前页面上没有找到发送按钮」——**这个失败与产品无关，是没人把它带到产品面前**。
已修：codegen 的稳定半区现在明说「前置是一个状态，不是注释；运行从入口开始，先发出走到那里的动作」。
修完之后生成的代码第一句就变成了 `Navigate to the Agent chat interface…`，这个洞是堵上了。

### 三次完整跑下来的样子

| 跑次 | 变化 | loose / strict | 退化 | 通过的那条 |
|---|---|---|---|---|
| 1 | —— | 死在 `[birpc] timeout on calling "execCase"` | — | — |
| 2 | 修好 RPC 截止时间 | 0.25 / 0.25 | 无 | US-17-1 |
| 3 | 修好「前置变动作」 | 0.25 / 0.25 | 无 | US-17-1 |
| 4 | 补上进程页的「累计成本」 | 0.25 / 0.25 | 无 | **US-18-1** |

**M2 未达标**（判据 100% 全绿）。tier1+tier2 占比 100%（判据 ≥50% ✅）。
**三次都是零退化**：修复循环从未改松断言，两次明确走 `product-defect` 出口。

### 这次自举最有价值的结论：tier 标注在执行链路上兑现不了

三次跑通过的用例不一样——第 4 次 US-17-1 反而挂了，理由是断言执行时模型回复还在「生成中」。
根子不在这条用例：**阶段一给每条用例标了 tier，阶段二执行时却全是 judge**。
`aiAssert` 就是「模型看一眼截图然后表态」，所以一条标着 tier1 的用例，
在执行时拿到的仍然是 tier3 的判定硬度，判定随模型抖动。

两个实例：

- `US-17-3` 断言「发送按钮保持禁用」。按钮**确实**是禁用的（DOM `disabled=true`、`cursor: not-allowed`），
  但判定模型看截图说「按钮是正常可用状态」。这是**判定假阴性**，不是产品缺陷。
  （顺带确实改了产品：禁用态原先只靠 50% 透明度表达，现在整块变灰——这条改动本身站得住，
  但要说清楚它是被这次失败**提示**的。）
- `US-18-1` 断言进程行显示六个字段。**真缺**「累计成本」——03 §4 要求「累计 calls/tokens/耗时」，
  实现只显示了「模型调用」。这是自举抓到的第一个真实产品/规格出入，补上后这条转绿。

所以 07 §4 那句「自举用例里**必须**包含足量 tier1/tier2 判据」，现在有了实证的第二层含义：
**光在设计阶段标 tier 没用，执行层得有能力兑现它**（DOM 断言 / 数值断言 / 状态断言），
否则 tier 只是一个写在产物里的形容词。这是阶段三该补的执行能力，已记在下面。

## 10. M3 的第一次闭环（2026-08-20）：**机制跑通，这条建议没被证实**

判据是「至少一次 harness 改动由 HarnessCritic 从失败轨迹中提出，并被配对评测证实为显著正向」。

### 先补的两个前置

**① Critic 提的是提示词改动，而配对评测两臂只能差消融开关——它提的东西根本没法评。**
现在两臂可以差**节点参数**，于是「更严的判据说明」被做成 `design.cases` 的
`oracleGuidance: default | strict` 参数：它存在的意义就是被比较，而不是被相信。

**② Critic 自己越了它自己的界。** 提示词里从第一天就写着「不许把清单或其中任何一条放进任何提示词」，
这次它照做不误——第 3 条建议把两条未覆盖清单项**原文抄进了**建议的提示词改动里。
规则只写在提示词里、没有任何东西检查输出，这正是这个项目反复重新发现的失败模式
（「提示词里说了也没用，门禁拦下来才是有效的那一道」）。已加**输出侧检查**：
建议里出现清单条目就标 `inadmissible`，保留展示但不再提供「拿去比一比」的按钮，也不计入可评测数。

### 裁决（`eval-mt13l1x4`，mock spec，12 条清单）

| | A：默认 | B：更严的判据说明（Critic 建议） |
|---|---|---|
| 用例数 | 32 | 32 |
| 调优集覆盖 | 0.67 | 0.78 |
| 留出集覆盖 | 1.00 | 0.67 |
| 门禁① | 0.969 | 1.000 |
| 成本 | 8579 tok / 7.4 min | 9654 tok / 8.0 min |

McNemar：A 独占 1 条、B 独占 1 条，**p = 1.0 —— 没有方向**。

**M3 未达成。** 覆盖率那 +0.11 落在噪声里，留出集还反着走。
顺带看它真正针对的那个指标（判据具体性），结论同样是「变了，但不是变好」：
warn 级的 `oracle-vague` 从 1 条降到 0，**info 级却从 2 条涨到 6 条**；
tier 分布被压成几乎全 t1（24/7/1 → 31/1/0），负例占比 31% → 41%。
形状变了，好坏说不清。

**这次闭环真正的产出是它拦住了一条建议**：证据（77 条 oracle-vague）是真的，
建议听起来也对，但配对评测说「没证据」。没有这一步，它会被当成改进采纳掉。

**还欠一件**：配对的单位始终是**清单条目**，所以一条冲着「判据质量」去的改动只能被间接衡量。
要真正裁决这类建议，评测层需要以**用例**为配对单位（这条用例在两版里是否被门禁标记）。
这是 M3 下一步该补的，不是这次能顺手带过的。

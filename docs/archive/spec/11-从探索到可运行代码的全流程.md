# 11 · 从探索到可运行代码的全流程

> 以 2026-08-27 的代码为准逐节点整理。每一处都指得到文件与行。
> **更新（同日）**：§13 列出的断链已修，逐条改成「修之前 / 修之后」；§2.2 探索改成循环；
> 新增 §3.0「一个跑了 21 次都没人发现的洞」。
> 与 05（harness 架构）的分工：05 讲三层为什么这么分，这份讲**一条数据从进来到跑起来，
> 每一层到底对它做了什么**，以及每一层是靠什么把粗粒度的东西拆细的。

## 0. 全景

```
材料的三个来源                    唯一的规格产出处
┌─────────────────┐
│ source.spec     │ 人写的文档 ──┐
│ source.explore  │ 看跑着的产品 ─┼──▶ spec.compose ──▶ plan.stories ──▶ design.cases ──▶ gate.textcase
│ （codebase，未做）│ 代码摘要 ────┘      标准规格          故事+验收标准      文本用例        门禁①
└─────────────────┘                                                                        │
                                                                                   复核队列 · 批准
                                                                                            │
   codegen.case ──▶ gate.code ──▶ repair.loop ──▶ 看板用例 ──▶ 导出工程
     代码           门禁②        执行+有界修复      夜间回归      独立 Playwright+Midscene
```

对应的 kind 契约（`casegen/types.ts:209`、`codegen/types.ts:144`）：

```
spec-material ─▶ spec ─▶ stories ─▶ cases ─▶ gated-cases ─▶ code ─▶ gated-code ─▶ repaired-code
```

这串字符串不是注释，是**保存图时就校验的连线规则**（`graph/graph.ts:74`）：
`fromDef.outKind !== toDef.inKind` 直接拒收，并定位到那条边。所以「哪些节点能接哪些节点」
在画布上拉线的那一刻就定了，不留到运行时才炸。

## 1. 每一层共用的「拆解装置」

粗 → 细这件事，在这套代码里不是靠模型自由发挥，而是靠一个四件套，每层参数不同、结构相同。

| 部件 | 干什么 | 落在哪 |
|---|---|---|
| ① 角色定义 + 一条禁令 | 把这一层的自由度压死 | `stable` 首句 |
| ② 固定输出形状 | **guided decoding**，不是建议 | `*_SCHEMA` → `response_format` |
| ③ 字段级可判定性约束 | 什么算数、什么不算数 | `stable` 的 Rules |
| ④ 交卷后程序去查 | 模型说了不算，能查到才算 | 节点 `run()` 里的确定性复核 |

**②要单独说。** `model/openai.ts:56` 把 schema 作为 `response_format: {type:"json_schema"}` 送给端点。
两处注释写明了它的地位：

> *"Guided decoding constrains the reply to this schema, so a field the prompt asks for and
> the schema omits is a field the model is not allowed to produce."*

也就是说，**「拆成什么」不是模型的发挥空间，是 schema 规定死的**。端点不支持时降一次级并
**记住**（`guidedSupported = false`，`openai.ts:77`），之后靠 zod 事后校验兜底——降级只发生一次，
不会每次调用都白试一遍。

**⑤（不算部件，但同等重要）：`stable` / `variable` 的切法。**
`model/client.ts:13` 强制把请求拆成两半，`stable` 在前进 system message，`variable` 在后进 user message。
理由写在文件头：这个端点上实测 9k token 的请求里 **6k 是前缀缓存命中的**，而缓存只在前导字节
完全一致时才命中。推论有两条，都是硬约束：

- `stable` 半区内**不许插值**——中间插一个变量，之后每次调用都会错过缓存。所以提示词是拼好的
  常量字符串数组，不是带洞的模板。
- 任何「这次运行想调一下」的旋钮（用例预算、语言指令）必须放 `variable` 半区。

## 2. 材料层：三个来源，同一种产物

三个 source 节点的 `outKind` 都是 `spec-material`，下游一个字都不用改。区别只落在
`derivedFrom` 这个印记上——而这个印记在下一层会改变模型被告知的事情。

### 2.1 `source.spec`（`casegen/nodes.ts:108`）

读文档。多份文档是**拼接**而不是二选一：

```ts
`===== ${p} =====\n${readFileSync(full, "utf8")}`
```

每份文档在材料里保留自己的名字。注释说明了为什么：**「a story traced back to "the spec" is
barely traced at all when the spec is four files」**——出处要能指到具体哪一份，这个分隔符是
后面 `splitDocuments` / `locate` 能工作的前提。

### 2.2 `source.explore`（`casegen/nodes.ts:152`）

跑着的产品是材料的另一个来源。这条链跨三个进程：

```
source.explore (agent 进程，没有浏览器)
   └─ ProductObserver.observe        casegen/nodes.ts:84  ← 注入的接口
      └─ child.parent.observeProduct  apps/agent/src/main.ts:150   RPC 回网关
         └─ observeForAgent           server/src/procs.ts:88
            └─ setAgentObserver       server/src/index.ts:1153     决定 url / launch
               └─ live.observe → runner → runObserve   exec/interactive.ts:96
```

`runObserve` 采的是**确定性的一屏事实**（`interactive.ts:110`）：

```
===== 入口页 =====
URL: …
TITLE: …
TEXT: document.body.innerText 前 4000 字
CONTROLS: button / a[href] / input / select / textarea / [role=button] 前 60 个的可见文案
```

**（2026-08-27 之前）** `deep: true` 时只花一次模型调用往前走一屏：

> *"If a login form is present, log in using any test/demo credentials shown on this page;
> otherwise click the primary button to enter the application."*

然后再采一屏。走不进去也照记：

```ts
screens.push(`===== 前进一屏 =====\n没能进入：${message}`);
```

注释写着理由：**「走不进去本身就是观察结果的一部分：下游会把它记成『没看到的』」**。
**（现在）** 这一步是一个循环：每轮采一屏、判是不是没见过的（判重取「地址 + 控件集合」）、
没见过就带着「已经去过哪些地方」再往前走一步，**连续 `dryRounds`（默认 2）轮没有新界面就停**，
或采满 `maxScreens`（默认 6）屏。

改的原因是它此前恒等于两屏：对任何一个登录页之后还有几屏的产品，材料里都缺着大半，
而**缺的部分在下游完全看不出来**——规格照样整理得出来、用例照样生成得出来，只是系统性地
少了那几屏对应的一切。

材料末尾多出一段「这次探索走到哪为止」：采到几屏、为什么停、哪些地方没能走进去，
以及一句「没有出现在这里的功能，是没有被看到，不是不存在」。这是这份材料唯一能自证
薄不薄的地方——`spec.compose` 被要求把材料没说的记进「没有答案的地方」，而它只有在材料
自己说了「这里我没看到」的时候才做得到。

`notes` 上限 60000 字（原 24000——循环之后旧上限会在第四五屏上把后面的界面整段切掉，
而被切掉的部分在下游看不出来：材料看起来是完整的，只是短）。

**这里有一条已经拍板的产品逻辑**（`index.ts:1179`）：**explore 不产用例，explore 产材料**。
旧的 explore→用例直通路 2026-08-21 已下掉（连同 `POST /api/projects/:id/explore` 等三个接口），
理由是：

> 把观察直接变成用例，等于把「产品现在这样」直接写成「产品应该这样」，
> 中间那步判断被跳过了，没有任何一处可以让人说「这条不该这么写」。

## 3.0 先说一个跑了 21 次都没人发现的洞

在往下读之前必须知道这件事，否则下面每一层写的「规格如何流下去」都会读得过于乐观。

**`design.cases`——写每一条用例的那个节点——在 2026-08-27 之前，从来没有见过规格。**

链路是这样断的：

```
pack.ts:21    g1Graph({ spec: { path: specPath } })     ← 只给了路径，没有内容
graph.ts:43   specText: params.specText ?? params.spec.text ?? ""
                        undefined         undefined        ← 落到 ""
nodes.ts:476  { name: "spec", text: params.specText ?? "", share: 1 }
```

节点参数的注释写着「the graph usually threads it in from source.spec」——**但图建不出来**：
建图时只有路径，文件要等节点运行时才读。

实测证据：存过的 7 个图版本（`g1-text-cases` v1–v4、`selftest-g1` v1–v3）全部 `specText` 缺失；
21 次历史运行全部没有 override。写用例的那次调用实际收到的是：

```
SPECIFICATION (for context — design cases for the STORY below only):
                                          ← 这里什么都没有
STORY US-01: …
ACCEPTANCE CRITERIA: …
```

**它只看得见故事的标题和验收标准。**

### 这动摇了哪些已有结论

不是说补上规格覆盖率就一定会涨——而是下面这几个结论都建立在一个不成立的前提上：

| 结论 | 问题 |
|---|---|
| M1 根因分析（07 §7）把缺口归给「清单比文档具体」 | **design 节点没读过那份文档** |
| 5 条 vs 10 条区分实验（p=0.375） | 两臂都是盲的，测的是「同一份盲区里多产几条」 |
| M3 的 `oracleGuidance` 配对评测（p=1.0） | 两臂同样都是盲的 |
| `fitToBudget` 的截断机制 | 生产里从未生效过——被预算的那半永远是空串 |

还有一处反讽：复核队列的 regenerate（`review.ts:468`）**是有**规格的。
**重写一条用例时模型看得到规格，第一次写的时候看不到。**

### 为什么能藏这么久

因为**没有任何一处检查过「规格进没进提示词」**。产出看起来完全正常：用例有标题、有步骤、
有断言、有 tier，门禁照样打分，只是系统性地薄。这类洞不会自己浮出来，它只会表现为
一个没有解释的覆盖率数字。

修法与出处（`origin` / `derivedFrom`）已有的做法一致：规格跟着故事一起往下走
（`StoryBundle.specText`）。参数保留为覆盖，但**空参数不再覆盖**——参数作为覆盖是对的，
一个空的不该压掉真正的规格。

## 3. explore → spec：本质是**不补全**

`spec.compose`（`casegen/nodes.ts:206`）是整个流程里**唯一**产出规格的地方。
一次模型调用，然后一整套确定性复核。

### 3.1 一句话决定这一层能干什么

`COMPOSE_STABLE`（`casegen/prompts.ts:248`）的首句：

> *"You organise raw material into a specification. You do not write the specification's
> content — you organise what is already there."*

**整理的对立面是创作。** 用户给的文档可能缺章少节、可能自相矛盾、可能一半是背景故事；
观察记录则根本不是规格。这一层要做的是归并与结构化，**不是补全**。

### 3.2 来源不同，被告知的事情不同

`composeVariable`（`prompts.ts:267`）按 `derivedFrom` 注入不同的一句：

| `derivedFrom` | 注入的话 |
|---|---|
| `exploration` | *"This material is OBSERVATION of a running product. It records what the product does, **not what it should do**. Write rules as statements of current behaviour; never phrase one as a requirement."* |
| `document` | *"This material is documentation written by people. It records intent."* |
| `codebase` | *"It records what is implemented, not what was intended."* |

**这是整条链上最容易漏、也最要命的一格。** 观察是「现在是这样」，文档是「应该这样」。
把观察写成需求就是越权——下游会拿规格当「应该」，于是**产品现在的样子自动变成产品正确的样子，
任何现存缺陷都会被固化成规格**，之后所有用例都去验证这个缺陷。共模失效在这里就发生了，
比 07 §4 讲的判定环节要早得多。

### 3.3 虚的部分怎么处理：不填实，改成**被点名的虚**

`COMPOSE_STABLE` 的五条约束，全部指向同一件事：

| 约束 | 原话 | 治什么 |
|---|---|---|
| evidence 必须逐字抄 | *"A rule you cannot quote for is a rule you invented — leave it out."* | 编规则 |
| 界面文案一字不差 | *"Downstream assertions are checked against these strings, so an approximation becomes a false failure later."* | 近似 → 二十分钟后的假失败 |
| `unknowns` 不可选 | *"An empty list is a strong claim. A specification that omits its own blind spots reads as complete, and everything derived from it inherits that claim."* | 把盲区当成完整 |
| 矛盾不许选边 | *"Never resolve a contradiction by choosing: record both, and put it in `unknowns`."* | 悄悄拍板 |
| 不许凭常识加规则 | *"Never add a rule because it is normal for this kind of product."* | 常识冒充规格 |

所以答案是：**虚的东西没有变实，它变成了一条写在 `unknowns` 里、有名有姓的空洞。**

### 3.4 交卷之后：程序去查，不再问模型

`nodes.ts:258` 起：

```ts
const docs = splitDocuments(material.text, material.origin ?? "inline");
const located = rules.map((r) => ({ ...r, source: locate(r.evidence, docs) }));
```

`locate` 是**确定性字符串包含**。注释写明为什么不再问一次模型：

> 一个「你这句是不是原话」的自评，量的是模型的自信，不是事实。

结果分三档报，含义差得很远：

| 情况 | 报什么 | 含义 |
|---|---|---|
| `evidence` 为空 | `N/M 条规则没有材料原话作为出处` | 编的 |
| 给了 `evidence` 但定位不到 | `它是转述或是编的，不是原话` | **比第一档更值得看** |
| `unknowns` 为空 | `这是一个很强的断言，值得人看一眼` | 声称材料没有盲区 |

0 条规则直接抛错：`the material produced no rules — nothing downstream could be traced to it`。

**净效果**：一坨 `URL / TITLE / TEXT / CONTROLS` 的屏幕文本
→ 一组带可回查原话的 `R-n` 规则 + 一份明写的盲区清单。

## 4. spec → stories：出处是查出来的，不是问出来的

`plan.stories`（`casegen/nodes.ts:314`）。**一次调用出全部故事**——不是每条一次，因为故事之间
要互相知道才不会重复，整份规格就是这一次调用的材料。

`STORIES_STABLE`（`prompts.ts:11`）的拆解单位是**「一个用户可见的能力 = 一条故事」**，
外加四条：保留规格自己的 id、`acceptance` 必须引用规格原话一条一项、明写不在范围内的不产故事、
**材料是多份文档时每一份都要覆盖**（「stopping after the first leaves half the product untested」），
预算不够时要摊开而不是耗在第一份上。

### 交卷之后的两级归属（`nodes.ts:360`）

```
先定位：拿每条验收标准回规格里找**已经定位过**的规则 → sourceBy: "located"
定不到：才用模型自己填的 source，且必须指向一份这次真读过的文档 → sourceBy: "claimed"
两者都不成立：整个丢掉
```

最后那条的理由写在注释里：**留着一个指不到任何读过文档的说法，界面上就会显示一个查无此处的
文件名，而那比空着更难发现**。

还会主动报两件事：哪份文档一条故事都没出（「一个静默的洞，不说的话要到很久以后才变成一个
没有解释的覆盖率数字」），以及多少条故事的出处是声称而非定位出来的。

> **已知欠账**（文档 10 §A）：`source` 字段本身仍可能整批缺失或整批指向同一份文档。
> 定位这一层是补丁，根治要在 stories 节点按输入切片归属。

## 5. stories → cases：这一层的规划最精细

`design.cases`（`casegen/nodes.ts:428`）。**每条故事一次调用**，两个理由写在函数头：

- 短调用命中前缀缓存，比一次长调用便宜得多；
- **一个故事的坏回复不该赔上整批**（失败进 `failures[]`，只有全军覆没才抛错）。

### 5.1 拆解维度一：五种设计方法（枚举，不是自由文本）

`CASES_STABLE`（`prompts.ts:29`）明列并要求每条用例自报用了哪种：

| 方法 | 定义 |
|---|---|
| `equivalence` | 每个有效/无效输入类取一个代表 |
| `boundary` | 空、最小、最大、刚过界 |
| `state-transition` | 一次状态变化，以及变化后必须成立的东西 |
| `decision-table` | 条件的组合 |
| `negative` | 错误路径——产品必须拒绝，并且说出来 |

`CASES_SCHEMA` 把它锁成 enum，所以模型不能自创第六种。

### 5.2 拆解维度二：判据硬度必须当场兑现

这是这一层最有意思的设计。`tier` 不是形容词，提示词逼模型**同时交出可执行形式**：

```
tier 1 = 程序能判（字面量、数字）
tier 2 = 两次观察之间的关系
tier 3 = 只能让模型看屏幕
Prefer 1. Use 3 only when nothing else can decide it.

tier 1/2 你**必须**同时给 oracle，五选一：
  {"kind":"text",  "value":"<页面显示的字面量>"}
  {"kind":"noText","value":"<页面必须没有的字面量>"}
  {"kind":"url",   "value":"<地址的一部分>"}
  {"kind":"count", "value":"<字面量>","op":"eq|gte|lte","n":<数>}
  {"kind":"delta", "value":"<数字旁边的标签>","direction":"increased|decreased|unchanged","by":<数>}  ← tier 2
```

收尾那句是整个 tier 机制的锚：

> *"Claiming tier 1 without an oracle is the one thing that makes the label worthless."*

`oracle` 在 schema 里是判别联合，`kind` 是 enum——**模型造不出第六种判据**。

### 5.3 其余的字段级约束

- `expected` 是**一个**具体可判定的结果，点名可观察的东西：一句字面消息、一个数字、一个状态。
  明令禁止 `works correctly` / `behaves normally` / `is fine`。
- 界面文案照抄规格，不许翻译、不许发明规格没承诺过的措辞。
- 步骤是短、具体、**端无关**的动作。没有选择器、没有页面对象、没有代码——所以阶段一的产物
  换 iOS/Android 不用重写。
- 凭证一律走 `${env.NAME}` / `${secret.NAME}`。
- `key` 是判重三元组 `transition|parameters|assertion`。
- 全是 happy path 的套件是坏套件。

### 5.4 `ORACLE_STRICT`：一条被做成参数的建议

`prompts.ts:107` 是 HarnessCritic 提的「更严的判据说明」，做成 `oracleGuidance: default | strict`
参数。它列出什么算可观察现象、什么不算（含反例：`弹出确认对话框，提示用户确认删除` —— 没点名
任何文案、元素或数字）。

注释点明它的地位：**「它存在的意义就是被比较，而不是被相信」**。
配对评测最后判它 **p = 1.0，没有方向**（07 §10）。这就是这套机制该有的样子。

### 5.5 预算参与规划，而且必须让模型知道

`casesVariable`（`prompts.ts:146`）把 `CASE BUDGET: at most N cases for this story` 放进
**variable 半区**。函数参数上那段注释记着一个踩过的坑：

> `maxCasesPerStory` 原先**只在解析完之后截断**——模型照旧按至多 8 条设计，harness 把超出的扔掉。
> 把它从 5 调到 10，除了少扔几条什么都不会变，那个「5 条 vs 10 条」的区分实验按原状根本做不出差异。

### 5.6 上下文预算：份额 + 再分配 + 截了要报

```ts
fitToBudget([
  { name: "story", text: JSON.stringify(story), share: 1, fixed: true },  // 故事不可截
  { name: "spec",  text: params.specText ?? "", share: 1 },               // 规格可截
], params.contextTokens);
if (specForCall.dropped > 0) ctx.emit("log", { text: `trimmed ${dropped} tokens…` });
```

`model/budget.ts:66` 的两条规则比算术重要：**没用完的份额再分配给超了的**（固定切分等于
把窗口变小），**截的是中间**（头说明这是什么，尾通常是刚追加的），并留 `…[trimmed]…` 标记。

## 6. 门禁①（`gate.textcase`）：不调模型，只标记不拒收

`casegen/gate.ts`。**十条规则全是关于这批用例的事实**，一次模型调用都不花。

| 规则 | 判什么 | 级别 |
|---|---|---|
| `traceability` | 用例指向的故事不存在 | warn |
| `granularity` | 步骤 > maxSteps 或没有步骤 | warn |
| `structure` | 没有 expected——没有可通过或失败的东西 | warn |
| `oracle-vague` | 命中 VAGUE 正则 / 不含 CONCRETE 痕迹 | warn / info |
| `tier` | 声称 tier 3 | info |
| **`tier-unbacked`** | **声称 tier≤2 却没有机器判据** | warn |
| `secret` | 凭证写进步骤而不是占位符 | warn |
| `duplicate` | 判重三元组撞了 | warn |
| `negative-ratio` | 负例+边界占比低于阈值 | warn |
| `story-uncovered` | 某条故事一条用例都没有 | warn |

**分数** = 没有 warn 级 finding 的用例占比。注释说明它是钝器：*"meant to move between versions,
not to be a certificate."*

**为什么不拒收**——文件头写着：

> 上一版那种「拒收 vague 断言」的正则**开火十几次、真阳性零次**，还误伤了
> 「登录按钮重新变为可点击」这样的好判据。**一个妨碍日常工作的门禁会被关掉，然后它什么都保护不了。**

**两个 tier 分布并排**（`gate.ts:127`）：`tiers`（声称）与 `tiersBacked`（`c.oracle ? tierOf(c.oracle) : 3`，
能兑现的）。两者的差就是那个值得盯的数——对存量自举批次实测过：100 条声称 77×t1/12×t2/11×t3，
**带机器判据的 0 条**。

## 7. 接缝：复核队列 → 看板

G1 的产物**不自动进看板**。`review.ts:264` 的 `approve()` 是产物变成看板用例的那一刻，
出处一并带上：故事 / 设计方法 / tier / **oracle** / 门禁分 / 来源运行 / `degraded` 标记 / code。

`oracle` 那一行的注释是关键：**「没有它，看板就只留下 tier 这个标签，丢掉背后撑着它的东西」**。

**接着跑**（`continue.ts:55`）靠 kind 对接：源运行末端节点的 `outKind` 对上另一张图根节点的
`inKind`，`g2-code` 就能吃下 `gated-cases` 从半路起跑，不用重问模型。目标端跟着源运行走——
「接着跑出来的代码属于同一个项目，让人再选一次只会让两半落在不同地方」。

## 8. cases → code：保留的是**含义**，不是文本

`codegen.case`（`codegen/nodes.ts:57`）。每条用例一次调用。

### 8.1 允许的调用面只有三个

`CODEGEN_STABLE`（`codegen/prompts.ts:6`）：`aiAction` / `aiInput` / `aiAssert`。加上六条规则，
其中两条是从真实事故里长出来的：

- **凭证**：*"If the case needs a username or a password and does not name a placeholder,
  use `${env.USERNAME}` and `${secret.PASSWORD}`: inventing a value makes the case fail for
  a reason that has nothing to do with the product."*
- **前置是状态，不是注释**：*"The run starts at the application's entry point… emit the actions
  that get there BEFORE the case's own steps. A case whose first step acts on a screen the run
  never navigated to does not fail because the product is broken; it fails because it was never
  taken to the product."*
  ——这一条是自举 M2 第二次跑抓出来补的（07 §8）。

### 8.2 `parseCode` 刻意不是 JS 求值器

`codegen/parse.ts:48`。正则扫允许的调用面，手写 `readString` 读字符串字面量。
**没有任何东西执行模型的输出。**

越界的调用（`page.` / `browser.` / `cy.` / `driver.`）记进 `unsupported` 而不是忽略——
「静默丢掉一行会产出一条跑的和说的不是一回事的用例」。

产物是**归一化动作表** `{kind: "action"|"input"|"assert", text, field}`。文件头写明它的地位：

> 生成器被要求产出 Midscene 源码，但 harness 保留的是**含义**而不是信任那段文本：
> **执行什么、门禁检查什么、修复循环 diff 什么，必须是同一个东西**，否则三方对这条用例
> 做什么这件事说的不是一回事。

### 8.3 片段提取：可复用必须意味着被引用

`extractFragments`（`parse.ts:99`）找**至少 2 条用例共享的最长开头序列**（≥2 个动作，
且**不含 assert**——「共享前置是 setup，不是判决」），提取成片段，用例改成 `uses: [name]`。

> 「可复用」必须意味着共享步骤被**引用**而不是被复制——一个每条用例都重复登录的套件，
> 改一次登录要编五十个文件。

## 9. 门禁②（`gate.code`）：有拒收权，但只对事实

`codegen/gate.ts`。静态检查，不运行代码。

| 拒收（block） | 理由 |
|---|---|
| `codegen-failed` | 压根没生成出来 |
| `unsupported-call` | 越界调用，跑不了 |
| `empty` | 没有任何动作 |
| `no-assertion` | **「这不是测试，这是一次访问」** |
| `inline-secret` | 凭证写进源码 |
| **`invented-credential`** | 见下 |

| 只警告 | |
|---|---|
| `granularity` | 动作 > 12 |
| `raw-sleep` | **「对时间的猜测在慢机器上一定错」** |
| `reuse` / `duplication` | 该引用片段而在重复 |

**`invented-credential` 的边界值得单看**（`gate.ts:50`）。它的来历写在注释里：生成器编了
`testuser`/`testpass`，登录理所当然失败，修复循环于是「合理地」报告**产品缺陷**——

> **编造的凭证不只是失败，它以嫁祸产品的方式失败**，而且悄无声息地毁掉这套件在登录页之后
> 抓到任何东西的能力。

豁免同样重要：负例本来就该输入无效值。判断证据取**标题 + 断言**，**步骤不算**：

> 用写死凭证这件事本身，来豁免写死凭证，是循环论证。

这条边界是一次真实误伤改出来的（文档 10 · A4）：`S-02-2-登录失败后页面url保持不变`
的断言写的是**后果**（URL 未跳转）而不是拒绝本身，`designMethod` 还是 state-transition，
只看 `expected` 就会把它拦下并给出错误建议——换成 `${env.*}` 会让登录**成功**，而这条用例
要的正是它失败。

**分数** = `1 - blocked/cases`。

## 10. `repair.loop`：循环在节点里，不在图里

`codegen/nodes.ts:153`。函数头写明这个选择：

> **thin graph, thick module**：图保持可校验、可排序、可部分重跑的 DAG，
> 而迭代——它需要自己的停止规则、自己的预算、自己的诚实性检查——留在一个能一眼读完的地方。

### 每条用例的循环

```
1. 执行 expandActions(case, fragments)          ← 执行的是动作表，不是代码文本
   oracle 取自**文本用例**，不取自生成的代码
2. 失败 → shouldContinue？
      轮数上限 / 无进展轮数上限 / **infra 失败立刻停**
3. 模型改代码
      回 {"verdict":"product-defect"} → 走产品缺陷出口，一个字都不改
4. parseCode → refold 回片段 → classifyRepair(before, after)
      两边都 expandActions 之后再比
5. assertion-semantics 或 case-removed → 打上 degraded
6. 重跑，回到 2
```

**第 2 步的 oracle 归属**：注释写着「修复会重写代码，判据要是长在代码里就会被一起重写」。

**infra 立刻停**（`repair.ts:104`）：*"Retrying a broken environment burns the budget without
ever addressing the fault, and it would file an environment outage as a product defect."*

**无进展上限**的来历（`repair.ts:84`）：一个已发表的案例研究里，修复循环跑满 16 轮上限
一百多次、**什么产物都没产出**——上限存在，进展检查不存在。

**`REPAIR_STABLE`（`codegen/prompts.ts:47`）明列可改与不可改**：

| 可以改 | 不可以改 |
|---|---|
| 动作的措辞（让驱动 UI 的模型找得到目标） | **断言的含义**——不许弱化、不许放宽、不许删除 |
| 动作的顺序，或流程需要的额外动作 | 用例的目的——不许换成一条更容易的 |
| 在动作里等一个**条件** | |

以及那个出口：*"If the product genuinely does not do what the case asserts, say so instead of
fixing: reply exactly `{"verdict":"product-defect","reason":"..."}` and change nothing."*

### `classifyRepair`：怎么认出一次不诚实的修复

`repair.ts:41`。`assertionWeakened` 三个信号，**刻意宽松**——「误报一次的代价是报告里多一行，
漏报一次的代价是这份报告失去意义」：

1. 断言整个消失；
2. 它原本检查的某个引号字面量消失；
3. 长度掉到原来的 2/3 以下（具体的主张被换成笼统的）。

改动分类：`assertion-semantics` / `case-removed` / `waiting` / `structure` / `selector-wording` / `none`。

### 两个通过率并排

`tally`（`repair.ts:76`）：

- `loosePassRate` —— 所有通过的
- `strictPassRate` —— 扣掉「只有把断言改松/删掉用例才变绿」的那些

文件头讲了为什么必须并排：在那份已发表的自动修复系统研究里，这条捷径被走得足够频繁，
把报告的收敛率**从 70% 打到 50%**。这个项目不设人工审批，**那么唯一的防线就是度量它**。

## 12. 图运行时给的保证

`graph/runtime.ts`。这些是「拆解」之外、让整条链可复现可调试的部分：

| 保证 | 怎么做到 |
|---|---|
| **稳定拓扑序** | 入度为 0 的节点按**声明顺序**入队（`graph.ts:105`）——同一张图两次运行序列相同，可复现从这里开始 |
| **契约三重校验** | 运行时对每个节点校验 `input` / `params` / **`output`**。输出不合自己的契约就地报错：「下游是凭这个契约连上来的」 |
| **部分重跑** | `only`（喂上游存的产物跑一个节点）/ `from`（这个节点及其下游）——三种调试模式的自动部分 |
| **断点** | 停在节点**之前**，运行仍可续。规则有一处特例：**被点名要跑的节点，它自己的断点不拦**，否则「继续」会永远停在同一个节点上 |
| **预算三闸** | `calls` / `usd` / `ms`。撞闸的结束状态是 `budget` 而不是 `done`——**「跑完」与「耗尽」是两种结束** |
| **消融** | `ctx.ablated`，五个开关各自被节点真正读取，每个都有测试证明它改变了行为 |
| **逐节点成本** | `ctx.spend` 双记账（节点 + 全局） |
| **一个节点一个输入** | 多入边直接判非法：「合并是一个有真实语义的操作（谁先谁后？谁覆盖谁？），它该是一个显式的 merge 节点，而不是一条没人看得见的隐式规则」 |

## 13. 三处断链（已修，记在这里因为它们说明了一类问题）

三条曾经是同一件事的三个面：**阶段二的产物是被携带和展示的，不是被运行的。**
2026-08-27 全部修掉。保留原状记录，是因为这一类洞的共同点比洞本身更值得记：
**每一处都不会自己浮出来**——产物看起来完整，只是少了它本该带上的那一半。

### ① 生成的代码从来没被执行过

**修之前**：工作流里执行的是 `expandActions()` 出来的动作表（这是设计），但批准进看板后
`POST /api/cases/:id/run` 跑的是 `c.steps`——阶段一的自然语言步骤。`case.code` 全仓库只有
写入、没有任何一处读出来执行。

**修之后**：批准时看板的 `steps` 改为取阶段二真的跑过的那串动作（见②）。执行的仍然是
动作表而不是源码文本——那是「保留含义而不是信任文本」这个决定的一部分，不是缺陷。
`codeline.ts` 里那句「it is what will execute tonight」已经改准：源码是给人读、给人 diff
的证据，执行走的是从它解析出来的动作。

### ② 修复循环的成果到不了看板

**修之前**：repair 改的是 `code`；`approve()` 写进看板的 `steps` 取自阶段一的 `gated.cases`。
修复循环加的等待、改的措辞，看板用例一条都没有——**它今晚仍然按原始步骤跑，
可能因为修复循环已经修好的那个理由而挂**。

**修之后**：`review.ts` 的 `stepsFromActions` 把阶段二的动作展开（含共享前置）写进看板。
优先级是「人的编辑 → 阶段二的动作 → 阶段一的文本」——人的编辑仍然排最前，
那是唯一一次有人看过这条用例并且表过态。断言不进步骤，它由 `expected` 与 `oracle` 表达。

### ③ 导出的工程把 tier 打回原形

**修之前**：`specForCase` 只读 `tc.steps` / `tc.expected`，无条件写 `aiAssert`，
不读 `tc.oracle`。平台内刚兑现的 tier1/tier2 机器判据，**一导出就全变回 tier3 judge**。

**修之后**：导出带一份 `tests/oracle.ts`，语义与 `exec/oracle.ts` 一致（文本按可见正文包含、
次数按字面量出现次数、`delta` 在动作前后各读一次）。有 oracle 就由程序判定，没有才退回
judge——与平台内同一条规则。

**顺带修掉的第四处，比前三处更糟**：导出的 `slug` 剥掉了 CJK，而这个平台产出的用例标题
**就是**中文的——每条标题都塌成空串、退回 `"case"`，于是同一优先级下所有用例写进同一个文件，
**一批用例导出之后只剩最后一条，一声不响**。

> 文档 10 §E 说「产出 → 看板 → 夜间回归 这一段从来没有真正合上过」。
> 以修完之后的代码为准：链是通的，但**还没有一次真跑走完过全程**——
> 这条链的合拢仍然欠一次「批准 → 执行 → 看结果」的实证。

### 这四处的共同点

| | 表现 | 为什么没被发现 |
|---|---|---|
| §3.0 空规格 | 用例系统性地薄 | 产出结构完整，只是内容少 |
| ① ② | 看板跑的是修复之前的版本 | 看板照样跑得出结果 |
| ③ | 导出的套件全是 judge | 导出的工程照样能跑 |
| ③ 附 | 导出只剩一条用例 | 导出照样「成功」了 |

**四处都是「看起来成功」的失败。** 这类洞唯一的防法是让每一处都能自陈：
探索报出走到几屏、design 报出有没有规格、导出撞名时报出来。这一轮加的检查全是这一类。

## 14. 一句话总结

> **每一层都不给模型「怎么拆」的自由，只给它「填哪些格子」的自由；
> 格子由 schema 锁死，填进去的东西由代码回查。模型负责语义，判定权在程序手里。**

而 explore → spec 这一层的特殊之处在于：它拆的不是任务，是**认识论**——
把「产品现在是这样」和「产品应该是这样」分开，并且把材料没回答的部分**点名留在 `unknowns` 里**，
而不是用一条看起来很合理的规则把它盖住。

# 01 设计依据与实测数据

调研出处：`zyblog/content/posts/harness-survey-0{1..4}`、`harness-papers-0{1..4}`，可跑原型 `zyblog/harness/`。
本文只保留**约束了设计决定**的结论，每条注明它管住了哪一处。

## 1. 概念底座

- `agent = model + harness`，harness = **模型之外的一切**。
- execution harness 的六类职责：Observation / Context / Control / Action / State / Verification，彼此耦合。
- 三层分工（本项目的目录边界就照这句话切）：
  - **graph**：什么被允许继续走（路由、分支、并行）
  - **loop**：做什么、何时停（迭代节奏、停止条件）
  - **harness**：在哪跑、能碰什么、崩了怎么办、怎么被看见
- Fowler 四象限：guides（前馈）× sensors（反馈）× computational / inferential。硬要求：**sensor 的信号要为模型消费而优化**，不是给人看的堆栈。

## 2. 垂类（测试用例生成）与通用 harness 的差别

| 职责 | 通用 coding agent | 本垂类 |
|---|---|---|
| Control | 模型每步自己决定 | **流水线写死**（可复现性是产品价值本身）；仅 explore 分支是 agent loop |
| Action | 工具注册表 | **模型不调工具**，只产结构化数据，动手的是确定性代码 |
| Verification | 二元（过没过） | **分层**：assert / invariant / judge 三档 |

清单外但决定成败的一格：**产物的可复用与参数化**（用例要天天跑、要共享片段、要一套骨架跑 N 组参数）。一开始不设计，后面补会污染全部存量。

**代价结构与通用 agent 相反：误报比漏报致命。** 一条判据模糊的用例周期性红绿，翻三次之后没人再信这份报告——然后漏报也跟着来，因为没人看了。

## 4. 由此得到的设计原则

1. 先把 harness 的信息量拉满并量一遍，再谈模型。
2. 主干确定性优先；只有"面对未知界面"才交控制权给模型。
3. 判定分层，并把分布报出来（66 条全 judge 与全 assert 是两批东西）。
4. 门禁打分不拦路；能拦路的只有"跑不起来"这类硬事实。
5. 无审批 ⇒ 退化必须被度量（双口径）。
6. 失败先归因再修；基础设施故障不进"产品有问题"的账。
7. 任何组件都要能被关掉做配对比较，否则等于没打算证明它。
8. 记全轨迹：今天的成本，是将来微调唯一的数据来源。
9. 每加一个组件先问：它改的是结果，还是只是日志的形状。

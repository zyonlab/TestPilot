# 06　中断、恢复与检查点

> 这一章回答的是一个能被证伪的问题，不是一个方向：
> **一次运行跑三天，中途进程重启一次，接得下去吗，具体丢什么。**
>
> 结论先给：**检查点这件事，这个仓库做对了，不用重建。**
> 撑不住三天的不是「没有检查点」，是四个可以分别定价的洞。而其中最贵的那个不在运行时里——
> 是**「恢复一次崩溃的运行」这个动作本身，会静默销毁这次运行的上限、已花费和消融记录**。

## 问题

### 三个尺度

三个数，全部来自当前工作副本的 `server/.data`（2026-09-01 查，下称「本机实测」）：

| 尺度 | 实测 | 对照「三天」 |
|---|---|---|
| 今天最长的一次运行 | `wf-mtbh0ylm`，`spend.ms = 4,128,313`（68.8 分钟） | 三天是它的 **63 倍** |
| 检查点的最大间距 | 单个节点最长 `repair = 4,068,930 ms`（67.8 分钟） | 一次崩溃最坏赔掉这么多 |
| 血缘的保留窗口 | `events.db` 200,009 行，跨 `2026-08-27T18:18` → `2026-08-31T17:46` = **3.98 天** | 只比三天多 0.98 天 |

第三行是最容易被忽略的一个：**一次三天的运行会在自己还没跑完的时候，把自己的开头挤出保留窗口。**
`keepLast: 200_000`（`server/harness.config.ts:19`）是计数式的，
而这 200,009 行里 `log` 占 148,464（74.2%）、`process.status` 占 40,520（20.3%），
真正的血缘 `wf.node.output` 只有 **679 行（0.34%）**。
`harness.config.ts:140` 已经把这个形状记下来过一次：
「一次实测 600 条事件里 457 条是它的崩溃日志，探索的日志全被挤掉」——**实测**。

### 一件已经发生过的事

不用假想。工作副本里就躺着一个证物：

```
wfRunId  wf-mtfmsfq8   status=interrupted
detail = {"mode":{"kind":"full"},"target":{},"ablate":["case-priority"],
          "prompts":{...},"error":{"message":"the gateway restarted while this run was in flight"}}
wf_node_outputs(wfRunId='wf-mtfmsfq8') → 只有一行：docs，1,870 字节
```

逐条读这个 JSON：

- **没有 `spend` 键。** 这一段花掉的调用、token、时间，一个数都没留下。
- **没有 `nodes` 键。** 哪些节点跑过、各花了多久，没有。
- **没有 `pausedAt` 键。** 于是 `resumeRun`（`server/src/graphs.ts:882-883`）第一句就抛：
  `this run is not paused at a breakpoint, so there is nothing to resume`。
- 但 `ablate: ["case-priority"]` **还在**。记录仍然声称这次运行关掉了 case-priority。

也就是说：那一行 `restart: "always"` 上面写着
「The agent resumes from its checkpoint, so respawning is always the right move.」
（`server/src/procs.ts:135`）——**这句话对 agent 进程是真的（它会被拉起来），
对那次运行是假的（没有任何代码去接着跑它）**。
真正发生的补偿动作是 `reconcileOrphanedRuns`（`graphs.ts:454-472`）把行改写成 `interrupted`，
而那是一个**记账**动作，不是一个**恢复**动作。

### 这不是一个洞，是四个

「三天撑不住」这句话如果只说一遍，会导致把整个检查点层推倒重来——那是最贵的返工。
把它拆开之后，四个洞的补法与代价完全不同，而其中两个是半天的活：

| # | 洞 | 层 |
|---|---|---|
| 1 | 崩溃的运行没有自动恢复入口，手工恢复会丢上限/已花费/消融集 | 网关（`graphs.ts`） |
| 2 | 花费只在运行结束时写一次，且是替换不是合并 | 网关（一个订阅） |
| 3 | 检查点粒度 = 一个节点，最坏 67.8 分钟 | 运行时 + 节点 |
| 4 | 血缘保留窗口 3.98 天 < 运行时长 | 存储（`obs/store.ts`） |

## 技术点

长运行的检查点有三个正交维度，加一个常被忘掉的外部约束：

| 维度 | 是什么 | 判据 |
|---|---|---|
| **粒度** | 两次写盘之间的最大工作量 | 一次崩溃赔掉的期望 ≈ 间距 / 2 |
| **完备性标记** | 一份部分产物必须**自己说自己是部分的** | 恢复方不能靠"看起来完整"判断 |
| **恢复入口** | 崩溃恢复必须走**携带上限与已花费**的那条路 | 否则恢复动作本身改变了运行的语义 |
| **（外部）保留窗口** | 血缘留存 ≥ 运行时长 + 复核时长 | 否则运行还没读完，证据先没了 |

第二条是这个仓库自己写下的纪律，只是写在另一个地方：
`obs/langfuse.ts:275` 的 `forTrace` 截断之后**必须留下 `__truncatedForTrace` 痕迹**，
理由是「悄悄截断的产出从外面看只是短了一点」。**部分检查点是同一个形状。**

## 现状

### 一、能撑住的——这些不用改

| 能撑住什么 | 为什么它撑得住 | 证据 |
|---|---|---|
| 节点产物跨进程重启存活 | 逐节点写盘，主键 `(wfRunId, nodeId)`，不在内存 | `graph/store.ts:15-57`；本机实测 381 行 / 8.29 MB |
| 「只跑这一个节点」「从这里往下跑」 | 复用 `wfRunId` **就是**续跑，恢复是一行 | `graph/runtime.ts:119` `await store.all(wfRunId)` |
| 上限跨段仍是整次运行的上限 | `spent` 接着上一段算，时间上限把起点倒推回去 | `runtime.ts:119-127`、`:139`、`:380-390` |
| 「跑完了」和「预算用尽」不混为一谈 | 五个提前 return 各带各的 status | `runtime.ts:180-190`、`:292` |
| 断点续跑不会悄悄撤掉上限 | 撞了上限的运行**拒绝**续跑；改上限是一个独立的 PATCH | `graphs.ts:636-641`、`:673`；`index.ts:1877` |
| 一次被取消的探索不是一次丢掉的探索 | 取消只在轮首检查，在飞的一轮跑完，**仍然返回材料与图** | `exec/interactive.ts:1019-1024`、`:1350` |
| runner 崩了只赔一条用例 | `restart:"never"` + 派发时按需拉起，死掉的 runner 留在进程页上 | `procs.ts:178`；`server/src/exec.ts:36-58` |
| 「running」不会永远卡着 | 开机把陈旧的 running 改写成 interrupted | `graphs.ts:364-382` |
| 复核物 / 执行记录 / 基线不跟着运行走 | 它们在 `testpilot.db` 与 `ARTIFACT_DIR`，不在 `wf_node_outputs` | `server/src/db.ts:1002`；`index.ts:254` |

第三行值得单独说：`RunGraphOptions.spent` 那段注释是全仓库最该被引用的一段——

> 一份少报花费的报告比没有报告更糟，因为它读起来像一次测量。
> —— `packages/harness-core/src/graph/runtime.ts:61-69`

它已经把「上限跨段」这件事做完了，而且 `runtime.test.ts:257-301` 三个用例钉住了它。
**本章的变更二，是把这条已经赢下来的战役从「续跑」推广到「崩溃」。**

### 三、最贵的那一处：恢复动作本身会改写运行的语义

`startRun` 把**合并过的值写进记录**：

```ts
// server/src/graphs.ts:510 / :514 / :520
ablate: input.ablate ?? previous.ablate,
budget: input.budget ?? previous.budget,
paramOverrides: params ?? previous.paramOverrides,
```

然后把**没合并的原始请求发给 agent**：

```ts
// server/src/graphs.ts:533-535
ablate: input.ablate,
budget: input.budget,
spent:  input.spent,
```

而今天恢复一次崩溃运行的唯一路径，是 `POST /api/wf/runs/:id/nodes/:nodeId/run?mode=from`
（`server/src/index.ts:1833-1848`），它三样都不传，也不传 `graphVersion`。后果逐条：

| 送进运行时的 | 记录里写的 | 后果 |
|---|---|---|
| `budget: undefined` | `previous.budget` | 恢复后的这一段**完全不限额**，而界面显示上限还在 |
| `spent: undefined` | — | 计数器从零重来，正是 `runtime.ts:61-69` 要消灭的那件事 |
| `ablate: undefined` | `previous.ablate` | 消融**没有生效**，而记录说它生效了 |
| `graphVersion`（未传） | 记录里钉着旧版本 | 落到 `graphs.get(id)`（`graphs.ts:445-448`）= **最新**版本 |

这是[第 00 章](./00-方法与约定.md)命名的**形状一**：
「上游算出来了、也写进记录了，却没写进下游真正读的那个字段」。
症状同样是「产出看起来正常，只是差了点」——因为差别只在故障路径上出现，
而故障路径没有人盯着看。

对配对评测来说这条更严重：一条经历过恢复的臂，会汇报它没有跑过的消融集和上限。
`graphs.ts:512` 那段注释（关于提示词指纹）写的正是这类事故的另一半——
「两次运行钉了同一个图版本、却由不同的提示词产出，被当成只差一条臂来比」。
这里是同一个洞的第三个门：**同一个 wfRunId，前后两段跑的是不同的配置。**

顺带记下一条：`config.budget = {calls:500, usd:0, ms:4h}`（`server/harness.config.ts:20`）
被 `resolveHarnessConfig` 解析出来，然后**全仓库零处读取**
（`grep -rn "config.budget" server/src packages/*/src` 无结果）。
所以今天一次没有显式传上限的运行，本来就是不限额的。
一个三天的运行现在没有任何东西拦得住它。

### 四、`source.explore` 的循环状态：整块不在检查点里

这是本章唯一一个**真自主循环**（按[第 00 章](./00-方法与约定.md)的定义，全仓库只有两个）
被问到的地方，所以要说清楚。

探索循环的全部工作记忆是函数作用域局部变量，一个都不落盘：

| 变量 | 行 | 它记的是什么 |
|---|---|---|
| `seen` | `interactive.ts:1017` | 已采过的屏签名 |
| `linksSeen` | `:564` | 每屏上见过的链接 |
| `sfgStates` / `sfgEdges` / `idBySig` | `:589` / `:590` / `:592` | **走过的那张图本身** |
| `frontier` | `:644` | 待访问队列 |
| `deadHref` | `:663` | 直接导航会 404 的地址（要改成点击） |
| `triedGoto` | `:684` | 试过的导航 |
| `shapeCount` | `:682` | 同形状控件的重复计数 |

`runGraph` 的检查点只在节点边界上（`runtime.ts:114-115`）。
`runtime.ts:112` 那句「what a library would have added is checkpointing, which the output
store already provides」对每一个节点都成立——**除了这一个**。
runner 进程崩在第 20 轮，这 20 轮全部作废；`mode:{kind:"from"}` 重跑的是整个探索。

**但这里我建议不补**，理由是这个仓库自己写下的：

> PetClinic 五次运行图完全一致、标准差为 0……一旦有写入，这个数就会开始飘，
> 而且没人知道是哪一次飘的。
> —— `packages/harness-testing/src/exec/interactive.ts:37-48`（**实测**）

> 因为探索是确定性的……所以两臂拿到的是同一张图，配对仍然成立。
> —— `evals/design-methods-headroom.json:4`

**一次被恢复的探索不是一次确定性的探索。** 让它可恢复，等于让 run N+1 依赖 run N，
而配对评测的合法性建立在两臂拿到同一张图上。收益那一侧又恰好最小：
本机 56 次 explore 的最长时长只有 4.2 分钟、平均 0.7 分钟
（这些运行的 `maxScreens` 多为默认值 6；`design-methods-headroom.json:12` 用的是 24，
按线性外推约 17 分钟——**这是推断**）。
用一条会污染配对评测合法性的机制，去救一个平均 42 秒的节点，不划算。

要做也可以，但必须付全价：恢复过的探索要在 `stopped:{kind,n}` 上留标记，
并且**在配对评测里被拒绝**。这条纪律和 `graph.abstraction` 的来源印记是同一条
（`exec/sfg.ts:76-82`）。在那个开关做出来之前，这一格如实写成「会丢，且我们接受」。

## 变更

四条，按「每天工作量买到多少」排。**变更一和变更二加起来不到两天，买下的是四个洞里的两个。**

### 变更一：让崩溃的运行走上「续跑」那条已经修好的路

两处，都在 `server/src/graphs.ts`：

1. `reconcileOrphanedRuns`（`:364`）改写行的时候，它手上已经有整份 detail。
   顺手推导 `pausedAt`：**拓扑序里第一个没有存储产物的节点**，写进 detail。
   这样 `resumeRun`（`:631`）就能接手——而它已经带上限、带已花费、带断点集，
   而且会在还卡着上限时正确地拒绝。
2. `startRun` 里把「写进记录的」和「发给 agent 的」变成**同一个对象**：
   构一个 `runtime = { ablate, budget, spent, params, graphVersion }`，
   `saveRun` 和 `rpc.startRun` 都读它。`resumeRun` 与
   `POST /api/wf/runs/:id/nodes/:nodeId/run`（`index.ts:1833`）额外补上
   `ablate: detail.ablate`、`params: detail.paramOverrides`、
   `graphVersion: Number(row.graphVersion)`。

**这一条的价值不在「能自动恢复」，在于让记录说的话变成定义上为真。**

顺带两个必须一起做的小口子，否则变更一会被绕过去：

- `apps/agent/src/main.ts:108` 的 `promise.catch(() => undefined)` 不能再吞掉 `runGraph`
  的 reject。那个 reject 之后**没有任何** `wf.run.finished` 事件，而那个事件是唯一能把行
  移出 `running` 的东西（`graphs.ts:694`）。`runtime.ts:192-193` 就在 try 之外
  （`def.nodes.find(...)!` 后跟 `node.type`），一个图里不存在的 nodeId 会在这里抛。
- 端点收到的 `nodeId` 要校验它在图里（`index.ts:1833` 直接从 URL 取）。
  `downstreamOf` 对图外的节点返回空数组（`graph.ts:124-130`），
  于是 `mode:"from"` 会一路走到 `finish("done")`（`runtime.ts:292`）——
  **一次什么都没跑的运行，报告说它成功了**，正是 `index.ts:1789` 那段注释记下的事故
  （**实测**），只是从第二扇门进来。

### 变更二：每个节点结束就记账，且合并而不是替换

`wf.node.finished` 事件**已经带着每个节点的 spend**（`runtime.ts:273-277`），
而网关侧**没有任何代码订阅它**（`grep` 全仓库，只有前端 `src/lib/wf.ts:738/1013/1081`）。
在 `graphs.ts:694` 那个订阅旁边加一个：把每个节点的 spend 累进 `RunDetail.spend`，
把节点记录 **append** 进 `RunDetail.nodes`。

两个必须写清楚的细节：

- **别重复计数。** `wf.run.finished` 的 `payload.spend` 在传了 `spent` 时**已经是累计值**。
  正确做法是在开跑时把这一段的基线（`spent`）记进 detail，结束时用它对账，
  而不是两处各加一遍。
- `RunDetail` 是一个开放接口，以 JSON 存（`graphs.ts:811`），
  且 `saveRun` 的 upsert 保留未列出的键（`store.ts:79`）——**不需要迁移**。

### 变更三：节点内检查点，走两条已经通到每个节点的缝

不新增机制，扩两个已有的接口：

```ts
// packages/harness-core/src/graph/runtime.ts:16  —— OutputStore 加两个方法
part(wfRunId: string, nodeId: string, key: string, value: unknown): Promise<void>;
parts(wfRunId: string, nodeId: string): Promise<Record<string, unknown>>;
```

```ts
// packages/harness-core/src/graph/node.ts:12  —— NodeContext 加两个入口
checkpoint(key: string, value: unknown): Promise<void>;
restore(): Promise<Record<string, unknown>>;
```

落在一张新表 `wf_node_parts`（与 `wf_node_outputs` 并列，`store.ts:23`），
**不要**把部分产物写进 `wf_node_outputs` —— `store.all(wfRunId)`（`runtime.ts:141`）
预载的是给 `upstreamOf` 用的完整产物表，混进部分键会让上游查找拿到半成品。
`MemoryOutputStore`（`runtime.ts:22`）同样实现两个方法，全部现有测试不动。

第一个接入点就是最贵的那个节点：`repair.loop` 的用例循环
（`packages/harness-testing/src/codegen/nodes.ts:208-306`），一条用例一行；
重启后跳过已完成的。第二个是 `design.cases` 的按故事循环——它**已经在**发
`wf.node.output` 进度事件（本机实测 payload 最大 140 字节，形如
`{"nodeId":"design","storyId":"S-03","produced":5}`），键是现成的。

**这一条的硬约束：每一份部分产物必须带完备性标记。**
这个危险今天就存在，不是新引入的：`codegen/nodes.ts:209` 的
`if (ctx.signal.aborted) break;` 跳出用例循环，节点**照样在 `:311` 返回一个 bundle**，
被 `runtime.ts:268-271` 以 `status:"done"` 存下来——只有下一轮循环才会返回 `cancelled`。
所以一份被取消的 bundle 和一份跑完的 bundle 在存储里**长得一模一样**，
而门禁分是按它里面的用例数算的。加了自动恢复之后，这个危险从「偶尔」变成「每次」。

### 变更四：按 kind 保留，加 WAL checkpoint

`EventStore.prune(keepLast)`（`obs/store.ts:51`）今天是一条
`DELETE WHERE id <= MAX(id)-?`，与 kind 无关。改签名成
`prune(policy: number | Record<string, number>)`，按 kind 分桶各发一条 DELETE
（`events_kind` 索引已经在，`store.ts:65`），上限配在 `harness.config.ts:19` 旁边。

按本机实测的构成算一笔：非 `log`、非 `process.status` 的行是
200,009 − 148,464 − 40,520 = **11,025 行 / 3.98 天 ≈ 2,770 行/天**。
在同一个 200k 预算下把 `log` 封到 20k、`process.status` 封到 10k，
剩下 170k 给血缘 → **约 61 天**。三天的运行不再挤掉自己的开头。

另外补一件不属于运行时但会一起丢数据的事：全仓库
`grep 'VACUUM|wal_checkpoint|\.backup('` 在 `server/src` 与 `packages/*/src` 下
**零命中**。本机 `workflows.db` 主文件 10,260,480 字节、WAL **10,328,872 字节**
（WAL 比主库还大），`events.db` 主文件 38 MB、WAL 4.6 MB。
后果很具体：**今天 `cp .data/workflows.db` 复制出来的是一个缺了一半的库。**
在 `db.ts` 与各 store 的构造里加开机与定时的 `wal_checkpoint(TRUNCATE)`，
再加一个用 `VACUUM INTO` 的 `backupTo(dir)`——这个动作现在只作为
`7a8c8a4` 的一句提交说明存在，代码里没有。

### 变更五：**不做**的三件事

| 不做 | 为什么 |
|---|---|
| 给 `source.explore` 加恢复 | 见现状第四节。它会破坏「探索是确定性的」这条配对评测的合法性前提，而救的是一个平均 42 秒的节点 |
| 把 `restart:"always"` 变成「supervisor 自动重跑这次运行」 | `supervisor.ts:10-13` 写死了这条线：「Whether to retry the WORK is the loop layer's call, not the supervisor's.」自动恢复要放在 agent 里，不放在 `maybeRestart` 里，否则架构边界移位 |
| 为并行/扇入改图模型 | `runtime.ts:184` 的上限只在节点之间检查，N 个节点在飞就会超上限 N 个节点；`graph.ts:81-86` 的「一个节点一个输入」是「失败停掉整条线」这条规则成立的前提。见[第 04 章](./04-编排三模式.md) |

## 收益

| 指标 | 今天 | 做完变更一~四 |
|---|---|---|
| 一次重启赔掉的工作 | 一个节点，最坏 67.8 分钟 | 一条用例 / 一个故事 |
| 崩溃段被记录下来的花费 | **0%**（`wf-mtfmsfq8` 无 `spend` 键） | ≈100%，节点粒度；用例粒度需变更三 |
| 续跑之后还剩几段的节点记录 | 1（替换） | 全部（合并） |
| 恢复一次崩溃运行 | 人手拼 URL，且静默丢掉上限/已花费/消融集 | `POST /api/wf/runs/:id/resume`，三样都带 |
| 血缘保留窗口 | 3.98 天 | ≈61 天（同一个 200k 预算） |
| 冷备份的可用性 | `cp` 出来的库缺 WAL 里的一半 | `VACUUM INTO` 出来的是完整快照 |

还有一项不在表里但对[第 12 章](./12-Langfuse可观测性.md)有直接影响：
一次运行被切成 N 段之后，**每一段开一条新的根 trace**，
而 `sessionId` 由网关按项目给（`graphs.ts:555`）——于是同一次逻辑运行的 N 段在 Langfuse 上
不归在一起。做法是在 `startRun` 里加一条 fallback：没有更具体的归属时用
`session: run:<wfRunId>`。**只能是 fallback，绝不能覆盖**——
配对评测的 sessionId 必须继续赢，否则两条臂不再是一次比较。

这条的价值比它听起来大：记录只留最后一段的 `nodes`（变更二之前），
所以**一次续跑之后，早先几段唯一的账本就是 trace 和事件**，而事件在 3.98 天上被裁掉。

## 代价与风险

| 项 | 说明 |
|---|---|
| **部分产物看起来和完整产物一样** | 变更三最尖的一条，且**今天已经存在**（`codegen/nodes.ts:209` → `runtime.ts:268-271`）。没有完备性标记就上自动恢复，等于把偶发变成必发 |
| **写入压力** | 逐用例写会把写次数放大到「每条用例一次」，而 `workflows.db` 被网关（`graphs.ts:263`）和 agent（`procs.ts:129`）两个进程同时持有，`store.ts:21` 只设了 `journal_mode`，**没设 `busy_timeout`**。这一条要先做 |
| **`store.set` 是 last-write-wins** | `ON CONFLICT DO UPDATE`（`store.ts:50-57`）没有版本号也没有 `updatedAt` 守卫。一次重试若与还在收尾的旧执行撞上，好的检查点会被旧值盖掉 |
| **自动恢复 = 崩溃循环** | 一个必然崩溃的运行会被反复拉起，退避是 `250ms × 2^(n-1)`（`supervisor.ts:369`），而 `ProcStatus.restarts` 是**按进程**计的，不是按运行。必须加一个 per-run 尝试计数 |
| **续跑到一张改过的图上** | 变更一在补 `graphVersion` 之前是**不安全**的。`store.ts:79` 的 upsert 特意保护了版本钉，`continue.ts:37` 也已经尊重它——只有恢复这条路没有 |
| **`prune` 改签名动 harness-core 公共 API** | `EventStore` 接口、两个实现、`startRetention`（`obs/retention.ts:45`）、`procs.ts:69` 要一起改。并且它削弱了一个现有保证：`since(id)`（`store.ts:76`）今天走的是连续 id 段，按 kind 不均匀地删之后，重连的客户端会看到空洞——**WS 的续传路径必须显式容忍这件事，而不是碰巧没坏** |
| **WAL 截断会短暂阻塞写者** | 定时的 `wal_checkpoint(TRUNCATE)` 要挑运行间隙，或者接受一次几十毫秒的停顿 |
| **恢复后的运行开始守上限** | 变更一之后，一条今天「不限额」的恢复运行会开始停在上限上。这**是对的**（`graphs.ts:626` 的理由），但对依赖这个漏洞的人读起来像退步，要提前说 |

**什么情况下不该做变更三**：如果这条流水线的实际用法始终停在一小时以内
（今天最长 68.8 分钟），那节点粒度就是够的，2–4 天的工作量买不到东西。
变更三的前提是**先有一次真的要跑三天的任务**——本章末尾把这件事列成了无法证伪的一项。

## 怎么证伪

四种手段用三种，第四种明写为什么用不了。

### 单元测试（主要手段）

三个恒等式，全部落在 `packages/harness-core/test/runtime.test.ts` 与
`server/test/` 里，与已有的 `runtime.test.ts:257-301`「续跑时的上限」三个用例并列：

| 不变量 | 钉住什么 |
|---|---|
| `resumeRun(id)` 之后，运行时收到的 `{budget, spent, ablate, graphVersion}` **逐字段等于** `getRun(id).detail` 里的那四个 | 直接钉死 `graphs.ts:510/514/520` 与 `:533-535` 的分裂。这是一个恒等式，不是一个期望 |
| 跑 N 个节点后模拟崩溃，`detail.spend.calls` 等于 N 个节点 spend 之和 | 钉住变更二，且防止重复计数 |
| 一份带部分标记的检查点被恢复后，**不许**被当作完整产物喂给下游节点 | 钉住变更三唯一的硬约束 |

第三条要配一个反向用例：**没有**完备性标记的部分产物必须让恢复失败，而不是继续。
按[第 00 章](./00-方法与约定.md)形状三的推论，`wf_node_parts` 的完备性字段
**必须进 `required`**，不能是可选的——可选的键，这个模型和这段代码都会跳过。

### 门禁规则

一条，在图校验里：**部分运行请求的 nodeId 必须在图里**
（`graph.ts:38` 的 `validateGraph`，以及 `index.ts:1833` 的端点各一道）。
这条有客观判据，可以逐条标记，且它堵的是仓库自己记录过的最坏一种 bug 形状
（`index.ts:1789`，**实测**）。

### 配对评测

一条真正的 A/B，而且它证伪的正是本章的核心断言「恢复是无损的」：

> **A 臂**：正常跑完一张图。
> **B 臂**：同一张图，在第 k 个节点之后强杀 agent，走恢复路径跑完。
> **判据**：两臂的门禁分与语义覆盖必须相等；`spend.calls` 之差必须小于一个节点的量。

要注意**这个开关不许进 `ABLATABLE`**。`ablation.ts:9-13` 的规则是
「每一条都必须是某个节点真的会读的东西」，而「注入一次崩溃」不是任何节点读的东西。
它应该是评测跑器自己的一个测试专用 hook。把它塞进 `ABLATABLE` 就是
`ablation.ts` 那段注释警告的事：一个改不了任何东西的开关，会让报告说出一句真话，
而那句真话说的不是这个组件不重要。

### 消融开关：**用不了，这里如实写下来**

检查点**不能**用消融证伪。理由：它的效果只出现在故障路径上，而消融跑的是正常路径。
关掉检查点再跑一遍配对评测，产出会**一模一样**——报告会显示「关掉它没有影响」。
这正是 `evals/README.md` 那句话描述的情形：

> 写一个没人读的开关，报告会显示「关掉它没有影响」——这句话是真的，
> 但它说的不是这个组件不重要，而是这个开关根本没接上。

### 无法证伪的一项

**「三天真的跑得完」这件事，今天没有任何证据。**
最长的实测是 68.8 分钟（`wf-mtbh0ylm`），三天是它的 63 倍。
本章所有关于三天的推理都是**外推**，包括那张按节点算的检查点间距表——
它假设三天的运行由同样形状的节点组成，而一个真的要跑三天的任务
（比方说 200 个变异体 × 一小时一套）根本不是这个形状。
唯一能验证的办法是跑一次，而跑之前必须先有变更一和变更二，
否则那次运行崩了之后，**连它崩在哪、花了多少都留不下来**。

## 验收

1. 杀掉 agent 进程再拉起，`GET /api/wf/runs/:id` 显示该运行状态为 `interrupted`
   且 **detail 里有 `pausedAt`**，值是拓扑序里第一个没有产物的节点。
2. 对该运行 `POST /api/wf/runs/:id/resume` 成功，且从 agent 侧日志能看到收到的
   `budget` / `spent` / `ablate` / `graphVersion` 与记录里的一致。
3. 对一个撞了上限的崩溃运行调 resume，**必须被拒绝**，错误信息指向
   `PATCH /api/wf/runs/:id/budget`。这条是回归防护：变更一不能把 `graphs.ts:636` 的拒绝弄丢。
4. 一次跑了 5 个节点的运行在第 3 个节点后被杀，重启后 `detail.spend.calls` 等于
   前 3 个节点 spend 之和，`detail.nodes` 有 3 条；续跑完成后 `detail.nodes` 有 5 条
   （**不是 2 条**）。
5. `repair.loop` 跑 10 条用例，在第 6 条时杀掉进程；恢复后执行器只被调用 4 次，
   而节点产物里 10 条 outcome 齐全，且**恢复前那份部分产物在存储里能被一眼认出是部分的**。
6. 按 kind 保留生效后，连续跑满 `keepLast` 预算，`wf.node.output` 的最老一行的时间戳
   比改之前推后至少一个数量级。
7. 服务运行中执行 `sqlite3 .data/workflows.db "VACUUM INTO '/tmp/x.db'"`，
   在 `/tmp/x.db` 上能查到最新一次运行的全部节点产物。
8. 514 个测试仍然全绿，且 `runtime.test.ts` 的用例数增加了三条恒等式。

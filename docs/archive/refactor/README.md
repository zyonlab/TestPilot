# TestPilot 重构手册

> 一本关于「把一条确定性流水线，改造成一个可被信任的垂类 Agent」的书。
>
> 基线：`v2` @ `1cab2d9`　·　起写于 2026-09-01

---

## 这本书为什么存在

TestPilot 现在是一个**能用的 QA harness**：它从文档或探索里整理规格，拆故事、设计用例、
过两道门禁、生成代码、执行、修复，再用三个互不替代的指标（语义覆盖、结构覆盖、缺陷检出）
量自己做得好不好。这些都不是设想，是跑过 193 次提交、13 次配对评测、留在 `evals/*.json`
里的结论。

但它有一个说不出口的句子：

> **「这套 harness 会把自己漏掉的东西补回来，而且我们量过补回来的那些真的能抓住缺陷。」**

`gaps.ts` 已经把缺口分成了三类、算得出、显示得出——然后停在那里。没有任何一条代码路径
把一条缺口变回一条用例。`evals/*.json` 全部手写。`critic.ts` 提得出改进建议，但它的产物
是给人读的文字，不是一份可以直接跑的评测。

**这本书写的是从「能用」到「能自己变好」之间缺的那些东西。**

它不是一份需求清单。每一章都要回答同一组问题，而第一个问题永远是「现在的代码是怎么做的」——
因为这个仓库里已经有大量做对了的机制，而**重构最贵的错误是把已经对的东西推倒重来**。

## 怎么读

### 三份文档的关系

| 文档 | 回答 | 位置 |
|---|---|---|
| **对位审计** | 现在做到了什么，没做到什么 | Artifact《用代码回答一份 JD》 |
| **补齐路线** | 八处缺口，按什么顺序补 | Artifact《补齐这八处》 |
| **本书** | 每一处要**怎么**补，改哪个文件，为什么是这样 | 你在读的这个 |

审计给结论，路线给顺序，本书给设计。三者的证据口径是同一个：**以代码为准，不以文档为准**。

### 读的顺序

- **只想动手** → 读 [00 方法与约定](./00-方法与约定.md)，然后直接跳到你要做的那一章。
  每章都是自足的，开头有「前置」一节写清它依赖哪几章。
- **要做技术决策** → 第一部（01–02）必读。第 02 章列的三条性质是**否决项**：
  任何一个把它们弄坏的方案，无论收益多大都不做。
- **要评估工作量** → 直接看 [17 实施路线与优先级](./17-实施路线与优先级.md) 与
  [18 风险登记册](./18-风险登记册.md)。

## 成书状态（重要）

这本书的十九个文件不是同一种成色，**读之前必须知道差别**。

| 章 | 作者 | 行号是否经二次核对 |
|---|---|---|
| README、00、09、11、12、13、14、15、16、17、18 | 主笔 | ✅ 写作时逐条验证；12 章的代码是本人实现并跑过 |
| **01–08、10** | 并行勘察后由分身撰写 | ✅ 2026-09-02 机器补做（见下） |

原因如实记录：撰写流程设计为「起草 → 逐条核对 `file:line` 并重写」两步，
**核对那一步在跑到一半时撞上了配额上限**，15 个核对任务全部失败。
起草出来的九章结构完整、证据来自同一批勘察材料，但它们引用的行号一度没有被第二双眼睛打开过。

### 2026-09-02 补做（U-66）

补做的不是「再读一遍」，而是**两个每次都能重跑的脚本**——行号会一直漂，
一次性的人工核对只能保证那一天是对的：

| 脚本 | 判什么 | 结果 |
|---|---|---|
| `scripts/check-doc-refs.mjs` | 十九章里每一处 `file:line`：文件还在不在、行号在不在文件长度之内 | **974 处，全部指得到**；这条会失败（exit 1），可以进 CI |
| `scripts/fix-doc-refs.mjs` | 按**标识符**把漂掉的行号重新对准（不按 diff 移位） | 自动对准 **153 处**；386 处机器判断不了，留给人 |

两条纪律写在脚本里，这里再说一遍：

- **按内容对准，不按 diff 移位。** 移位要求知道「上次对准时是哪一版」，
  而那个信息没有留下来——本次补做第一版正是这么做的，结果把 21 处引用推到了文件末尾之外。
- **含糊就不动。** 只在「文件唯一确定 + 那个标识符在文件里只有一处声明 + 名字够特别」
  三条都成立时才改。一个理直气壮指错地方的行号，比一个有点旧的行号更坏。

386 处「机器判断不了」的多数是指向一段注释、一个区间或一处调用点，
**它们仍然可能是旧的**。读到关键结论时，请照 00 章的证据口径打开那一行确认。

> **因此：动手改代码之前，仍然先打开被引用的那一行确认。**
> 脚本保证的是「指得到东西」，不是「指对了地方」——后者需要读懂两边，机器给不出可信的答案。

## 一条贯穿全书的纪律

这个仓库的注释里记着一件反复发生的事，它在不同章节里会以不同面貌出现，
所以在开头就点破：

> **凡是有门禁的要求，模型就照做；凡是没有的，就漂。**
> —— `packages/harness-testing/src/codegen/gate.ts`

提示词里写了「不许写目标式动作」，模型照样写，直到有一条规则去查它；
提示词里写了「不许把黄金清单抄进建议」，critic 照样抄，直到 `critic.ts:164` 去查它；
schema 里把 `priority` 写成可选，模型就一条都不产，而报告看起来完全正常。

**所以本书里每一个「引入 X」的提案，都必须回答「X 怎么被证伪」。**
一个加进来却没人能证伪的组件，报告会说它有用，而那句话没有含义。
这条纪律在 [00 方法与约定](./00-方法与约定.md) 里落成了每章都要填的一栏。

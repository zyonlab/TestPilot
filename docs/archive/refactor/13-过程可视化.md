# 13　过程可视化

> 思考链、工具调用、引用来源——三样东西的答案完全不同：
> **一样根本不存在，一样已经很强，一样正在坏着而没人知道。**

## 问题

「过程可视化」被当成一件事，是这个主题最常见的错误。在这个仓库里它是三件事，
而且三件的答案互相矛盾：一件不该做，一件正在坏着，一件已经很好只差呈现。
下面按这三样分别盘。

---

## 现状

### 思考链：**这里没有思考链可渲染**

不是「还没做」，是**不存在**。三条独立的证据：

- 主干流水线跑在 `temperature: 0` + 约束解码下（`model/traced.ts` 的 modelParameters）。
- `ChatResponse`（`model/client.ts:47`）**没有 reasoning 字段**。端点即使回了推理，也没被接住。
- 探索循环的「决策」是代码不是模型：`nextAction`（`interactive.ts:1269`）是一个八级 if 级联。

`TP_MODEL_THINK` 默认开着，而且那个默认值是量出来的（`openai.ts` 的 `modelFromEnv`：
方差从 ±8.5 降到 ±0.6，门禁从 0.982 升到 1.000）。**但开着思考产出的是更稳的答案，
不是一段可以显示的推理**——推理 token 被端点消耗掉了，没有回到我们手里。

> **结论：不要做「思考面板」。**它会显示一个不存在的东西。
> 真要显示模型在想什么，先得让 `ChatResponse` 接住 reasoning——那是另一件事，
> 而且要先回答「接住之后谁读它、读它做什么判断」。

### 工具调用：streaming 的脊梁是好的，但历史回放是坏的

**实测：124 / 125 次运行的 trace 是空的。**

`loadTrace`（`src/lib/wf.ts:1289`）重建历史 trace 的方式是：
GET **全局** `/api/events?limit=1000`，然后在浏览器里按 `wfRunId` 过滤。

对着实际的事件表量一下就知道这必然失败——最后 1000 行里**只有 20 行带 `wfRunId`，
而且全属于同一次运行**。其余 124 次运行的事件**仍然在 `events.db` 里**，
只是那 1000 行的窗口根本够不到。

`docs/spec/06-通讯协议.md:92` 列了 `GET /api/wf/runs/:id/lineage` 这个端点。
grep `server/src/index.ts`：`:id`、`:id/nodes/:nodeId`、`:id/continuations`、`:id/budget`、
`:id/resume`、`:id/cancel`、`:id/traceability`——**没有 `/lineage`**。
规格写了，端点没建，前端于是拿全局列表凑合。

### 工具调用：交互会话的 2,305 帧不可回放

**实测：2,305 条 `session.progress` 行，`shotRef` 指向的文件全部已被删除。**

链条是这样断的：

| 环节 | 代码 | 行为 |
|---|---|---|
| 产生 | `shooter()`，`interactive.ts:412` | 返回**绝对主机路径** `/Users/admin/.../live/observe-….jpg` |
| 持久化 | `supervisor.ts:277` | 原样存进血缘 |
| 转发 | `inlineShot`，`server/src/exec.ts:169` | 为 SSE 构造**新对象**，**不改信封**，然后**删掉文件** |
| 广播 | `attachWs`，`server/src/ws.ts:18` | 转发**原始信封**（仍是绝对路径） |

于是血缘里留下 2,305 条指向不存在文件的绝对路径，**顺带把操作者的家目录广播给每个
WebSocket 客户端**。

而 `docs/spec/06-通讯协议.md:75` 明明白白写着：

> 截图一律以引用（`/api/artifacts/:name`）传递，不内联 base64

这条要求在字面上被满足了（确实没内联 base64），**实质上是空的**（引用指向删掉的文件）。
这正是 [第 00 章](./00-方法与约定.md) 说的形状一：要求写了，数据没给。

另外：`EventKind.artifactReady` 在 `obs/envelope.ts:64` 声明了，**从来没有任何地方发布过它**。

### 引用来源：**这是全仓库最强的部分之一**

和上面两样相反，出处追溯做得非常扎实，而且是**在数据层做的，不是在 UI 层**：

| 产物 | 出处字段 | 关键性质 |
|---|---|---|
| 规则 | `evidence` + `source` | `source` 是**回材料里定位出来的**，不是模型说的；定不到就留空并记数（`nodes.ts:497-508`） |
| 故事 | `source` + **`sourceBy: "located" \| "claimed"`** | 两种可信度**分开**（`nodes.ts:766-776`）；模型声称的出处若指向本次没读过的文档，直接丢弃 |
| 用例 | `covers`（转移 id） | 挂回产品模型，是结构覆盖率的分子 |
| 判据 | `OracleCheck.decidedBy: "machine" \| "judge"` | 谁下的判决（`run.ts:203-208`） |
| trace | `anchors: {text, grounded, where}` | `server/src/trace.ts:179` 的 `build()`，**确定性子串匹配**：先在原始材料里找，再在规格里找 |

`src/pages/ProductMap.tsx` 已经把这些渲染出来了：实线 vs 虚线区分走过与仅看见，
琥珀色标「走过但没有用例验它」，规则是**每一处视觉差异都必须回答复核者的一个问题**。

## 技术点

承上：三样各自需要的东西完全不同——

| | 需要 | 这里的状态 |
|---|---|---|
| 思考链 | 模型回传 reasoning + 一个消费它的理由 | 两者都没有 → **不做** |
| 工具调用 | 一条可按运行检索的事件流 + 稳定的产物引用 | 脊梁在，检索和引用都坏了 → **修** |
| 引用来源 | 出处随产物一路带下来 | 数据层已完成 → **只补呈现** |

## 变更

### 变更一：把 `/lineage` 端点建起来　【修 124/125】

两条路，选便宜的那条：

```sql
-- 已在本机 SQLite 3.53.2 上验证可用
ALTER TABLE events ADD COLUMN wfRunId TEXT
  GENERATED ALWAYS AS (json_extract(scopeJson,'$.wfRunId')) VIRTUAL;
CREATE INDEX events_wfrun ON events(wfRunId);
```

`EXPLAIN QUERY PLAN` 确认走 `SEARCH events USING INDEX events_wfrun`。
**零存储、零写入方改动**，正好放进 `store.ts:58` 那段幂等 DDL 里。`projectId` 同理。

然后加 `GET /api/wf/runs/:id/lineage`，前端 `loadTrace` 改读它。

### 变更二：合并两份手写的事件→行映射　【修一个已经发生的漂移】

`traceRowFor`（`wf.ts:1401`）是实时那一路，`loadTrace`（`wf.ts:1401-1425`）是重建那一路。
**两份手写映射已经漂了**：重建那边发 `tr.gateFindings`（带 findings 计数和 `${tokens} tok`），
实时那边发 `tr.gate` 且不带 tokens——**同一条事件在两个地方长得不一样**。

`wf.ts:1067` 那句注释本来就是为了防这件事写的。抽成一个函数，删掉重建侧的 switch。

> ⚠️ 唯一的真风险是 `live` 标志的契约（`wf.ts:985`）：合并后的映射**绝不能**让回放的行
> 触发 `refreshRun()`——那个标志存在的全部理由就是打断那个循环。

### 变更三：截图引用改成相对路径，并让文件活下来

(a) `shooter()`（`interactive.ts:412-420`）返回**相对 `ARTIFACT_DIR`** 的路径。
这个形状已经被证明可行：`server/src/graphs.ts:203` 就是 `relative(ARTIFACT_DIR, p)`，
而 `/api/artifacts` 已经是那个目录的静态服务。

(b) 停止在 `inlineShot`（`server/src/exec.ts:169-177`）里删文件，改为发布
`EventKind.artifactReady`（那个声明了却没人发的 kind），让 SSE 与 WS 都携带
`/api/artifacts/...` 而不是 data URI。

> **这一条有一个必须同时做的配套**，否则会造出下一个事故。
> `server/src/exec.ts:116-118` 写得很清楚：现在的「读完即删」是**承重的**——
> 「每一帧都带一个必须被消费掉的截图文件，而非流式的 explore 根本没有 watcher。
> 没有这个，live/ 会永远长下去。」
>
> 所以改成引用传递就**必须**同时给 `live/` 一个保留任务，否则它会变成下一个 `exec/`
> ——那个目录实测 914 个文件 / 57.5 MB，无人回收。

### 变更四：探索的每一轮发一个结构化帧

结构化的 `(from, action, to, ok, walked, note)` 在循环里 `interactive.ts:1254` 就有了，
但**只在最后 `:1418` 才组装**，所以 `ProductMap` 只能事后从成品节点产物读。

而且**每一步「为什么这么走」从来没被记下来**——`nextAction` 的八级级联里
是哪一级触发的，日志里只有 `{type:"log", message:"第 12 轮：点 Sign In（#login）"}` 这样的散文。

改：给 `Step` 联合类型（`interactive.ts:1269`）加一个 `rung` 标签（`nextAction` 每个 return 点一个字面量，
八处），并在 `interactive.ts:1269` 现有的 `emit({type:"navigated"})` 旁边发一条结构化帧：

```ts
{ type: "round", round, rung, from, action, to, ok, dry, screens, budgetLeft }
```

**`rung` 是这一条的重点**：它把「探索为什么这样走」从不可见变成可筛。
而 `interactive.ts` 的注释说每一级的位置都是一个实测的覆盖率结果——
既然位置是实测调出来的，**哪一级实际在触发就应该被记下来**。

### 变更五：复核的重新生成要有过程

`regenerate()`（`review.ts:762-815`）是一个串行的 for 循环，跑完才返回；
页面只显示一个「进行中 N 条」的计数（`Review.tsx:1096-1115`）。20 条用例就是几分钟的沉默。

机器就在隔壁：`server/src/mutationRun.ts:71` 发 `mutation.${kind}`，
`server/src/ws.ts:19` 桥接总线到浏览器，`src/lib/ws.ts` 是客户端。

改：照 `mutationRun.ts:71` 的样子发 `review.revise.started` / `.case` / `.finished`，
scope 带 `{ wfRunId }`；前端订阅后把计数换成逐条状态。
单条失败已经是逐条报的（`review.ts:798`），应该落到那一条上，
而不是拼进一个合并的错误串（`Review.tsx:860-862`）。

### 变更六：把 `requestKey` 存到复核编辑上

`traced.ts` 已经把 `requestKey` 放进了 generation 的 metadata，`revise.ts:83` 有
`revise:<caseId>` 的 label。把这两个存到 `ReviewEdit` 上，
diff 面板就能链到**产生这次改写的那一次具体生成**。

这正好闭合 `traced.ts` 里那句话——「两条 trace 上指纹相同，发出去的就是同一个请求」——
而且闭合在**唯一一次有人真的在等的模型调用**上。

| 变更 | 收益 | 可测量 |
|---|---|---|
| 一 · `/lineage` | **124/125 次运行的 trace 从空的变成有内容**；每次查看从 O(万行) 全表扫变成索引查找 | ✅ 直接数 |

## 代价与风险

| 项 | 说明 |
|---|---|
| **变更三（最大）** | 「读完即删」是承重的。改成引用传递**必须**同时上 `live/` 的保留任务，否则造出下一个 `exec/`（914 文件 / 57.5 MB） |
| 变更三（血缘） | 已有 2,305 行的绝对路径要处理。**这个仓库的规矩是血缘不重写**（`.gitignore:8`：「清库时旧数据是移走而不是删掉的（lineage 补不回来）」）。所以做**读侧归一化 + 写侧修正**，不要 UPDATE |
| 变更二 | `live` 标志的契约不能破，否则回放会触发刷新循环 |
| 变更四 | 每轮多一条事件，直接压在保留预算上。**见 [第 11 章](./11-工具返回值治理.md)**：血缘现在只占事件表的 1.47%，加事件之前先把分桶保留做了 |
| 变更一 | 生成列是本机验证过的，但要确认部署环境的 SQLite 版本 ≥ 3.31 |

**什么情况下不该做**：变更四（每轮结构化帧）在第 11 章的分桶保留之前不要上。
现在这张表已经卡在 20 万行上限、正在丢东西，再加一类高频事件只会让血缘更快被挤掉。

## 怎么证伪

| 手段 | 内容 |
|---|---|
| **单元测试** | ① 一次运行写入若干事件后，`/lineage` 必须返回全部且只返回该运行的；② 同一条事件喂给合并后的映射，实时路径与回放路径产出**完全相同**的行（这条直接钉住变更二修的那个漂移）；③ `shooter()` 返回的路径不含 `/Users` 且能被 `/api/artifacts` 解析 |
| **可量测的前后对比** | 「125 次运行里有多少条 trace 非空」——做之前是 1，做完应该是 125。这是本章最硬的一个验收数 |
| **门禁规则** | `session.progress` 的载荷若含绝对路径，发一条 `error` 事件（复用 `supervisor.ts:263` 那条已经在的拒绝路径） |
| **无法证伪的** | 变更四的 `rung` 是否真的帮人定位到了差探索——没有客观判据。可行的替代：统计有多少次探索问题的排查用到了它。**这个数今天没人收** |

## 验收

1. 打开任意一次历史运行，trace 面板有内容（今天 125 次里有 124 次是空的）。
2. `EXPLAIN QUERY PLAN` 对按运行查事件显示走索引。
3. 任一 `session.progress` 事件的载荷里没有 `/Users/`，且其 `shotRef` 能被
   `/api/artifacts/...` 取到。
4. 一次交互式探索结束后，隔一天仍能从血缘回放它的帧。
5. `live/` 目录在连续跑一周之后没有无限增长。
6. 复核里点「重新生成 20 条」，屏幕上逐条变化，而不是一个数字。
7. **不存在**「思考链」面板。如果有人加了，它显示的是一个这条流水线不产生的东西。

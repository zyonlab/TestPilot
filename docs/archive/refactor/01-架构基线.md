## 问题

这一章要防的不是一个技术缺陷，是一类返工。

这个仓库有**三套互不重合的坐标系**——进程（`processId`）、图（`wfRunId`/`nodeId`）、
事件（`Envelope.id`）——它们只在事件的 `scope` 字段上交汇（`obs/envelope.ts:7`）。
只学会其中一套的人，会在另外两套上做出看起来合理、实际上错的判断。三个已经发生过的例子：

| 读错了什么 | 后果 | 出处 |
|---|---|---|
| 把「节点」当成「进程」 | 以为把节点拆成进程就得到了角色分工。实际上节点这一层的契约（每步 zod 校验输入/参数/输出）比进程这一层强得多——进程身份只有一个小写环境变量 | `graph/runtime.ts:224-265` vs `harness/supervisor.ts:247` |
| 把事件总线当成日志 | 以为可以随便往里加高频 kind。实际上它就是血缘，而保留策略是全局按条数的 FIFO——加一族新事件等于缩短所有其它事件的可回放窗口 | `obs/store.ts:44-48`、`obs/retention.ts:11-13` |
| 把 `ModelClient` 当成一个可替换的 HTTP 封装 | 以为换成某个 SDK 是等价替换。实际上它那 180 行里编着五个分别量出来的行为，其中四个的失败形态是「产出看起来正常，只是短了一截」 | `model/openai.ts:44-58`、`:115-124`、`:152-158` |

**重构最贵的错误是把已经对的东西推倒重来。**这个仓库里已经对了的机制密度很高，
而它们对在哪往往写在注释里、不写在结构里——所以本章有一节专门列
[「这套架构已经解决了什么」](#这套架构已经解决了什么)。那一节不是恭维，
它是后面十六章的地基：每一章都要在这些之上建。

## 技术点

四层，自下而上。本章只定义它们各自的边界，不讲实现细节。

| 层 | 是什么 | 身份 | 代码位置 |
|---|---|---|---|
| **进程拓扑** | 一个监工进程 + N 个被托管的子进程，IPC 上跑双向 RPC，事实走事件总线 | `processId`（`TP_PROCESS_ID`） | `packages/harness-core/src/harness/` |
| **图运行时** | 一次运行 = 按稳定拓扑序走一遍 DAG，每个节点的产物落盘 | `wfRunId` / `nodeId` / `nodeRunId` | `packages/harness-core/src/graph/` |
| **事件总线** | 一个信封、一份 append-only 的 SQLite 表、先落库后通知 | `Envelope.id`（单调递增） | `packages/harness-core/src/obs/` |
| **模型出口** | 一个单方法接口，外面套装饰器：`traced(gated(client))` | `requestKey(req)` | `packages/harness-core/src/model/` |

四层全在 `@testpilot/harness-core` 里，**不知道什么是测试用例**；垂类知识全在
`@testpilot/harness-testing`（九个节点类型、门禁、判据、修复循环），以一个 pack 注册进
节点注册表（`apps/agent/src/main.ts:233`）。这条切分是真的——`harness-core` 的 22 个测试
文件里没有一个提到用例。

## 现状

### 一、进程拓扑：谁 owns 什么

```
  浏览器 ──HTTP/WS──▶  gateway（Express + WS + Supervisor）
                          │ fork          │ fork        │ spawn
                          ▼               ▼             ▼
                        agent        runner-1..N    capability
                          │               ▲          （exec 类）
                          └── execCase ───┘   经网关中转，不是直连
```

**四个进程角色，两种 kind。**`node` 类用 `fork` 起（`supervisor.ts:243`），
带 IPC 通道因而有 RPC；`exec` 类用 `spawn` 起（`:296`），没有 RPC，
靠健康探针证明自己活着（`harness/capability.ts:33`）。被测应用本身也是一个 `exec` 类能力
（`server/harness.config.ts:74-142`）——**被测对象和 harness 用同一套托管**，
理由写在配置文件里：「怎么起这个基准」必须和「用它跑出来的数字」放在同一个可版本化的地方。

**owns 表**，本章最常被引用的一栏：

| 进程 | owns | 明确不 owns |
|---|---|---|
| gateway | 事件总线与 `events.db`（`procs.ts:44,46`）· `testpilot.db` · `workflows.db` · `graphs.db` · 准入闸 `Gate`（`:58`）· 监工 · HTTP/WS · 环境与加密凭证 · artifact 目录 | 图运行时（在 agent）· 浏览器（在 runner） |
| agent | 图运行时（`runGraph`）· 节点注册表 · 节点产物的写入侧（`SqliteOutputStore`，`apps/agent/src/main.ts:64`）· 绝大多数模型调用 | 数据库 · 环境绑定 · 浏览器（`main.ts:26-31` 明说了） |
| runner-N | 一次执行：Midscene 会话、截图、性能采集、链上断言。无状态、可杀 | 任何跨执行的状态 |
| capability | 什么都不 owns。它是被托管的外部服务 | — |

**重启策略是每个进程各自的决定，不是全局的**（`supervisor.ts:7-16`）：

| 进程 | 策略 | 写下来的理由 |
|---|---|---|
| agent、capability | `always` | 丢了它一切都停；「它从检查点恢复，所以重新起来总是对的」（`procs.ts:135`、`capability.ts:21-23`） |
| runner | `never` | 「一个不值得重试的失败必须立刻显形。**要不要重试这份工作是循环层的判断，不是监工的**」（`supervisor.ts:11-13`、`procs.ts:176-178`） |

> ⚠️ **一处代码与注释不符，本章记下来，不在这里修。**`procs.ts:135` 说
> 「agent 从检查点恢复，所以永远重启是对的」，但 agent 的在途运行是进程内存
> （`running` Map，`apps/agent/src/main.ts:65`），重启就没了；真正发生的补偿动作是网关启动时
> 的 `reconcileOrphanedRuns`（`server/src/graphs.ts:454`）把 `running` 行改写成 `interrupted`。
> 这条差异属于 [第 06 章](./06-中断恢复与检查点.md)，不属于本章。

**监工借给孩子的四个方法。**子进程不能持有住在父进程里的互斥量，所以它持有的是**票**。
`extendParentApi(processId)` 是唯一的出借口（`supervisor.ts:97`），网关在
`procs.ts:93-103` 挂了四个：

| 方法 | 来源 | 为什么必须借 |
|---|---|---|
| `acquireModel` / `releaseModel` | `lendGate`（`model/lending.ts:23`） | 闸必须是单实例，而孩子在别的进程里 |
| `execCase` | `setAgentExecutor`（`procs.ts:82`） | agent 跑图，但没有数据库也没有浏览器 |
| `observeProduct` | `setAgentObserver`（`:88`） | 同上：看一眼跑着的产品需要浏览器 |

出借配套的回收也在：`bus.subscribe` 监听 `process.status`，进程一 crashed/exited
就 `lending.releaseAllFor`（`procs.ts:107-111`），理由写在那一行上方——
**「一个崩掉的 runner 恰恰是槽位会丢的时刻：它永远走不到自己的 finally」**。

**IPC 的两条关键约定。**（1）**命令走 RPC，事实走总线**（`protocol.ts:37-42`）：`ParentApi`
只有 `emit` 和 `heartbeat` 两个方法（`:37-40`），且在 `EVENT_METHODS` 里被标成单向（`:43`）
——不等回复，因此也没有背压。（2）**用死讯，不用时限**：两个方向都设了 `timeout: -1`
（`rpc.ts:27`、`:99`），补上的那一半是 `settleOnDeath`（`:27`），对面一断所有在途调用立刻失败。
注释记着这个洞的症状（实测）：birpc 默认 60 秒把一次 `execCase` 腰斩，报出来的是
`[birpc] timeout on calling execCase`——**读起来像网关不可达，其实是一个没人打算设的上限**。

**三条与 `fork` 细节绑死的保证**（`supervisor.ts:243-254`、`child.ts:35,59`）：
`serialization: "advanced"`（否则 Error 跨进程之后变成 `{}`）、`TP_PROCESS_ID` 环境注入
（子进程的全部身份）、`process.on("disconnect")` 自杀（否则孤儿 runner 还攥着浏览器、端口和
测试账号）。三条都有测试钉着（`test/supervisor.test.ts:266,280`）。

**调度分两层**：`enqueue`（`queue.ts:21`，p-queue）决定同时跑几条，`pickRunner`
（`exec.ts:40`）按字符串前缀（`:33`）和 `alive && currentTask === "idle"` 挑一个。
今天 `runnerCount: 1, queueConcurrency: 1`（`harness.config.ts:18`），所以「挑」没有分支。

### 二、DAG 运行时：怎么走图

**为什么是自己写的，写在代码里**（`runtime.ts:105-113`）：要的是从任意节点部分重跑、
按节点缓存产物给画布看、版本钉死的可复现性，而**循环放在节点里**——「一个有界的修复循环是
一个节点，不是图上的一条环」。库能补上的那件事是检查点，而产物存储已经提供了。

**两级契约。**边契约（`inKind`/`outKind`，`node.ts:37-38`）在**保存图时**查谁能连谁
（`graph.ts:74-78`）；zod（`input`/`params`/`output`）在**每次运行每个节点**时查实际负载
（`runtime.ts:224,227,261`）。两级并存的理由写在 `node.ts:27-31`：画布必须在一条边
**正被画出来**的时候就拒绝它，那时候还没有任何负载可看。

**保存时的三条硬规则**（`graph.ts:38`）：**一个节点只能有一条入边**（`:84-86`，合并多个上游
是一个有真实语义的操作——哪个顺序？谁覆盖谁？——所以必须是一个显式的 merge 节点）、
**不许有环**（`:92`）、参数必须过该节点类型的 zod（`:50`）。

**执行序是稳定的**（`:106-107`）：拓扑排序的入队顺序就是节点的声明顺序，所以同一张图两次
运行产生同一条序列——**可复现性从这里开始**。

**三种运行模式**（`runtime.ts:37-43`）映射画布的三种调试动作：`full` 走 `topoOrder(def)`
并吃种子 `opts.input`；`only`（调试②）只走 `[mode.node]`，`from`（调试③）走
`downstreamOf(def, node)`——后两者的上游一律取存储里的上次产物。被点名的节点不受自己身上的
断点阻拦（`askedFor`，`:125-127`），否则「继续」会永远停在同一个节点前面。

**检查点就是一行**（`runtime.ts:268-269`）：

```ts
outputs[nodeId] = out;
await store.set(wfRunId, nodeId, out);
```

只在 `nodeDef.run(...)` 返回**并且**它的输出通过了自己的 zod 之后才写。
恢复也是一行——`const outputs = await store.all(wfRunId)`（`:141`）。
**所以「复用同一个 `wfRunId`」就是恢复**，这件事只写在注释里，没有 API 名字说它。

**五个提前 return，四个不是失败。**主循环被抽成 `walk()` 闭包（`:177`），
为的是让整次运行能被一个根观测包住，而循环里有五个出口：

| 出口 | 触发 | 终态 | 行 |
|---|---|---|---|
| 取消 | `signal.aborted` | `cancelled` | `:179` |
| 断点 | `breakpoints.has(nodeId) && nodeId !== askedFor` | `paused` | `:180` |
| 预算 | `overBudget(...)` | `budget` | `:184` |
| 上游缺产物 | `rawInput === undefined` | `failed` | `:197` |
| 节点抛错 | catch | `failed` | `:288` |

「跑完了」和「预算花光了」被刻意分成两件事（`:186-187`）：一份把两者混为一谈的报告，
会诱使人把一个部分结果读成一个完整结果。

**预算是整次运行的，不是每一段的。**`RunGraphOptions.spent`（`:61-69`）把上一段
已经花掉的量带进来，`overBudget` 里的时间上限也按倒推回去的起点算（`:377-379`）。
注释记着不这样做的后果：上限悄悄变成了「每次续跑一份」，而运行记下的成本比真实成本低——
**一份低报成本的报告比没有报告更糟，因为它读起来像一次测量**。
两条测试钉着（`test/runtime.test.ts:258,272`）。

代价也要说清：`overBudget` 只在**节点之间**跑（`:184`），节点内部没有任何检查。
一个自主循环（`repair.loop`）可以在一个节点里把整次运行的额度花光，
而在它返回之前没有任何东西能介入。

**九个节点类型，各自声明自己在追踪上算哪一类观测。**声明在节点侧而不是运行时猜，
理由在 `node.ts:39-47`：运行时是通用的，它不该知道「`source.explore` 是个 agent
而 `gate.textcase` 是道门禁」。

| 节点类型 | 观测类型 | 声明处 |
|---|---|---|
| `source.spec` | `retriever` | `casegen/nodes.ts:242` |
| `source.explore` | `agent` | `casegen/nodes.ts:873` |
| `spec.compose` / `plan.stories` / `design.cases` | `chain` | `:396`、`:700`、`:917` |
| `gate.textcase` | `guardrail` | `:1043` |
| `codegen.case` | `chain` | `codegen/nodes.ts:66` |
| `gate.code` | `guardrail` | `codegen/nodes.ts:134` |
| `repair.loop` | `agent` | `codegen/nodes.ts:177` |
| 根（整次运行） | `span` | `runtime.ts:303-305` |

按 [00 章](./00-方法与约定.md) 对 Agent 的受限定义（自己决定下一步、自己决定何时停），
**全仓库只有两个 Agent**：`source.explore` 和 `repair.loop`。而这两个恰好就是上表里
唯二报 `agent` 的。**照着代码报，不照着期望报**——根节点报 `span` 而不是 `agent`，
因为这一层就是一条确定性 DAG。

G1 的默认图是五个节点一条线（`casegen/graph.ts:34-66`）：
`docs → spec → stories → design → gate`。完整流水线由 `pack.ts` 再接上
codegen / gate.code / repair.loop。

### 三、事件总线：信封与 kind 词表

**一个信封**（`obs/envelope.ts:21`）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `v` | `1` | `PROTOCOL_VERSION`（`:19`），在 `EnvelopeSchema` 里是 `z.literal` |
| `id` | number | **由存储分配的单调递增值**。重连的客户端就从它续 |
| `ts` | string | ISO 时间 |
| `scope` | `Scope` | 六个全部可选的字段：`projectId` / `wfRunId` / `nodeRunId` / `runId` / `caseId` / `processId`（`:7-16`） |
| `kind` | string | 见下 |
| `payload` | unknown | 不校验 |

`scope` 是三套坐标系唯一的交汇处，也是唯一在跨进程边界上被 zod 校验的东西：
监工对每一条子进程发来的事件做 `ScopeSchema.safeParse`，拒掉的变成一条 `error` 事件
而不是被静默丢弃（`supervisor.ts:263-278`）。

**两条规则，系统其余部分都靠它们**（`obs/bus.ts:21-33`）：

1. **先落库，再通知。**订阅者永远不可能看到一条不在血缘里的事件，
   所以「界面当时显示了什么」永远可回放。
2. **合并只是投递侧的事。**高频 kind 在小窗口内按 `(kind, scope)` 合并后才送到订阅者
   （`COALESCED_KINDS`，`envelope.ts:76`；`coalesceKey`，`:85`），
   但**每一条都存**。合并前会先冲刷待发批次（`bus.ts:111`），
   所以订阅者不会先看到 `run.finished` 再看到它前面那条进度。

**kind 词表与实际发生的事情不一致。**`EventKind`（`:49-69`）是一个 const map，
注释说「生产者不能凭空造一个 kind——总线上出现未声明的 kind 是 bug，不是新功能」。
但 `NodeContext.emit` 的签名是 `emit(kind: string, ...)`（`node.ts:15`），没有任何强制。
实测（2026-09-01 读 `server/.data/events.db`，200,009 行）：

| 现象 | 实际 |
|---|---|
| 声明了但一行都没有 | `case.created`、`case.updated`、`artifact.ready`、`budget.update` |
| 没声明但大量存在 | `eval.started/finished/mutant`、`critic.finished`、`mutation.*` |

**保留是全局按条数的 FIFO。**`keepLast: 200_000`（`harness.config.ts:19`），
`prune` 是一条 `DELETE WHERE id <= MAX(id) - keepLast`，不分 kind、不分 scope
（`obs/store.ts:51`）。刻意选按条数而不是按时间（`retention.ts:11-12`）：
要保持有界的是文件，而忙一小时产生的行数比闲一星期多。

实测的后果，是本章里最值得记住的一组数：

| kind | 行数 | 占比 | 单条 payload 最大 |
|---|---|---|---|
| `log` | 148,464 | 74.2% | 615 B |
| `process.status` | 40,520 | 20.3% | 290 B |
| `session.progress` | 7,991 | 4.0% | 260 B |
| `run.progress` | 851 | 0.4% | 135 B |
| `wf.node.output` | 679 | 0.34% | **140 B** |
| `wf.node.finished` | 467 | 0.23% | 2,910 B |
| `wf.run.finished` | 121 | 0.06% | 6,283 B |

- 表已经**顶在 200,000 上**，此刻正在裁；200,009 行只覆盖 2026-08-27T18:17 →
  2026-08-31T17:46，**3.98 天**，而这还是机器大部分时间空闲的情况。
- 带 `wfRunId` 的行只有 **2,377 条（1.19%）**——三套坐标系的交汇点本身是稀疏的。
- 同样的事故配置文件里已记过一次（实测）：模型代理崩溃重启时「一次实测 600 条事件里
  457 条是它的崩溃日志，探索的日志全被挤掉」（`harness.config.ts:166`）。

`wf.node.output` 单条最大 140 B 不是缺陷，是设计：**总线不载产物**。
真正的产物去 `wf_node_outputs`，二进制去 artifact 目录。这一条属于
[「已经解决了什么」](#这套架构已经解决了什么)。

**WS 是这条总线的一个投影**（`server/src/ws.ts:38`，77 行）：先查协议版本、
不匹配就发 `WIRE_VERSION` 并 `close(4400)`（`:27-34`）；按 `lastEventId` 续；
落后超过 `REPLAY_LIMIT = 500`（`:8`）就发 `resync` 让客户端走 REST 重取。
新连接不重放全部历史，从 head 开始（`:41-43`）。

### 四、`ModelClient`：为什么是唯一出口

接口只有一个方法（`model/client.ts:65-67`）：

```ts
export interface ModelClient {
  chat(req: ChatRequest): Promise<ChatResponse>;
}
```

**「唯一出口」这句话的真实含义是：它是唯一一个可以被一次性包住的地方。**
装饰器包的是**接口**而不是 `OpenAIModel` 实现（`model/traced.ts:6-10` 写着理由）。
生产环境**六个构造点全部是同一个形状**：`agent/main.ts:167`、`graphs.ts:248`（`gateway.model`）、
`chat.ts:351`（`chat.draft`）、`review.ts:711`（`review.revise`）、
`evals.ts:274`（`eval.adjudicate`）、`evals.ts:534`（`harness.critic`）。

**顺序是有意义的**：`traced(gated(x))` 的 span 覆盖排队等准入槽位的时间，
`gated(traced(x))` 只覆盖 HTTP 往返。选前者的理由（`traced.ts:23-26`、`agent/main.ts:162-166`）：
模型并发是 1–3，最长的一段恰恰是排队——**一个把等待藏起来的延迟数字，
会让人去优化模型而不是去优化并发**。

**准入是跨进程的一个闸，三段式：**

| 段 | 在哪 | 做什么 |
|---|---|---|
| `Gate` | `model/gate.ts:10`，网关持有唯一实例（`procs.ts:58`） | FIFO 计数信号量 |
| `ModelLease` | `model/lease.ts:9-19` | 模块级可变量。`withModel` 包**一次调用**，粒度是刻意的（`:17`） |
| `lendGate` | `model/lending.ts:23` | 把槽位借给子进程：父进程留住 release 函数，孩子拿一个整数票 |

三个进程各自绑一次：`procs.ts:59`（网关直接绑自己的闸）、`agent/main.ts:153`、
`runner/main.ts:155`（后两者绑成一次 RPC）。

> ⚠️ **`lease` 的默认值是直通**（`lease.ts:11`），理由是「一个单元测试不该需要知道这东西存在」。
> 代价是：一个忘了绑的新进程会**静默地绕过闸**，症状只表现为压力下的 502。
> 这条属于 [第 05 章](./05-子Agent与上下文隔离.md)。

**`OpenAIModel` 那 180 行里编着五个分别量出来的行为**（`model/openai.ts`）。
列在这里是因为后面任何一章提「换成某个 SDK」都要逐条回答：

## 这套架构已经解决了什么

**这一节是后面十六章的地基。**下面每一条都是已经成立的机制，
任何一章的方案如果把其中一条弄坏，那个方案就是错的——无论它的收益写得多好看。

| # | 已解决 | 机制 | 为什么它是对的 |
|---|---|---|---|
| 1 | **血缘与界面是同一批行** | 先落库后通知（`bus.ts:26-31`）；进程页是 `process.status` 流的纯投影（`supervisor.ts:239`） | 不存在「界面显示过但没记下来」的状态。UI 与血缘不可能漂 |
| 2 | **跨进程的死活是知道的，不是猜的** | `timeout: -1` + `settleOnDeath`（`rpc.ts:27,67,99`） | 慢是允许的，永远等下去不是。这条是拿一次真实事故换来的 |
| 3 | **大产物不上总线** | runner 写 PNG 返回**路径**（`runner/exec.ts:72-80`）；网关读完即删（`server/src/exec.ts:74`）；`wf.node.output` 实测最大 140 B | 「二十万 token 的日志」这个问题的**图片那一半已经解决了**，而且解法是写下来的规则，不是巧合 |
| 4 | **一次运行 = 一条 trace，且树形是真的** | 节点包一层 active 观测，模型调用靠 OTEL 上下文自动挂进去（`runtime.ts:239`） | `traced()` 不需要知道自己在哪个节点里。这是正确树形的全部机制，没有额外接线 |
| 5 | **观测类型照着代码报** | `NodeDef.observationType`（`node.ts:48`），只有两个节点报 `agent`，根报 `span` | 把根报成 `agent` 会让 Agent Graph 好看，但那是假的 |
| 6 | **消融是一等公民** | `ABLATABLE`（`eval/ablation.ts:9`）七个开关，进 trace 标签（`runtime.ts:346`），未知开关直接报错（`agent/main.ts:76`） | 「每一条都必须是某个节点真的会读的东西」——一个改变不了任何东西的开关会让消融报告说谎 |
| 7 | **上限是整次运行的上限** | `RunGraphOptions.spent` 跨段累计（`runtime.ts:61-69`），两条测试钉着 | 续跑不等于把上限悄悄撤掉 |
| 8 | **图是数据，版本钉死** | `graph_versions` 追加式（`graph/store.ts:120-124`），运行记录钉住版本号 | 今天在画布上的一次编辑，不会改写昨天那个结果的含义 |
| 9 | **两级契约** | 边契约保存时查，zod 运行时每步查（`node.ts:27-31`） | 画布必须在边被画出来的那一刻就拒绝它 |
| 10 | **准入闸跨进程且死后可回收** | `Gate` + `lendGate` + `releaseAllFor`（`procs.ts:107`） | 崩掉的进程恰恰是槽位会丢的时刻 |
| 11 | **能力是声明式的** | `CapabilityRecipe` → `ExecProcSpec`（`capability.ts:13`），配方存成数据不写回源文件（`procs.ts:210-218`） | 生成的**配置**可复现可审查，生成的**spawn 调用**两者都不是 |
| 12 | **五个终态互不混淆** | 完成 / 暂停 / 预算 / 取消 / 失败，在结果、事件和 trace level 上三处一致（`runtime.ts:179-189,363-367`） | 一份把「花光了」读成「跑完了」的报告，会把部分结果当完整结果 |

**推论（本书通用）：**遇到某个主题落在上面十二条里，正确的动作是**引用它，不是重做它**。
后面各章凡是说「这里不用改」的地方，指的就是这张表。

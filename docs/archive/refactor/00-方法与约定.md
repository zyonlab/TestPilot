# 00　方法与约定

> 这一章定的是**全书的写法**。它很短，但后面每一章都按它写，读之前花五分钟看完，
> 后面十七章都会读得快很多。

---

## 1　证据口径

**以代码为准。** 每一处对现状的断言，都要指向一个可以打开的 `文件:行号`。
`docs/spec/` 下有 18 份规格文档、`docs/archive/REVIEW.md` 有 18KB 自评——它们可以用来理解**动机**，
不能用来作为**现状的证据**。理由是这个仓库自己写下的：

> 一份可以被人随手改掉且不留痕迹的判断依据，不再是判断依据。
> —— `server/src/evalspecs.ts`

三种证据，可信度不同，本书会标注：

| 记法 | 含义 |
|---|---|
| `path:line` | 我读过那一行 |
| 「实测」 | 代码注释里记录的真实运行结果。这个仓库的注释记的是**失败**，不是意图——它们是一手材料 |
| 「推断」 | 从代码结构推出来的，没有直接跑过。**任何带这个标记的结论都不能作为决策的唯一依据** |

## 2　每章的固定结构

八节，顺序固定。缺哪一节说明那一章还没写完。

```
## 前置          依赖哪几章、哪几个已有机制
## 问题          不引入这个技术点，会具体地烂在哪里（要有代码或实测证据）
## 技术点         它是什么。简洁，不写教程
## 现状           代码今天怎么做的。file:line
## 变更           引入后：哪些文件、哪些接口、哪些类型改成什么
## 收益           尽量可测量。测不了的就说测不了
## 代价与风险      工作量、会弄坏什么、什么情况下不该做
## 怎么证伪        ★ 见下
## 验收            做完之后，什么现象能证明它真的成了
```

### 允许的偏离

三类章节按性质不适用这个模板，**但必须在开头说明自己偏离了**：

| 章 | 性质 | 结构 |
|---|---|---|
| 00（本章） | 体例 | 自定义 |
| 15 | **对比章**：两个互不相干的提议要分开算账 | 前置 / 问题 / 第一部分 / 第二部分 / 收益 / 代价 / 怎么证伪 / 验收 |
| 17、18 | **合成章**：不提新论点，只汇总 | 自定义 |

其余每一章都必须八节齐全。**静默的偏离不算偏离，算漏写。**

### ★「怎么证伪」是必填项

全书最重要的一栏。每章提出的改动，必须能落到下面**至少一种**上：

| 手段 | 什么时候用 | 落在哪 |
|---|---|---|
| **消融开关** | 这个组件可以被关掉，关掉之后产出会变 | `ABLATABLE`（`packages/harness-core/src/eval/ablation.ts:9`） |
| **配对评测** | 两种做法只差一件事，可以跑 A/B | 一份 `evals/*.json` |
| **门禁规则** | 这件事有客观判据，可以逐条标记 | `casegen/gate.ts` 或 `codegen/gate.ts` |
| **单元测试** | 这是一个恒等式或不变量 | `test/*.test.ts` |

写不出任何一种，就在那一栏里**明写「无法证伪」**，并说明为什么。
这不是失败——`evals/README.md` 已经说过 `"unknown"` 是诚实的答案。
真正有害的是给一个假的证伪手段，因为：

> 写一个没人读的开关，报告会显示「关掉它没有影响」——这句话是真的，
> 但它说的不是这个组件不重要，而是这个开关根本没接上。
> —— `evals/README.md`

## 3　术语表

这个仓库的词和业界常用词不总是对得上。本书统一用**仓库的词**，第一次出现时给对照。

| 本书用词 | 业界常见叫法 | 代码里是什么 |
|---|---|---|
| 节点（node） | step / task | `NodeDef`，`graph/node.ts` |
| 图（graph） | workflow / DAG | `GraphDef`，`graph/graph.ts` |
| 运行（wf run） | trace / execution | 一次 `runGraph`，`wfRunId` |
| 门禁（gate） | validator / guardrail | `runGate()`，标记不拦 or 有牙齿 |
| 判据（oracle） | assertion / verifier | `MachineOracle`，`exec/oracle.ts:43` |
| 材料（material） | raw input / source | `SpecMaterial`，未整理的东西 |
| 规格（spec） | requirements | `SpecDoc`，整理后的标准形状 |
| 来源印记（provenance） | — | `SpecProvenance`，`casegen/types.ts:273` |
| 消融（ablation） | feature flag / A-B arm | `ABLATABLE` |
| 缺口（gap） | coverage hole | `Gap`，`server/src/gaps.ts:34` |

**「Agent」这个词在本书里是受限的。** 只有满足下面两条的东西才叫 Agent：

1. 它自己决定下一步做什么（不是由图的拓扑决定）；
2. 它自己决定什么时候停。

按这个定义，今天整个仓库里**只有两个** Agent：`source.explore`（探索循环）和
`repair.loop`（修复循环）。其余全部是流水线节点。这个区分不是文字游戏——
第 03、04 两章的全部内容都建立在它上面。

## 4　三个反复出现的形状

这三件事在不同章节里会以不同面貌回来。先在这里命名，后面直接引用。

### 形状一：「要求写了，数据没给」

上游算出来了、也喂给模型了，却**没写进下游真正读的那个字段**。

实测记录（`casegen/nodes.ts`）：
- 规则的 `altitude` 标了，但没写进正文 → 下游看到的还是一片没有层次的规则；
- 模块算出来了，但没写进正文 → 故事图七列里六列只有一个故事；
- 流程的转移 id 没渲染 → 要求用例引用 `from->to`，而 35 条里只有 11 条填得出。

**症状永远是「产出看起来正常，只是差了点」。**

### 形状二：「一条规则的正确性建立在另一处的行为上，而那处行为被改了」

`codegen/gate.ts:137` 的「代码里没断言 = 不可能失败」，在机器判据出现之后不再成立，
而规则没跟着改 → **40 条用例里 38 条被 block，一条都执行不了**。

### 形状三：「可选的键，模型直接不写」

约束解码的 schema 里可选的字段，这个模型跳过。后果是配对评测**白跑三次而报告完全正常**
（`evals/README.md`）。其中最阴险的一次看起来像方差，作者一度为它编了一个机制。

> **推论：本书里任何新增的 schema 字段，都必须进 `required`，并在
> `packages/harness-testing/test/casegen.test.ts` 里加一根钉子。**

## 5　交叉引用约定

- 章间引用写成 `[第 08 章](./08-Prompt是代码.md)`。
- 引用路线图的缺口编号写成 **G1**–**G8**，对应《补齐这八处》。
- 引用代码写成 `` `packages/...`:123 ``，路径一律相对仓库根。
- 引用实测数据时，**必须带上它出自哪次运行或哪个文件**，否则就是一个没有出处的数字——
  这正是 `SpecRule.evidence` 那个字段存在的理由。

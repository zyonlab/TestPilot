# 03　从节点到角色

> 「节点」是执行单位，「角色」是责任单位。两者不是一回事，而这个仓库今天只有前者。
>
> **本章的核心判据写在最前面：把节点重命名成角色，如果不改变任何行为，那是纯粹的包装，不做。**
> 后面每一条提案都要先回答「它带来哪一件实质变化」。

## 问题

JD 那一句要求可以拆成三个能被代码回答的问题：

| JD 要求 | 拆成 | 今天的答案 |
|---|---|---|
| 定义 QA Agent 的**角色** | 谁是一个责任单位？ | 没有这个概念。有节点类型、有进程、还有**四个游离在图外的模型调用者** |
| 定义它的**输入输出** | 契约在哪，谁校验？ | 节点有，而且是全书最强的一处；进程只有一个小写字符串；图外调用者一个字都没有 |
| 定义它与其他 Agent 的**协作方式** | 交接怎么发生？ | 图内是「上游产物 → 下游输入」；跨进程是 `as never` 强转 |

### 先把反对意见写完

**反对：这一整章可能只是改名。** 这个反对是对的，而且这个仓库里改名不是「无害」，是**有害且看不出来**：

- 画布上节点卡的主标题是 `label: n.id`（`src/pages/Workspace.tsx:889`，渲染在 `:111`），节点类型作为次要的等宽小字在 `:125`。
- 而产物卡是按**节点实例 id** 分支出来的：`full.design?.cases`、`full.gate ?? full.codegen`、`full.repair ?? full.codegate ?? full.codegen`（`src/lib/wf.ts:647`、`:656`、`:678`）。
- 把 `g1` 里的 `{ id: "design", type: "design.cases" }`（`packages/harness-testing/src/casegen/graph.ts:45`）改名成 `case-designer`，用例卡、门禁卡、分层卡三张一起消失。
- 而「没有卡」是一个**被设计成合法**的状态：「a node whose output is missing is simply absent — an empty card claiming "0 cases" would be a statement about the run that the run never made」（`src/lib/wf.ts:562-568`）。

所以纯改名的收益是 0，代价是一次画布看起来完全正常的回归。**不做。**

### 那么什么才值得做

本章给自己定的门槛：一次角色化改动必须至少带来下面**四件实质变化中的一件**，否则不写进变更。

| # | 实质变化 | 判据 |
|---|---|---|
| ① | **独立的失败归因** | 出事了能说清记在谁头上，而不是记在「这次运行」头上 |
| ② | **独立的预算与停机** | 这个角色可以被单独停下来，且停在一个有意义的边界上 |
| ③ | **独立的提示词与指纹** | 改了这个角色的指令，运行记录里的指纹会动 |
| ④ | **独立的评测** | 这个角色可以被单独消融，或者单独成为配对评测的那一处差异 |

「独立的 context 窗口」**故意不在这四条里**。理由：这个代码库今天唯一能强制的 context 边界是进程（`fork` + `TP_PROCESS_ID`，`packages/harness-core/src/harness/supervisor.ts:115` 注入、`harness/child.ts:35` 读取），而 `Supervisor` 只有 `register` 没有 `unregister`——整个 `packages/harness-core/src` 里没有一处删除。在那之前，「给这个角色开一个干净窗口」这句话在代码里**没有对应物**。这是第 05 章的题目。

### 不做会烂在哪：三处具体的

**第一处：责任的名册是手写的，所以它已经错了。**

`promptSources()`（`packages/harness-testing/src/prompts.ts:18-26`）列了 6 条，注释把理由写得很硬：

> 「Listed by hand rather than scanned: a prompt that someone forgets to add here is a prompt that can change without the fingerprint moving, and a fingerprint with holes in it is worse than none — it would be believed.」

而它**已经漏了一条图内节点的提示词**：`COMPOSE_STABLE`（`packages/harness-testing/src/casegen/prompts.ts:451`）由 `spec.compose` 在 `casegen/nodes.ts:457` 使用，独立定义，不由 `CASES_STABLE` 派生，**不在 `promptSources()` 里**。`spec.compose` 是整条流水线的地基——它的注释自己说「这里编一句，后面每一层都会把它当成事实」（`prompts.ts:448-450`）。今天改它一个字，`detail.prompts.combined`（`server/src/graphs.ts:519`、`:585`）纹丝不动，两次运行看起来是同一批指令产出的。

这就是本章问题的最小实例：**没有角色这个对象，责任名册就只能手写；手写的名册会漏，而漏了不会响。**

**第二处：图外有四个模型调用者，没有一个是节点。**

| 调用点 | 它是什么 | 有 observationType 吗 | 记 `ctx.spend` 吗 | 在 `ABLATABLE` 里吗 | 提示词在指纹里吗 |
|---|---|---|---|---|---|
| `server/src/chat.ts:377` | 草稿台（能力配方 / 图 / 提示词 / 问答） | 否 | 否 | 否 | 否（4 条 stable） |
| `packages/harness-testing/src/critic.ts:180` | harness 批评者 | 否 | 否 | 否 | 否 |
| `packages/harness-testing/src/casegen/revise.ts:20` | 复核重写 | 否 | 否 | 否 | 否（`REVISE_STABLE` 的修订段） |
| `packages/harness-core/src/eval/semantic.ts:86` | LLM-as-judge | 否 | 否 | 否 | 否 |

其中 `revise` 那条是全系统**唯一一个有人坐在屏幕前等**的模型调用：`server/src/review.ts:711` 建客户端，`:746` 起一个串行 `for` 循环逐条重写，返回时才有输出。

> **这里有两个已经做对了的，明说，别改。** `critic.ts:11-15` 写下了「the critic proposes, the paired evaluation decides」，并且把「无法表达成一次可跑 A/B 的建议」标成 `inadmissible` 而不是悄悄采纳；`semantic.ts:7-18` 把自己的产出明确标成「model-assisted: not comparable」，只跑在确定性那一遍漏掉的条目上。这两个是全仓库**角色边界写得最清楚**的东西——它们缺的只是身份和账本，不是纪律。

**第三处：两个真 Agent，都没有属于自己的停机点。**

`repair.loop`（`packages/harness-testing/src/codegen/nodes.ts:177` 自报 `agent`，注释「有界的自主循环：它自己决定改什么、改几轮、什么时候放弃」）一个节点里最多跑 200 条用例（`params.limit` 上限 200，`:186`），每条用例内嵌一个模型修复循环（`:225-306`）。而预算检查在 `runtime.ts:184`——**只在节点之间**。所以一个跑飞的修复循环可以把整次运行的额度吃光，中间没有任何一处能拦。

`source.explore` 更微妙：它一个节点里**塞了两个互相竞争的任务**——爬行（走更多屏）与做实验（故意提交坏输入以到达校验态）。仲裁机制是 `nextAction`（`packages/harness-testing/src/exec/interactive.ts:1269`）那个 400 行闭包里的**梯级顺序**，而两个方向都在实测里翻过车：

- 实验吃光预算：「一次实测里这样打出 15 条实验，把 30 屏预算吃光，注册、关于、联系三页全部丢失，命中从 6/7 掉到 3/7」（`interactive.ts:912`，实测）。
- 只爬不实验：「实测在 PetClinic 上，13 条黄金清单未覆盖的 7 条里有 5 条是这一类（必填校验、格式校验、搜不到的提示）」（`interactive.ts:739-740`，实测）——注释接着说「那不是『覆盖还不够高』，是黑盒遍历的**结构性缺口**」。

两次都是**同一个形状**：两份责任共用一个预算，而预算的分配方式是一个不能被参数化、因此不能被评测的排序。

## 技术点

**角色**（role）：一个有名字的责任单位。要成为角色，得同时有四样东西。

| | 是什么 | 今天在哪 |
|---|---|---|
| **身份** identity | 一个稳定的、**机器可枚举**的名字 | 节点类型有（`NodeRegistry`）；进程只有 `TP_PROCESS_ID` 一个小写串；图外调用者没有 |
| **契约** contract | 输入输出，且能在**运行时**被校验 | 节点有 `inKind`/`outKind` + 三个 zod（`graph/node.ts:68-69`、`runtime.ts:224-263`）；跨进程是 `as never` |
| **账本** ledger | 花了多少，归谁 | `ctx.spend` 按节点累计（`runtime.ts:400-407`）；图外调用者不记；进程侧的 `child.addSpend`（`harness/child.ts:88`）**全仓库只有一个调用点**（`apps/runner/src/main.ts:48`，而且报的是调用次数） |
| **停机** stop | 谁能停它，凭什么停 | 整次运行一个 `AbortSignal`，加节点之间的 `overBudget`（`runtime.ts:400`）。角色自己没有 |

三个词的关系，必须分清：

```
角色（责任）   ≠   节点类型（NodeDef.type）   ≠   节点实例（图里的 id）   ≠   进程
    ↑                      ↑                            ↑                    ↑
 本章要引入的          今天最接近角色的东西         今天前端拿它当名字     今天唯一的隔离边界
```

**关键事实：今天最接近「角色」的对象是节点类型，不是节点实例。** 因为三处按类型索引、只有一处按实例索引：

| 索引方式 | 按什么 | 位置 |
|---|---|---|
| 提示词名册 | **类型** | `prompts.ts:19-25`（`"plan.stories"`、`"design.cases"`…） |
| Langfuse 观测名 | **类型** | `runtime.ts:239`（`observe(node.type, ...)`，实例 id 进 metadata——名字要低基数） |
| 消融开关的落点 | **类型** | `ABLATABLE` 每条注释都写「design.cases stops…」「repair.loop executes but…」（`eval/ablation.ts:9-24`） |
| 前端产物卡 | **实例 id** | `src/lib/wf.ts:595-697` |

最后一行就是本章开头那个「改名会静默删卡」的全部原因。**角色化的正确方向是往类型这一侧走，不是给实例改名。**

| 已经对了的 | 为什么不动 |
|---|---|
| **节点的双层契约** | `inKind`/`outKind` 在存图时查（画布还在连线就要能拒），三个 zod 在每一步查（`node.ts:26-30` 把两层的分工写清楚了）。这是全书最强的一处契约，不要为了「角色化」再叠一层 |
| **`observationType` 的报法** | 「声明在节点这一侧，而不是在运行时按类型名猜」+「照代码报，不照期望报」（`node.ts:12-18`）。第 12 章已经端到端验过 |

## 变更

四件，按依赖排序。每件对应「四件实质变化」中的至少一条。

### 变更一：让责任名册变成机器可枚举的　→ ③

**问题**：`promptSources()` 手写，已经漏了 `COMPOSE_STABLE`。

**不做**「扫描全部字符串」——那正是那条注释拒绝的做法（扫描出来的东西没人能说清它是谁的）。**做法是把提示词挂到它的角色上**：

| 改哪 | 改成什么 |
|---|---|
| `packages/harness-core/src/graph/node.ts:32` | `NodeDef` 加可选 `prompts?: Record<string, string>`（键是变体名，如 `"no-methods"`）。类型故意是裸的字符串表——harness-core 不该知道提示词长什么样 |
| `packages/harness-core/src/graph/node.ts:32` 附近 | `NodeRegistry.list()` 顺带汇总 `prompts`，键拼成 `${type}` 或 `${type}:${variant}` |
| `packages/harness-testing/src/prompts.ts:18` | `promptSources()` 改成「从 registry 汇总」+「一份显式的图外角色清单」（`chat:*`、`critic`、`review.revise`、`eval.semantic`） |
| 新增 `packages/harness-testing/test/prompts.test.ts` | 一根钉子（见「怎么证伪」） |

**代价**：`NodeDef` 多一个字段；图外那四个角色仍然是手写的一行——但它们**只有四个，而且都在名册里出现过**，这跟「漏了一个没人知道」是两回事。

### 变更二：给自主角色一个可执行的停机点　→ ②

**问题**：`overBudget` 只在节点之间跑（`runtime.ts:400`），而 `repair.loop` 一个节点最多 200 条用例。

```ts
// packages/harness-core/src/graph/node.ts:12 —— NodeContext 是唯一一条统一通道
export interface NodeContext {
  …
  /** 现在超预算了吗；返回撞上的是哪一档。节点在自己的循环边界上自己查。 */
  overBudget(): "calls" | "usd" | "ms" | undefined;
}
```

`repair.loop` 在 `codegen/nodes.ts:205` 那句 `if (ctx.signal.aborted) break;` 旁边加一句同形状的检查，并把停机理由写进已经存在的 `stoppedBecause` 表（`codegen/nodes.ts:203`、`:311`）。

**这里必须写下一个反对意见，因为它反对的是更"正确"的那个方案。**
更彻底的做法是运行时给每个节点开第二个 `AbortController` 强制执行，不依赖节点自觉。但它会直接撞上一个**已经存在**的坑：`codegen/nodes.ts:209` 中断后循环 `break`，函数**仍然返回一个完整形状的 bundle**（`:311`），`runtime.ts:261-271` zod 校验通过、按 `status: "done"` 存进检查点。**一个残缺的产物被存成完整的，而且下游读不出区别。**强制版会把这个坑从「取消时才踩」变成「预算紧时经常踩」。

所以本章建议**先做 opt-in 版**，强制版留到第 06 章的「完整性标记」落地之后。这不是妥协，是顺序：先加一个不新增危险的机制，再加一个需要前置的。

opt-in 的已知弱点是「加了没人调用」——README 那条纪律点名的东西。缓解手段不是加消融开关（它不是一个组件），是一根单测钉子，见「怎么证伪」。

### 变更三：把探索里两份竞争的预算拆成两个数　→ ①④

这是全仓库**唯一一处「两个角色挤在一个节点里」的真实案例**，而且两个方向都有实测事故。

**不拆成两个 Agent。** 理由很硬：整条探索循环**只有一次模型调用**（`interactive.ts:1202`，`withModel(() => session.agent.aiAction(...))` 那句登录），其余全是浏览器动作。没有第二份 context 可以分给第二个角色——拆开只是把一个闭包变成两个闭包，落在四件实质变化的哪一件上都说不出来。

**拆成两个计数器加两个停机理由**：

| 改哪 | 改成什么 |
|---|---|
| `ObserveSpec`（`interactive.ts:429` 一带） | 加 `probeBudget?: number`，默认 `ceil(maxScreens / 3)`；在探针梯级里查 |
| 同上 | 把 `maxRounds`（今天硬编码 `maxScreens * 5`，`interactive.ts:429`）提成可选参数，默认仍是这个式子 |
| `interactive.ts:994-1015` | 探针返回是一次 goto 到已见状态，落进 `seen.has(sig)` 分支并让 `dry += 1`。**探针返回不是停滞，是记账动作**，不该计入。默认 `dryRounds` 是 3，两次探针返回就吃掉三分之二的停滞额度 |
| `interactive.ts:1354` 一带 | `stopped.kind` 加 `probeBudget` 一档；`src/lib/stopReason.ts` 的回落机制已经能接（见「不用改」） |
| `casegen/nodes.ts:311-330` | 两个参数上到 `source.explore` 的 params schema，于是它们进图、进 `paramOverrides`、进配对评测 |

**收益的形状**：「探索里应该有多少比例是实验」从一个关于梯级顺序的争论，变成一个**能被配对评测量的数字**。今天这个争论无法收敛，因为唯一的调节手段是重排一个 400 行闭包里的 if 顺序，而没有一行测试钉住那个顺序。

### 变更四：给进程一个角色名，并且真的用它派活　→ ①

| 改哪 | 改成什么 |

**明确不做：把节点升成进程。** 每一次升级要付两跳 IPC，并且**丢掉 zod 契约**——这笔账这个仓库已经付过：agent→gateway 的观察交接此前只转发了 `projectId`，`envRef` 和 `url` 一个都没带过去，于是

> 「一次声明『跑在 bench-juiceshop』的运行，浏览器打开的是 local 的地址、带的是 local 的请求头和凭证。**而产出物看不出任何异常。**」

## 代价与风险

| 变更 | 工作量 | 会弄坏什么 |
|---|---|---|
| 一 | 半天 | `NodeDef` 多一个字段，harness-core 沾上「提示词」这个概念（今天它完全不知道）。补齐名册会让指纹**一次性变化**——所有历史运行的 `prompts.combined` 与新运行不可比，必须挑在两次配对评测**之间**合，并在 `evals/README.md` 记一笔 |
| 二 | 半天到一天 | opt-in 的检查会被忘。**更大的风险是别人顺手把它改成强制版**——那会踩「残缺产物存成 done」（`codegen/nodes.ts:209` → `runtime.ts:261-271`）。在 `NodeContext` 那个字段的注释里把这句话写死 |
| 三 | 一到两天 | **压在第 02 章第一条性质上。** 探索的确定性是配对评测合法性的前提：「PetClinic 五次运行图完全一致、标准差为 0；一旦有写入，这个数就会开始飘，而且没人知道是哪一次飘的」（`interactive.ts:37-48`，实测），而 `evals/design-methods-headroom.json` 的 `why` 字段明写两臂可比正因为这个。**改 dry 记法会改变停机行为**，所以变更三必须先跑一次冻结基准、合完再跑一次，两次图完全一致才算过 |
| 四 | 一到两天 | 加宽 runner 池会暴露 `pickRunner` 的 read→await→dispatch 非原子（`server/src/exec.ts:40-60`）：输家被 runner 的模块级 `busy` 标志拒掉（`apps/runner/src/main.ts:29`、抛在 `:37`），被记成 `failCode: "EXEC_ENV"`（`server/src/graphs.ts:212`），而 `infraError` 的定义是「excluded from flake/gate」（`packages/harness-testing/src/exec/run.ts:199`）。**一个调度 bug 会被算到被测产品头上，然后从会揭发它的指标里被剔掉。**今天只因为 `runnerCount` 与队列宽度都是 1 才没发作。所以：**先给 `pickRunner` 一个原子占位，再动 `runnerCount`** |

**什么情况下整章都不该做**：如果目标只是「文档上出现『角色』这个词」。那种改动的成本不是零——它会把改名这件事变成一次静默回归，见「问题」第一段。

**全章最大的风险**：角色化会诱使人把节点搬进进程。变更四里那条 `envRef` 事故就是这么来的。

| 手段 | 内容 |
|---|---|
| **单元测试** | **(a) 名册完整性**（对变更一）：`packages/harness-testing/test/prompts.test.ts`，断言仓库里每一处 `model.chat({ stable: X })` 的 `X` 都能在 `promptSources()` 的取值里找到。实现方式是把「登记」变成唯一入口（节点从 `NodeDef.prompts` 汇总、图外四个从显式清单来），再加一个 `scripts/check-prompts.mjs` 数 `stable:` 的出现次数与名册长度比对——**这个测试今天就会红**，因为 `COMPOSE_STABLE` 不在里面。红了才说明它接上了 |

## 验收

1. 把 `COMPOSE_STABLE` 改一个字符，重启网关跑一次 g1，`GET /api/wf/runs/<id>` 的 `detail.prompts.combined` 变化；改回去再跑，变回来。**今天两次都不变。**
2. `detail.prompts.entries` 里出现 `spec.compose`、`review.revise`、`critic`、`eval.semantic`、`chat:graph` 这几个键。
3. 用 `budget:{calls:10}` 跑 `g2-code`（`repair.loop` 的 `limit` 保持 50），运行以 `status:"budget"` 停下，`repair.outcomes.length` 明显小于 `runnable.length`，且 `stoppedBecause` 里有一条写着撞的是哪一档。**今天是跑满 50 条再看预算。**
4. 进程页上每个进程显示 `role` 与 `capabilities`；把 runner 的 `capabilities()` 改成 `{web:false}`，一次执行请求应当报「没有能跑 web 的 runner」，而不是派给它再被 `busy`/环境错误拒掉。
5. `evals/probe-budget.json` 两臂都跑得出来，`stopped.kind` 在两臂上不同，界面两边都渲染得出人话（不出现 `stop.probeBudget` 这种内部串）。
6. **冻结基准回归**：变更三合入前后各跑 PetClinic 五次，两组各自 σ=0，且两组的图**互相一致**。不一致就退回——第 02 章第一条性质高于本章任何收益。
7. （仅当同时做了 `loadArtifacts` 按 `outKind` 索引）把 `g1` 里 `design` 改名成 `case-designer`，存图重跑，用例卡、门禁卡、分层卡三张都还在。**这一条是本章「不是包装」的最终检验：只有当改名不再破坏任何东西时，角色名才真的和执行解耦了。**

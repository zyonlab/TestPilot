## 问题

### 不引入这个技术点，会烂在哪

**第一处：`spec.compose` 是全流水线最大的一次输入，而它没有输入预算。**

```ts
// packages/harness-testing/src/casegen/nodes.ts:456-458
const res = await opts.model.chat({
  stable: COMPOSE_STABLE,
  variable: composeVariable(material.text + flowText, …),
```

`material.text` 是探索产物，实测最大 128,430 字节（`survey/storage-memory`：`workflows.db` 里
`explore` 节点产物的最大值）。它唯一的保护是网关的那一刀：

```ts
// server/src/index.ts:1270-1273
if (result.notes.length > 240000)
  console.warn(`[explore] 材料 ${result.notes.length} 字，超过护栏 240000——按屏分配的预算算错了`);
return { notes: result.notes.slice(0, 240000), … };
```

`slice(0, N)` 是**从尾巴切**——正是 `budget.ts:4-6` 开宗明义说错的那个算法。
而 `spec.compose` 的输出预算已经被治好了（`nodes.ts:450-455`，按图的规模自己算，注释里写着
「这个数不该再由人来调」），输入侧一个字都没有。同一个节点，一半治好了一半没治。

后果的形状，仓库自己记过（`nodes.ts:404-407`）：**回复被腰斩，解析出来是「JSON 格式错误」，
看起来像提示词的问题，其实是预算的问题。**

**第二处：`repair` 是唯一一处把执行器原始输出逐字插进提示词的地方，而它对着 1200 个 token。**

```ts
// packages/harness-testing/src/codegen/prompts.ts:99-105
`FAILURE (${input.failKind ?? "unknown"}): ${input.failure}`,
"CURRENT CODE:",
input.code,
```

```ts
// packages/harness-testing/src/codegen/nodes.ts:243-251
variable: repairVariable({ …, failure: outcome.message ?? "", … }),
maxTokens: 1200,
```

`outcome.message` 和 `current.code` 都无界。一条 Playwright/Midscene 的长堆栈直接走进去，
出来的是 900 秒超时（`openai.ts` 的默认 `timeoutMs`）或者一个不会被重试的 4xx——
**两者读起来都是「模型坏了」，不是「我们发多了」。**

**第三处：`design.cases` 把整份规格按故事重发 N 次，每次独立地按同一条规则截到同一个数。**

```ts
// packages/harness-testing/src/casegen/nodes.ts:964-975（循环体内）
for (const story of bundle.stories) {
  const budget = fitToBudget(
    [{ name: "story", …, fixed: true }, { name: "spec", text: specText, share: 1 }],
    params.contextTokens,   // 默认 8000，nodes.ts:932
  );
```

`specText` 在循环外算一次（`:955`），循环内每次重新裁一遍。8 条故事就是 8 份规格，
而且每一份都被 `trimMiddle` 按同样的比例删掉同样的中间那段。
**如果这条故事对应的规则恰好落在规格正文的中间，它会从最需要它的那次调用里被删掉**——
除了一行 token 数，没有别的迹象。

### 还有一件已经发生了的事：两套压缩器已经漂了

| | `fitToBudget` | `budgeted()` |
|---|---|---|
| 单位 | token（`estimateTokens`） | 字符 |
| 分配 | 份额制 + 未用份额重分配 | 按屏等分 |
| 保底 | 无（`fixed` 部分整份豁免） | 每屏 600 字地板 |
| 越界 | 不会（`fits` 可为 false 但不越 limit） | **会**（地板 + 未裁的尾巴） |
| 锚点 | `budget.ts:66-102` | `interactive.ts:89-99` |

两份实现，各自记着**同一条教训**（见下节），而且已经在单位上分道扬镳了。
「200000 字」这个数对中文页面是 ~15 万 token，对英文页面是 ~5 万——同一个常数在两种被测产品上
含义相差三倍。

## 技术点

上下文压缩只有三条路，它们的区别不在压缩率，在**失真的类型**：

| 路 | 失真长什么样 | 确定性 | 失真可见吗 | 成本 |
|---|---|---|---|---|
| **截断** | 缺了一段，而且知道缺了多少 | 是 | **是**（可以上报字数） | 零 |
| **摘要** | 一段看起来完整的、可能是错的话 | 否 | **否** | 一次模型调用 |
| **分层召回** | 该召回的没召回到 | 取决于检索器 | 部分（可以报召回了几条） | 零到一次嵌入 |

这个仓库选了截断，理由不是性能，是第三列。整本书的纪律是
「凡是有门禁的要求，模型就照做；凡是没有的，就漂」——一个失真不可见的压缩器，
就是一个没有门禁的地方。

「分层召回」在这条流水线里有一个便宜的实现路径，而且**已经半实现了**：
`describeGraph()`（`sfg.ts:268`）把结构摘要排在原始屏幕转储前面，注释写着
「LLM 吃结构，不吃原始屏幕转储」——这是把召回做成了**排序**而不是检索。
真正的检索原语也已经有了：`locate()`（把一句原话定位回它出自哪份文档）和
`overlaps()`（`attribute.ts:54`、`:61`），今天只用在溯源上，没用在压缩上。

| `spec.compose` 的材料 | **无** | — | — | `casegen/nodes.ts:456-458` |
| `repair` 的失败信息与代码 | **无** | — | — | `codegen/nodes.ts:243-251` |
| `codegen.case` 的用例 | **无** | — | — | `codegen/nodes.ts:84-91` |

`fitToBudget` 在 `casegen/nodes.ts:6` 被 import，**全仓库只有一个生产调用点**（`:969`）。
八处压缩里有三处根本没压，两处是裸 `slice`。

### 已经做对的部分：`fitToBudget`

四条设计，每条都不是显然的：

| 设计 | 代码 | 为什么 |
|---|---|---|
| 份额制 | `budget.ts:75` | 由**节点**说哪部分值多少窗口，不由压缩器猜 |
| 未用份额重分配 | `budget.ts:77-90` | 注释：固定切分「等于把窗口对所有其他人变小了」 |
| `fixed` 整份豁免 | `budget.ts:69`、`:81` | 「schema、指令一截就废」 |
| 保头保尾、删中间 | `trimMiddle:105-115` | 「开头说明它是什么，结尾通常是刚追加的那一段」 |
| **上报 `dropped`** | `budget.ts:38-39`、`:47` | 「让一个被缩过的提示词是可见的，不是静默的」 |

还有一个容易被忽略的细节：`trimMiddle:110` 的每 token 字符数是**从这段文本自己算出来的**
（`text.length / estimateTokens(text)`），不是拍一个常数——所以中英文混排的材料不会被裁错比例。

### 已经做对的部分：`budgeted()` 和它记的那次事故

`interactive.ts:75-88` 是全仓库关于上下文压缩最有价值的一段注释，它记的是**实测**：

> 网关那边有一刀 `notes.slice(0, 60000)`。屏数只有 8 的时候它从不生效；探索改进到
> 25–30 屏之后，它每次都生效——而**从尾巴切会整屏整屏地消失**。一次实测里 about 和
> contact 两屏被整个切掉，材料里于是既没有 `Corporate History` 也没有 `CAPTCHA`，
> 看起来像是探索没走到，其实走到了、记下了、然后在最后一步被丢掉。
>
> 从尾巴切还有一层更坏的性质：**丢掉的总是最后探索到的那些屏**，而那恰好是新加的
> 「未访问路由优先」「全局队列」费力够到的部分。**改进越有效，被丢掉的越多。**

最后那句话是这一章的地基。它说的是：**截断的失真是有偏的**，而且偏向的正是系统里
最新、最费力得到的那部分内容。一个「平均只丢 10%」的压缩器，可能把 100% 的新增能力丢掉了。

同一条教训在 `budget.ts:4-6` 和 `server/src/index.ts:1261-1268` 各记了一遍——
三处独立记录，说明它撞了不止一次。护栏那处的注释还写着一句判据：
**「它再生效就说明 `budgeted` 的预算算错了」**——即：护栏是探测器，不是压缩器。

### 已知的两个缺陷

1. **`budgeted()` 会越界。** `interactive.ts:359-362`：`room = max(0, total - tail.length - 2)`，
   `per = Math.max(600, …)`。尾巴（图 + 覆盖摘要）不参与裁剪，600 字地板无条件生效——
   于是屏数足够多时返回值超过 `total`，掉进那把 head slice 护栏里，
   **而护栏切掉的正好是那条「一截就废」的结构尾巴**。今天 `maxScreens ≤ 30`（30×600=18000）
   够不到，但 `maxScreens` 是用户可调参数。
2. **调用点从不传 `total`。** `interactive.ts:988` 用的是默认值 200000——
   一个下游任何消费者都没有同意过的数。真正知道窗口的是 `spec.compose`
   （它才是读这份材料的人），而它连自己的输入预算都还没有。

## 变更

### 变更一：把三处未预算的调用接上 `fitToBudget`（只动 `variable` 半边）

| 调用点 | 怎么分 |
|---|---|
| `casegen/nodes.ts:456` `spec.compose` | `{material, share:4}` + `{flows, share:1, fixed:true}`，新增 `contextTokens` 参数，形状照抄 `:932` |
| `codegen/nodes.ts:243` `repair` | `{code, fixed:true}` + `{failure, share:1}` |
| `server/src/review.ts:781` | 用 `fitToBudget` 取代 `slice(0, 6000)` |

三处都按 `nodes.ts:977-981` 已有的形状把 `dropped` 发成日志。

**这里有一条硬约束：只能动 `variable`。** `stable` 的前几个字节是一份被实测过的性能契约——

> 端点缓存提示词前缀，在自托管模型上这个缓存就是速度的大半。在这个项目的端点上实测，
> 一个约 9k token 的请求里约 6k 是前缀缓存命中——而这只在两次调用的开头字节完全一致时发生。
> —— `packages/harness-core/src/model/client.ts:7-11`

对 `stable` 做任何裁剪、重排或插入，代价是**丢掉大半速度，而所有测试仍然全绿**。

### 变更二：统一单位，修掉越界，但**不要**把屏幕交给 `fitToBudget`

- `budgeted()` 的 `total` 改成 token，内部用 `estimateTokens`；
- `room < 600 × n` 时**整屏丢弃并写明丢了几屏**，而不是无条件给每屏 600 字地板；
- 调用点（`interactive.ts:429`）从 `ObserveSpec` 拿这个数，源头是 `spec.compose` 的 `contextTokens`；
- 网关护栏（`index.ts:1270`）由同一个数派生，且必须是 `total × k`（k>1）——
  否则 `console.warn` 会天天响，一个天天响的告警等于没有告警。

**但两个压缩器要保留两种策略。** 把屏幕列表交给 `fitToBudget` 是这一章最诱人的「顺手统一」，
而它会**精确地重演 `interactive.ts:75-88` 那次事故**：`trimMiddle` 保头保尾删中间，
作用在一份拼起来的屏幕列表上，删掉的就是中间那几屏——整屏消失。

两者共享的应该是**单位**（`estimateTokens`）和**上报形状**（`dropped`），不是分配算法。
`fitToBudget` 的份额制适合「几个语义不同的部分抢一个窗口」；
`budgeted` 的等分适合「N 个同质的东西，每个都必须留下痕迹」。这是两个问题。

### 变更三：分层召回——用已有的 `overlaps()`，做成参数而不是替换

`design.cases` 的规格部分，从「整份规格按份额裁」改成「先给这条故事自己的规则，剩下的份额再填正文」：

```ts
// 今天：{ name: "spec", text: specText, share: 1 }
// 改后（specScope === "story-rules" 时）：
//   命中的规则原文（share 高） + 规格其余部分（share 低）
const hit = (spec.rules ?? []).filter((r) =>
  (story.acceptance ?? []).some((line) => overlaps(line, r.text) || overlaps(line, r.evidence)),
);
```

`overlaps()` 就在 `attribute.ts:61`，而且这个匹配 `nodes.ts:765-767` **已经在用**了
（把故事的验收标准对回已定位的规则）。所以这不是新机制，是把一个已有的匹配多用一次。

**必须做成参数，不能做成替换**：`specScope: z.enum(["full","story-rules"]).default("full")`。
理由见「代价与风险」。

### 变更四：摘要——判据先行

这一节是本章的重点，因为它给出的是**一条否决线**。

#### 三问判据

一段内容能不能被模型摘要，问三个问题，**任何一个是「是」就不能摘**：

| # | 问题 | 命中它的地方 |
|---|---|---|
| 1 | 下游是否要求**逐字引用**这段内容？ | `interactive.ts:222-224`：采集必须原样，「因为下游 `spec.compose` 要求逐字引用界面文案，而一段被模型转述过的描述，引出来的文案是它记得的样子，不是屏幕上的样子」<br>`attribute.ts:9-13`：定位器**只认得真的原话**，「模型转述过的、翻译过的、概括过的句子都定位不到」 |
| 2 | 这段内容是否是**某个指标的输入**？ | `eval/semantic.ts:7-11`：「主覆盖率必须可复现，因为两个版本之间做配对比较正是它存在的全部理由——而把模型放进测量中间，同一次运行会给出两个不同的分数」 |
| 3 | 摘要错了，**下游看得见吗**？ | 若看不见，就是第 02 章 P3 那个形状：一份看起来完整的绿色报告，而它建立在一句没人核对过的转述上 |

#### 按这三问过一遍全仓库

| 内容 | 问 1 逐字 | 问 2 指标输入 | 问 3 可见 | 结论 |
|---|---|---|---|---|
| 探索材料（屏幕文案） | ✅ 要求逐字 | ✅ 规则的 `evidence` 要被 `locate` | ❌ | **绝不能摘要** |
| 规格正文 | ✅ 断言要引规格原话 | ✅ 语义覆盖的黄金清单对着它 | ❌ | **绝不能摘要** |
| 故事、用例 | — | ✅ 覆盖率的分子分母 | ❌ | **绝不能摘要** |
| 执行失败信息 | ❌ | ❌ | 部分（修复轮次可见） | 见下 |
| 送进 trace 的产物 | ❌ | ❌ | ✅ 有 `__truncatedForTrace` | 已经在压，而且**不在模型路径上** |

**结论是反直觉的：今天这条流水线上，没有一处需要摘要。**

原因不在于「摘要不好」，在于**摘要解决的不是这里的问题**。摘要治的是**累积的上下文窗口**——
一个 Agent 转了 40 轮，历史越堆越长，必须把前 30 轮压成一段。而这条流水线没有累积窗口：

```ts
// packages/harness-core/src/model/client.ts:13-24
export interface ChatRequest {
  stable: string;    // 角色、方法、输出 schema
  variable: string;  // 这一次的材料
  …
}
```

**没有 `history` 字段，而且不该有。** 每个节点开一个干净的窗口（见 [第 05 章](./05-子Agent与上下文隔离.md)），
循环长在节点**内部**而不是图上的环。所以「二十万 token 的日志毒死一个不断累积的窗口」
这个经典失败模式在 TestPilot 上**结构性地不可能发生**——真正会疼的是另外两个，
而它们都是**单次**的过大输入（`spec.compose` 的材料、`repair` 的失败信息），
截断就能治，用摘要治等于请一个不可复现的第三方来处理一件确定性的事。

#### 唯一的候选，以及它为什么也先不做

`repair.loop` 跨轮的失败历史（第 2 轮及以后的旧轮次）在理论上过了三问：
它不要求逐字，它不是指标输入，而且修复轮次在界面上是可见的。

即便如此也建议先不做，两个理由：

1. 模型是全系统最稀缺的资源。`gate.ts:4-8`：「自托管的 VL 模型是系统里最稀缺的资源，
   它一次只能体面地服务一个请求」；准入并发是 1–3（`server/harness.config.ts:17`，
   而且注释说明这个 3 是**限流**理由不是稳定性理由）。为了省输入 token 去多打一次模型调用，
   在这个系统上是负收益。
2. `repair` 的轮数上界很小，把旧轮次直接丢掉（而不是摘要）已经够了，而且丢掉是可见的。

**如果将来真要做**：摘要必须写进 `OutputStore` 的**兄弟槽位**（`${nodeId}#summary`），
原文一个字节都不动。仓库对这件事有明文规矩：一次运行的产物
「必须保持原样（它是每次后续比较里的证据）」（`server/src/db.ts:277`）。
一个覆盖原文的摘要，等于把证据换成了对证据的转述。

| 收益 | 可测量吗 | 怎么测 |
|---|---|---|
| `spec.compose` 的截断从「下游 JSON 格式错误」变成一行带数字的日志 | ✅ | `dropped > 0` 的日志条数；对照今天 `parseJson` 的报错次数 |
| `repair` 的超长失败信息不再表现为 900 秒超时或不重试的 4xx | ✅ | trace 上 `repair:*` 的时延分布 |
| 重复的规格 token：N 故事 × `contextTokens` → 按命中规则数走 | ✅ | 分项用量（`TokenUsage.input`，[第 12 章](./12-Langfuse可观测性.md) 变更三）两臂对比 |
| 一个单位、一处 `dropped` 上报形状，而不是两套会继续漂的实现 | ❌ 说不了数 | — |
| 「该给这条故事的规则」不再因为坐在正文中间而被删掉 | ✅ | 配对评测（见下） |

关于最后一条要诚实：**它可能是负收益。** `overlaps()` 是启发式的，
一条验收标准跟任何规则都不重叠的故事，在 `story-rules` 臂下拿到的规格会比今天**小得多**。
这正是它必须做成参数并跑一次配对评测的理由，而不是直接换掉。

## 代价与风险

| 项 | 说明 |
|---|---|
| **`estimateTokens` 是近似，不能升级成硬闸** | `budget.ts:18-20` 明说它是故意近似的（CJK 约 1 token/字，拉丁约 1/4）。把它变成「超了就抛」，中文材料会被系统性高估而误伤。保持 **advisory + 日志**，真正的窗口由端点说了算 |
| **不能碰 `stable`** | `client.ts:7-11` 的前缀缓存契约。改它的代价是丢掉大半速度而**所有测试仍然全绿**——这是本书 [第 18 章](./18-风险登记册.md) 里最典型的一条静默回归 |
| **`budgeted()` 换单位会改行为** | `packages/harness-testing/test/sfg.test.ts:276-297` 四条测试钉着现有行为，会红。**不许靠放宽断言变绿**——那等于在测试里复刻 24000 → 60000 → 240000 那三次 |
| **分层召回是启发式** | 见上。做成 `specScope` 参数，默认 `full`，不改默认路径 |
| **`spec.compose` 的裁剪会让规则变得不可引用** | 这个节点的保证是「每条规则引一句材料原话」（`interactive.ts:917-919`）。被裁掉的材料里的规则就引不出来了。所以 `dropped` **不能只进日志**，还要进规格的「没有答案的地方」那一节——否则是拿一个响的失败换了一个哑的 |
| **不要为了压缩去加一次模型调用** | `gate.ts:4-8` + `harness.config.ts:17`：并发 1–3。省下的是输入 token，付出的是一个准入槽位 |
| 工作量 | 变更一 半天，变更二 半天（含改测试），变更三 半天 + 一次配对评测的机器时间，变更四 零（它是一条判据，不是代码） |

**什么情况下不该做这一章：** 如果正在跑长评测。这些改动动的是提示词材料的字节，
会一次性作废所有 `RecordedModel` 录像（`client.ts:157` 的 `requestKey` 把 stable+variable+schema
一起哈希），并且让改动前后的运行在配对评测里不可比。要么在两次评测之间做，要么一次做完。

## 怎么证伪

| 手段 | 内容 |
|---|---|
| **单元测试**（新增，`packages/harness-core/test/budget.test.ts`） | **性质测试：`fitToBudget` 只要裁了，`dropped` 必须 > 0。** 这条保证 `nodes.ts:977` 那行日志永远不会变成静默 |
| **单元测试**（新增，`packages/harness-testing/test/sfg.test.ts`） | **性质测试：`budgeted(n 屏, total)` 的返回长度 ≤ k×total，n 取 1..50。** 这条**今天就是红的**（600 字地板），这正是它的价值——它把一条注释变成一个断言 |
| **单元测试**（新增） | 变更二之后：屏数多到放不下时，返回值里必须出现「丢了 N 屏」这句话，且图和覆盖摘要必须完整存在（沿用 `sfg.test.ts:292-296` 的形状） |
| **配对评测** `evals/spec-scope.json` | 两臂只差 `design.cases` 的 `specScope`（`full` vs `story-rules`），Juice Shop 黄金清单，形状照抄 `evals/design-methods-headroom.json`。零代码——评测格式已经带每节点参数。**注意**：这个配对之所以合法，是因为探索是确定性的（同一份材料、同一张图），这一点 `design-methods-headroom.json` 的 `why` 字段已经论证过 |
| **消融开关** | **不加。** 一个「关掉上下文预算」的开关不是消融，是让长材料直接撞窗口——那不产生一个可比的臂，产生一次崩溃。`ablation.ts:3-7` 要求每个开关都必须是某个节点真的会读的东西，且**关掉之后产出要变而不是消失**。如实记在这里，而不是造一个假的开关 |

### 无法证伪的部分（如实记）

**「摘要会不会其实更好」这个问题，在这条流水线上无法证伪。**

理由是链条上的：要比较「摘要臂」和「截断臂」，主指标得是语义覆盖；
而语义覆盖一旦引入 `eval/semantic.ts` 的判官就不可复现（`semantic.ts:7-11` 自己说的）；
只用确定性的关键词覆盖，又恰恰量不到摘要造成的那种失真——
**摘要的错误是「一句通顺的、意思偏了的话」，关键词匹配对它免疫。**

所以本章对摘要的结论（「今天没有一处需要摘要」）是一个**架构论证**，
不是一个测量结果：它建立在「`ChatRequest` 没有 `history`、窗口不累积」这个可以打开看的事实上
（`client.ts:13-24`），而不是建立在一次跑赢的配对评测上。

按第 00 章的口径，这一段标注为**推断**。它不能作为「以后永远不做摘要」的唯一依据；
它能作为「现在不做，并且做之前必须先说清楚是哪个累积窗口需要它」的依据。

## 验收

1. `spec.compose` 跑一次超大材料（≥ 200k 字符的探索产物），事件日志里出现一行
   `trimmed N tokens of material`，且规格的「没有答案的地方」里出现对应的一句；
   **今天这次运行的表现是下游 `parseJson` 报「JSON 格式错误」**。
2. `server/src/index.ts:1270` 的 `console.warn` 在同一次运行里**不响**——护栏回到探测器的位置。
3. 构造一条超长失败信息（≥ 50k 字符）喂给 `repair`，模型调用正常返回，
   trace 上 `repair:*` 的 `promptChars.variable` 是一个有上界的数。
4. `budgeted()` 的性质测试从红变绿，且 `sfg.test.ts:276-297` 原有四条仍然绿
   （断言没有被放宽——这一条要人看 diff，不是机器判的）。
5. `evals/spec-scope.json` 跑完，两臂在 Langfuse 上按 `ablate:*` / 参数标签可分，
   报告里同时给出语义覆盖和**输入 token 中位数**——后者是这一章唯一确定会改善的数。
6. `grep -rn "slice(0, [0-9]\{4,\})" server/src packages/*/src` 在提示词材料路径上返回空
   （`forTrace` 与日志截断不在此列）。

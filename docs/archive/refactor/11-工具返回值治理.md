## 问题

这个仓库**没有工具循环可以治理**——`packages/harness-testing/src/guard.ts:6` 写得很清楚：
「There is no tool registry to police here」。模型产出数据，代码去动手。

所以「工具返回值」在这里指的是**跨边界的载荷**：跨进程、跨 SQLite、跨 HTTP、跨提示词。
而这些边界上的治理**做得极不均匀**：像素治理得堪称典范，文本几乎完全没治理。

代价已经发生了，而且量得出来。

### 实测一：事件表被日志吃掉了

`events.db`，200,014 行（**正好卡在 `harness.config.ts:19` 的 20 万上限，也就是说它此刻正在丢东西**）：

| kind | 行数 | 占比 |
|---|---|---|
| `log` | 148,523 | **74.3%** |
| `process.status` | 40,464 | 20.2% |
| **真正的工作流血缘**（`wf.*` / `gate.result` / `run.*` / `repair.round`） | **2,938** | **1.47%** |
| 其中 `wf.node.output` | 681 | 0.34% |

**血缘只占 1.47%，而这张表是这个项目「一次运行发生了什么」的唯一记录。**

这不是新问题，`harness.config.ts:140` 已经把同一件事记下来了：

> 把事件缓冲刷满（一次实测 600 条事件里 457 条是它的崩溃日志，探索的日志全被挤掉）

一个崩溃重启循环的进程，占掉了 600 条窗口里的 457 条，把探索的日志全挤没了。
当时的处理是把那个能力的 `autostart` 关掉——**治的是那一个进程，不是这个机制**。

### 实测二：日志的合并语义是反的

`log` 在 `COALESCED_KINDS` 里（`obs/envelope.ts:76`），而 `coalesceKey`（`envelope.ts:76`）
**没有逐行成分**，`bus.ts:107` 是 `pending.set(key, e) // last one wins`。

于是：**日志是唯一一种「载荷本身就是信息」的事件，却被按「重绘」的语义合并掉了。**
进度条合并掉中间帧是对的，日志合并掉中间行是丢数据。

### 实测三：像素被构建了两遍，其中一遍直接扔掉

`exec/run.ts:118` 的 `shot()` 每次截图都构建 base64 data URI；
`apps/runner/src/exec.ts:85` 一句 `void _dataUrls` 原地丢弃。

实测：平均 PNG 62,934 B（n=914），一次 25 张截图的运行**白白分配约 2.1 MB 字符串**，
runner 进程峰值 RSS 约 2.3 倍。而网关那边本来就用 `pngBuffers` 自己经 `toDataUrls`
重建（`server/src/index.ts:1057`）。

### 实测四：几个 HTTP 端点在返回兆级 JSON

- `GET /api/runs`（`index.ts:692`）返回最多 200 条完整 `RunRecord`，**无投影**。
  按实测 41,069 B/行的 data-URI 均值，这是一个 **~8 MB** 的 JSON。
- `GET /api/wf/runs/:id`（`index.ts:1819`）**先把所有节点产物跨 IPC 拉过来**，
  然后才在 `:1899` 用 `summarize` 缩掉。实测一次 ~205 KB 的 IPC 传输 + JSON 解析，
  只为了显示几 KB。

## 技术点

治理不是「加个 slice」。三种手段，代价与信息损失各不相同：

| 手段 | 做法 | 损失 | 适用 |
|---|---|---|---|
| **源头限流** | 不产生就不用治 | 无 | 那 2.1 MB 白建的 base64 |
| **引用替代内容** | 写盘，传路径 | 无（多一跳 IO） | 像素、大文本、帧 |
| **分级** | 给模型 / 给人 / 存档三份不同大小 | 有，但**可控且可声明** | 日志、节点产物 |

第三种是最容易做错的，因为它必然有损。**唯一能让有损变得可接受的，是让损失可见。**

## 现状

### 做得好的那一半：像素

这一半是范本，而且它被写进了**类型**而不是约定：

```ts
// apps/runner/src/exec.ts:78
type ExecResult = Omit<RunResult, "pngBuffers" | "screenshots"> & { pngPaths: string[] }
```

配套的理由写在 `apps/runner/src/exec.ts:72`：

> Passing megabytes of base64 across the IPC channel would make every screenshot a copy in three places

网关侧 `readPngs`（`server/src/exec.ts:74`）读完即删；帧订阅刻意保持整个会话，
免得帧文件泄漏（`exec.ts:116`）。`server/src/exec.ts:74` 写着「Pixels cross as file paths, never as bytes」。

**但这句话目前还不完全是真的**：`exec/diagnostics.ts:87`、`:119`、`:167` 三处诊断 RPC
仍然内联返回 base64，直接跨 IPC 再出 HTTP。

### 做得不好的那一半：文本

| 载荷 | 边界 | 有上限吗 |
|---|---|---|
| `RunResult.logs: string[]`（`exec/run.ts:18`） | IPC → 运行记录 → 节点产物 | ❌ 全程无界 |
| `parentApi.emit` 的 `payload`（`supervisor.ts:263`） | 跨进程事件 | ❌ `kind` 和 `scope` 过 zod，**载荷原样透传** |
| 单行 stdout | 事件总线 | ✅ `text.slice(0, 2000)`（`supervisor.ts:325`）——**唯一的字节上限**，且只管单行不管行数 |
| 节点产物 | `SqliteOutputStore` | ❌ zod 校验形状不校验大小（`runtime.ts:222`） |
| 送进 chat 提示词的节点产物 | 提示词 | ✅ `brief(value, 900)`（`server/src/chat.ts:293`） |

### 一个已经写下来、但自己违反了的原则

`src/components/JsonView.tsx:9` 记着这个仓库关于截断最锋利的一段论证：

> 节点产物曾经是 `JSON.stringify(x,null,2)` 塞进 `<pre>`，在 20k 字符处切断。
> **截断是最糟的那部分：被切掉的部分不给任何信号，于是读的人以为自己看到了全部。**

由此定了三条规矩：数组折叠成计数、搜索按路径与值过滤、**什么都不截断**。

而同一个前端在两个地方违反了它：`wf.ts:811` 与 `:1061` 的 `slice(-TRACE_CAP)` /
`slice(-LOG_CAP)` 没有任何提示，`Workspace.tsx:1409` 的 `log.slice(-40)` 也没有标记。

## 变更

按「收益 ÷ 风险」排序。前三项都是小改动。

### 变更一：删掉那 2.1 MB 白建的 base64　【最省事，收益立刻可见】

删 `exec/run.ts:14` 的 `screenshots.push(...)`，并从 `RunResult`（`run.ts:14-48`）
去掉 `screenshots: string[]`。

**看起来最危险，实际上是免费的**：`executeRun` 没有任何本地调用方，
所有路径都经 runner，而 runner 已经在 `exec.ts:85` 把它丢掉了。

### 变更二：给跨进程事件加字节预算　【一个choke point管住全部】

`supervisor.ts:263` 的 `parentApi.emit` 已经在做「校验失败就变成一条 `error` 事件」
——**拒绝要响，不能静默**，这条路径已经写好了。在同一处加字节上限：
超限的载荷替换成 `{ truncated: true, bytes, ref }`，正文写进 artifact store。

上限要设在**最大的合法载荷之上**：实测 `runObserve` 的 notes 最大 128,430 B。

### 变更三：把像素规则套用到文本上

`logs` 在 `apps/runner/src/exec.ts:92`（就是那个已经剥掉 `pngBuffers` 的函数）里
截断 + 落盘，像 `pngPaths` 一样返回路径。

同时给 `supervisor.ts:320` 的 `pipeLogs` 加**行数**速率上限——它今天只管单行长度。

### 变更四：让日志不再被合并掉

`bus.ts:64` 的 `subscribe` 接受一个 `coalesced?: ReadonlySet<string>`，
透传给 `new Sub(...)`。两行。注入点本来就存在（`BusOptions.coalesced`，`bus.ts:16`）。

于是日志消费者拿到每一行，画布继续合并。

### 变更五：让保留策略按 kind 分桶

`store.ts:101` 的 `prune` 现在是一条不分 kind 的 `DELETE`。把 `EventStore` 接口
（`store.ts:7`）的 `prune` 签名改成 `number | Record<string, number>`，逐桶删。
`events_kind` 索引（`store.ts:66`）已经在了，这些删除是走索引的。

**收益是算得出来的**：按实测构成，在同样 20 万行预算内把 `log` 限到 2 万、
`process.status` 限到 1 万，真正的血缘保留窗口从 **3.96 天变成约两个月**。
无需改 schema，无需改任何写入方。

### 变更六：HTTP 层做投影

- `GET /api/runs`：加投影，不返回截图字段。
- `GET /api/wf/runs/:id`：在 agent 侧就 summarize，别把全部产物拉过来再缩
  （更好的做法见 [第 06 章](./06-中断恢复与检查点.md)：网关本来就握着同一个 DB 句柄）。

### 变更七：治理必须带信封

这条是**前六条的前提**，也是最容易被跳过的一条。

被治理过的返回值必须以 `{ shown, total, droppedBecause }` 的形状到达消费者，
而不是一个已经被切短的裸值。否则 `JsonView` 那条「什么都不截断」的保证
就变成了**前端替后端说的一句谎**——它以为自己收到的是全部。

同时修掉前端那两处自己的违规（`wf.ts:811`/`:1061`、`Workspace.tsx:1409`）：
加一行「还有 N 条未显示」。

## 与第 10 章的分工

两章都在处理「东西太大」，但方向相反，不要混：

| | 第 10 章 上下文压缩 | 第 11 章（本章） |
|---|---|---|
| 治的是 | **送进模型的** | **工具吐出来的** |
| 边界 | 提示词的 token 预算 | 进程 / DB / HTTP / 事件总线 |
| 主要机制 | `fitToBudget` 份额制 | 源头限流、引用替代、分桶保留 |
| 失败长相 | 回复被腰斩、JSON 解析错 | 血缘被挤掉、IPC 变慢、内存翻倍 |

有一处交叉，两章都要提到：**`spec.compose` 的输入没有走预算**
（`nodes.ts:458` 的 `composeVariable(material.text + flowText, ...)` 是裸传），
而 500 行外的 `design.cases`（`nodes.ts:969-983`）做得完全正确。
**这条流水线里最大的一个工具返回值，恰恰没有用这条流水线自己的预算机制。**
详见第 10 章。

## 收益

| 变更 | 实测收益 |
|---|---|
| 一 · 删白建 base64 | 每 25 张截图的运行少分配 ~2.1 MB，runner 峰值 RSS 约降到 1/2.3 |
| 五 · 分桶保留 | 血缘保留窗口 **3.96 天 → 约两个月**，零 schema 变更 |
| 六 · 运行详情投影 | 一次页面加载的 IPC 从 ~205 KB 降到 ~2 KB |
| 六 · `/api/runs` 投影 | 列表响应 **~8 MB → 几百 KB** |
| 二 · emit 字节预算 | 一个病态进程不再能把血缘挤没 |
| 四 · 分订阅合并 | 日志不再丢行 |

最后一条不在表里，但可能最值钱：**变更二让「载荷过大」从一个隐形成本变成一条事件**。
现在没有任何机制会告诉你某个产物大得离谱。

## 代价与风险

| 项 | 说明 |
|---|---|
| 变更一 | 看着危险，实际免费（无本地调用方）。但**必须保留 `pngBuffers`**——它和 base64 不可互换，视觉基线比对读的是它 |
| 变更五 | `EventStore` 是 harness-core 的公开接口，两个实现加 `startRetention`，改动要跨 `obs/store.ts`、`obs/retention.ts`、`server/src/procs.ts:69` 协调 |
| 变更五（真风险） | **分桶删除会打破 `since(id)` 的连续 id 假设**（`store.ts:76`）。今天客户端断线重连走的是连续 id 区间，不均匀剪枝之后会出现空洞。恢复路径要能容忍空洞，否则这是一次协议变更 |
| 变更三 | 头尾各留多长是判断题。**往长了留**——网关是从本地磁盘读的 |
| 变更七 | 如果先做了限流而没有先定信封形状，前端检测不到，`JsonView` 的保证当场变成谎话。**先定信封，再限流** |
| 变更二 | 上限必须高于最大合法载荷（实测 128,430 B）。设低了会开始丢真东西 |

**什么情况下不该做**：变更五（分桶保留）在恢复路径改造完成之前不要上。
宁可让日志继续挤占血缘，也不要让断线重连开始丢事件——前者是容量问题，后者是正确性问题。

## 怎么证伪

| 手段 | 内容 |
|---|---|
| **单元测试** | 变更二：一个超限载荷必须产生一条 `error` 事件而不是被持久化；变更五：分桶剪枝后各 kind 的行数符合各自上限；变更一：`RunResult` 不再有 `screenshots` 字段而视觉基线测试仍绿（`test/baselines.test.ts` 已存在） |
| **可量测的前后对比** | 五项实测数字每一项都可以复量：事件表构成（一条 SQL）、运行详情的 IPC 字节数、`/api/runs` 响应体大小、runner 峰值 RSS。**做之前先量一遍存档，做完再量**——这是本章唯一诚实的验收方式 |
| **门禁规则** | 变更七的信封可以做成一条检查：节点产物超过阈值而**没有**带 `{shown,total,droppedBecause}` 时报一条 finding |
| **无法证伪的部分** | 「头尾留多长才够诊断」没有客观判据。只能靠事后：统计有多少次排查因为日志被截而失败。**这个数今天没人在收，做之前先开始收** |

## 验收

1. 一次 25 张截图的运行，runner 峰值 RSS 相比改造前明显下降，且视觉基线测试仍全绿。
2. `events.db` 里 `log` 占比降到设定上限以下，`wf.*` 的最早一条事件时间戳往前推到周级以上。
3. 打开一次运行详情，IPC 传输量在数 KB 量级。
4. 人为制造一个超大载荷（例如让某个节点返回 10 MB），结果是**一条 `error` 事件**，
   不是一行被静默持久化的巨型 JSON。
5. 前端任何一处显示被截断的内容时，屏幕上有一行说「还有 N 条未显示」。
6. 一个崩溃重启循环的进程跑十分钟，**同期的探索日志仍然查得到**。
   这条直接对应 `harness.config.ts:140` 记下的那次事故——它是这一章存在的理由。

## 问题

一个跑了 80 次运行、留下 913 份执行产物和 381 条节点产物的 harness，
**每一次仍然从零开始面对同一个产品**。

具体的浪费是量得出来的。`interactive.ts:1141-1158` 的 `deadHref` 记的是一条关于
**被测产品路由形状**的知识：

> `/user/signin` 直接导航会 404，但点过去可以

这是这个 SUT 的一条稳定性质。而**每一次运行都要烧掉一轮去重新学它**，
然后 `goBack` 再恢复。在一个 pushState 的 SPA 上，24 屏的探索预算里有可观的一部分
花在重新发现同一批 404 上。

这是「程序性记忆缺失」的教科书案例。但下面会说明，**补它比看起来危险得多**。

---

## 技术点

四层的通行划分，以及各自的存续期与失效方式：

| 层 | 存的是 | 存续 | 典型失效 |
|---|---|---|---|
| **会话记忆** | 这一轮对话/交互的上文 | 一次会话 | 换了话题还带着旧上文 |
| **工作记忆** | 当前任务的中间状态 | 一次任务 | 任务中断即丢失 |
| **长期记忆** | 跨任务的事实 | 无限 | 陈旧、污染 |
| **程序性记忆** | 「这件事怎么做」的策略先验 | 无限 | 先验错了，且错得看不见 |

关键区别不在存多久，在**失效之后错得有多隐蔽**。会话记忆错了，人当场就看出来；
程序性记忆错了，它会**安静地改变以后每一次运行的行为**。

## 现状

三层半已经有了，而且不少做得很好——只是没有用「记忆」这个词。

### 工作记忆　✅ 做得最好的一层

`SqliteOutputStore`（`graph/store.ts:15`），键 `(wfRunId, nodeId)`。
实测：80 次运行、381 行、8.29 MB JSON。

`runtime.ts:112` 把这件事说死了：

> what a library would have added is checkpointing, which the output store already provides

探索循环内部还有一套纯内存的工作记忆：`seen` / `triedGoto` / `triedClick` /
`shapeDry` / `frontier`（`interactive.ts:1183`）/ `deadHref`（`:663`）/ `linksSeen`（`:565`）。
全部函数作用域，`finally { session.cleanup() }` 时全部丢弃。

**其中一个细节值得单独指出：这些结构一个都不给模型看。**整个探索循环里
喂给模型的只有一句登录指令（`:1201`）。工作记忆在这里是**代码的状态**，不是提示词的一段。
这是一个刻意且正确的设计——见下面「反对意见」。

### 会话记忆　✅ 刻意不做，而且理由写下来了

`DiagnoseDrawer.tsx:41` 把对话轮次放在 `useState` 里，`:46-47` **每次换作用域就清空**：

> 换一个对象就是换一个问题：把上一个对象的对话留着，会让追问带上不属于它的上文

`DiagnoseDrawer.tsx:11-27` 还记着为什么删掉了常驻的聊天栏：

> 一个永远在场的对话栏，是在宣称这个产品主要靠聊天驱动——它不是，也不该是

**这不是缺失，是决定。**本章不提议改它。

### 长期记忆　✅ 有，但只有一条被消费

| 表 | 存的是 | 备注 |
|---|---|---|
| `test_cases` | 认可的用例 | 看板 = 「我认的套件」 |
| `baselines` / `perf_baselines` | 视觉与性能基线 | 真正的跨运行参照 |
| `review_decisions`（`db.ts:264`） | **否定记忆**：拒过的东西不再出现 | 少见且正确的设计 |
| `flakiness`（`db.ts:1098`） | 滚动 10 次窗口 → stable/flaky/broken/unknown | **系统里唯一一条「固化的信念」** |

`flakiness` 值得停一下：它是四层模型意义上唯一一个**共识层**（把多次观察压成一个判断）。
而它**当前实例里是 0 行**——因为实际上没有东西在算它。

> 这条事实本身就是本章最重要的证据：**一个固化层会在没人注意的情况下腐烂。**

### 程序性记忆　✅ 有，而且已经进版本库了

这是最容易被误判为「缺失」的一层。实际上它齐全，只是分散：

| 载体 | 是什么 |
|---|---|
| `*_STABLE` 提示词 | 「这件事怎么做」的策略——**这就是程序性记忆**（版本管理见 [第 08 章](./08-Prompt是代码.md)） |
| `graphs.db` 的图版本 | 流程本身，可 diff、可按版本复现 |
| `evals/*.json` | 「我们靠什么判断做得好不好」 |
| `midscene_run/cache/*.cache.yaml` | **事实上的学到的操作缓存**，实测 101 个文件 / 464 KB |

最后一条是唯一没被当成记忆管理的：它唯一的失效原语是 `index.ts:783` 的一句 `rmSync`。

### 真正缺的那半层

`docs/spec/05:92` 设计过一个语义层（带 promote 阈值与陈旧度），**没有实现**：

- `ls packages/harness-core/src` → `config` `eval` `graph` `harness` `model` `obs` `util`
  ——**没有 `memory` 模块**。
- `ABLATABLE`（`eval/ablation.ts:9`）7 个开关，**没有一个是 `memory`**，
  尽管 spec 第 100 行点名要一个。

## 变更

### 变更一：程序性记忆——探索的策略先验　【最小、收益最直接】

一个按 `(project, env)` 存的 `ExploreProfile`：

```ts
{ deadHref: string[], shapeFamilies: string[], loginRung: "configured" | "guessed" }
```

存在网关已经在维护的 environment 记录旁边（`server/src/index.ts:1185-1209` 已经从那里
读 baseUrl / headers / login / session），经 `ObserveSpec` 传入（它已经带了 login 和 resolve），
在 `interactive.ts:429` 种进 `deadHref`。

**这是本义上的程序性记忆：不是一份转录，是一个策略先验。**

### 变更二：语义层，如果要做，就照现有的形状做

`docs/spec/05:92` 设计的那一层。做法上有三条不要走错：

- **不要新建数据库。**照 `datasets.ts:30` 那个自注册模式加一个 `server/src/memory.ts`
  （`PRAGMA table_info` 守卫 + 自己的 CREATE，只 import `db` 和 `newId`）。
- **不要发明第二套寻址。**键用现成的 `ScopeSchema` 字段（`obs/envelope.ts:7`）。
- **行的形状照 `flakiness`（`db.ts:1098`）抄**，但补上它缺的两个字段：
  `observations`（promote 阈值）和 `staleAt`（陈旧度）。

### 变更三：**记忆必须有一个消融开关**　【这条是前两条的前提】

`ABLATABLE` 加 `memory: "memory"`，并让至少一个节点真的去读它。

理由不是形式主义。`eval/ablation.ts` 的规矩是「每一条都必须是某个节点真的在读的东西」，
而配对评测机制（`eval/paired.ts`）现成。**没有这个开关，「记忆有没有用」这个问题
永远只能靠感觉回答**——而这正是这个仓库全部方法论反对的东西。

### 变更四：记忆归网关所有，经 `extendParentApi` 借出

进程拓扑决定了它只有一个正确的家。只有网关持有 DB、事件存储和总线（`procs.ts:44-48`）；
子进程能**产生**事实但不能读——agent 的 "bus" 是一个 forwarder，
它的 `subscribe`/`head`/`replay` 是**刻意留空的桩而不是假实现**（`apps/agent/src/main.ts:141-150`）。

所以：`recall(query, scope)` / `remember(fact, scope)` 加在 `procs.ts:93-103`，
走 `supervisor.ts:97` 的 `extendParentApi`——那条缝已经在承载模型闸、`execCase`、
`observeProduct`，而且是**按 processId 构建的**，所以按 agent 分域和授权是白送的。
进程死掉时的清理也有现成先例：`lending.releaseAllFor`（`procs.ts:107`）。

> **不要**为了让子进程能读记忆而去把 `forwarder.subscribe`（`agent/main.ts:115`）实现掉。
> 那会让每个子进程都变成总线消费者，破坏 `protocol.ts:1-6` 定的
> 「命令走 RPC，事实走总线」。

## 反对意见（本章最重要的一节）

### 代码在这里反驳得最凶

`interactive.ts:37-48` 记着一条实测性质：

> **PetClinic 五次运行图完全一致、标准差为 0**

而 `evals/design-methods-headroom.json` 的 `why` 明确依赖它：

> 两臂可比，**因为探索是确定性的……所以两臂拿到的是同一张图**

**一个让第 N+1 次运行依赖第 N 次的记忆，会把这条性质摧毁——而且是以这个仓库
最害怕的那种方式：看不见地。**

后果具体是：配对评测的两条臂不再面对同一个起点，于是两臂之差里混进了
「A 臂恰好先跑、把先验留给了 B 臂」这个成分。而报告上，它长得和真实效应一模一样。

这与 `baselines/frozen.ts` 那次事故是**同一个形状**：PetClinic 的 owner 数从 10 漂到 13，
黄金清单 G-03 当场失真，而**没有任何机制会报警，是顺手数了一下才发现的**。

### 由此得出三条硬约束

1. **记忆默认关闭，配对评测时强制关闭。**
   这不是配置建议，应当由代码保证：评测跑起来时 `memory` 开关强制在关的位置。
2. **记忆只允许存「产品的稳定性质」，不允许存「上次的结论」。**
   `deadHref`（这个路由直接导航会 404）是产品的性质；
   「上次这条用例判了失败」是结论——后者一旦成为先验就是污染。
3. **每一条记忆都要能说出它被观察了几次、什么时候过期。**
   这就是 `flakiness` 缺的那两个字段。而 `flakiness` 是 0 行这件事说明：
   **没有这两个字段的固化层，会安静地烂掉。**

### 一层明确不做：长期记忆的向量召回

探索循环**没有查询可服务，也没有模型可服务**——整个循环里只有一次模型调用
（那句登录指令）。给它加 embedding 召回是在解决一个不存在的问题。

聊天抽屉那边倒是有一个真实的、小的长期读需求（见下），但那也不是向量召回。

### 一个小而实的补充：聊天的工作记忆再宽一点

`chat.ts:272` 的 `ChatContext {kind: "node"|"run"}` 可以加 `"case"|"finding"|"gate"`。
`docs/spec/09 §5` 把「选中什么给什么」列为应该做的事，且后端的读取已经有了。

理由：这个抽屉存在的意义是**跨产物推理**（表格答不了的问题），
而它今天**不能以一条用例或一条 finding 为主语**——那恰恰是最常见的提问形式。

但要守住 `docs/spec/09:94` 记的那条：

> 把一百条用例塞进模型上下文是几万 token。必须是选择性上下文（选中什么给什么）

## 收益

| 变更 | 收益 | 可测量性 |
|---|---|---|
| 一 · 探索策略先验 | 收回每次运行都在浪费的那几轮 404 探测 | ✅ 直接比屏数与轮数 |
| 二 · 语义层 | 80 次运行留下的 913 份产物变成可复用先验 | ⚠️ 要靠配对评测 |
| 三 · 消融开关 | **让上面两条的收益第一次可测** | ✅ 它本身就是测量手段 |
| 四 · 网关持有 | 一个进程持有 = 一个进程能分域、能过期、能审计 | — |
| 补充 · 聊天上下文 | 抽屉能以用例/finding 为主语 | ⚠️ 主观 |

## 代价与风险

| 项 | 说明 |
|---|---|
| **确定性（首要）** | 见上。记忆与冻结基准的可比性直接冲突。**这不是可以缓解的权衡，是必须靠开关隔离的对立** |
| 固化污染 | `docs/spec/05` 自己的警告：「一次误判固化会传染后续全部任务」 |
| 腐烂无声 | `flakiness` 0 行就是证据 |
| IPC 阻塞 | 每次 recall 是一次 RPC 往返，而 rpc 的 `timeout: -1`（`rpc.ts:63,99`）——**一个慢的记忆后端会把运行卡住，且只有对端进程死掉才能结束调用** |
| 级联删除 | `deleteProject`（`db.ts:813`）**已经漏掉了 `datasets`**；照它的模式新加一张表会继承同一个洞，删掉项目之后记忆会复活 |
| 键的变更 | 变更二里把 `OutputStore` 的键从 `(wfRunId,nodeId)` 拓宽，会碰到 `runtime.ts` 的 `store.all(wfRunId)` 预载路径和两个实现 |

**什么情况下不该做**：语义层（变更二）在消融开关（变更三）之前不要做。
顺序反了，你会得到一个无法证明有用、也无法证明无害的组件——
而按 [第 00 章](./00-方法与约定.md) 的纪律，那样的组件不该存在。

## 怎么证伪

| 手段 | 内容 |
|---|---|
| **消融开关** | `memory` 进 `ABLATABLE`，至少一个节点读它。这是本章的主要手段，也是变更三本身 |
| **配对评测** | `evals/memory-explore-profile.json`：A = 冷启动探索，B = 带 `ExploreProfile`。**看的不是覆盖率**（B 必然不低），看的是**相同屏数预算下走到的新状态数**，以及**总模型调用数** |
| **单元测试** | ① 评测运行时 `memory` 必须被强制关闭——这条要有测试，否则它只是一句话；② 同一个 `ExploreProfile` 喂两次，图必须一致（先验不能引入随机性）；③ `deleteProject` 之后记忆表必须无残留 |
| **回归防护** | 把「PetClinic 五次运行图完全一致、标准差为 0」做成一个可重跑的检查。**它今天是一句注释里的实测，不是一个会红的测试**——而本章的全部风险都压在这条性质上 |

最后一条值得单独说：本章提议的每一件事都可能弄坏那条性质，
而那条性质今天**没有任何自动化保护**。**先把它变成测试，再谈记忆。**

## 验收

1. `ABLATABLE` 里有 `memory`，且 `parseAblation` 对它不报 unknown（说明真有节点在读）。
2. 跑一次配对评测，日志里能看到记忆被强制关闭。
3. 同一 `(project, env)` 连跑两次探索：第二次在相同屏数预算下到达的新状态数**更多**，
   且两次的图在去掉先验影响后一致。
4. 每条记忆行都有 `observations` 和 `staleAt`，且有一条过期路径真的会删东西。
5. 删掉一个项目，`memory` 表里没有残留（顺带把 `datasets` 那个洞一起补上）。
6. 「五次运行图一致」成为一个会红的测试，而不是一句注释。

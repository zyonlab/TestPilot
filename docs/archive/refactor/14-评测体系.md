# 14　评测体系

> 离线集、LLM-as-judge、人工标注、线上采样——四样里**两样已建成且比重写更好，
> 一样的原料就在库里却一次都没被消费，一样不存在。**
>
> 而最刺眼的一条是：这套体系里**唯一用来防自欺的机制，本身没有在跑**。

## 问题

这套评测体系已经强到一个程度：**主要的风险不再是「没有指标」，而是
「有指标但它在量别的东西」**。这一章要找的就是那些地方。

四样各自的状态：

| | 状态 | 一句话 |
|---|---|---|
| 离线集 | ✅ 建成，**但撞到天花板** | 每份清单 12–16 条；六份评测里四份的两臂都在 0.889–1.000 |
| LLM-as-judge | ✅ 建成且**刻意受限**（这是对的） | 但它**没有 `inconclusive` 桶**，端点挂了和认真看完没发现，字节级相同 |
| 人工标注 | ⚠️ **原料在库里，一次都没被消费** | `listReviewDecisions` 全仓库只有一个调用方：队列自己 |
| 线上采样 | ❌ 不存在 | 而且「线上」在这个产品里指什么，得先定义 |

---

## 技术点

四种手段回答的**不是同一个问题**，混着谈是这个主题最常见的错误：

| 手段 | 回答 | 真值从哪来 | 主要失效 |
|---|---|---|---|
| **离线集** | 该测的测了多少 | 人写的清单 | 天花板效应；清单本身有多全没人知道 |
| **LLM-as-judge** | 语义上算不算覆盖到 | 模型 | **不可复现**——同一次跑分两次不一样 |
| **人工标注** | 人认不认这条 | 人 | 覆盖不均匀；一旦进调优回路即污染 |
| **线上采样** | 真实使用里出了什么 | 生产流量 | 这个产品**没有生产流量**，「线上」需先定义 |

三条设计纪律，这个仓库已经在守：

1. **判官只能加、不能减。**否则主指标又依赖模型，配对比较失去意义。
2. **人写的清单不能由模型生成。**考卷不能由考生出（[第 02 章](./02-三条不可动摇的性质.md)）。
3. **预注册预判，且预判不作为断言。**会红的评测会被调到绿为止。

## 现状

### 已经建成、且比重写更好的部分

| 机制 | 位置 | 为什么好 |
|---|---|---|
| 确定性覆盖 + 保留集 | `eval/coverage.ts:81`、`:30` | `heldOut` 单独计分，**改进无法被拟合到它上面** |
| 受限的判官 | `eval/semantic.ts:66` | **只允许加、不允许减**，且永远标注「不可比」 |
| 精确二项 McNemar | `eval/paired.ts:39` | 20 条一批时卡方假设不成立 |
| 评测即文件 | `evals/*.json` + `evalspecs.ts` | 「一份评测是一个文件，不是一次表单提交」 |
| 预注册的 `expect` | `evals.ts:113-125` | **不作为断言**——「一个会红的评测会被人调到绿为止」 |
| 消融开关 | `eval/ablation.ts:31` | `parseAblation` 拒绝没有节点在读的名字 |
| 单变量由构造保证 | `prompts.ts:177` 的 `subtract()` | 两条臂从同一份原文减出来，不手写第二份 |

**本章不动这些。**

### 缺陷一：预注册机制没有在跑　【最刺眼的一条】

`evalspecs.ts` 把 `expect` 称为**「评测唯一能防止自欺的机制」**——
先写下预判，再看它对不对。

而实测：**48 条 eval 记录，没有任何东西在给 `expect` 记分。**
「我们的预判准不准」这个问题，对这 48 条里的任何一条都答不上来。

原因很朴素：`expect.direction` 和 `observedDirection` 都埋在一个不透明的 `json` 列里，
跨评测查不了。

> 一个写下来了、但没有在运行的防自欺机制，和没有这个机制的区别，
> 只在于**前者会让人以为自己有**。

### 缺陷二：判官没有「不知道」这一档

`semantic.ts:76-82` 把**失败或解析不了**的裁决直接推进 `stillMissing`；
而 `calls` 在 `semantic.ts:76` 是**成功之后**才自增。

于是一个每一项都 404 的判官，产出 `calls: 0, matched: [], stillMissing: [全部]`
——**和一个认真看完、确实什么也没找到的判官字节级相同。**

这正是这个仓库在变异测试那边**已经解决过**的同一个问题。
`mutate/score.ts` 的四分类（killed / survived / **inconclusive** / notApplied）
就是为它建的，注释里记着 2026-08-29 那次模型下架导致的假结论。

**同一条教训，在判官这条路径上还没有被应用。**

另外 `semantic.ts:73` 的 `cases.slice(0, maxCandidates)`（默认 40）
**静默丢掉第 41 条以后的候选**——批次超过 40 条时，判官根本看不到那条覆盖了目标的用例，
而报告只说「仍然缺失」。

### 缺陷三：离线集撞到天花板

| 清单 | 条数 |
|---|---|
| `fixtures/mock-spec` | 12 |
| `petclinic` | 13 |
| `juiceshop` | 14 |
| `dimeshift` | 12 |
| `self-test` | 16 |

六份评测里**四份**打的是 `fixtures/mock-spec`，而那上面两臂都在 0.889–1.000。
`evals/design-methods-headroom.json:4` 自己把这件事点名为天花板效应。

还有：**四份评测有 `expect` 而没有 `result`**——
包括那份旗舰的提示词消融，**在当前模型上一次都没跑过**。

### 缺陷四：两因子消融被当成两因子报，实际只跑了一因子

`casegen/nodes.ts:977-985` 的选择器是一串**提前 return**：

```ts
if (ctx.ablated.has(ABLATABLE.designMethods)) return CASES_STABLE_PLAIN;
if (ctx.ablated.has(ABLATABLE.casePriority))   return CASES_STABLE_NO_PRIORITY;
if (ctx.ablated.has(ABLATABLE.caseCleanup))    return CASES_STABLE_NO_CLEANUP;
```

而它自己的注释说的是「**同时开两个时按顺序减**」。
**同时开两个开关，只有第一个生效，报告却按两个报。**

这和 `prompts.ts:154` 记的那次「比较了两个不同的东西」是同一类错误。

### 缺陷五：人工标注是唯一的外部真值，而它没有被消费

- `listReviewDecisions` 全仓库**只有一个调用方**：`review.ts:362`，队列自己。
- `decisionForCreatedCase` 只有一个：`codeline.ts:101`。
- 通过率、拒绝率、编辑距离——**一个都没算过**。
- **拒绝理由根本没被采集**：`reject()` 接受 `note`（`review.ts:655`），
  `review_decisions.note` 列存在（`db.ts:814`），
  但界面只 POST `caseIds`（`Review.tsx:1080-1087`），页面上那个 note 输入框接的是重新生成。

这一条特别值得强调：**今天判断一次 harness 改动好不好，用的是门禁①（同一批人自己写的 lint）
和变异得分。通过率是唯一一个产生在 harness 之外的信号，而它没被用。**

### 缺陷六：评测事件带空作用域，互相合并

`bus.publish("eval.started", {...}, {})`（`evals.ts:393`），
`eval.finished`（`:448`、`:459`）、`eval.mutant`（`:672`、`:685`）、
`critic.finished`（`:543`）、`mutation.${kind}`（`mutationRun.ts:71`）——**全是空作用域**。

后果有两个：

1. `coalesceKey`（`envelope.ts:85`）把同一 kind 的全部事件塌成一个键——
   **两条并发的评测臂在 100ms 内发的 `eval.mutant` 会合并成一条**，A/B 观察者只看到一条臂。
2. 无法把评测事件关联到它评的那次运行。实测：41 条 `eval.mutant`、13 条 `eval.started`、
   12 条 `eval.finished`，**没有一条是可关联的**。

顺带：`eval.*` / `mutation.*` / `critic.finished` **都不在 `EventKind` 里**，
而那个 map 的注释写着「producers can't typo a kind into existence」。

### 缺陷七：`critiques` 表 0 行

judge 那条路建好了，**实际上从来没跑过**。

## 变更

按「修复已建成机制」优先于「新建」的顺序。

### 变更一：让预注册机制真的跑起来　【最高优先，最便宜】

按标准的 `PRAGMA table_info` 守卫模式（`db.ts:152`），把 `expect.direction` 与
`observedDirection` 从 `json` blob 提成 `evals` 表的两列。

**两列加一个查询，「预判准不准」这个问题就有答案了**——而这是 48 条记录里
一直存在却读不出来的信息。

同时把 `listEvals(limit = 30)`（`evals.ts:161`）和 `listCritiques(limit = 20)` 提高：
任何基于它们写的分析，今天都在**静默地只看见被截断的过去**。

### 变更二：给判官变异测试那套纪律

`SemanticCoverage`（`semantic.ts:27-40`）改成同时带 `unjudged: string[]` 和 `stillMissing`，
`semantic.ts:27` 的 catch 相应拆开，计 `attempted` 而不是 `calls`，
并加上 `truncatedCandidates: cases.length - shortlist.length`。

同时给 `model.chat` 传 `schema:`——**仓库里其它每一处调用都传，只有这里没传**，
它现在靠正则从散文里抠 JSON。

> 这一条移除的，正是这个仓库记录得最多的那种失败：**把工具自己的失败伪装成一个发现。**

### 变更三：修两因子消融

把 `nodes.ts:977-985` 的 IIFE 改写成**逐次 subtract**：从 `CASES_STABLE` 出发，
每个激活的开关调用一次 `subtract()`——也就是它注释本来声称的行为。

需要让 `CASES_STABLE_NO_PRIORITY` / `_NO_CLEANUP` 从模块加载期常量变成运行期计算
（**优先这个**，而不是再加一个 `_NO_PRIORITY_NO_CLEANUP` 常量）。

加一个测试：**同时消融 case-priority 与 case-cleanup，产出的文本必须两段都缺**。

### 变更四：把缺陷检出接进变异运行

`detectionCases` 已经写好了，`runMutation`（`mutationRun.ts:74`）手里
恰好握着它需要的全部东西：`clean`、`{mutant, outcomes}[]`、逐用例的判据类型。
接上，喂给 `scoreDetection`，把 precision/recall/leaning 放到 `MutationReport` 上。

**两端都已建好，中间没有管子。**

> ⚠️ 做之前**先修一行**：`NOTICEABLE_BY`（`mutate/detection.ts:76`）**没有 `delta` 判据那一行**。
> 不修的话，基于关系的断言会被静默记成 0 召回——
> 和 `detection.ts:66` 记录的 relink 那个 bug **一模一样**。

### 变更五：把人工标注变成可用的信号

**(a) 先把拒绝理由收起来。**`reject()` 和 DB 列都在，只差界面 POST 上去。

**(b) 新增 `server/src/reviewMetrics.ts`**：直接从 `review_decisions` + `review_edits`
算通过率、拒绝率、按 `edit.by`（human / model）分的编辑率、逐字段编辑分布、
以及已经算好的 `gateScore → editedGateScore` 差值（`review.ts:445-446`）。

复用 `codeline.ts:243-254` 的 `NOT_A_REWRITE` 集合，
**免得「只改了个优先级」被算成一次重写**。

**(c) 暴露成 arm 级结果**，让 `evals/*.json` 可以像点名 `coverage` 那样点名 `approvalRate`。

于是「`review.ts:598` 那个 steps-to-board 的修复，有没有降低人工编辑率」
这类问题第一次可以被回答——**今天在任何一侧都答不了。**

### 变更六：给评测事件真实的作用域

每个调用点一行：`{wfRunId, projectId}`，并给 `ScopeSchema`（`envelope.ts:7`）加 `evalId`。
向后兼容（每个字段都是可选的）。

顺带把 `eval.*` / `mutation.*` / `critic.finished` 加进 `EventKind`，
让那句「不能凭空造出一个 kind」变成真的。

### 变更七：线上采样——先定义「线上」

这个产品没有生产流量。**能够充当「线上」的只有两样**：

1. **人在复核队列里的行为**——已经在发生，见变更五。
2. **对基准应用的定期无人值守运行**——需要 [第 13 章](./13-过程可视化.md) 的
   `/lineage` 与作用域索引才查得动。

在这两样之外去建一个「采样系统」是没有对象的。**本章不建议做。**

## 明确不做的一件事：把通过的用例喂回黄金清单

这是最诱人也最危险的一条，必须写下来。

`coverage.ts:31` 写着：

> Never used for tuning; scored separately so improvements cannot be fitted to it

把人工通过的用例提升成 `GoldItem`，同时又拿黄金清单去给生成打分，
**就闭合了一个自己量自己的环**。

这和 [第 02 章](./02-三条不可动摇的性质.md) 的「考卷不能由考生出」是同一条，
也和 `critic.ts:164` 那条运行时禁令同源——
**一个被展示过清单的 harness 会停止测量、开始背诵。**

如果真要从复核结果里长出黄金条目，唯一可接受的形态是：
**人工另行确认过、且一律标 `heldOut: true`、且永远不参与调优**。
即便如此，它的覆盖也是不均匀的（只有被人复核过的运行才有决策），
这一点必须写进那份清单自己的元数据里。

## 代价与风险

| 项 | 说明 |
|---|---|
| **污染（首要）** | 见上。人工标注一旦进了调优回路，整套数字就失去意义 |
| 变更四的前置 | `NOTICEABLE_BY` 缺 `delta` 行**必须先修**，否则新指标一上来就是错的 |
| 变更五(c) | 复核覆盖不均匀——只有被人看过的运行才有决策。任何基于它的指标都要带上样本量 |
| 变更三 | 改成运行期计算之后，标记漂移会**在节点 run() 里抛**而不是模块加载时抛——失败点变晚了 |
| 变更六 | 有消费者把 `EventKind` 当穷尽联合用，加成员要跟着加分支 |
| 天花板 | 扩充清单是**人工**成本，且必须由人写（第 02 章）。这是本章唯一一件买不到的东西 |
| 机器时间 | 跑那四份没跑过的评测，每份是两次完整运行、几十分钟。**且有一条运维约束：评测跑着的时候不要改服务端代码** |

## 怎么证伪

| 手段 | 内容 |
|---|---|
| **单元测试** | ① 判官端点全 404 → 结果必须是 `unjudged` 非空且 `stillMissing` 不含它们（直接钉住缺陷二）；② 同时消融两个开关 → 文本两段都缺（钉住缺陷三）；③ `delta` 判据在 `NOTICEABLE_BY` 里有行，且一个 delta 用例在对应变异下被算作「本该失败」 |
| **配对评测** | 变更二、三改的是评测器本身，**不能用评测来验自己**——只能靠单元测试。这一点要说清楚 |
| **可量测** | 「48 条评测里预判命中多少」——做完立刻有数；「一次并发双臂运行里 `eval.mutant` 事件是否互相合并」——可构造 |
| **无法证伪的** | 扩充黄金清单是否真的把天花板打开了。只能事后看：新清单上两臂的分是否离开 0.889–1.000 区间。**这是一个观察，不是一个检验** |

## 验收

1. 「过去 48 次评测里，预判方向对了几次」——有一条 SQL 能回答。
2. 构造一个全 404 的判官，报告里出现 `unjudged`，**不是**一片 `stillMissing`。
3. 同时开 `case-priority` 与 `case-cleanup`，产出的提示词**两段都缺**，且有测试钉住。
4. `MutationReport` 上有 precision / recall / leaning，且 `delta` 判据不再恒 0 召回。
5. 拒绝一条用例时可以写理由，且理由能被聚合。
6. `evals/*.json` 里可以写 `approvalRate` 当作 arm 级结果。
7. 两条并发评测臂的 `eval.mutant` 事件互不合并，且都能关联回各自的 `wfRunId`。
8. **黄金清单里没有任何一条是从复核结果自动提升上来的**，除非它被人另行确认且标了 `heldOut`。

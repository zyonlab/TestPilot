## 该看什么（按重要性排）

### 1. 两级产物是不是真的分开了

- **阶段一**：`fixtures/mock-spec/acme-portal.md` → 用户故事 → 文本用例 → 门禁①
  画布上选 `g1-text-cases`，点 `gate` 节点，右边就是整批产物（故事带验收标准、用例带
  设计方法与 tier）。
- **阶段二**：文本用例 → 代码 → 门禁② → 有界修复。选 `g2-code`，点 `repair` 节点，
  看 `gate` 与 `repair` 两段。

产物是**端无关**的：阶段一的用例里没有选择器、没有页面对象，换 iOS/Android 不用重写。

### 2. 门禁是不是真在管事

- **门禁①（`packages/harness-testing/src/casegen/gate.ts`）只打分标记不拒收**。
  理由写在文件头：上一版那种拒收门开火十几次、真阳性零次。
- **门禁②（`codegen/gate.ts`）有拒收权，但只对事实**：跑不了的代码（没有断言、
  用了不允许的调用、把凭证写死）拒收；风格问题只警告。

### 3. 修复循环会不会作弊

`codegen/repair.ts`。两个数并排发布：

- `loosePassRate` —— 所有通过的
- `strictPassRate` —— 扣掉「只有把断言改松/删掉用例才变绿」的那些

这套机制存在的唯一理由是：这个项目不设人工审批，那么**唯一的防线就是度量它**。
每一轮修复的改动都被分类落盘（结构 / 措辞 / 等待 / **断言语义** / **删除用例**）。

### 4. 评测层是不是可复现

- `Coverage`（`harness-core/src/eval/coverage.ts`）对着**人写的**黄金清单打分，
  留出集单独计分，匹配是确定性关键词——可复现，代价是措辞差异会漏判，**这个数是下界**。
- `P/R/F1`（`eval/detect.ts`）以 Fail 为正类，并报告这一版**滑向误报还是漏报**。
- `McNemar`（`eval/paired.ts`）配对比较，小样本用精确二项检验。

## 之前列的四个问题，三个已按行业通行做法实现

**1. 工作流运行现在绑定环境** ✅
`POST /api/wf/runs` 接受 `{ projectId, envRef, url }`，运行记录里存着它，
**重跑单个节点会复用同一个 target**（否则"这批用例通过了"是一句不指向任何东西的话）。
执行时解析 `${env.*}` / `${secret.*}`、注入固定头/query/已捕获会话、必要时跑登录步骤——
和用例看板那条路完全同一套。密钥在日志里始终是模板形态。
实测：一条带占位符的用例经 G2 生成代码后，在内置 `/testlogin` 上**真的登录成功**（loose 1 / strict 1）。

**2. Coverage 增加语义兜底，但主指标仍是确定性的** ✅
`eval/semantic.ts`：**只对确定性匹配漏掉的条目**做模型判定，判定结果单独成一个数
（`semanticCoverage`），并报告它自己花了多少 calls/tokens。
理由：主指标必须可复现，否则配对比较没有意义；而只认关键词又会系统性低估。
所以两个数并排：**`coverage` 是可跨版本比较的下界，`semanticCoverage` 是更准但不可比的估计**。
判定失败一律算"仍未覆盖"——安全的方向是继续报告缺口，而不是凭空补上覆盖。

**3. 网关不再打开任何浏览器** ✅
`/api/dapp/verify`、`/api/wallet/check`、`/api/wallet/dapp-test`、会话捕获——四条全部走 runner。
`server/src/index.ts` 里 `launchSession` 出现次数：**0**。
一个进程拥有浏览器：卡死只死一处、泄漏只查一处。

**4. 画布可编辑节点参数** ✅（拓扑编辑仍在阶段二）
右侧面板可改参数，保存 → **服务端校验 → 新版本**；参数非法会被拒并高亮到具体节点
（实测 `minNegativeRatio: 5` 被拒："Number must be less than or equal to 1"）。
已完成的运行仍指向它当时用的版本。改完直接「只跑此节点」——不必再问模型。

**仍然留着的**：拓扑编辑、版本 diff、断点开关（阶段二）；Coverage 的确定性匹配依然会漏判
（这是它作为下界的定义，不是缺陷）。

## 检测力（缺陷注入）——一条完整的度量闭环

`/testlogin?defect=` 可注入五种已知缺陷。按**变异测试**口径计分（健康版任何失败＝误报；缺陷版有人发现＝击杀）。
**刻意不出逐用例 P/R/F1**：那需要「这条用例本该抓到这个缺陷」的标注，凭空造标注等于在量我自己的标注。

| 同一份 spec、同两条用例 | 误报率 | 变异分数 |
|---|---|---|
| 门禁修正前（用例里是编造的凭证） | **0.5** | **0** |
| 门禁修正后（负例用真实的非法字面量） | **0** | **0.5** |

第二行里 `no-error` 被两条用例同时抓到；`empty-user-ok` 逃掉了——而且逃得**有道理**：
两条用例都不会走到"空用户名 + 正确密码"这条路径。这是这套用例真实存在的覆盖缺口，正是变异分数该说的话。

顺带印证了「只跑此节点」的价值：改完门禁规则后**重新过一次门禁只花 20 秒、零模型调用**（`gate② 0.5 → 1.0`）。

## 这一轮实跑抓到的真 bug（都已修 + 加了测试）

1. **回复被 `max_tokens` 截断** → 一个故事的全部用例丢失。第一轮 17 条、第二轮 28 条的差别主要来自这个。
2. **空输入被契约拒收** —— `aiInput('', '用户名输入框')` 是「用户名为空」用例的**正确**写法，
   而 schema 要求非空。运行时的输出契约把它拦下来了，说明契约在干活；但契约本身写错了。
3. **生成的代码自己编了凭证**（`testuser` / `testpass`）→ 登录必然失败 →
   修复循环于是报告「这是产品缺陷」。**编造的凭证不只是失败，它以嫁祸产品的方式失败**，
   而且会静默摧毁整套用例的检测力（上表第一行就是证据）。已加门禁规则拒收。
4. **提示词里说了也没用**：加了"不要编凭证"的指令之后，模型照编不误——门禁拦下来才是有效的那一道。
5. **我自己的门禁规则有假阳性**：负例本来就该用错误的字面量密码。改成
   **看证据不看标签**——断言在要求"拒绝/错误"的用例，允许非法字面量（生成器经常把这类用例
   标成 `equivalence`，标签不可信，断言可信）。

# 这一轮（你睡觉期间）的细节

## A. 复核队列：产物落库不再等于入库

生成 ≠ 入库。工作流跑完的用例先进 `/#/review`，每条旁边挂着门禁①对它的逐条判据结果；
**批准才创建用例**，拒绝会被记住（`review_decisions` 表），队列不再重复问。

- 批准时带上出处：`storyId` / `designMethod` / `tier` / `gateScore` / `sourceRunId`。
  看板上一条用例可以回答"你从哪来、按什么方法设计的、当时门禁给你打了多少分"。
- **未绑定项目的运行不能批准**——那样创建出来的用例不属于任何产品，是一条无处安放的记录。
  自举的运行就是这种（它跑的是文档，不是某个项目），所以队列里给它一个**显式的项目选择器**：
  不选就批不了。默认到某个项目是错的——用例落在哪块看板是个决定，不该由代码替人做。
- 阶段二代码若被门禁②拒收，那条会标红；断言在修复中被改松的会标「已退化」。

实测两次：mock 批次 25 条 → 批准 3 条 → 队列 22 条；
自举批次（100 条，未绑项目）→ 选「TestPilot 自举」项目 → 批准 3 条，
看板拿到的第一条是 `选择Web目标端时显示Web3选项 | US-01 | equivalence | tier1 | gate 0.94 | wf-mt0efic7`。

## B. HarnessCritic：让它读自己的失败

`packages/harness-testing/src/critic.ts`。它读的是**聚合后的证据**（门禁 findings 按规则计数、
失败按 infra/locate/assert 分桶、修复改动分类、覆盖漏项），不是原始轨迹——把二十条轨迹丢给模型，
它会去修它最后读到的那一条。

提示词里禁了两件事，都是有记录的失败模式：

1. 拿 `infra` 失败提 harness 改动（环境问题不是 harness 的错）；
2. 提"放松门禁"（门禁存在的理由就是防止"绿着但什么都没断言"）。

第一次对真实历史（6 次运行）跑出来的三条建议：

```
证据: 门禁 findings [invented-credential ×8, duplication ×2, oracle-vague ×2]
      失败分桶 {infra 0, locate 0, assert 1} | 退化 [] | 修复改动 {none 1}
[prompt] 凭证必须走环境变量注入   (建议用 design-methods 开关比)
[prompt] 断言必须给出可观测现象   (建议用 oracle-grading 开关比)
[prompt] 设计阶段加去重检查      (建议用 dedupe 开关比)
```

第一条正是我人肉发现的头号问题（编造凭证），它自己从数据里找出来了。

**后来又加了两道禁令，都是因为它真的这么提了：**

1. 喂进自举的覆盖漏项之后，它提议"把这 15 条清单项写进故事规划的提示词"——
   **那是把尺子交给被量的人**：覆盖率会立刻好看，同时彻底失去意义（留出集正是防这个的）。
   已加禁令：不许把清单或其中任何一条放进任何提示词，要改就改"怎么读素材"。
2. 覆盖漏项属于**拆解**问题，门禁只看得见已经存在的用例——收紧门禁变不出缺失的用例。
   已要求这类证据只能提到故事规划/用例设计上。

加完之后它的四条建议全部落在合法位置（断言可观测性、负例配比、凭证占位符、tier 3 的使用边界）。
两条禁令各有一个测试盯着，提示词被改回去会红。

**一个必须说清楚的局限**：它挑的消融开关和它提的改动经常只是"沾边"——
第一条讲凭证，却建议用 `design-methods` 开关去比。所以那个按钮的正确读法是
**"去比一下这个开关重不重要"**，不是"这条建议已被证明"。我只做了"开关不存在就降级为
不可评测"的校验，没做也做不了"开关与改动是否对口"的校验——那需要人看一眼。

## C. 自举：以我们自己的文档为 spec

见 `docs/spec/07 §7`。已接上的：`selftest-g1` 图、手抽的 16 条黄金清单（4 条留出）、
`TP_DATA_DIR` 实例隔离、单次运行评分接口 `POST /api/evals/score`。

### 需要你确认的一处偏差

07 §4 写着「gold checklist **必须人写**」。`fixtures/self-test/gold-checklist.json`
是本次会话**逐条手抽**的（零模型调用），但作者与被测系统的作者是同一个——共模失效没有完全消掉。
**它需要你复核之后才算数**，尤其 S-03 / S-06 / S-11 / S-15 这四条留出项。
在那之前，自举的 Coverage 应读作"对一份待确认清单的覆盖率"。

### M1 实测：**没达标，而且这是这次自举最有价值的产出**

| 跑法 | 故事 | 用例 | 调优集覆盖 | 留出集 | 耗时 |
|---|---|---|---|---|---|
| `maxStories=12`（首跑） | 12（全部来自 `docs/02`） | 94 | **8%** | 0% | 25 min |
| `maxStories=20`（修好之后） | 20（US-13~20 来自 `docs/03`） | 100 | **25%** | **50%** | 41 min |

判据是 ≥30 条用例 + Coverage ≥ 0.7：**条数达标，覆盖率没到**。

把 11 条未命中交给语义兜底（模型判定，`adjudicateMisses`）复核，**结论一条没变**——
全是真缺口，不是"措辞不同的近似命中"。所以这个 0.25 不能用"确定性匹配太严"解释掉。

一个具体例子说明差在哪：清单 S-01 要求"**进程页列出网关/agent/runner**"，
生成的是"验证进程列表展示所有必需字段"（断言六个字段值非空）——
它检查了表长得对不对，没检查**该在的三个进程在不在**。

两个可能主因我没证据区分（写在 `docs/spec/07 §7`）：清单比文档更具体 / 每故事 5 条摊太薄。
区分办法也写在那里：把 `maxCasesPerStory` 5→10 跑一次配对评测，看覆盖率动不动。
**这个结论需要你先复核黄金清单**——毕竟尺子是我抽的。

### 自举第一次跑就抓到的三个真缺陷

**① 截断被报成了格式错误。** 真实 spec 比 mock 大三倍，第一跑死在：

```
plan.stories: reply is not valid JSON — Expected ',' or ']' at position 2543
```

实际是 `max_tokens=1200` 截断。两者的修法**相反**（加预算 vs 改提示词），报错却把人指向了后者。
已修：`ChatResponse.truncated` 从 `finish_reason` 带出来，解析失败时直说是截断；
`plan.stories` 的预算随 `maxStories` 缩放。

**② 多份材料时，第二份可能一条故事都没进。** 修好截断后跑出 12 个故事、94 条用例——
但 12 个故事**全部来自 `docs/02`**，`docs/03` 颗粒无收：`maxStories: 12` 正好被第一份文档吃满。
对着从 `docs/03` 抽的清单打分，覆盖率只有 8%。

这不是模型笨，是 harness 没有任何机制保证"每份材料都被覆盖"。已修三处：
提示词要求跨文档铺开、故事带上 `source`（来自哪份文档）、**某份文档一条故事都没产出时直接报出来**
——否则这个洞会一路静默到覆盖率数字上，那时已经没人说得清是为什么。

修完立刻又抓到一个连锁问题：那条"没有故事来自 X"的警告**第一次就误报了**，说两份文档都颗粒无收。
原因是 `source` 字段只加进了提示词，没加进**引导解码的 JSON schema**——
schema 里没有的字段，模型根本没被允许输出。提示词和 schema 不一致时，schema 说了算。
已修 schema，并把警告改成分两种说法：分不清出处 ≠ 某份文档没被覆盖。

**其三：单次调用的超时上限对本地模型太紧。** `maxStories` 提到 20 后，`plan.stories` 要生成约 5200 token，
本地 27B 跑了 362 秒——**旧的 300 秒硬上限会直接判它死**，而报错只说
"The operation was aborted due to timeout"，既没说哪一步也没说上限多少。
已改成默认 900 秒、`TP_MODEL_TIMEOUT_MS` 可配，报错带上节点名、请求 token 数与上限。

## D. 画布：拓扑可编辑 + 版本 diff

- 编辑发生在**浏览器里的草稿**上：半张连线不是图，不该让网关存。保存才发出去，
  且保存**必然新起一版**（已完成的运行仍指向它当时那一版）。
- 版本落库到 `graphs.db`（此前编辑只在内存里，重启就没了）。
- diff 是逐条的：节点增删、类型替换、**参数按 key 比**、边增删。
  "参数变了"不是"你改了什么"的答案，而这个项目的循环通常就是改一个阈值。
  节点位置不算变更——挪一下摆位没有改变图做什么。

顺带修掉一个一直存在、但表现得像"手感问题"的真 bug：画布是 React Flow 的**受控模式**却没接
`onNodesChange`，于是每次重建节点对象都会抹掉 React Flow 量出来的尺寸。后果有三个，
都不像同一个原因：**fitView 永远是空操作**（自带的"适应视图"按钮点了没反应）、
**节点在测量回来之前是隐藏的**（运行中每来一个事件就闪一次）、
**未测量的节点不画边**。修法是把测量结果合并回节点对象。

实测：编辑拓扑 → 加 `codegen.case` 节点 → 连 `gate → case` → 保存为 v2 →
`GET /api/graphs/g1-text-cases/diff?from=1&to=2` 得到

```
+ node case (codegen.case)
+ edge gate → case
```

（随后已还原成 v3，实验留在版本历史里。）

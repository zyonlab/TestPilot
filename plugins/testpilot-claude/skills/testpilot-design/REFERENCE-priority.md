# `priority`：坏了要付多大代价

> 这一份对应 `prompts.ts` 里可被 `subtract` 掉的「优先级」那一段
> （消融臂 `CASES_STABLE_NO_PRIORITY`）。在 skill 世界里，消融 = **卸掉这份文件**。

`priority` 说的是**把这件事坏着发出去要付多大代价**，不是它有多大可能坏。

| 值 | 含义 |
|---|---|
| `P0` | 认证、支付、结账，以及这条故事的核心正常流。**坏了产品就没法做它存在的那件事。** |
| `P1` | 重要的次要流程，以及保护数据的那些拒绝（防止坏记录的校验、权限）。 |
| `P2` | 观感的、信息性的，或者只有走一条罕见路径才够得着的。 |

## 判据

- **判的是这条故事的重要性，不是这条用例的难度。** 一条 P0 故事的边界用例，
  仍然比一条 P2 故事的正常流值钱。
- **多数故事不是 P0。** 一批全是 P0 的用例什么也没说。
- **每条用例都必须给一个优先级。** 拒绝选择本身就是一种选择，
  而且它会把每条用例都扔进同一个桶——那和没有优先级是一回事。

## 这个口径是从哪来的

不是新发明的：`server/src/settings.ts` 里早就有一份写好的（登录/支付/结账/核心正常流 = P0），
它服务于另一条老路径。同一个概念在两处用两套标准，迟早会得到两批对不上的优先级，
所以这里抄的是那一份。

## 一个键的缺席能传多远

这个键此前**根本不在返回格式里**——模型从没被问过。后果一路往下：
设计节点不产出优先级 → 看板的 P0/P1/P2 三列恒空 → 批准时只能默认 P1 →
导出的文件名全变成 `p1-*` → 「先跑 P0 冒烟」这条本该最有用的路径不存在。

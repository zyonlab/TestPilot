# 任务：为 TestPilot 自己的规格设计测试用例

工作区的 `materials/` 里是 TestPilot 的产品规格，人写的：

- `02-业务规格与用户故事.md`——业务规格与用户故事
- `03-UI交互规格.md`——UI 交互规格，逐条列出断言点

## 要交的东西

在 `runs/<runId>/` 下：

| 文件 | 内容 |
|---|---|
| `stories.json` | 从规格里抽出的用户故事 |
| `cases.json` | 每条故事的文本级测试用例 |
| `meta.json` | 这次运行的来源印记 |

（`gate.json` 不用你写——写 `meta.json` 时它会自动生成。）

外加 `scans/<runId>.json`：对自己这批产物的审计。

## 材料的性质

**这是人写的文档，表达的是意图。** 所以对着它写的用例挂了，
**可能意味着「产品错了」**——这一点和从跑着的产品上观察来的材料不同。

规格里每条规则都标了高度：`[screen]` 一屏显示什么、`[flow]` 用户做了某件事之后发生什么、
`[domain]` 与屏幕无关的陈述。

## 覆盖

规格明确列出了断言点。一条用例覆盖了哪一条，就用它自己的话写清楚——
不要复述规格的编号当成断言。

规格列出流程时，每步带一个反引号包着的转移 id。用例走到某一步，
就把那个 id 逐字抄进 `covers`（去掉反引号）。**只抄规格里真有的。**

## 规格里没说的

规格会有说不清、自相矛盾或者根本没提的地方。
**不要替它决定**：那些写进故事的 unknowns，或者写一条用例但标 tier 3 并说明「规格未定」。
一份不写自己盲区的规格读起来像是完整的，而由它衍生的一切都会继承这个错觉。
